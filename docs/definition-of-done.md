## 0.2.0 で作った例外と、繰り越したもの

**タッチ標的の例外が 2 つある**（base-spec §43 の 44px を割る）。どちらも
理由を設計書に書いてある。

| 場所 | 高さ | 理由 |
|---|---|---|
| Scientific の関数列 | 34px | 誤爆しても DEL で戻せる（S1 設計書 §4） |
| フッタのリンク | 11px（実測。390×844、`page.getByRole("link", { name: /^CalcArc .+ @terapyon$/ }).boundingBox()`） | 広げる縦が無い。押せなくても計算に影響しない（0.2.0 設計書 §5） |

**Finance のモード行と項目行は、0.2.0 で例外から外れた**（34px → 68px）。

**繰り越した表示の問題**（計算結果には影響しない。0.2.1 以降で直す）:

- ~~**360px 幅で関数列のボタンが 8px 横に溢れる。**~~ **0.2.1 で解消。**
  原因はキーの `min-width: 44px` が grid の `1fr` の下限になり、7 列 × 44px
  ＋ gap 8px × 6 = 356px が 336px（360px − padding 24px）に入らなかったこと。
  **gap のほうを譲らせて 44px は守った**（`Keypad.module.css`）
- **`env(safe-area-inset-top)` を誰も吸っていない。** standalone 起動で Nav が
  ステータスバーに潜る可能性がある。実機確認が要る
- **更新のトーストがフッタに重なる。** 一過性

## 0.3.0 の後に直すもの

- **`(29 nCr 4) nCr 2` が `Math ERROR` になる**（ユーザー裁定 2026-08-20: **後で直す**。
  **誤った値を出しているのではなくエラーに落ちているので急がない**）。
  原因は **nCr / nPr / n! の整数判定が、除算を先にやる f64 の誤差で偽陰性になる**こと
  ——`(29 nCr 4)` の内部値は **23751.000000000004** で、**表示は `23751`** なので画面からは分からない。
  次の `nCr` がその値を「整数でない」と見て弾く。
  修正候補は **整数演算に置き換える**か、**整数判定に許容誤差を設計する**か。
  後者は**厳密一致の罠**に注意（[[exact-string-needs-exact-input]] と同じ型で、
  許容幅を決めると別の境で偽陽性が出る）。実測は重量級側の `docs/corpus-measurements.md` にある。

**対応する画面幅の下限は 360px とする**（0.2.1 で決めた）。**320px は対象外**——
7 列 × 44px = 308px は、gap と padding を 0 にしても 320px にほとんど隙間が
残らず、**44px と 7 列は 320px で両立しない**。算数であって、直し方の問題では
ない。gap を譲る修正の副作用として 320px でも横スクロールは出なくなったが、
**関数列の隙間が 0 になり右端に接する**ので、誤爆しやすい状態のままである。

### 0.3.0 で悪化した分（実測 2026-08-20）

**Scale が 3 カテゴリになり、カテゴリの `<select>` が 1 行増えた。** 同じ測り方
（`scrollHeight − innerHeight`、実機ビルドを preview で配信、パネルが出てから測る）で
採った値:

| | 390×844 | 360×640 |
|---|---|---|
| Data Scale（0.2.1） | 0 | **66** |
| Data Scale（0.3.0） | 0 | **94** |
| LLM のメモリ（新規） | **33** | **204** |
| データ転送量（新規） | 0 | **66** |

**Data Scale は 360×640 で 28px 悪くなった**（66 → 94）。390×844 で 0 のままなのは、
この幅では余りが 107px あって増分が吸われるからで、**予算が増えたわけではない**。

**LLM は 390×844 でも 33px 溢れる。** iPhone 相当の幅で 1 画面に収まらないのは
3 カテゴリで LLM だけである。360×640 の 204px はフッタの免責文が画面外に完全に
出る量で、**この表で最も重い**（0.2.1 の Finance 149px より大きい）。

**上の表と縦に読まないこと**——0.2.1 の Data Scale（66）と 0.3.0 のデータ転送量（66）が
たまたま同じ値である。別の行である。

**直すのは 0.3.0 の範囲外**（S-0 spec §8。悪化量を測って記録するところまでが仕事）。
**未解決の項目がこれで 3 行増えた**ことを、次に縦を触る人へ渡す。

**【ユーザー裁定 2026-08-20】LLM のメモリは実験的機能であり、この溢れは許容する。**
390×844 の 33px も 360×640 の 204px も**直さずに共用する**——条件は「**他の機能を
壊していないこと**」で、それは満たしている（Data Scale は 390×844 で 0 のまま。
360×640 の 66 → 94 は `<select>` 1 行ぶんの共通コストで、この列は 0.2.1 の時点から
既に溢れている）。**上の 3 行のうち LLM の 2 マスは、未解決の債務ではなく
「承知のうえで許容した状態」である。**

**この 3 行は E2E が巡回していない。** `viewport-budget.spec.ts` の `TABS` が持つ
Scale の代表は `#scale/data-scale` **だけ**で、`#scale/llm` と `#scale/transfer` は
溢れの検査にもフッタ位置の検査にも**一度も現れない**。だから **E2E 全緑と、LLM が
390×844 で 33px 溢れていることは矛盾なく両立する**——緑を「1 画面に収まっている」と
読んではいけない。（上の 0.2.1 の表にある「測っているのは 390×844 だけ」は**列**の
話で、こちらは**route が巡回に入っていない**という別の穴である。）

#### 単位変換（U-1 で新規、実測 2026-08-20）

同じ測り方（`scrollHeight − innerHeight`、`pnpm build` の実機ビルドを preview で
配信、**パネルが出てから測る**）。Convert は **7 カテゴリ**で盤面を 1 つ共有する
（`UnitPanel`。U-1 の 3 つ + U-2 の 4 つ）ので、**カテゴリを替えても縦は 1px も
動かない**:

| | 390×844 | 360×640 |
|---|---|---|
| 単位変換 / 長さ（新規） | 0 | **66** |
| 単位変換 / 質量（新規） | 0 | **66** |
| 単位変換 / 温度（新規） | 0 | **66** |
| 単位変換 / 面積（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / 体積（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / 速さ（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / データ量（U-2、実測 2026-08-20） | 0 | **66** |

**【追記 2026-08-20】U-2 の 4 カテゴリを足しても値は 1 つも動かなかった。**
**7 カテゴリで最も重い体積（15 単位・5 行、枠の容量いっぱい）が、最も軽い温度
（3 単位・1 行）と同値である。** 数字面のままでも単位面を開いても同じ値だった
（両方測った）。したがってこの表の 390×844 = 0 / 360×640 = 66 は**書き換えて
いない**——`aspect-ratio: 1 / 1` が中身の行数を縦の予算から切り離している、という
下の説明が 7 行に広がっただけである。

**7 行が同じ値なのは偶然ではない。** 枠の高さは中身の行数ではなく
`UnitPanel.module.css` の `aspect-ratio: 1 / 1` が決めており、単位が 15 個でも
3 個でも面の寸法が変わらない。**その不変条件を機械で見張っているのは
`web/tests/e2e/convert.spec.ts` の "swapping faces moves neither the frame nor
DEL and AC" 1 本だけ**である（CSS の面名を 1 文字変えると vitest は緑のまま
通り、実ブラウザで単位面が length・面積・データ量 366×291 / mass 366×216 /
速さ 366×142 / **温度 366×67** に潰れることを、この検査の赤確認で実測した。
**体積だけは 366×366 のまま変化しない**——15 単位 5 行が枠の容量ちょうどなので、
行数指定を失っても高さが同じである。**容量いっぱいの面は、あふれの番人には
なれても潰れの番人にはならない**）。

**360×640 の 66px を Convert 固有の債務と読まないこと。** この列は 0.2.1 の
時点で Scientific 52 / Data Scale 66 / Finance 149 と既に溢れている。Convert は
カテゴリの `<select>` を 1 行持ちながら 66px で、**0.3.0 の Data Scale（94）より
軽い**——ただし**なぜ軽いかは測っていない**（内訳を分解していない）。
**上の 2 つの表と縦に読まないこと**——66 という数字が 3 か所に出るが、別の行である。

**巡回には入れた。** `viewport-budget.spec.ts` の `TABS` から `#convert`（素の
ハッシュ）を外し、**`#convert/length` `#convert/mass` `#convert/temperature` の
3 route を並べた**。理由は 2 つ:

1. **緑を「収まっている」と読ませないため。** S-0 で記録したとおり、巡回に
   入っていない route は溢れていても E2E が緑になる。Convert は 390×844 で
   3 route とも 0 なので、**足しても赤にならず、穴だけが消える**（実測）。
2. **タブの href と同じ URL を測るため。** `Nav.tsx` の Convert は
   `#convert/length` を指しており、素の `#convert` はどのリンクも作らない
   （同じ画面に URL を 2 つ作らない、設計書 §3）。

**Scale の 2 route は依然として巡回の外である**（`#scale/llm` と
`#scale/transfer`）。上に書いたとおり LLM は 390×844 で 33px 溢れており、
足せば赤くなる——**ユーザー裁定で許容した状態**なので足していない。

**【訂正 2026-08-20】「巡回に入っていない route」は 2 つではなく 6 つである。**
ここには当初「0.3.0 の終わりでも 2 つ残る」と書いていたが、**U-2 が Convert を
7 カテゴリに増やした時点で数が変わった**。`TABS` に居るのは
`#convert/length` `#convert/mass` `#convert/temperature` の 3 つのままで、
**`#convert/area` `#convert/volume` `#convert/speed` `#convert/data-size` の
4 route は巡回の外にいる**。合わせて Scale の 2 つと 6 つである。

**この 4 つは溢れていない**（上の表。390×844 で 0、360×640 で 66 は 3 route と
同値、横のはみ出しも 360px で 0——**2026-08-20 に手で測った**）。**Scale の 2 つ
とは性質が違う**——あちらは「溢れているのを許容している」穴で、こちらは
「収まっているのを機械が確認していない」穴である。**巡回に足せば緑になる。**
足さなかったのは U-2 spec §5 が **`pnpm e2e` に足す検査を「面が枠に収まって
いるか」の 1 本に限った**からで、**測った値が理由ではない**。
