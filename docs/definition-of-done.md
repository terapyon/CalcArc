**繰り越した表示の問題**（計算結果には影響しない。0.2.1 以降で直す）:

## 0.3.0 の後に直すもの

- **`(29 nCr 4) nCr 2` が `Math ERROR` になる**（ユーザー裁定 2026-08-20: **後で直す**。
  **誤った値を出しているのではなくエラーに落ちているので急がない**）。
  原因は **nCr / nPr / n! の整数判定が、除算を先にやる f64 の誤差で偽陰性になる**こと
  ——`(29 nCr 4)` の内部値は **23751.000000000004** で、**表示は `23751`** なので画面からは分からない。
  次の `nCr` がその値を「整数でない」と見て弾く。
  修正候補は **整数演算に置き換える**か、**整数判定に許容誤差を設計する**か。
  後者は**厳密一致の罠**に注意（[[exact-string-needs-exact-input]] と同じ型で、
  許容幅を決めると別の境で偽陽性が出る）。実測は重量級側の `docs/corpus-measurements.md` にある。

- ~~**`FinancePanel.tsx:74` の「コアの `MAX_TERM_MONTHS` と同じ」は、掛かる場所が違う。**~~
  → **直した（0.5.0）。** 註を書き直し、**数の一致は機械が見張るようにした**——
  `token_parity.rs` の `the_panel_period_cap_matches_the_compound_domain` が
  盤面の `MAX_PERIODS` と `finance::compound::MAX_PERIODS` を突き合わせる。
  **名指しの誤りは検査では捕まらなかった**（`compound::MAX_PERIODS`・
  `loan::inverse::MAX_TERM_MONTHS`・盤面の 3 つとも 1200 で、数では区別が付かない）。
  **製品として置くべき上限**の議論は別件のまま。
- **期数 0 の複利は、コアの `SyntaxError` が画面から観測できない**（**欠陥とは限らない。設計の記録**）。
  盤面が `periods > 0` を先に見るので、コアの検査に到達しない。**「コアが守っている」と
  「画面で確かめられる」は別**という記録として残す。出典は同上。

**対応する画面幅の下限は 360px とする**（0.2.1 で決めた）。**320px は対象外**——
7 列 × 44px = 308px は、gap と padding を 0 にしても 320px にほとんど隙間が
残らず、**44px と 7 列は 320px で両立しない**。算数であって、直し方の問題では
ない。gap を譲る修正の副作用として 320px でも横スクロールは出なくなったが、
**関数列の隙間が 0 になり右端に接する**ので、誤爆しやすい状態のままである。

配信、**パネルが出てから測る**）。Convert は **8 カテゴリ**で盤面を 1 つ共有する
（`UnitPanel`。U-1 の 3 つ + U-2 の 4 つ + U-4 の通貨）。**下の 7 行はカテゴリを
替えても縦が 1px も動かない**——**動くのは通貨だけ**で、理由は表の下の
【追記・U-4】にある:

| | 390×844 | 360×640 |
|---|---|---|
| 単位変換 / 長さ（新規） | 0 | **66** |
| 単位変換 / 質量（新規） | 0 | **66** |
| 単位変換 / 温度（新規） | 0 | **66** |
| 単位変換 / 面積（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / 体積（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / 速さ（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / データ量（U-2、実測 2026-08-20） | 0 | **66** |
| 単位変換 / 通貨（U-4、実測 2026-08-20） | 0 | **97** |
| 単位変換 / 通貨・**案内が出ている状態**（U-4、実測 2026-08-20） | **10** | **181** |

**【追記 2026-08-20・U-4】通貨だけは縦が動く。** 上の 7 行は「カテゴリを
替えても 1px も動かない」だが、**通貨はレート日付の行を 1 行持つ**
（U-4 spec §7）ので、盤面が **+31px**（行 19 + gap 12）高い——390×844 では
それでも 0 に収まり、360×640 では 66 → 97 になる。**枠が動いたのではない**
（単位面は他の 7 カテゴリと同じ 366×366 で、DEL と AC の相対位置も同値。
`convert.spec.ts` の "swapping faces moves neither the frame nor DEL and AC"
が 8 カテゴリで見張っている）——**盤面の上に 1 行増えただけ**である。

**キャッシュ無しの案内が出ている状態は 390×844 でも 10px 溢れる。** 案内の
箱が 72px あるためで、**レートが届けば消える一時的な状態**である
（初回にオフラインだった端末でだけ起きる）。文言は U-4 spec §5 が決めており、
縮めると案内の意味が変わるので**直していない**。**`viewport-budget.spec.ts`
の巡回に `#convert/currency` は入っていない**ので、この 10px は E2E 全緑と
矛盾なく両立する。

**【訂正 2026-08-20・レビュー指摘】ここには当初「この表の他の行と同じ性質の穴で
ある」と書いていた。誤りである。** この表の他の行（Convert の 8 カテゴリ）は
**390×844 では 0**——「収まっているのを機械が確認していない」穴だった。
**案内が出ている通貨は 390×844 で溢れる**ので、性質は**上の Scale の 2 route と
同じ**（承知のうえで許容した溢れ）である。**足せば緑になる、が成り立たない
唯一の Convert route** である。

**そして足さない理由も、他の Convert route とは違う。** `viewport-budget.spec.ts`
は**ネットワークを塞いでいない**（`page.route` を持つのは `convert.spec.ts` だけ）。
`#convert/currency` をあの巡回に足すと**本物の `open.er-api.com` を叩き**、
取得が成功すれば 0、失敗すれば 10 になる——**測る値が回線で変わる非決定な検査**
になる。塞ぎを先に用意しない限り足せない。

**【追記 2026-08-20】U-2 の 4 カテゴリを足しても値は 1 つも動かなかった。**
**7 カテゴリで最も重い体積（15 単位・5 行、枠の容量いっぱい）が、最も軽い温度
（3 単位・1 行）と同値である。** 数字面のままでも単位面を開いても同じ値だった
（両方測った）。したがってこの表の 390×844 = 0 / 360×640 = 66 は**書き換えて
いない**——`aspect-ratio: 1 / 1` が中身の行数を縦の予算から切り離している、という
下の説明が 7 行に広がっただけである。

**7 行が同じ値なのは偶然ではない。** 枠の高さは中身の行数ではなく
`UnitPanel.module.css` の `aspect-ratio: 1 / 1` が決めており、単位が 15 個でも
3 個でも面の寸法が変わらない。**その不変条件を機械で見張っているのは
`web/tests/e2e/convert.spec.ts` の "swapping faces moves neither the frame nor
DEL and AC" 1 本だけ**である（CSS の面名を 1 文字変えると vitest は緑のまま
通り、実ブラウザで単位面が length・面積・データ量 366×291 / mass 366×216 /
速さ 366×142 / **温度 366×67** に潰れることを、この検査の赤確認で実測した。
**体積だけは 366×366 のまま変化しない**——15 単位 5 行が枠の容量ちょうどなので、
行数指定を失っても高さが同じである。**容量いっぱいの面は、あふれの番人には
なれても潰れの番人にはならない**）。

**360×640 の 66px を Convert 固有の債務と読まないこと。** この列は 0.2.1 の
時点で Scientific 52 / Data Scale 66 / Finance 149 と既に溢れている。Convert は
カテゴリの `<select>` を 1 行持ちながら 66px で、**0.3.0 の Data Scale（94）より
軽い**——ただし**なぜ軽いかは測っていない**（内訳を分解していない）。
**上の 2 つの表と縦に読まないこと**——66 という数字が 3 か所に出るが、別の行である。

**巡回には入れた。** `viewport-budget.spec.ts` の `TABS` から `#convert`（素の
ハッシュ）を外し、**`#convert/length` `#convert/mass` `#convert/temperature` の
3 route を並べた**。理由は 2 つ:

1. **緑を「収まっている」と読ませないため。** S-0 で記録したとおり、巡回に
   入っていない route は溢れていても E2E が緑になる。Convert は 390×844 で
   3 route とも 0 なので、**足しても赤にならず、穴だけが消える**（実測）。
2. **タブの href と同じ URL を測るため。** `Nav.tsx` の Convert は
   `#convert/length` を指しており、素の `#convert` はどのリンクも作らない
   （同じ画面に URL を 2 つ作らない、設計書 §3）。

**Scale の 2 route は依然として巡回の外である**（`#scale/llm` と
`#scale/transfer`）。上に書いたとおり LLM は 390×844 で 33px 溢れており、
足せば赤くなる——**ユーザー裁定で許容した状態**なので足していない。

**【訂正 2026-08-20】「巡回に入っていない route」は 2 つではなく 7 つである。**
ここには当初「0.3.0 の終わりでも 2 つ残る」と書き、次に「6 つ」と直した。
**U-2 が Convert を 7 カテゴリに増やし、U-4 が 8 つ目（通貨）を足した**——
数は**足すたびに変わる**。`TABS` に居るのは
`#convert/length` `#convert/mass` `#convert/temperature` の 3 つのままで、
**`#convert/area` `#convert/volume` `#convert/speed` `#convert/data-size`
`#convert/currency` の 5 route は巡回の外にいる**。合わせて Scale の 2 つと
7 つである（全 route は 13 = scientific 1 + convert 8 + scale 3 + finance 1）。

**この訂正印を 2 度打つはめになった理由を残す。** 1 度目（U-2）は表だけを直し、
**同じ在庫を持つこの訂正印と `viewport-budget.spec.ts` の冒頭注記を直さなかった**。
在庫は 3 か所にあり、**カテゴリを足すたびに 3 か所とも動く**——
表 / この訂正印 / E2E の注記である。次に足す人は 3 か所を grep で起こすこと。

**この 4 つは溢れていない**（上の表。390×844 で 0、360×640 で 66 は 3 route と
同値、横のはみ出しも 360px で 0——**2026-08-20 に手で測った**）。**Scale の 2 つ
とは性質が違う**——あちらは「溢れているのを許容している」穴で、こちらは
「収まっているのを機械が確認していない」穴である。**巡回に足せば緑になる。**
**5 つ目の `#convert/currency` はこの 4 つの仲間ではない**——案内が出ていると
390×844 で 10px 溢れ、しかも**あの巡回は通信を塞いでいない**ので足すと非決定に
なる（上の【訂正・レビュー指摘】）。
足さなかったのは U-2 spec §5 が **`pnpm e2e` に足す検査を「面が枠に収まって
いるか」の 1 本に限った**からで、**測った値が理由ではない**。

#### 盤面の幅を揃えたぶん（実測 2026-08-20）

**ユーザーが 0.3.0 を実機で見て出した指摘 2 件のうち、「Scale の電卓部分が他より
小さい」を直した副作用である。** 原因は `.panel` に `width: 100%` が無かったこと
——`margin: 0 auto` が flex の交差軸で `stretch` を止めるので、器（`.scale`）の中で
盤面が**中身の max-content まで縮んでいた**（U-2 が `UnitPanel.module.css` に
書き残したのと同じ壊れ方）。

**痩せていた盤面が本来の幅に戻ると、縦も伸びる。** キーの格子は
`aspect-ratio: 1 / 1` なので、**横に広がった分だけそのまま高さになる。**

390×844 の実測（盤面の幅 / 数字キーの一辺 / `<main>` と盤面の高さの差）:

| | 修正前 | 修正後 |
|---|---|---|
| Data Scale | 292 / 52 / 余り 163.38 | **366 / 67 / 余り 105.31** |
| データ転送 | 360 / 66 / 余り 167.25 | **366 / 67 / 余り 161.31** |
| LLM のメモリ | 366 / — / 余り 56 | 366 / — / 余り 56（不変） |
| 単位変換（U-2 で修正済み） | 366 / 67 | 366 / 67（不変） |
| Finance | 366 / 67 / 余り 22.31 | 366 / 67 / 余り 22.31（不変） |
| Scientific | 366 / 67 | 366 / 67（不変） |

`scrollHeight − innerHeight` の実測（同じ測り方——実機ビルドを preview で配信し、
パネルが出てから測る）:

| | 390×844 | 360×640 |
|---|---|---|
| Data Scale | 0 → **0**（変わらず） | 94 → **122**（**+28 悪化**） |
| データ転送 | 0 → 0 | 66 → 66 |
| LLM のメモリ | 33 → 33 | 204 → 204 |
| 単位変換（7 カテゴリ） | 0 → 0 | 66 → 66 |
| Scientific | 0 → 0 | 52 → 52 |
| Finance | 0 → 0 | 149 → 149 |

**動いたマスは 1 つだけである**——Data Scale の 360×640 が **94 → 122**。
**幅を記録する**（ユーザー指示 2026-08-20）: **悪化幅は 28px。**

**390×844 で 0 のままなのは、直っているからではない。** 余りが **163.38 → 105.31**
（**58.07px 減**）に痩せている。**この幅の Data Scale は、あと 105px しか余裕が無い。**
増分（74px の幅ぶん）より実際の縮み（58px）が小さいのは、**盤面が広くなったことで
「10 進 (KB) を主に」が 2 行から 1 行になった**からである（撮って確認した）。
360×640 で +44px ではなく +28px なのも同じ理由である。

**キーは 44px を大きく上回る側で揃った**（52 → 67）。**44px を割った面は無い**
——`viewport-budget.spec.ts` の 360px の 44px 検査と横のはみ出し検査は、
新しい寸法でも全件緑である（実測）。

**巡回の穴は増えても減ってもいない。** `viewport-budget.spec.ts` の `TABS` は
6 route のままで、`#scale/llm` `#scale/transfer` と Convert の 4 カテゴリは
依然として外にいる。**新しく足した `panel-sizing.spec.ts` は縦ではなく横を見る**
——6 route の盤面の幅が互いに一致すること、カテゴリの `<select>` が盤面と同じ幅で
あること（1280 / 768 / 390 の 3 幅）を突き合わせる。**幅は「他の面と並べて初めて
分かる」**ので、1 面ずつ見る検査では 292px を捕まえられなかった。
