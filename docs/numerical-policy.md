# Numerical Policy

CalcArc が数値をどう扱うかの規則。実装より先にここを読むこと。

## 内部表現

すべての値を複素数 `Value { re: f64, im: f64 }` として保持する。実数は虚部 0
の複素数である。実数型と複素数型を分けないため、演算に型分岐が生じない。

角度は内部では常にラジアンで保持する。度への変換は表示層でのみ行う。

## 表示

- 有効数字 10 桁。
- 丸めは round-half-to-even（Rust の書式化に一致）。
- `|x| >= 1e10` または `0 < |x| < 1e-9` で指数表記。
- 整数部には 3 桁ごとにカンマを入れる（`1,234,567`）。**既定で常に入る。**
  小数部には入れない（`1,234.5678`）。指数表記の仮数・指数部にも入らない
  （仮数はどの指数表記でも 4 桁に届かず、カンマを要する桁数にならない）。
- 直交形式は `3+j4`、極形式は `5 ∠ 53.13010235`。
- 入力欄は 12 文字まで受け付けるが、表示は有効数字 10 桁に丸める。したがって
  12 桁の入力は `=` を押した瞬間に見た目が変わりうる（`999999999999` →
  `1e12`）。値そのものは変わらず、変わるのは表示規則だけである。

表示のための丸めは表示文字列を作るときにのみ行い、保持している値には
書き戻さない。`▸∠` は表示形式を切り替えるだけで再計算しない。したがって
表示上の丸め値が次の計算の入力になることはない。

### ENG（工学表記）

ENG はモードで、既定では入っていない。**ENG を入れない限り、上の規則
（有効数字・指数表記の閾値・カンマ）は変わらない。** ENG を入れていると
きだけ、次の規則が上の指数表記に代わって適用される。

- 指数は常に 3 の倍数、仮数は 1 以上 1000 未満（負なら絶対値がその範囲）。
  例: `12345` → `12.345e3`、`0.0022` → `2.2e-3`、`1500000` → `1.5e6`
- 有効数字は上と同じ 10 桁のまま。仮数の整数部が最大 3 桁を取るぶん、
  小数部の桁数がその分減る
- **指数が 0 になる値は指数を書かない**（`999` は ENG でも `999`）。`999e0`
  は情報を増やさず、電卓の表示として見慣れない
- 極形式では**半径にだけ**掛かる。角度には掛けない——角度は度かラジアン
  であって工学量ではないため

**この節は上の既定の箇条書きを書き換えていない。** ENG は既定では発火し
ないので、既定の規則（有効数字・指数の閾値）は変更なしのまま成り立つ。
カンマは既定として常に入るので、上の箇条書き自体を書き換えた。**この扱い
の非対称は意図的である**——この「表示」節は、電卓の表示文字列を数値に
読み戻して検証する外部のテストコーパスが「表示書式が変わったかどうか」を
判定する基準として参照している。既定を変えないもの（ENG）を書き換えで
足すと、変わっていない既定まで変わったと読まれる。既定を変えるもの
（カンマ）を追記のままにすると、変わったことが伝わらない。だから前者は
追記、後者は書き換えとし、扱いを分けている。

### 入力中と確定後で規則が違う

上の規則（有効数字・指数表記・カンマ・ENG）は、**確定した値の表示にしか
掛からない**。`render()` の `main` はこう分岐している。

```rust
} else if let Some(buffer) = &state.buffer {
    buffer.text()                 // 入力中。打った文字がそのまま出る
} else {
    format_rect(state.current)    // 確定値。ここだけが format_real を通る
}
```

`format_real` を通るのは確定値だけである。入力中（`=` を押す前）は打った
文字がそのままの形で出る。したがって `10000000000`（1e10 相当の数値）を
打っている途中は、確定後なら `1e10` になる値でも平坦な `10000000000` の
まま表示され、カンマも入らない。上の規則が掛かるのは `=` を押した瞬間で
ある。これは `render()` の構造に依存する意図した挙動であり（打っている
途中で表示が書き換わると、何を打ったか分からなくなる）、偶然の一致では
なく仕様として固定する。

### 整数値の表示（Data Scale）

- 小数第 1 位まで、round-half-to-even で丸める。
- 丸めで表示値が単位の基数（10 進は 1000、2 進は 1024）に達したら、
  1 つ上の単位で丸め直す（最上位の単位は例外——そのまま伸びる）。
- 換算経路に f64 を使わない。商と剰余の u128 演算だけで丸める。

規則の詳細は
[docs/superpowers/specs/2026-08-11-data-scale-design.md §3](superpowers/specs/2026-08-11-data-scale-design.md)
を見ること。

## 第 3 の分類: Loan は決定的概算

数値の扱いは 3 つに分かれる。**Scientific = 浮動小数点**、
**Data Scale = 厳密整数**、そして **Loan = 決定的概算**である。

決定的概算とは、**実額の機関一致を目標にしない**という宣言である。返済額の
端数処理・手数料・日割りは金融機関ごとに違い、「どの銀行とも一致する」計算は
存在しない。代わりに保証するのは決定性——同じ入力は常に同じ答を返し、方法は
仕様に書かれ、Python 独立実装が検証する。UI には免責を常設する。

Loan の中では経路が 2 本に分かれる。

**償還表は厳密整数だけで走る。** 各行の利息は
floor(残高 × 月利分子 / 月利分母) を u128 中間で計算し、f64 を通さない。
金額は u64 円で持つ。

理由は実測である。年 2.7%・残高 1,200 万円の 1 か月分の利息は、厳密には
**27,000 円ちょうど**（12,000,000 × 27/12000）。同じ計算を f64 で
`floor(12_000_000.0 * 0.00225)` とすると **26,999 円**になる。丸い元本と
bp 刻みの金利という**最頻の入力**がまさに円境界を踏むので、この 1 円は例外
ではなく常態である（3,000 万円は全 bp 刻み金利で境界上）。

**f64 は閉形式の月額決定にだけ使う。** そこでも `(1+r)^n − 1` を素朴には
計算せず `expm1(n·log1p(r))` で評価する。素朴式は低金利で桁落ちし、年
0.001% では ~1e-5 円まで悪化する。expm1 経路の誤差上限は入力依存で概ね
月額 × max(n·ε/2, ε/(2r))。

**逆算 2 種の答は f64 が決めない。** f64 の閉形式は候補を出すだけで、
「n 回で完済する最小の n」「n 回で完済する最大の元本」を厳密償還表への単調
探索で確定する。実測では厳密表の答は候補より離れうる——85,000 円 × 420 回・
年 1.5% の借入可能額で **167 円**高い（各行の利息切り捨てが積み上がるぶん、
連続式より多く借りられる）。

### 境界近接ガードは golden 生成側にある

f64 を floor して決まる出力（= 月額）が円境界に近すぎるケースは、Python の
生成側が `ValueError` で落とし、golden に入れない。基準は
max(1e-6 円, 値 × 1e-9)。**相対の項が要る**のは、絶対 1e-6 円が 9 万円の
月額を守れても 3,000 万円の月額を守れないからである（f64 自身の誤差が
すでに 0.03 円ある）。

第 2 の根拠: golden 生成と CI は x86、実行はブラウザ（wasm32）で、
expm1/log1p の libm 実装が違えば ulp 差がありうる。境界から離しておくことは
その差の吸収層でもある。

逆算 2 種は上記のとおり表が答を確定するので、**floor される f64 出力が
存在せず、ガードの対象にならない**（設計書 §1-4 は逆算にもガードを課して
いたが、それは答が候補の floor で決まる前提の記述だった。表確定にした結果、
守るべき floor が消えている）。

## 複利は同じ切り捨て、違う理由

Finance の複利（一括預入・毎月積立）も、1 期の利息を
floor(残高 × 分子 / 分母) で計算して元本に組み入れる。式はローンの各行利息と
同一で、`Rate::interest_floor` をそのまま使う。

**しかし切り捨てを選ぶ根拠が反転している。**

ローンでは切り捨ては**安全な向き**だった——月額が理論値を下回るぶん残高が
高めに残り、端数は最終回が吸収する。借主に不利な方向へは倒れない。

積立・預金では、各期の利息を切り捨てるのは**受取を減らす向き**であり、
利用者に不利である。「切り捨て = 安全」はここでは成り立たない。

**それでも切り捨てを採るのは、実際の金融機関が付利単位 1 円で切り捨てるから
である。** 根拠が「安全な向き」から**「慣行の再現」**に変わる。同じ 1 語でも
理由が分野で違うことをここに残すのは、後から「利用者に不利だから直そう」と
いう誤った修正が入るのを防ぐためである。

### 丸めない方式は採らない

同じ入力に 2 つの正解がある。100 万円・年 1%・5 年・半年複利で:

| 方式 | 元利合計 | 税額 |
|---|---|---|
| 各期切り捨て（採用） | 1,051,136 円 | 10,387 円 |
| 途中丸めなし・最後に 1 回 | 1,051,140 円 | 10,389 円 |

**銀行の公開試算例と一致するのは後者である。**「銀行方式」は慣行の名前で
あって、特定の銀行の公開値の裏付けではない——ここを書いておかないと、
将来「銀行の例と合わない」という誤った修正を招く。

丸めない方式を採らないのは、答を出すのが f64 か Decimal になり、
「答は厳密整数」という上の規律を破るからである。

### 月利換算は名目のみ

年利 r の 1 期あたりの利率は **r ÷ 期/年**（月次なら r/12）とする。
実効換算 (1+r)^(1/12) − 1 は**無理数**なので分数の `Rate` では表せず、
厳密整数の経路に載らない。2 方式が実在すること（金融庁つみたて
シミュレーターは 2025 年に後者へ移った）は
[F1 設計](superpowers/specs/2026-08-14-finance-compound-design.md) §5 に
記録があるが、実装は名目のみである。

### 積立は期末

利息を付けてから積み立てる。その期に入れた金はその期の利息を生まない。
明記しているシミュレータは期末型が多数派で、Excel の `FV` の既定も期末である。

### 税

源泉分離課税 20.315% は、**国税 15.315% と地方税 5% を別々に円未満切り捨てる**
（国税庁 タックスアンサー No.1310）。`i·15315/100000` と `i·5/100` はどちらも
整数演算で表せる。**合算 20.315% を 1 回切り捨てるのとは結果が違う**——
利息 2,648,906 円で 1 円ずれる（別: 405,679 + 132,445 = 538,124 /
合算: 538,125）。課税対象は利息で、元本は含まない。

### 手取りは期数について単調でない

**税を引いた手取りは、期数を増やすと減ることがある。** 実測（元本 999 円・
年 1.5%・月次・積立なし）:

| n | 残高 | 利息 | 国税 | 地方税 | 手取り |
|---|---|---|---|---|---|
| 19 | 1,018 | 19 | 2 | 0 | **1,016** |
| 20 | 1,019 | 20 | 3 | 1 | **1,015** |

残高が 1 円増える間に税が 2 円増えている。利息 20 円が `0.15315 × 20 = 3.063` と
`0.05 × 20 = 1.00` の**両方の閾値を同時に跨ぐ**ためで、国税と地方税の floor が
同じ期に跳ぶ。別々に切り捨てる（No.1310）以上、避けられない。

**帰結 1: 目標額から必要年数を求めるとき、二分探索を使ってはならない。**
単調性を前提にする探索は静かに間違った答を返しうる。`MAX_PERIODS` まで
1 期ずつ前に進め、**最初に届いた期**を返す。

**帰結 2: 必要年数の直後に、目標を下回る期がありうる。** 上の例で目標
1,016 円の必要年数は 19 期だが、20 期では下回り、21 期で戻る。**これは仕様
である**——税の階段の性質であって不具合ではない。

**積立額については単調である。** 積立 +1 円で残高は `S ≥ n` 増え、利息は
`S − n` 増える。税の増分は 2 つの floor で `0.20315(S − n) + 2` を超えないので

    手取りの増分 ≥ S − (0.20315(S − n) + 2) ≥ n − 2

`n ≥ 3` で正。`n = 1` は積立が期末なので利息が動かず +1、`n = 2` は利息の増分が
0 か 1 で残高の増分が 2 か 3 なので +1 以上。**だから必要積立額は二分探索でよい。**

反例の探索範囲は
[複利の逆算 設計](superpowers/specs/2026-08-15-compound-inverse-design.md) §15。

## 式は有理数で評価し、着地で 1 回だけ丸める

金額・件数・期間・年利の入力欄では四則演算が打てる。**評価は既約分数で行い、
丸めるのは項目に着地させる 1 回だけ**である。

```
100万 ÷ 3 × 3   →  1000000/1  →  1,000,000
100万 ÷ 3       →  1000000/3  →    333,333（floor）
年利 1.5 + 0.25 →   175/100   →  1.75
```

各演算のたびに丸める方式（実物の電卓の多く）は採らない——`100万 ÷ 3 × 3` が
999,999 になり、**打つ順序で答えが変わる**（結合則が壊れる）。

**評価器は 1 つで、着地が項目ごとに違う。**

| 項目 | 定義域 | 着地 |
|---|---|---|
| 金額（借入額・残価・元本・積立額…） | u64 円 | floor |
| 件数・次元数 | u128 | floor |
| 期間 | u32 かつ ≤1200 | floor |
| 年利 | 小数 4 桁以内・0〜100% | **4 桁に収まらなければ SyntaxError** |

負の中間値は許すが、**着地で負なら SyntaxError**——金額も件数も期間も
符号なしの定義域だからである。0 除算は `DivisionByZero`。

年利の 4 桁は新しい規則ではない。`1.23456` は入口で拒否される（`Rate` は
小数 4 桁までの分数で持つ）ので、**計算で出た値にも同じ線を引く**——
`1 ÷ 3` % は表せないので拒否する。**表示できない値を黙って丸めない。**

### 分子・分母は `i128` で有界

Rust の標準ライブラリに多倍長整数は無い。多倍長のクレートを足す案も自前で
書く案も採らない——**依存ゼロと実装の小ささを優先する**。`calcarc-core` の
依存は `serde` だけである。

**分子か分母が `i128` に収まらなくなった時点で `Overflow` を返す。** その結果、
**数学的には定義域に戻る式もエラーになる**:

```
39桁 ÷ 3        → OK（分子は動かない）
100万 ÷ 3 × 3   → OK（約分で分母が消える）
39桁 × 2 ÷ 2    → Overflow（× の時点で分子があふれる）
```

**`i128` で足りるのは、使用域が天井よりずっと下だからである。** Data Scale の
現実的な上限を実測すると:

| 例 | bytes | 桁 |
|---|---|---|
| 1 億件・768 次元・float32 | 307,200,000,000 | 12 |
| 10 億件・1536 次元・float32 | 6,144,000,000,000 | 13 |
| 1 兆件・4096 次元・float64 | 32,768,000,000,000,000 | 17 |

**17 桁**である。`i128` の 39 桁は天井であって使用域ではない——38 桁は世界の
総データ量の 10^15 倍にあたる。

**天井は符号について対称である。** `i128::MIN`（`-170141183460469231731687303715884105728`）
は **`i128` に表現できるのに受けない**——**バグではなく、そう決めてある**。リテラルは
**絶対値の数字列を積んでから符号を付ける**ので、受ける帯は ±`i128::MAX` になる。
**符号は積む前に分かっている**（`parse_decimal` は最初に `-` を剥がす）ので、
`MIN` を通すのに要るのは**上限を 1 つずらすことだけ**である——**だから 1 行で
入り込む**。入れれば **2 の補数の非対称が入力の文法に漏れる**。
**`x` が打てるなら `-x` も打てる**という対称性のほうを採った。**止めているのは
`testdata/currency.json` の正負の対だけ**である。

**入口の検査は引数の位置順である**（`convert_currency`）。`value` → `from_rate` →
`to_rate` の順に、**各引数について構文 → 天井**を見て、前で落ちたら後ろは読まない。
だから**前の引数の天井超えと、後ろの引数の構文エラーが同時にあるとき、出るのは
`Overflow`** である。決めずに置くと、2 実装が別々に決めて静かに割れる
（実際に割れていた。2026-08-29）。

**`testdata/currency.json` は 2 件で留めているが、役割は違う。** 順序を判別するのは
**「前が天井超え・後ろが構文不正」の 1 件だけ**である（種類順なら `SyntaxError` に
なる）。逆向きの「前が構文不正・後ろが天井超え」は**どちらの順でも `SyntaxError`**
なので順序を判別しない——**対照**として置いてあり、「何が来ても `Overflow` を返す」
実装を排除する。

**観測できる契約は引数の位置順だけ**である。1 つの引数の中の「構文 → 天井」の順は
**原理的に観測できない**——構文が壊れた文字列は天井にも達しないので、どちらを先に
見ても同じ答になる。

**他の入口（`expr` の複数引数、`convert` の `category`/`from`/`to`）が同じ順序を
守っているかは未確認である**（2026-08-29 時点）。通貨で契約にしたのは、
**言語間で割れる実例がそこで出たから**であって、全入口を調べた結果ではない。

**継ぎ目**: 件数の着地は u128 のままである（`parse_count` は変えない）。
したがって **`i128::MAX` を超える件数は、直接入力なら通るが式に入れると
`Overflow`** になる。中間オーバーフローと同種の角で、理由も同じ——
**使う人がいない帯のために表現を重くしない。**

### 約分は最適化ではなく正しさの一部

**各演算のあとに必ず約分する。** 多倍長なら約分は「桁が爆発しないための
最適化」だが、**有界では「収まるかどうか」を左右する**。`100万 ÷ 3 × 3` が
通るのは、約分によって分母の 3 が消えるからである。約分をやめると、より長い
式で**予期しない `Overflow`** になる。

### 単位を解釈するのはコア

`3000万` はそのままコアへ渡り、コアが 30,000,000 にする。**単位表は
`calcarc-core` の中の定数**で、TypeScript は持たない——単位表を両方の言語に
置くと二重管理になり、ずれが静かに沈む（`KEY_TOKENS` と `Key::ALL` で
一度踏んだ形）。

TypeScript が持つのは**ラベル**（画面に出す文字）と**並び順**
（「億 の次に 万 は置けるが逆は不可」の判定）だけで、**scale の数値は要らない**。
評価器はどの単位表を使うかを引数で受ける（`yen` / `count` / `months` /
`periods:<n>`。複利では `年` の scale が 1 年あたりの期数になる）。

**単位は下る向きにしか置けない**（`1万億` は `SyntaxError`）。この規則は
盤面がキーを閉じて到達させないが、**契約としてコアにも置く**。

**単位トークンの綴りはワイヤ契約である。** 綴りがずれたら `SyntaxError` に
なる（黙って誤答にはならない）。

## エラー

| エラー | 条件 |
|---|---|
| `DivisionByZero` | 除数が 0 |
| `Overflow` | **定義域を超えた**。Scientific は f64 の有限範囲外（inf / NaN）、Data Scale は u128、Loan と複利は u64、式は中間の `i128` |
| `TrigPole` | Deg モードの `tan(90 + 180n)` |
| `SyntaxError` | 対応しない `)`、`.` の重複、**昇る向きの単位、着地が負、年利が 4 桁に収まらない** |

計算コアは panic しない。すべてのエラーは `Result` を通る。

**`Overflow` は 1 つの語で 4 つの定義域を指す。** モジュールごとに違うのは
定義域であって、意味（「その項目が持てる範囲を超えた」）は同じである。

## 実軸は演算で閉じている

実数だけを入力した計算は、実数のまま返る。出力の虚部は近似的にではなく
**厳密に 0** である。`5` と表示されるべき値が `5+j1e-16` になることはない。

**虚軸への出口は `j` キーだけである。**

かつては 2 つあった。`sqrt(-4)` が `j2` を返すのが設計上の機能で、
「従来機が `Math ERROR` を返す入力にこの電卓は答えられる」と誇っていた。
**S-1（2026-08-16）でその出口を塞いだ**——関数は実数に閉じる、という裁定で
ある（下の「関数の定義域」を参照）。

この性質は個々の関数の実装詳細に支えられている。`mul` の虚部が
`a.re*b.im + a.im*b.re` なので両虚部が 0 なら厳密に 0 になること、`div` が
`b.im == 0` のとき第 1 分岐で `t = 0` になること、`sin` / `cos` の
`sinh(0)` を負ゼロの均しが吸収すること、`tan` が実数どうしの `div` に
帰着すること。

**S-1 で足した 8 つ（`ln` `log10` `eˣ` `1/x` `asin` `acos` `atan` `xʸ`）は
この性質を弱めない。** 弱めるどころか自明にしている——どれも `real_arg` で
実数を取り出してから `f64` の関数に渡すので、**複素数が入ったら計算せずに
`DomainError` を返す**。虚部を作る経路そのものが無い。

守っているのは `crates/calcarc-core/tests/engine_robustness.rs` の不変条件
I3 で、打鍵列に対して継続的に検査している。**I3b（負の実数の `sqrt` は
純虚数）は S-1 で削除した**——`sqrt` がエラーを返すようになり、例外が
不要になったためである。例外を消したことで網は強くなった: `sqrt` を旧実装に
戻すと、名指しの検査 3 件に加えて網羅列挙も落ちる（実測）。

ただし**関数ごとの網羅ではない**。網羅列挙は後置関数を `√` 1 つに畳んで
いるため、他の単項関数に I3 を掛けているのは重みつきの proptest だけである。
**単項関数を足すときは、まず個別の固定テストを書くこと。**

## 関数の定義域

**関数は実数に閉じる**（S-1 の裁定、2026-08-16）。実数の答が一意に決まらない
入力は `DomainError` になる。

| 関数 | 定義域 | 外れたとき |
|---|---|---|
| `sqrt` | `x ≥ 0` | `DomainError`（**かつては `j2` を返していた**） |
| `ln` / `log10` | `x > 0` | `DomainError` |
| `asin` / `acos` | `−1 ≤ x ≤ 1` | `DomainError` |
| `atan` | 全実数 | — |
| `eˣ` | 全実数 | f64 に入らなければ `Overflow`（`DomainError` ではない） |
| `1/x` | `x ≠ 0` | **`DivisionByZero`** |
| `xʸ` | 下の表 | |

**どの関数も複素数の引数を受け取らない。** 実部だけ使う案は採らなかった
——それは**黙って別の計算をする**からである。

**【訂正 2026-08-17】** **`sin` / `cos` / `tan` は複素数の引数を受け取る**
（`trig_accepts_complex_arguments` が固定している）。S-1 で実数に閉じたのは
**新しく足した 8 つ**で、既存の三角関数はこの非対称を残したままである。

### `tan` の極は実数引数にしか掛からない

**`tan` の極（Deg で 90 + 180n 度）を `TrigPole` として弾くのは、実数の引数の
ときだけである。** 実部がちょうど 90 でも、虚部を持つ値は極として扱われず、
`sin / cos` の商がそのまま返る——値は巨大だが有限である。

| 入力（Deg） | 結果 |
|---|---|
| `90` | `TrigPole` |
| `90 + εj` | 商をそのまま返す（エラーにならない） |

**これは制約から出た形であって、見落としではない。** 極かどうかは
`a >= 90.0 && (a - 90.0) % 180.0 == 0.0` という**実数の順序と剰余**で決めて
いる。**複素数には順序が無い**ので、実数であることを先に確かめないとこの式が
書けない。複素の極を見るなら別の判定（`cos(z)` の絶対値が 0 にどれだけ近いか）
が要り、それは**近さの閾値を決める話**になる——`f64` の `tan(PI/2)` が
`1.633e16` という有限値を返すのと同じ問題を、複素平面でもう一度解くことになる。

盤面からこの入力に届くのは、`j` で虚部を打ってから `tan` を押した場合である。
`the_pole_guard_does_not_look_at_complex_arguments` が挙動を固定している。

**`1/x` が `DomainError` でないのは、利用者にとってそれがまさに 0 除算だから
である。** `5 ÷ 0` と `0` `1/x` が違うエラーを返す理由が無い。

`xʸ` の定義域:

| `x` | `y` | 答 |
|---|---|---|
| `x > 0` | 任意 | `exp(y·ln x)` |
| `x = 0` | `y > 0` | `0` |
| `x = 0` | `y = 0` | **`1`**（不定形だが電卓の慣行。IEEE 754 の `pow` も 1） |
| `x = 0` | `y < 0` | `DomainError` |
| `x < 0` | 整数 | 実数で一意（`(-2)^3 = -8`） |
| `x < 0` | 非整数 | `DomainError` |

**`0^(y<0)` が `DivisionByZero` ではなく `DomainError` なのは規約である**
——`1/x` の 0 とは別の裁定で、名前が非対称になっている。数学からは導けないので、
参照実装にも Rust にも「これは規約である」と明記してある。

**`sqr`（x²）と `+/−` は関数ではない。** 2 乗は乗算、符号反転は減算であり、
どちらも四則の側にあるので複素数のまま動く。**複素数は入力と四則と表示の
機能であって、関数の値域ではない。**

## 整数を返す演算を f64 でやること

`n!` `nPr` `nCr` は数学的には整数を返すが、`Value` は f64 である。

**`20!` = 2,432,902,008,176,640,000 は `2^53` を超えており、f64 では既に厳密でない。**
それでも困らないのは、**表示が有効数字 10 桁だから**である。

実測（2026-08-16）:

| | 相対誤差 | 表示に必要な精度 |
|---|---|---|
| `170!`（f64 の逐次乗算） | 6.9e-16 | 1e-10 |
| `nCr` 掛けてから割る（`n ≤ 1028` の格子で最悪） | 3.7e-15 | 1e-10 |
| **`nCr` 割ってから掛ける（採用。同じ格子で最悪）** | **4.5e-15** | 1e-10 |

**4 桁以上の余裕がある。表示される 10 桁はすべて正しい。**

**この 2 行は無作為抽出ではなく格子で測り直した値である**（`n = 0..1028`、
各 `n` について `r ∈ {0, 1, 2, n/4, n/3, n/2, n}`）。無作為 4,000 組で先に
測ったときは 3.5e-15 級と出たが、**中心二項係数の近くを取りこぼしていた**。
最悪値を主張するなら、悪くなる場所を狙って測ること。

上限は `170!` ≈ 7.257e306 で、**`171!` は `Overflow`** になる。

**厳密な整数表示はスコープ外である。** `20!` は `2.432902008e18` と出る——
19 桁は画面に入らない。

### `nPr` / `nCr` の溢れる境目は、ここに書かない

**書かないのは不作為ではなく判断である**（2026-08-30 に明文化）。

**階乗には境目が 1 つある**——引数が 1 つなので、`170` と `171` の間で切れる。
**`nPr` / `nCr` には無い。** 溢れるかどうかは `n` と `r` の**両方**で決まり、
**境目は 1 点ではなく `(n, r)` 平面の曲線**である——`C(1200, 600)` は溢れるが
`C(1200, 1)` は溢れない。**代表点を 1 つ選んで書けば、それは仕様ではなく
「書いた人が選んだ点」になる。**

**そのかわり、この文書は確かめたいものを名指ししている:**

- **`n ≤ 1028` の格子**（上の誤差の表）——**最悪値を狙って測る場所**
- **`n = 1022`〜`1028` の中心二項係数**（下の「掛けてから割る」の行）
  ——**答は収まるのに段の中で溢れる帯**。**採用した順序が落ちない**ことを
  主張したいのは、ここである

**生成コーパスはその帯を踏んでいる**（`combinatorics-000.json` の上限は
`COMBINATORICS_MAX_N = 1200`。実測の最大は `(1099 nPr 102) = 1.2037e308`）。
**溢れた側は `combinatorics-display-000.json` が `(171)!` で持つ**——
**そちらは境目が名指しできる唯一の形だからである。**

### `nCr` は「割ってから掛ける」

`acc ← acc / (i+1) × (n − i)`。**順序が定義域を決める。**

| 書き方 | 落ちるところ |
|---|---|
| 素直な `n!/(r!(n−r)!)` | `200 nCr 100`（答は 9.05e58 なのに `200!` が溢れる） |
| 掛けてから割る | `n = 1022`〜`1028` の中心二項係数（**答は収まるのに段の中で溢れる**） |
| **割ってから掛ける** | 答が f64 に収まる限り落ちない |

**「答が収まるなら途中も収まる」は、この順序でしか成り立たない。**
掛けてから割る形の途中ピークは `C(n, i+1) × (i+1)` で、**答の最大 `r` 倍**である。

**途中値の主張は、段の切れ目ではなく段の中のピークで検算すること**
——この帯は「各段の値は `C(n, i+1)` である」という正しい観察から
「だから途中も収まる」を導いて見落とされた。

## 60 進表示（`°'"`）

**値は 10 進の f64 のままで、60 進は入力と表示の形式である**（S-4 設計書 §1）。
だから四則演算を 1 つも足していない——`1:30 + 2:45` は `1.5 + 2.75` である。

同じ形式が**経過時間と角度の両方**を表す。`3.75` は `3°45'0"` とも
「3 時間 45 分」とも読め、**どちらの意味かは利用者の頭の中にしかない。**

**24 で割らない**（裁定 5）。`30.5` は `30°30'0"` と出る——経過時間の計算では
`30:00:00` が要る。

**秒の小数桁は `DISPLAY_DIGITS` の残り**（裁定 7）。度が `nd` 桁、分が 2 桁、
秒の整数部が 2 桁を使うので、秒の小数は `10 − nd − 4` 桁になる。
秒に小数を許さないと `0.001` 時間（= `0°0'3.6"`）が表せない。

**丸めで秒が 60 になったら繰り上げる。** `0.999999999` は秒が 59.9999996 で、
5 桁に丸めると 60.00000 になり、**分へ、さらに度へ二段繰り上がって `1°0'0"`**
になる。繰り上げを外すと `0°59'60"` が出る（実測）。`format_real` が
`9999999999.6 → 1e10` で踏んだのと同じ形で、手も同じ——**先に丸めてから
桁を決める**。

**60 進にできない値には何もしない**（裁定 6）。非有限と、度が有効数字を使い切る
値（`1e10` 以上）がそれで、**表示を変えないだけでエラー状態には落とさない。**
表示の操作でエラーにするのは重い。

## `xʸ` は右結合である

`2 xʸ 3 xʸ 2` は `2^(3^2) = 512` であって `(2^3)^2 = 64` ではない。
**このエンジンで右結合なのは `xʸ` だけ**で、`+` `−` `×` `÷` は左結合のまま
である（`10 − 3 − 2` は `5`）。

数学の慣行に合わせた、というだけではない。**独立検証層（mpmath）が慣行に
従う**ので、左結合を選ぶと恒久的に食い違い、それを消す唯一の方法は Python に
engine の意味論を教えることになる。それは CONTRIBUTING の「参照実装を Rust の
移植にしない」に真正面から当たる。**独立した検証層が、実装前に設計判断を
動かした事例である。**

優先順位は `+ −` が 1、`× ÷` が 2、`xʸ` が 4。**3 は空けてある**
（`nPr` / `nCr` の席）。

**【訂正 2026-08-17】** **3 は埋まった。** `nPr` / `nCr` がその席に入っている
（S-3、`crates/calcarc-core/src/engine/state.rs`）。

## 既知の制約

- Rad モードの `tan` は極を検出できない。`PI / 2` が f64 で厳密に表現できず、
  `tan` が有限の巨大値を返すため。Deg モードでのみ検出する。
- `sin(180°)` は `1.224646799e-16` を返す。極近傍のゼロ吸着は
  Milestone 3 後半で扱う。
- **`sqrt` は複素数を受け取らない**（S-1、2026-08-16）。かつては一般の複素数を
  極形式経由で、負の実数を専用経路で扱っていたが、どちらも `DomainError` に
  なった。理由は「関数の定義域」節に書いた。
- 原点 `0 + j0` の偏角は数学的には未定義である。IEEE 754 の
  `atan2(+0, +0) = +0` に従い、0 と定める。Rust の `f64::atan2` は標準どおり
  この値を返し、Python 参照実装も同じ約束を明示的に採る。SymPy の
  `atan2(0, 0)` は nan を返すため、参照実装側で先に潰している。
- **複利の厳密ループは閉形式より小さい。** 各期の切り捨てが積み上がるため
  で、向きは常に一方向である（閉形式のほうが大きい）。ずれは期数と率で決まり、
  上界は 期数 × (1+r)^期数 円。実測では月 3 万円・年 5%・50 年（600 期）で
  1,290 円（上界 7,272 円）、100 万円・年 1%・5 年・半年複利で 4.13 円
  （上界 10.5 円）。Python 参照実装はこの不等式を毎回検査し、番人にする。
- 角度の単位変換は度からラジアンへ f64 で `π/180` を掛けるため、角度が
  大きいほど誤差が増幅する。Python 参照実装（mpmath 50 桁）との実測差は
  1e5 度で 9.1e-15、1e6 度で 3.3e-13、1e7 度で 1.8e-12 であり、
  突き合わせの許容誤差 1e-12 を超えるのは 1e6 度と 1e7 度のあいだになる。
  ラジアンモードでは変換が入らないため、1e6 まで全桁一致する。
- アンダーフローで結果が 0 になっても、オーバーフローとは違いエラーには
  ならない。base-spec §27 はアンダーフローもオーバーフローと並べて挙げて
  いるが、この非対称は現時点では意図的な仕様であり、ここに明記しておく。
- Data Scale の単位表示は 1000..=1023 bytes で非対称になる。10 進は
  `"1.0 KB"` が出るが、2 進の最小単位は 1024 なのでこの範囲は bytes の
  ままで、KiB 行は出ない（`crates/calcarc-core/src/data_scale/format.rs`
  の `below_the_smallest_unit_there_is_no_line`）。
- Deg モードの `tan` の極検出は、90° の厳密な整数倍しか捕まえない。
  `89.99999999` は誤差にならず `5729578980` を返す。
- Deg モードは実部・虚部の両方を π/180 倍する。したがって `j1` に `sin` を
  適用すると Deg モードでも `j0.01745417863`（= `sinh(1°)`）になる。これは
  複素数の引数を「角度の単位を持つ量」として読む、意図的な解釈である。
- Loan の残価は、まれに 1 円届かない。最終回の支払は
  X + floor(X × 月利)（X は 1 回前の残高）で、この階段関数は 1 か 2 ずつ
  増えるため残価 B を飛ばすことがある。飛んだときは B を超えない最大値
  = B − 1 円を最終回とする（切り捨てに揃える丸め規約と同じ向き）。年 2% で
  B = 1,201 円がその例（f(1199) = 1200、f(1200) = 1202）。言語間検証で
  固定しているのは `finance.json` の `loan_forward/3000000/3.9/60/1200195`
  （300 万・5 年・年 3.9%・残価 1,200,195 円 → 最終回 1,200,194 円）。
- Loan の期間逆算は 1,200 か月（100 年）で打ち切り、超えるものは発散として
  SyntaxError にする。月額が初回利息をわずかに上回るだけの入力は数学的には
  収束しても現実の期間に収まらない。なお「終わるかどうか」を決めるのも表で
  ある: 年 12%・月額が利息 +1 円のとき、元本 100 万円なら各行の利息切り捨てが
  効いて 884 回で終わり、1 億円なら 100 年でも終わらない。
- Loan は残価とボーナス併用を同時に扱わない。設計が残価（正算のみ）と
  ボーナス（2 列独立）をそれぞれ決め、両者を重ねた式を決めていないため、
  UI でも片方が埋まっている間は他方を無効にする。

  **【訂正 2026-08-17】** **排他が効くのは月額モードだけである**
  （`web/src/ui/Finance/FinancePanel.tsx:336-345`）。残価は月額モードでしか
  使えず、ボーナスは期間モードでは使えない。借入可能額モードでは残価が
  計算に入らないので、そこに残っている値でボーナスを塞がない。
- 値そのものが有限でも、極形式の絶対値だけが f64 の範囲を超えることがある。
  `hypot(f64::MAX, f64::MAX)` は inf になるが、実部・虚部それぞれは有限で
  `Value::finalize()` を通り抜ける。この溢れは engine の
  `Value::finalize()` では捕まえられず、表示層の `try_format_polar` で
  初めて分かる。engine の状態はエラーにせず
  （直交形式では表示できるため）、表示された `DisplayState` の側で
  `error = Some(Overflow)` を報告して自己矛盾を防ぐ。`▸∠` で直交形式に
  戻れば通常どおり使える。

## 許容誤差

Rust と Python の突き合わせに使う許容誤差は `testdata/*.json` の
`tolerance` に置く。テストコードに誤差値を書かない。

### 複素数の比較はノルムで行う

複素数の乗除算は成分ごとの相対精度を保証しない。小さいほうの成分は大きな
数どうしの積の差として復元されるため桁落ちし、成分比が偏るほど失う桁が
増える。これは実装の不備ではなく複素数演算の性質である。

実測（issue #3、恒等式 `(a*b)/b == a` を乱数 50 万件、成分 -1000..1000）:

| 指標 | 最大相対誤差 |
|---|---|
| 成分ごと | 7.26e-12 |
| ノルム | 4.30e-16 |

この実測は恒等式 `(a*b)/b` の往復（Rust 内部の自己整合）であり、golden の
比較そのもの（Rust と Python の突き合わせ）ではない。

最悪ケースでは虚部が実部の 9.4e-6 倍で、虚部の相対誤差 7.26e-12 に対し
ノルムの相対誤差は 6.8e-17 —— f64 の丸め誤差の水準であり、計算は限界まで
正しい。成分ごとに見たときだけ誤差が大きく見える。

そのため golden の比較は、期待値が複素数であるものすべてについて
**差ベクトルのノルム**で行う（`golden.rs` の `close_complex`）。`r` と
`theta_deg` は独立に意味を持つスカラーなので成分ごとのまま。

**この一様な線は、加減算については意図的な弱体化である。** 加減算は成分
ごとに独立に正しく丸められるため、成分ごとの相対精度を保証できる演算で
あり、成分ごと比較のほうが強い検査になる（例: `(1e6, 1e-8)` の加算で虚部が
100% 狂っても、差 1e-8 < rel×ノルム 1e-6 で通る）。それでも一様な線を採る
のは、演算ごとに基準を分けると次に演算を足す人が毎回この判断をやり直すこと
になるため。加減算の成分レベルの厳密さは `value.rs` の単体テスト（完全一致）
が固定しており、実害はない。見落としではなく選択である。

同様に、期待値が実数（im = 0）の複素ケース（`scientific.json` の全件と
`polar_to_rect` の実軸上ケース）では、虚部の許容が絶対 1e-12 から
rel × |re| に緩む（実測: sqrt(1e8) で 1e-8 と 1 万倍、tan 89° で 5.7e-11 と
57 倍）。「結果が実数であること」の検査としては絶対ゼロ判定から相対判定への
緩和である。実数性そのものは `scientific` の単体テスト（`Value::imag` の
完全一致等）が担保しており、ここでも一様な線を優先する。これも見落としでは
なく選択である。

**golden の期待値は「実際の f64 入力の厳密解」ではなく「10 進表記の入力の
厳密解」である。** 参照実装の `_exact()` が str 経由で入力を有理数化する
ため——10 進で書いた入力を 10 進として扱う意図的な設計であり
（`complex_ref.py` 参照）、f64 の二進表現には戻さない。ノルム比較はこの差
（入力の 1e-16 級）に頑健だが、条件数の大きいケースでは成分ごとの見え方に
増幅されて効く——下表の凍結ケースでは成分差の約 97% がこれに由来する
（`cases.py` の帰属分解を参照）。

golden に凍結した実証ケース（`cases.py` の BINARY_INPUTS 末尾、除算）の実測:

| 量 | 相対誤差 |
|---|---|
| Rust（Smith 法）自身の誤差 | 3.89e-10 |
| 参照側の 10 進入力丸め由来（条件数 ~6e8 で増幅） | 1.36e-8 |
| ノルム（golden が検査する量） | 2.16e-16 |

成分ごとに見れば Rust 自身の誤差だけでも rel tol を桁違いに超えて赤になり、
ノルムでは丸め誤差の水準に収まる——これが比較をノルムにした理由の、
golden 自身による実証である。
