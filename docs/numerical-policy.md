# Numerical Policy

CalcArc が数値をどう扱うかの規則。実装より先にここを読むこと。

## 内部表現

すべての値を複素数 `Value { re: f64, im: f64 }` として保持する。実数は虚部 0
の複素数である。実数型と複素数型を分けないため、演算に型分岐が生じない。

角度は内部では常にラジアンで保持する。度への変換は表示層でのみ行う。

## 表示

- 有効数字 10 桁。
- 丸めは round-half-to-even（Rust の書式化に一致）。
- `|x| >= 1e10` または `0 < |x| < 1e-9` で指数表記。
- 直交形式は `3+j4`、極形式は `5 ∠ 53.13010235`。
- 入力欄は 12 文字まで受け付けるが、表示は有効数字 10 桁に丸める。したがって
  12 桁の入力は `=` を押した瞬間に見た目が変わりうる（`999999999999` →
  `1e12`）。値そのものは変わらず、変わるのは表示規則だけである。

表示のための丸めは表示文字列を作るときにのみ行い、保持している値には
書き戻さない。`▸∠` は表示形式を切り替えるだけで再計算しない。したがって
表示上の丸め値が次の計算の入力になることはない。

### 整数値の表示（Data Scale）

- 小数第 1 位まで、round-half-to-even で丸める。
- 丸めで表示値が単位の基数（10 進は 1000、2 進は 1024）に達したら、
  1 つ上の単位で丸め直す（最上位の単位は例外——そのまま伸びる）。
- 換算経路に f64 を使わない。商と剰余の u128 演算だけで丸める。

規則の詳細は
[docs/superpowers/specs/2026-08-11-data-scale-design.md §3](superpowers/specs/2026-08-11-data-scale-design.md)
を見ること。

## 第 3 の分類: Loan は決定的概算

数値の扱いは 3 つに分かれる。**Scientific = 浮動小数点**、
**Data Scale = 厳密整数**、そして **Loan = 決定的概算**である。

決定的概算とは、**実額の機関一致を目標にしない**という宣言である。返済額の
端数処理・手数料・日割りは金融機関ごとに違い、「どの銀行とも一致する」計算は
存在しない。代わりに保証するのは決定性——同じ入力は常に同じ答を返し、方法は
仕様に書かれ、Python 独立実装が検証する。UI には免責を常設する。

Loan の中では経路が 2 本に分かれる。

**償還表は厳密整数だけで走る。** 各行の利息は
floor(残高 × 月利分子 / 月利分母) を u128 中間で計算し、f64 を通さない。
金額は u64 円で持つ。

理由は実測である。年 2.7%・残高 1,200 万円の 1 か月分の利息は、厳密には
**27,000 円ちょうど**（12,000,000 × 27/12000）。同じ計算を f64 で
`floor(12_000_000.0 * 0.00225)` とすると **26,999 円**になる。丸い元本と
bp 刻みの金利という**最頻の入力**がまさに円境界を踏むので、この 1 円は例外
ではなく常態である（3,000 万円は全 bp 刻み金利で境界上）。

**f64 は閉形式の月額決定にだけ使う。** そこでも `(1+r)^n − 1` を素朴には
計算せず `expm1(n·log1p(r))` で評価する。素朴式は低金利で桁落ちし、年
0.001% では ~1e-5 円まで悪化する。expm1 経路の誤差上限は入力依存で概ね
月額 × max(n·ε/2, ε/(2r))。

**逆算 2 種の答は f64 が決めない。** f64 の閉形式は候補を出すだけで、
「n 回で完済する最小の n」「n 回で完済する最大の元本」を厳密償還表への単調
探索で確定する。実測では厳密表の答は候補より離れうる——85,000 円 × 420 回・
年 1.5% の借入可能額で **167 円**高い（各行の利息切り捨てが積み上がるぶん、
連続式より多く借りられる）。

### 境界近接ガードは golden 生成側にある

f64 を floor して決まる出力（= 月額）が円境界に近すぎるケースは、Python の
生成側が `ValueError` で落とし、golden に入れない。基準は
max(1e-6 円, 値 × 1e-9)。**相対の項が要る**のは、絶対 1e-6 円が 9 万円の
月額を守れても 3,000 万円の月額を守れないからである（f64 自身の誤差が
すでに 0.03 円ある）。

第 2 の根拠: golden 生成と CI は x86、実行はブラウザ（wasm32）で、
expm1/log1p の libm 実装が違えば ulp 差がありうる。境界から離しておくことは
その差の吸収層でもある。

逆算 2 種は上記のとおり表が答を確定するので、**floor される f64 出力が
存在せず、ガードの対象にならない**（設計書 §1-4 は逆算にもガードを課して
いたが、それは答が候補の floor で決まる前提の記述だった。表確定にした結果、
守るべき floor が消えている）。

## エラー

| エラー | 条件 |
|---|---|
| `DivisionByZero` | 除数が 0 |
| `Overflow` | 結果が f64 の有限範囲外（inf / NaN） |
| `TrigPole` | Deg モードの `tan(90 + 180n)` |
| `SyntaxError` | 対応しない `)`、`.` の重複 |

計算コアは panic しない。すべてのエラーは `Result` を通る。

## 実軸は演算で閉じている

実数だけを入力した計算は、実数のまま返る。出力の虚部は近似的にではなく
**厳密に 0** である。`5` と表示されるべき値が `5+j1e-16` になることはない。

虚軸への出口は 2 つだけで、どちらも意図したものである。

- `j` キー
- **負の実数の平方根。** `sqrt(-4)` は `j2` を返す。従来の関数電卓が
  `Math ERROR` を返す入力に、複素数を扱うこの電卓は答えられる。このとき
  実部は厳密に 0 である（極形式を経由する実装では 1.2e-16 が残るため、
  負の実数には専用の経路を用意している）

この性質は個々の関数の実装詳細に支えられている。`mul` の虚部が
`a.re*b.im + a.im*b.re` なので両虚部が 0 なら厳密に 0 になること、`div` が
`b.im == 0` のとき第 1 分岐で `t = 0` になること、`sin` / `cos` の
`sinh(0)` を負ゼロの均しが吸収すること、`tan` が実数どうしの `div` に
帰着すること。`ln` / `exp` / `asin` / `acos` / `atan` / `xʸ` を足すと
自明でなくなる。

守っているのは `crates/calcarc-core/tests/engine_robustness.rs` の不変条件
I3 / I3b で、打鍵列に対して継続的に検査している。ただし**関数ごとの
網羅ではない**。網羅列挙は後置関数を `√` 1 つに畳んでいる（設計書 §5.2）
ため、`sin` / `cos` / `tan` / `x²` と `÷` に I3 を掛けているのは重みつきの
proptest だけである。`ln` などを足すときは、まず個別の固定テストを
書くこと。

## 既知の制約

- Rad モードの `tan` は極を検出できない。`PI / 2` が f64 で厳密に表現できず、
  `tan` が有限の巨大値を返すため。Deg モードでのみ検出する。
- `sin(180°)` は `1.224646799e-16` を返す。極近傍のゼロ吸着は
  Milestone 3 後半で扱う。
- 一般の複素数の `sqrt` は極形式を経由する。負の実数だけが専用経路を
  通る理由は「実軸は演算で閉じている」節に書いた。
- 原点 `0 + j0` の偏角は数学的には未定義である。IEEE 754 の
  `atan2(+0, +0) = +0` に従い、0 と定める。Rust の `f64::atan2` は標準どおり
  この値を返し、Python 参照実装も同じ約束を明示的に採る。SymPy の
  `atan2(0, 0)` は nan を返すため、参照実装側で先に潰している。
- 角度の単位変換は度からラジアンへ f64 で `π/180` を掛けるため、角度が
  大きいほど誤差が増幅する。Python 参照実装（mpmath 50 桁）との実測差は
  1e5 度で 9.1e-15、1e6 度で 3.3e-13、1e7 度で 1.8e-12 であり、
  突き合わせの許容誤差 1e-12 を超えるのは 1e6 度と 1e7 度のあいだになる。
  ラジアンモードでは変換が入らないため、1e6 まで全桁一致する。
- アンダーフローで結果が 0 になっても、オーバーフローとは違いエラーには
  ならない。base-spec §27 はアンダーフローもオーバーフローと並べて挙げて
  いるが、この非対称は現時点では意図的な仕様であり、ここに明記しておく。
- Data Scale の単位表示は 1000..=1023 bytes で非対称になる。10 進は
  `"1.0 KB"` が出るが、2 進の最小単位は 1024 なのでこの範囲は bytes の
  ままで、KiB 行は出ない（`crates/calcarc-core/src/data_scale/format.rs`
  の `below_the_smallest_unit_there_is_no_line`）。
- Deg モードの `tan` の極検出は、90° の厳密な整数倍しか捕まえない。
  `89.99999999` は誤差にならず `5729578980` を返す。
- Deg モードは実部・虚部の両方を π/180 倍する。したがって `j1` に `sin` を
  適用すると Deg モードでも `j0.01745417863`（= `sinh(1°)`）になる。これは
  複素数の引数を「角度の単位を持つ量」として読む、意図的な解釈である。
- Loan の残価は、まれに 1 円届かない。最終回の支払は
  X + floor(X × 月利)（X は 1 回前の残高）で、この階段関数は 1 か 2 ずつ
  増えるため残価 B を飛ばすことがある。飛んだときは B を超えない最大値
  = B − 1 円を最終回とする（切り捨てに揃える丸め規約と同じ向き）。年 2% で
  B = 1,201 円がその例（f(1199) = 1200、f(1200) = 1202）。言語間検証で
  固定しているのは `finance.json` の `loan_forward/3000000/3.9/60/1200195`
  （300 万・5 年・年 3.9%・残価 1,200,195 円 → 最終回 1,200,194 円）。
- Loan の期間逆算は 1,200 か月（100 年）で打ち切り、超えるものは発散として
  SyntaxError にする。月額が初回利息をわずかに上回るだけの入力は数学的には
  収束しても現実の期間に収まらない。なお「終わるかどうか」を決めるのも表で
  ある: 年 12%・月額が利息 +1 円のとき、元本 100 万円なら各行の利息切り捨てが
  効いて 884 回で終わり、1 億円なら 100 年でも終わらない。
- Loan は残価とボーナス併用を同時に扱わない。設計が残価（正算のみ）と
  ボーナス（2 列独立）をそれぞれ決め、両者を重ねた式を決めていないため、
  UI でも片方が埋まっている間は他方を無効にする。
- 値そのものが有限でも、極形式の絶対値だけが f64 の範囲を超えることがある。
  `hypot(f64::MAX, f64::MAX)` は inf になるが、実部・虚部それぞれは有限で
  `Value::finalize()` を通り抜ける。この溢れは engine の
  `Value::finalize()` では捕まえられず、表示層の `try_format_polar` で
  初めて分かる。engine の状態はエラーにせず
  （直交形式では表示できるため）、表示された `DisplayState` の側で
  `error = Some(Overflow)` を報告して自己矛盾を防ぐ。`▸∠` で直交形式に
  戻れば通常どおり使える。

## 許容誤差

Rust と Python の突き合わせに使う許容誤差は `testdata/*.json` の
`tolerance` に置く。テストコードに誤差値を書かない。

### 複素数の比較はノルムで行う

複素数の乗除算は成分ごとの相対精度を保証しない。小さいほうの成分は大きな
数どうしの積の差として復元されるため桁落ちし、成分比が偏るほど失う桁が
増える。これは実装の不備ではなく複素数演算の性質である。

実測（issue #3、恒等式 `(a*b)/b == a` を乱数 50 万件、成分 -1000..1000）:

| 指標 | 最大相対誤差 |
|---|---|
| 成分ごと | 7.26e-12 |
| ノルム | 4.30e-16 |

この実測は恒等式 `(a*b)/b` の往復（Rust 内部の自己整合）であり、golden の
比較そのもの（Rust と Python の突き合わせ）ではない。

最悪ケースでは虚部が実部の 9.4e-6 倍で、虚部の相対誤差 7.26e-12 に対し
ノルムの相対誤差は 6.8e-17 —— f64 の丸め誤差の水準であり、計算は限界まで
正しい。成分ごとに見たときだけ誤差が大きく見える。

そのため golden の比較は、期待値が複素数であるものすべてについて
**差ベクトルのノルム**で行う（`golden.rs` の `close_complex`）。`r` と
`theta_deg` は独立に意味を持つスカラーなので成分ごとのまま。

**この一様な線は、加減算については意図的な弱体化である。** 加減算は成分
ごとに独立に正しく丸められるため、成分ごとの相対精度を保証できる演算で
あり、成分ごと比較のほうが強い検査になる（例: `(1e6, 1e-8)` の加算で虚部が
100% 狂っても、差 1e-8 < rel×ノルム 1e-6 で通る）。それでも一様な線を採る
のは、演算ごとに基準を分けると次に演算を足す人が毎回この判断をやり直すこと
になるため。加減算の成分レベルの厳密さは `value.rs` の単体テスト（完全一致）
が固定しており、実害はない。見落としではなく選択である。

同様に、期待値が実数（im = 0）の複素ケース（`scientific.json` の全件と
`polar_to_rect` の実軸上ケース）では、虚部の許容が絶対 1e-12 から
rel × |re| に緩む（実測: sqrt(1e8) で 1e-8 と 1 万倍、tan 89° で 5.7e-11 と
57 倍）。「結果が実数であること」の検査としては絶対ゼロ判定から相対判定への
緩和である。実数性そのものは `scientific` の単体テスト（`Value::imag` の
完全一致等）が担保しており、ここでも一様な線を優先する。これも見落としでは
なく選択である。

**golden の期待値は「実際の f64 入力の厳密解」ではなく「10 進表記の入力の
厳密解」である。** 参照実装の `_exact()` が str 経由で入力を有理数化する
ため——10 進で書いた入力を 10 進として扱う意図的な設計であり
（`complex_ref.py` 参照）、f64 の二進表現には戻さない。ノルム比較はこの差
（入力の 1e-16 級）に頑健だが、条件数の大きいケースでは成分ごとの見え方に
増幅されて効く——下表の凍結ケースでは成分差の約 97% がこれに由来する
（`cases.py` の帰属分解を参照）。

golden に凍結した実証ケース（`cases.py` の BINARY_INPUTS 末尾、除算）の実測:

| 量 | 相対誤差 |
|---|---|
| Rust（Smith 法）自身の誤差 | 3.89e-10 |
| 参照側の 10 進入力丸め由来（条件数 ~6e8 で増幅） | 1.36e-8 |
| ノルム（golden が検査する量） | 2.16e-16 |

成分ごとに見れば Rust 自身の誤差だけでも rel tol を桁違いに超えて赤になり、
ノルムでは丸め誤差の水準に収まる——これが比較をノルムにした理由の、
golden 自身による実証である。
