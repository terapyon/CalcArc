## 1. いまの約束（`docs/numerical-policy.md` の原文）

**「関数の定義域」の表に `sin`/`cos`/`tan` の行は無い**（`sqrt`・`ln`/`log10`・
`asin`/`acos`・`atan`・`eˣ`・`1/x`・`xʸ` の 7 行だけ）。**大きさの上限は、どこにも約束されていない。**

**「既知の制約」には、この件そのものが既に書かれている**（原文）:

> 角度の単位変換は度からラジアンへ f64 で `π/180` を掛けるため、角度が
> 大きいほど誤差が増幅する。Python 参照実装（mpmath 50 桁）との実測差は
> 1e5 度で 9.1e-15、1e6 度で 3.3e-13、1e7 度で 1.8e-12 であり、
> 突き合わせの許容誤差 1e-12 を超えるのは 1e6 度と 1e7 度のあいだになる。
> ラジアンモードでは変換が入らないため、1e6 まで全桁一致する。

**つまり「誤差が増える」ことは既知で、文書に数まで在る。** **約束していないのは
「どこから先は答えないか」**である。

## 2. engine は大きな引数で何をするか——**何も見ていない**

`crates/calcarc-core/src/scientific/mod.rs`:

```rust
pub fn sin(v: Value, mode: AngleMode) -> CalcResult<Value> {
    let z = to_rad(v, mode);
    let (sine, cosine) = circular(v, mode, z);
    Value::new(sine * z.im.cosh(), cosine * z.im.sinh()).finalize()
}
```

- **引数の大きさを見る判定は 1 つも無い。** 見るのは `quadrant_exact` の
  `x % 360.0` が 0・90・180・270 かだけで、**これは位置の判定で大きさの判定ではない。**
- **エラー経路は `Value::finalize` の 1 つだけ**（`value.rs:46`、非有限なら `Overflow`）。
  **`sin`/`cos` の値は有界なので、実引数では決して非有限にならない**（§12 で実測）。
- **`sin`/`cos`/`atan` は自前の `Err` を 1 件も持たない。** `tan` だけが `TrigPole`
  （`mod.rs:125`、リポジトリ唯一の生成点。**Deg の実数引数限定**）。
  **`asin`/`acos` だけが大きさを見る**（`-1.0..=1.0`）。
- **上の層（`engine/mod.rs` の `apply_unary`）にも門番は無い**（関数キーは素通し）。

## 3. 実測——**RAD は無傷、DEG だけが崩れる**

**engine に通した値を、mpmath 60 桁の真値と並べた**（`sin`/`cos`/`tan` × 22 点 × 2 モード）。
**判定は「画面に出る有効数字 10 桁が真値と一致するか」**——利用者が見るのはそれである。

### 3.1 RAD

**1e1 から 1e18 まで、66 件すべて 10 桁一致。** 誤差は 1e-17〜1e-16 台。
**`f64::sin` は引数の縮約を正しくやっている。**

### 3.2 DEG——10 桁が初めて狂う点

| 関数 | 10 桁が初めて違う x |
|---|---|
| `tan` | **1e7** |
| `cos` | **1e8** |
| `sin` | **1e9** |

**1e9 以上は 3 関数すべて違う。** 例（左が engine、右が真値）:

```
Deg 1e+09 sin  -9.8480775281e-01  /  -9.8480775301e-01   rel 2.0e-10
Deg 1e+15 sin  -9.8495454229e-01  /  -9.8480775301e-01   rel 1.5e-04
Deg 1e+18 tan  -2.3307307423e+00  /  -5.6712818196e+00   rel 5.9e-01
```

### 3.3 桁ごとに無作為に撒いて数えた（各桁 300 件、種 20261003）

**★ 帯は `[1e(k-1), 1e k)` である。** **最初この表を上限の桁（`1e6` など）で
呼んでいたが、それだと 1 桁ずれる**（`uniform(10**(e-1), 10**e)` を `1e{e}` と
印字していた）。**下は帯で書き直したもの**（各帯 300 件）。

|---|---|---|---|
| `[1e0, 1e5)` | 0 | 1.39e-13 | 0 |
| **`[1e5, 1e6)`** | **4** | 1.28e-12 | 0 |
| `[1e6, 1e7)` | 23 | 1.62e-11 | 0 |
| `[1e7, 1e8)` | 80 | 1.29e-10 | 0 |

| `[1e9, 1e10)` | 293 | 1.67e-08 | 0 |

**`[1e15, 1e16)` から 300 件中 2〜6 件**が違う。

## 4. 誤差の出どころ——**`sin` ではなく、度→ラジアンの変換**

**3 つを並べて測った**（f64 で模擬し、**(a) が engine のビットと完全一致することを先に確かめた**）:

- **(a) いまの順**: `sin(x * (π/180))`
- **(b) `% 360` を先**: `sin(fmod(x, 360) * (π/180))`
- **(c) 真値**: mpmath

| | 10 桁が真値と違う件数 |
|---|---|
| **(a) いまの順** | **10 / 22**（10 の冪の標本）／**上の §3.3 の表** |
| **(b) `% 360` が先** | **0 / 22**。**無作為の掃引では `1e15` 度未満で 0 件**、帯 `[1e15, 1e16)` で 3/300、`[1e16, 1e17)` で 6/300、`[1e17, 1e18)` で 2/300 |

**`x % 360` は IEEE の `fmod` で厳密**であり、**この式は既にコードに在る**
（`quadrant_exact` が象限を決めるのに使っており、その docstring に
「**`% 360` は IEEE の `fmod` で厳密**」「**ずれを持ち込んでいるのは `to_rad`**」と書かれている）。

**つまり原因は 1.0.0 の時点で特定されていて、直したのは表に載る 4 つの角だけだった。**

## 5. 1.0.0 は何を直して、何を直していないか（`4f81d7a` の差分）

**足したのは `quadrant_exact`（22 行）と `circular`。** **`x % 360` の絶対値が
0・90・180・270 のときだけ、`sin`・`cos` を厳密な 0・±1 の表から返す。**
**それ以外の角は 1 行も変えていない。** **RAD は触っていない**（docstring:
「**RAD には広げない。** あちらは**入力そのものが厳密でない**」）。

**CHANGELOG 1.0.0 の原文**も、範囲をそう書いている:

> **90°ごとでない角も、いままでどおり**です。30°の【sin】は 0.5 と出ますが、
> **これは表示の桁でそう見えているだけ**です

**利用者の「修正したと思うけど」が指すのはこれ**で、**大きな角は範囲に入っていなかった。**

### 6.1 ★ golden を足せば捕まるのか——**捕まる**

`reference/src/calcarc_reference/scientific_ref.py`:

```python
mp.mp.dps = 50
def _to_radians(x: float, mode: str) -> mp.mpf:
    v = mp.mpf(str(x))
    if mode == "Deg":
        return v * mp.pi / 180
```

**参照は 50 桁の π で変換する**ので、**真値を出す。** **`sin Deg 1e9` の golden を
足せば、engine の `-9.8480775281e-01` は `abs/rel 1e-12` の外で赤くなる**
（実測の相対誤差 2.0e-10）。**手順も違う**（Rust は libm の f64、参照は mpmath 50 桁）
——**独立性は保たれている。**

## 7. 利用者の仮説を、測った数に当てる

> **オーバーフローエラーにすべき所を誤差ありで計算しているとかなのかな?**

- **「誤差ありで計算している」は当たっている。** 上の §3。
- **「オーバーフローにすべき所」は、文字通りには外れている。**
  **`sin`/`cos` の値は ±1 に有界で、`finalize` が見る inf/NaN には決してならない**
  （**§12 で `f64::MAX` まで実測。`Overflow` は 1 件も出ない**）。
  **溢れているのは値ではなく、入力が持っている情報**である。
- **ただし、仮説の形を変えると当たる所が在る**（下の §8）。

## 8. ★ もう 1 つ測れたこと——**1e18 あたりから「真値」自体が二義的になる**

**盤面から打てる形**（仮数 12 文字・指数 3 桁）**で無作為に撒き、
「打った十進を f64 が厳密に持つか」と「2 つの読み方で真値が変わるか」を数えた**
（各桁 200 件）:

| 桁 | f64 が厳密に持つ | 持たない場合に 2 つの真値の 10 桁が違う |
|---|---|---|
| 1e0・1e3 | 0 | **0**（1 ulp の差が 10 桁目より下に収まる） |
| 1e6 | 0 | 9 |
| **1e9〜1e16** | **200 / 200** | 0 |
| **1e18** | 137 | **63**（残り全部） |
| 1e20 | 3 | 197 |
| 1e22 以上 | 0 | 193〜200 |

**例**（`1e23` と打ったとき）:

```
綴り 10^23 に対する真値     : -9.8480775301e-01
f64 が持つ 9.999…e22 の真値 :  5.2991926423e-01
```

**1e16 までは、打った数を f64 が厳密に持っている**ので、**「正しい答え」は一意に決まる**
——**そこの誤差は engine のものである。**
**1e18 以上では、電卓が持っている数は打った数ではない**ので、
**「正しい答え」を言うには、どちらを指すかを先に決める必要がある。**
**利用者の「エラーにすべき」が議論として立つのは、この帯である**
（値が溢れるからではなく、**入力が角度を指し示さなくなるから**）。

## 11. ★ 測って出てきた別の欠陥——`tan` が、極でない所で `Math ERROR` を返す

**盤面から 8 打鍵で届く**（実測、実 WASM の E2E）:

```
1.161e18        → "1.161e18"
1.161e18 sin    → "0"
1.161e18 cos    → "1"
1.161e18 tan    → "Math ERROR"     ← ★ 自己矛盾
1.17e18  tan    → "Math ERROR"
1.162e18 tan    → "0.06155352777"  （180 の倍数でなければ数が返る）
```

**`sin = 0` かつ `cos = 1` なら `tan = 0` である。** **`1.161e18` は f64 が厳密に持つ整数で、
360 の倍数**（1161000000000000000 ÷ 360 = 3225000000000000）——**`sin`・`cos` の表は正しい。
間違っているのは極の判定である。**

### 11.1 仕組み（`is_tan_pole`、`scientific/mod.rs:142`）

```rust
let a = v.re.abs();
a >= 90.0 && (a - 90.0) % 180.0 == 0.0
```

**`a` が大きいと `a - 90.0` が `a` そのものになる**（90 が ulp の半分より小さい）。
**そうなると式は `a % 180 == 0` に化け、「180 の倍数」＝**本当は `sin = 0` の角**を
極として弾く。**

**★ 帯の条件は、最初に書いた数が誤っていた**（レビュー役が当て直し、私も実測で確認）。
**正しくは 2 段ある**:

- **`2^54 ≈ 1.80e16` から、`a - 90.0` が厳密でなくなる**——**ulp が 4 以上で、
  90 は 4 の倍数でない**ので `a - 88` や `a - 92` に丸まる（実測: 2^54 の帯の
  中ほどで誤差 2.0）。
- **`2^60 ≈ 1.153e18` より上で、`a - 90.0` が `a` そのもの**になる（**ulp が 256 で、
  90 がその半分より小さい**）。**そこで式が `a % 180.0 == 0.0` に化ける。**
  **実測: `2^60` ちょうどでは `a-90 == a` は偽、`1.161e18` では真。**

**誤判定が起きるのは 2 段目の帯**で、**条件は `a % 180 == 0`** である。
**最初に書いた「`90 × 2^53 ≈ 8.1e17`」は誤り**——**実測で `8.106e17` では
`a - 90.0 == a` は偽**である（ulp が 128 しかない）。

**打てる綴りがどれくらい在るか**: **仮数 4 桁 × 指数 15〜99 の 27,261 通りを
解析と同じ作り方で当てて、`1.161e18` から連続して当たる**
（`1.161e18`・`1.17e18`・`1.179e18`・`1.188e18`…**0.009e18 刻み**＝
**1.161e18 以降の 180 の倍数**）。**仮数の有効数字が 12 桁まで打てるので、帯の中には
いくらでも在る。**

**★ `2^54 ≈ 1.80e16` 以上に、本物の極は 1 つも存在しない**（レビュー役が示した、
私の最初の主張「帯の中には無い」より広い形）——**`2^54` 以上の f64 はすべて
4 の倍数**（仮数に掛かる 2 の冪が 4 以上）だが、**極は `90 + 180n ≡ 2 (mod 4)`**
（90 も 270 も 450 も 4 で割って 2 余る）。**両立しない。**
**実測でも、`2^54` 以上の 200,000 標本に `a % 180 == 90` は 0 件**
（4 の倍数でない標本も 0 件）。**だから直しで失われる判定は 1 つも無い。**

### 11.2 ★ この節は、最初に測り間違えた

**最初は `10f64.powi(80)` で探し、`1e80`・`1e81`・`1e82`・`1e190` が当たったと書きかけた。**
**盤面で確かめたら `1e80 tan` は数を返した**——**`powi` の累積丸めで出来た f64 は、
盤面が `1e80` を解析して得る f64 とは別物**だったからである
（`powi(80)` は `1.0000000000000001e80` と印字される）。

**[[test-strings-in-the-parsers-spelling]] と同じ形**: **入力は、読む層と同じ作り方で作る。**
**解析（`float("1.161e18")`）で探し直して、盤面で当て直した。**

### 11.3 この欠陥は §8 の二義性とは別である

**`1.161e18` は f64 が厳密に持つ**ので、**「正しい答え」は 0 に決まっている。**
**そして `tan` が `Math ERROR` を返す一方で `cos` は 1 を返しているので、
どちらの解釈を採っても engine は自分と食い違っている。**
**つまりこれは精度の話ではなく、判定の式が大きな引数で意味を変える話である。**

## 12. 実引数で `Overflow` になるか——**ならない**（実測）

| x（Deg） | sin | cos | tan |
|---|---|---|---|
| `f64::MAX` | −9.285212e−1 | 3.712794e−1 | −2.500869e0 |
| `1e308` | 9.709672e−1 | −2.392128e−1 | −4.059010e0 |
| `-f64::MAX` | 9.285212e−1 | 3.712794e−1 | 2.500869e0 |
| `f64::MIN_POSITIVE` | 3.883486e−310 | 1.0 | 3.883486e−310 |
| `5e-324`（最小の非正規化数） | 0 | 1.0 | 0 |

**RAD も同じで、`Overflow` は 1 件も出ない。** **`sin`/`cos` は ±1 に有界で、
`x × (π/180)` も f64 の範囲を出ない**ので、**`finalize` が見る inf/NaN には決してならない。**
（**これで §2・§7 の論証は実測に置き換わった。**）

**唯一エラーになったのは `tan` の `TrigPole`** で、**それが §11 の偽の極である。**

## 13. 他社・規格はどうしているか（下請けの調査。**一次資料の URL と原文つき**）

**「エラーにする」と「正確に計算する」の両方が、根拠つきで実在する。**

### 13.1 ★ エラーにする側

| | 何を切るか | 一次資料 |
|---|---|---|
| **Casio の科学電卓** | **DEG: `0 ≦ |x| < 9 × 10^9`／RAD: `0 ≦ |x| < 157079632.7`** を**マニュアルの表に明記**。**範囲外の入力は `Math ERROR` の原因として列挙**されている | fx-991EX/570EX マニュアル "Function Calculation Input Ranges and Precision"（p.40 付近）、fx-991CW（p.144）、fx-991ES PLUS（p.52）、日本語版 fx-JP700CW/900CW。**内部計算桁数は 15 桁（CW は 23 桁）** |
| **AT&T SVID** | **規格として `TLOSS` を要求していた**——「完全に有効桁を失う入力では 0.0 を返し、標準エラーに TLOSS を印字し、`errno = ERANGE`」 | System V Interface Definition Issue 2 Vol 1 (1986) p.236 `TRIG(BA_LIB)` |
| **Cephes**（Moshier） | **`x > 2^30 = 1.073741824e9` で TLOSS を立てて `0.0` を返す。** 註に「**`x > 2^49 = 5.6e14` では結果は無意味かもしれない**」 | netlib `cephes/sin.c` の冒頭註とコード。度版 `sindg.c` は `x > 1.0e14` |
| **Intel x87 `FSIN`** | **`|x| > 2^63` は計算しない**——**C2 フラグを立てて `ST(0)` を据え置く**（例外は投げない） | Intel SDM Vol.2 `FSIN` |

**★ Casio の DEG の上限 `9e9` は、私の実測で崩れる帯のすぐ上に在る**
——**§3.3 では 1e9 で 300 件中 241 件、1e10 で 293 件の 10 桁が狂っている。**
**向こうは内部 15〜23 桁を持っていてなお 9e9 で切っている。**

**RAD の上限 `157079632.7` は 9e9 度と同じ角度である**（下請けの実測:
9e9 度 = 157079632.67948967 ラジアン）——**Casio は両モードで同じ角度で切っている。**
**CalcArc の RAD は 1e18 まで 10 桁一致する**ので、**この点では Casio より広い。**

### 13.2 エラーにしない側

| | 立場 | 一次資料 |
|---|---|---|
| **IEEE 754-2019** | **`sin` の定義域は `(−∞, +∞)`。有限の浮動小数点数はすべて定義域内**で、**`shall return results correctly rounded … for all operands in its domain`**。大きさによる例外は無い（`|x| = ∞` だけが invalid） | §9.2 と Table 9.1 |
| **C (N1570)** | **精度は implementation-defined**（"The implementation may state that the accuracy is unknown"）。**`sin` の記述は「Return sin x」の 2 行で、範囲の記述は無い** | §5.2.4.2.2 p6、§7.12.4.6 |
| **C99 Rationale** | **「大きな引数では 0 ビットしか合っていないことが珍しくない」**と明記。**ただし「エラーにせよ」とは書かず、`x - (2*pi) * (int)(x/(2*pi))` のような素朴な縮約を `ill-advised` と勧告** | C99 Rationale §5.2.4.2.2、§7.12.4 |
| **glibc / fdlibm / FreeBSD libm / Go / Sun libm** | **Payne–Hanek で厳密に縮約してエラーにしない。** Go は `2^29` を超えると Payne–Hanek に切り替える（Ng の論文を名指しで引用）。**Sun/Oracle は「SVID の TLOSS を三角関数では出さない」と公言** | `k_rem_pio2.c` の註、Go `trig_reduce.go`、Oracle *Numerical Computation Guide* 付録 E |
| **HP-15C** | **エラーにしない**と公式に文書化——**13 桁の内部 π `p` を使い、`TRIG(x) = trig(xπ/p)` を第 10 桁の ±0.6 以内で返す。** 根拠は**後退誤差解析**（出力の第 10 桁と入力の第 13 桁の 2 つの摂動に帰せられる）。**ただし「`x` が厳密に既知・厳密に計算されたとみなされる場合を除いて」と自分で但し書きしている** | HP-15C Advanced Functions Handbook pp.184–186 |
| **HP 28S / 48SX / 20-s** | **`sin(1e22)` で正解を返した**（1992 年の機種横断の実測表） | K. C. Ng, "Argument Reduction for Huge Arguments: Good to the Last Bit" (1992) Table 1 |

### 13.3 「無意味だから拒む」を名指しで否定している一次資料

K. C. Ng (SunPro, 1992) pp.1–2:

> When the argument is large, most early software writers did not attempt to perform
> argument reduction precisely. **Instead they returned junk, or 0.0, or an error message.
> As a result many users (and some implementors) have formed the impression that obtaining
> the correct function value for large inputs is simply impossible.** That is why [8] requires
> an error message be signaled and the result be 0.0 … **That restriction is unnecessary.
> The correct answer can be computed quite efficiently.**

> **It is often argued that being concerned about large arguments is unnecessary, because
> sophisticated users simply know better than to compute with large angles. It is our
> contention that this position is suboptimal** […] 2. The consequences of producing
> incorrect (inaccurate) answers may be catastrophic […] 3. It is a vendors responsibility
> to provide answers that are as correct as possible.

**ここが「エラーにする／正確に返す」の分岐点の、いちばんはっきりした原文である。**
**なお `[8]` は 13.1 の SVID であり、Ng はそれを名指しで否定している。**

### 13.4 ★ 出せなかった根拠（**推測で埋めていない**）

- **Kahan 本人が「大きな引数の三角関数」を論じた文章**——当たったが見つからない
  （HP-15C の付録の著者が Kahan という通説の裏も取れていない）。
- **Muller ほか *Handbook of Floating-Point Arithmetic* §11 の本文**（有料）。
  代わりに同じ著者陣の IEEE TC 論文を引いた。
- **TI 機が大きな引数で実際に何を返すか**（マニュアルに範囲の記載が無い）。
- **Casio の実機で `Math ERROR` が出ることの観測**——**マニュアルの 2 つの記述
  （入力範囲の表 ＋ Math ERROR の原因）を合わせた帰結であり、実機は叩いていない。**

## 14. 何を直したか（2026-10-03、利用者の裁定 4 件のうち 3 件）

**枝 `fix/tan-pole-large-args`**（`origin/main` の上に 4 本）。
**④「上限を設けてエラーにする」は、利用者が「やらない」と裁定した**

| | 直し | 番人 |
|---|---|---|
| **①** | **`is_tan_pole` を `a % 180.0 == 90.0` に**（引き算を剰余の中へ） | `engine_table.rs` の `an_angle_that_is_not_a_pole_is_not_refused_however_large`（**帯の 4 点 ＋ 帯の外 1 点 ＋ 本物の極 2 点**） |
| **②** | **`to_rad` で度の実部を `% 360` で畳んでから掛ける** | `engine_table.rs` の `the_same_angle_gives_the_same_answer_however_many_turns`（**`10^k` 度が全部 280 度であることを使った不動点**） |

| **③** | **大きな角の golden を 8 件**（三角 20 → 28 件）＋ **生成器の番人** | `testdata/scientific.json` ＋ `generate.py` の `check_angle_inputs_are_exact` |

**①の効果**: **`1.161e18 tan` が `Math ERROR` → `0`**（`sin` は 0、`cos` は 1 のまま）。
**②の効果**: **絶対誤差がどの帯でも 5.5e-16 以下**（畳む前は帯 `[1e14, 1e15)` で
1.12e-03）。**③の効果**: **畳みを外す変異で golden が鳴る**（**②の直後は 0 本だった**）。

そこまで解像できない」と書いてあった**（**還元していなかっただけである**）。

## 15. 今日出た規律 3 つ

### 15.1 「コミット前に 3 つ」ではなく、「直したあとにもう 1 度」

**②の実装直後には `clippy` を回した。** **そのあと註を書き替えて、回さなかった。**
**積み直しのときに `doc list item without indentation` で 3 件赤になった。**

**註だけの変更でも `clippy` は動く**（`clippy::doc_lazy_continuation` ほか）。
**[[commit-gate-is-three-checks]] は「コミット前に 3 つ」だが、
今日の形は「直したあとにもう 1 度」**である——**最後の編集のあとに回す。**

### 15.2 数を書くときは、測り方を添える

**`numerical-policy.md` の同じ段に、`10^k` ちょうど 1 点の値（1e5 度で 9.1e-15）と
「帯の最大」を名乗る文が同居していた。** **同じ点を帯の最大で測ると 1 桁大きい。**

**今日 3 度目の形である**（staging の timeout が 1 走行ぶん／台帳の 335 と 33／ここ）。
**数には「1 点か、帯の最大か」「標本数」「真値を十進に取るか f64 に取るか」を添える。**

### 15.3 帯を、上限の桁で呼ばない

**`uniform(10**(e-1), 10**e)` を `1e{e}` と印字していた。**
**だから「1e6 で 4 件」は帯 `[1e5, 1e6)` のこと**で、**1 桁ずれて報告していた。**
**監視役はその数をそのまま利用者に伝えている。**

**帯は `[下限, 上限)` で書く。** **上限の桁で呼ぶと、読む人は「その桁の値」と読む。**
**主張の境目も 1 段動く**——**「畳んだあと 1e15 まで 0 件」は、正しくは
「`1e15` 度未満で 0 件、`[1e15, 1e16)` で 3 件」**であり、
**文書の文も直した**（`detail.ja.md`・`CHANGELOG.md`・`cases.py`・`numerical-policy.md`）。

### 15.4 ついでに記録——測ったものを、作り方ごと書く

**「1e15 まで 0 件／1e16 以上 2〜6 件」の測り方**:
**`sin`、度、各帯 300 件を一様に引き、真値は `mpmath` 50 桁で
`mpf(x) * pi / 180`（＝f64 が持つ値に対する真値）、
判定は表示と同じ有効数字 10 桁の綴りの一致。**

**★ 真値を「十進の綴り」に取るか「f64 の値」に取るかで、`1e16` 以上では答えが
変わる**（§8）。**上の表は f64 の値に対する真値である。**
**参照実装は `mp.mpf(str(x))`＝十進の綴りを読むので、両者が食い違う入力は
golden に入れない**——**その番人が ③ の `check_angle_inputs_are_exact`
