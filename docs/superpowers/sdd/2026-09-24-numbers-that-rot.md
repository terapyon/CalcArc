# 数の主張が腐る 3 つの型（0.9.7、検証側の台帳）

**2026-09-24 の 1 日で、同じ「数の主張」が 3 通りの壊れ方をした。** 3 つとも**数は正しく書かれて
いた**——**壊れたのは数の周りである。**

## 型 1: 数は合っているが、**何を数えた数かが変わった**

**F16 の番人の床 10,368**（`crates/calcarc-core/src/value.rs`）。
格子は確かに 10,368 升だが、**そのうち 128 回は 0 と 0 を比べていた**
（`big = 1` で `gap` が 1077〜1080 の 4 升。`small` が入力の時点で 0 に丸まる）。
**床は「1 度も比べずに緑にならない」ための数**なのに、**「失敗しうる比較の回数」として
読まれていた。**

**直し方**: 数える対象を変え（0 と 0 の升を数から外す）、**外した 128 も assert する**。
**黙って外せない形にした。**

## 型 2: **対象が増えても鳴らない**（`>=` の床）

**`short-screens.spec.ts` の床 425**。`PROMISED_URLS` を回す巡回が **0.9.6 で 13 → 14 画面**に
増えた（`#manual`）のに、**床は `>=` なので赤くならない**。
**425 が何を数えた数かは変わっていた**（盤面のキー＋マニュアルの冊を選ぶボタン 3 つ）。

**直し方**: 実測で **428** に据え直し、**註に「この数は『押せるものを何個見たか』であって、
盤面のキーの数ではない」**と書いた。

## 型 3: **番人が在り、突き合わせも緑で、両方が古い**（★ いちばん質が悪い）

**報告書の `CERTIFICATE_PROBES = 70115`**（`heavy/tests/corpus/report.ts`）。

- **2026-08-20 の実測**で、`docs/corpus-measurements.md:1351` の表の合計行に**釘で留めて**
  あった。**番人（`report.spec.ts`）が、定数と表を実際に突き合わせていた。**
- **2026-09-24 に数え直すと 147,737。** **2 倍以上古い数を、報告書は出し続けていた。**
  **比べる相手の範囲まで古かった**——**`70,115` は当時の `finance-000` だけの数**で、
  **そのシャード単独でも今日は 70,141（＋26）**、さらに **`finance-start-000` の 77,596 が
  丸ごと入っていない**（1e の実測、2026-09-25）。
- **それでも番人は緑だった**——**表と定数が同じだけ古いあいだ、突き合わせは一致する。**

**「手で書いた数は一次資料に釘で留める」という手当てそのものが原因だった。**
**一次資料が日付つきの測定記録である限り、留めた側も一緒に古くなる。**

**直し方**: **定数を消し、`CERTIFICATES` の `build()` を、いまディスクに在るシャードに当てて
数える**（`certificateProbes()`）。**番人は数を assert しない**——**数えていること**を見る
（各シャードの寄与の合計と一致する／寄与のあるシャードが 2 枚以上）。
**数を書かなければ腐らない**の、いちばん強い形である。

**★ 番人の述語も 1 段直した**（2026-09-25、1e の注記）。最初は「**各シャードの寄与の合計と
一致する**」と書いたが、**合計との一致は、両側が同じ `loadCallShards()` を使うぶんだけ盲点を
持つ**——**loader が 1 枚落とせば、数えた側も比べる側も同じだけ減って一致する。**
**だから「対応」で書いた**: **証明書の op を持つケースが在るシャードは、その証明書の
プローブが正／無いシャードは 0。** **数ではなく対応なので、ディスクの中身が変わっても
意味が変わらない。**

**しかも「シャードごとの合計」では粗かった**——**証明書 1 本を黙らせても、残り 3 本が
埋めて緑になった**（実際に試して鳴らなかった）。**証明書ごと × シャードごとの全組**を見る形に
直し、**組を 1 つも見ずに緑にならないよう、見た組の数も assert した。**

**赤の確認**（2026-09-24〜25、corpus 設定で `report.spec.ts` を 1 本）:
報告書だけ古い定数に戻す → 赤／**証明書 1 本が何も作らない → 赤**（`finance-000.json:
compound_periods_for のケースが在るのに、その証明書が 1 本も発行していない`）／
**証明書が対象外のシャードにも出す → 赤**（`data-scale-000.json: loan_principal のケースが
無いのに…`）／**loader が 1 枚落とす → 赤**（別の番人「`### finance-start-000.json (calls)`
の見出しが 1 本ではない」が拾う）／戻して **135 passed**。

**走行そのものは exit 1 で終わる**——**部分走行では teardown の門が
「`report: no shard summary survived the run — refusing to write a report at all`」と言って
報告書を書かない**（`report.ts`）。**「既知の仕様」と書かず、門の言葉を印字ごと見せること。**

## ★ 数え直せる数と、走行に属する数は書き分ける

**同じ節に、留めたままの数が 1 つ残っている**——`CERTIFICATE_PROBES_BROKEN_BY_TAX_MUTATION`
= **124**（`tax-combined-rate` の変異で赤くなったプローブ数）。

| | 数え直せる数 | 走行に属する数 |
|---|---|---|
| 例 | 証明書のプローブ **147,737** | 変異で落ちた **124** |
| 出どころ | **いまディスクに在るコーパス** | **その日の 1 回の走行** |
| 扱い | **数えて出す。定数にしない** | **一次資料に留める以外に手が無い** |
| 腐り方 | 腐らない | **走行の条件が変われば古くなる。日付とともに読む** |

**留めるのが悪いのではない。** **数え直せる数を留めたことが悪い。**
**次に数を置く人は、まず「この数は、いまここで数え直せるか」を問うこと。**

## 3 つに共通していたもの

**どれも「数が間違っている」形では現れなかった。** 1 は註が、2 は床の向きが、3 は一次資料が、
**それぞれ数の意味を保証しているように見えていた。**
**数の隣に「何を数えた数か」を書く**のは、そのための最低限である——**0.9.6 で決めた 3 つの観点
（①現物と合うか ②番人が在るか ③何を数えた数かが数の隣に書いてあるか）の ③ は、
この 3 つの型を全部拾う。**
