# 間欠的に落ちるテストの一覧

**この一覧は「壊れている」の一覧ではない。「赤を見た人が照合するための一覧」である。**

CI や手元で赤が出たとき、**まずここを見て、同じテスト・同じエラー原文が載っていないか
を確かめる**。載っていれば、**その走行の条件を下に足す**——標本が増えるほど、原因の
当たりが付く。載っていなければ、それは新しい赤である。

**直しは、ここに書くこととは別の判断である。** 待ちの上限を伸ばして緑にするのは
**「緩めれば緑になる数字」を 1 つ増やすだけ**なので、この一覧に載せることの帰結には
しない。

### エラーの原文

```

```

**これは「結果が違った」ではない。** 期待値と実際の値を比べて食い違った、という形の
失敗ではなく、**待ちが終わらないうちに制限時間が来て、Playwright が context を
畳んだ**という形である。**つまり主張そのものは一度も評価されていない。**

同じ走行の別の行に `8 did not run` が出ることがある——**先に落ちた 1 本が走行を
畳むため**で、8 本が壊れているわけではない。

### 条件別の実測（2026-08-29）

| 条件 | 結果 |
|---|---|
| `feature/currency-golden-gaps`・**他の重い走行の直後／連続走行の中** | **4 走行中 2 回失敗** |
| 同じ枝・**単独で 1 回ずつ**（他に何も走らせない） | **3/3 緑** |
| **`main`（`f64bd30`）・単独で 1 回ずつ** | **3/3 緑** |
| 当該 spec だけを単独で（`playwright test tests/e2e/data-scale.spec.ts`） | **4/4 緑** |
| `integration/coverage-and-currency`・単独で 1 回ずつ | **2/2 緑** |

### そのとき何が同時に走っていたか

**私の側で走っていたもの（実測）**: `cargo test --workspace`、`wasm-pack test
--headless --firefox`、`cargo clippy --workspace --all-targets`。**負荷を制御した
実験ではない**——スイープの流れの中で連続して回していた、というだけである。

**重量級担当が同時刻に変異検査（`crates/` を書き換えて回すもの）を走らせていた**と
監視役から聞いているが、**私はそれを確かめていない**。

### 落ちた枝の変更とは無関係である根拠

- 落ちた枝の差分に **`web/` のファイルが 1 つも無い**（`reference/` 3 件と
  `testdata/currency.json` だけ）
- **`testdata/currency.json` を読む spec は grep で 0 件**（`testdata` への言及は
  `convert.spec.ts` と `finance-compound.spec.ts` のコメント 2 か所だけ）
- **`main` でも同じ条件なら落ちうる**——上の表の 2 行目と 3 行目は同じ静かな条件で、
  どちらも緑である。**枝と `main` を分けているのは条件のほうであって、差分ではない。**

### ★ 何が分かっていないか

- **どの待ちで間に合わなかったのかを特定していない。** WASM の読み込みか、描画か、
  タブの遷移か、`aria-current` の反映か——**切り分けていない。**
- **標本は 4 走行（うち失敗 2）だけ**である。失敗率も、負荷との関係の強さも、
  **この標本では言えない。**
- **「CPU の食い合い」は筋であって実測ではない。** 測ったのは
  **「並走しているときに落ち、単独なら落ちない」という相関まで**である。
- **CI で出たことがあるかを確かめていない。** 手元でしか見ていない。

**次に赤を見た人へ**: 上の表に 1 行足してください。**条件（何と一緒に走らせたか）と、
落ちたか緑だったか**が分かれば、標本になります。**特定できなくても足す価値があります**
——「静かな条件でも落ちた」という 1 行が出た時点で、上の相関は崩れます。

## `complex-rules.spec.ts` — classify and classifyComplex agree on every real case in the corpus

| | |
|---|---|

| テスト名 | `classify and classifyComplex agree on every real case in the corpus` |
| 走行 | `pnpm heavy`（Playwright、`corpus` プロジェクト） |
| 初出 | 2026-08-30 |

### エラーの原文

```
✘  42 tests/corpus/complex-rules.spec.ts:121:1 › classify and classifyComplex agree
   on every real case in the corpus
（走行全体は「239 passed / 1 failed」、所要 16.4 秒）
```

**原文をこれ以上取れていない。** 気づいたのが**同じコマンドの再走のあと**で、
**1 回目の出力を残していなかった**——`grep` で行を拾った時点のものがこれである。
**次に踏んだ人は、まず出力を丸ごと保存してください。**

### 条件別の実測（2026-08-30）

| 条件 | 結果 | 所要 |
|---|---|---|
| `pnpm heavy`（1 回目、`coverage` を載せた直後） | **失敗** | 走行全体 16.4 秒 |
| 同じコマンドを続けて再走 | **緑** | 走行全体 31.0 秒・当該テスト 28.4 秒 |
| その後の `pnpm heavy` 3 回（Task 4・5 の確認） | **3/3 緑** | 31 秒前後 |

**★ 目に付く差は所要時間である。** 落ちた走行は**全体で 16.4 秒**、緑の走行は
**当該テスト 1 本で 28.4 秒**かかっている。**落ちた走行では、このテストは
最後まで走っていない**と読める——ただし**それは推測で、原文がそう言っている
わけではない。**

### そのとき何が同時に走っていたか

**確かめていない。** 私の側では直前に `generate_corpus.py`（6 秒）を回していたが、
**`pnpm heavy` と並走はしていない**。**他セッションが何を走らせていたかは把握して
いない。**

### 落ちた変更とは無関係である根拠

- 当該テストが読むのは **`complex-000.json` と `complex-display-000.json` の
  `expect`（`re` / `im`）**である。私の変更が足したのは **`levels` と `coverage`**
  の 2 欄で、**`expect` は 1 バイトも動いていない**（`git diff` で確認済み）
- **同じコーパスで 4 回走らせて、落ちたのは 1 回だけ**である。決定的な壊れ方なら
  4 回とも落ちる

### ★ 何が分かっていないか

- **1 回目の完全な出力を残していない。** タイムアウトなのか、別の失敗なのかを
  **原文で確かめていない**——上の「最後まで走っていない」は**読みであって実測ではない**
- **標本は 4 走行（うち失敗 1）**である。失敗率は言えない
- **1 件目（`data-scale.spec.ts`）と同じ原因かどうかは分からない。** どちらも
  Playwright で、どちらも「長くかかるものが落ちる」形に見えるが、**共通の原因を
  測ってはいない**
