# 試験空間モデル 第 3 段の置き場——候補を測った（2026-09-02）

**モデルの本体はまだ書いていない。** **置き場を実測で決めるところまで**である。

**出発点は引き継ぎ §2 の材料 3**——「第 3 段階をどこへ置くか。`convert` は候補から
外してよい（軸が 2 本、単位はすでに満点。**産物が当てる前に分かっている**）」。

## 判定の物差し（3 つ）

1. **軸が何本あるか**（データから読める／読めないと思える、を分けて）
2. **いまのコーパスが水準をどれだけ覆っているか**
3. **★ 産物が当てる前に分かっているか**——**`convert` を外した理由がこれ**

**★ そして第 2 段の教訓を効かせた。** あちらでは**「この軸はキー列から読めない」と
宣言していた 6 軸のうち、正しかったものが 1 つも無かった。**
**だから「読めない」と思った軸を、根拠を現物で確かめずに外していない。**

### ★ 推し: `llm`（18 件、軸 7 本）

### 次点: `transfer`（11 件、軸 4 本）

### `data-scale`（コーパス 2000 + golden 28、軸 3 本）——**有力だが 3 番手**

```

# 追測（2026-09-02、同日）——`currency` と `equivalence` を空けたまま確定しない

**前半で「`currency` は軸の数で `llm` を上回る可能性がある」「`equivalence` は
在るのに読めていないだけかもしれない」と書いて、どちらも測っていなかった。**
**その 2 つを埋めた。**

## `currency`（43 件）——**外す。産物が当てる前に分かる**

**水準の一次資料は `currency_ref.MINOR_UNITS`**——**ISO 4217 List One の
minor unit で、16 通貨・小数桁は 0 か 2 のみ**。**spec §3.1 が
「0 か 2 のどちらか」という単純さを明示的に選んでいる**（小数桁 3 の
`KWD` `BHD` などを入れない、と書いてある）。**2026-08-20 に `list-one.xml` と
16 行すべてを突き合わせた記録つき。**

**被覆（実測）:**

```
通貨            16 / 16      触れていないものは無い
★ 小数桁の組    4 / 4        from 桁0×to 桁0 が 10 件、0×2 が 1、2×0 が 7、2×2 が 24
エラー経路      3 種すべて   Overflow 4 / SyntaxError 5 / DivisionByZero 1
値の帯          負 6・ゼロ 1・整数 28・小数あり 8
レートの帯      ゼロ 1（DivisionByZero 用）・構文外 2
```

**仕様が言う唯一の構造的な区別（小数桁 0 と 2）は 4 組すべて覆われている。**
**`convert` と同じ形**である——**当ててもモデルは「満点」としか言わない。**

**★ 軸の数では `llm` を上回らなかった。** 通貨の 16 は**水準であって軸ではなく**、
**構造としては「小数桁 2 値 × 2 辺」に畳まれる**（仕様がそう畳んでいる）。

## `equivalence`（2000 件）——**残す。ただし単独では小さすぎる**

**「読めない」で外さなかったのは正しかった。読めた。**

**水準の一次資料は `EQUIVALENCE_FORMS = 3` と `_equivalent_pair`**
（`generate_corpus.py`）——**生成器が名前で 3 つの形を選んでいる:**

# 確定（2026-09-02）——**第 3 段は置かない**

**ユーザーの判断で Scale 側（`llm` / `transfer` / `data-scale` / `currency`）を
候補から外した**（2026-09-02）:

> スケールの所は正確性やテストが簡単だと思うので、そこまで重要視しなくていいかな。
> 関数電卓や金融に比べると間違えに対する問題が少ないと思っていて、すでにテストは
> あると思うので空間モデルまで持ち込む必要があるのかが気になっています。

**上の Scale 側の測定は消していない**——**「測って外した」ことそのものが結論**である。
**次に同じ問いを立てた人に、「当てる前に分かる領域だった」という根拠が要る。**

**残った候補は `typed` と `equivalence` の 2 つ**（どちらも Scale 側でなく、
**打鍵と式の作り方そのもの**を扱う。**盤面をまたいで効く**）。

## `typed`（2000 件）の実測

**水準の一次資料は `TYPED_FORMS`**（`generate_corpus.py:842`）——
**4 つの打ち方**: `_typed_integer` / `_typed_decimal` / `_typed_zeros3` /
`_typed_exponent`。

**被覆: 4 つとも在る**（decimal 1275 / zeros3 956 / exponent 924 / integer は全件）。

### ★ 前半の所見を訂正する

**前半に「`exp` が `dot` 無しで 1 度も現れない——当てる前に分からなかった」と
書いた。結論が誤っていた。**

**`_typed_exponent` は必ず `dot` を打つ**（キーは
`mantissa, dot, frac, exp, exponent`。`generate_corpus.py:832-838`）。
**つまり「現れない」のは穴ではなく、生成器の構造である。**

**ただし、そこから本物の穴が 1 つ出た**——**盤面は `15 exp 3` を打てる。**
`engine/state.rs:295` の `push_exponent` は**60 進の段が途中のときしか
拒まない**（小数点を要求しない）。**コーパスには 0 件**（指数を含む 924 件すべてが
小数点つきの仮数。実測）。

**「打てるのに 1 件も無い」——第 2 段の `Rad × 逆三角` と同じ形である。**

### そして、もう 1 つの軸は**既に報告されている**

**`_typed_node` は「指数入力の直後の `neg`」を意図して避けている**
（`generate_corpus.py:869-871`）。**避ける理由も、避けた結果どうなるかも
docstring に書いてある:**

> **指数の符号を変える打ち方そのものはまだ検証していない**——レポートがそう書く。

**実測でも 0 件**（指数を含む 924 件のうち、直後に `neg` が来るものは 0）。

**★ これは「モデルが見つける穴」ではない。既に見つかっていて、報告書が
毎回そう言っている穴である。**

## `equivalence`（2000 件）の実測——前掲

**形 3 つ**（√(x²) / 二重否定 / +0）は**キー列から読める**（809 / 787 / 404）。
**符号は読めないが記録できる**（生成器が `value` を持っている）。
**要求セルは 3 × 2 − 1（`sqrt × 負` は不可能）= 5。**

## ★ 2 つを 1 括りにしても、当てる価値が薄い

| | 軸 | 水準 | 要求セル（実測前） |
|---|---|---|---:|
| `typed` | 葉の打ち方 | 4 | 4 |
| | 指数の直後の `neg` | 2（在る/無い） | 2 |
| | 仮数の形 × 指数 | 2 × 2 | 4 |
| `equivalence` | 同値の形 | 3 | 3 |
| | 値の符号 | 2 | 2（1 つは不可能） |
| **合計** | | | **約 14** |

**第 2 段は 78 セルだった（実測）。** **1 括りにしても 1 桁小さい。**

**そして、出てくる産物が当てる前に分かっている:**

- **`typed` の 4 つの打ち方は全部覆われている**
- **`指数 × neg` は既知で、報告書が毎回書いている**
- **`equivalence` の形 3 つは全部覆われている**
- **残るのは「符号」と「整数の仮数 + exp」の 2 つ**——**どちらも、この記録に
  もう名前を付けて書いてある**

**モデルを建てて出てくるのは、この 2 行である。** **2 行のために因子表・射影・
突合・受け入れ門を作るのは、道具が仕事より大きい。**

## 結論: **第 3 段は置かない**

**ユーザーの問い（「空間モデルまで持ち込む必要があるのか」）への答は「無い」である。**
**無理に置き場を見つけなかった。**

**理由を 3 つに畳むと:**

1. **Scale 側は、間違いの帰結が軽く、件数も少ない**（ユーザーの判断）。
   **そして測った 4 領域のうち `currency` は既に満点、`convert` も満点**だった
2. **`typed` と `equivalence` は、盤面をまたいで効く良い領域だが、
   合わせても約 14 セル**で、**第 2 段の 1 桁下**である
3. **★ その 14 セルから出る産物が、当てる前に分かっている**——
   **`convert` を外したのと同じ理由**である

kv_precision     （満点）
```

**そして重み × KV の精度は 9 / 20**。**覆われていないのは**
`fp32×fp32` `fp32×bf16` `fp32×int8` `fp16×fp32` `fp16×bf16` `fp16×int8`
`bf16×fp32` `bf16×bf16` `bf16×int8` `int4×fp32` `int4×bf16`
——**「重みと KV が同じ精度」がほとんど無い。**

### 所見: **盤面が出せない綴りが golden に在る**

**`fp8` は `PRECISION_TOKENS` に無いのに `llm.json` に 2 件在る**
（どちらも `SyntaxError` を期待するエラー経路）。**盤面からは打てない綴り**である。

**同じ形が他にも 2 つ見つかった**（この記録の前半）:

- **`transfer` の `tbps` / `week`**——`transfer_ref` の単位表に無い（エラー経路 2 件）
- **`currency` の `xyz`**——`MINOR_UNITS` に無い

**3 領域とも「知らない綴りを与えたときエラーになる」を確かめている**ので、
**意図した形である。** **穴ではない**——**ただし、golden の水準を数えるときに
「仕様の水準」と混ぜてはいけない**（前半で `transfer` の単位を 5 と数えかけた。
**実際は 4 で、5 番目はエラー経路だった**）。
