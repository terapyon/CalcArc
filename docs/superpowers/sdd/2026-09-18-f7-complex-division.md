# F7 複素除算の境界（検査側の台帳、0.9.4）

**枝** `test/complex-div-boundary`（3d の `fix/complex-div-scaling` = `e0fdd76` の上）。
**コアの直しは 3d、検査側（何を守るか・検査がどこまで届くか）は calcarc-88。**

---

## 1. 何が壊れていたか

| 式 | 期待 | v0.9.3 |
|---|---|---|
| `10^308 ÷ (10^308 + 10^308 j)` | `0.5 − 0.5j` | **0、エラー無し** |
| `(10^308 + 10^308 j) ÷ (10^308 + 10^308 j)` | 1 | **Overflow** |

**境目は「指数 308」ではなく `f64::MAX / 2`**（二分探索の実測）——
**最後に通る `8.988465674311579e307`**（＝`MAX/2` ちょうど）／**最初に落ちるその次の f64**。

**機序**: Smith 法の分母 `d = re + im*t` **自身が溢れる**。
分子が有限なら `有限/inf = 0` で**静かに嘘**、分子も溢れれば `inf/inf = NaN` → **偽 Overflow**。

**引き金の代数**: `|re| + im²/|re| > MAX`。`im = re` で `|re| > MAX/2`、
`im = re/8` なら `MAX/1.016` まで**狭まる**。**`im = 0` なら `d = |re| <= MAX` で決して溢れない。**

## 2. 直す前の実測（3d の直しの合格条件にした表）

**572 件中 80 件が壊れ、すべて「真の答えが有限」。**
静かに 0 が **24**／偽 Overflow **40**／値違い **16**／範囲外なのに値を返す **0**。
**逆向きは 0 件**——**「出しすぎ」ではなく「殺しすぎ」**だった。

**分母の形で決まる**: 対称・実部優勢・虚部優勢・符号違いは踏み、
**純実数・純虚数は 104/104 健全**（対照として表に置いてある）。

**下端にも別口があった**（報告に無かったもの）——`1e-320` で **16 件が値違い**、
**相対 2.4e-4**。**「非正規化数だから仕方ない」ではない**（`z/(2z)` の真値 `0.5` は厳密に表せる）。
**私の最初の切り分けは対称形しか試しておらず、ここを見落としていた**
（対称形は `t=1` で `im*t` が丸めを起こさないので通る）。

## 3. 直したあと

**80 → 8。** 残る 8 件は**非正規化域の 1 ULP**（相対 2.220e-16 = 2^-52）。
**8 件はすべて `e-320` の `double` 族（`z/(z÷2)`）の実部優勢・虚部優勢**（4 符号 × 2 形）で、
**`self`・`half`・`real_over_sym` は 0 件、対称形にも出ない**
——**非正規化域が丸ごと不正確なのではなく、非正規化域で入力を作る演算が絡んだときだけ。**

**native と wasm32 で件数も id も完全に一致**（2026-09-18）。
**違っていたら数を緩めず、両者を別々に記録する**という合意だったが、**その必要は無かった。**

## 4. 恒久の置き場と、許容の形

- `reference/src/calcarc_reference/complex_div_boundary.py` が `testdata/complex_div_boundary.json` を生成
- `crates/calcarc-core/tests/complex_div_boundary.rs`（native）と
  `crates/calcarc-wasm/tests/complex_div_boundary.rs`（wasm32）が**同じ JSON を読む**

**許容は `rel` のみ。`abs` を置かない**——期待値が `1e-320` 前後の行に対して絶対許容は
桁違いに緩く、**表の下端が丸ごと無検査になる**。**許容を置いた側が無検査の帯を作る**形である。
**0 であるべき成分は「厳密に 0」**で別に見張る（実測 512 個すべて厳密に 0）。

**`rel = 1e-15`** は実測 2.220e-16 の約 4.5 倍で、**直した壊れ方（2.4e-4）より 11 桁厳しい**
——**あの形はこの許容をすり抜けない。**

**期待値に参照実装は要らない。** 使ったのは**倍率に依らない恒等式**——
`z/z = 1`、`a/(a+aj) = 0.5−0.5j`、`z/(2z) = 0.5`、`z/(z÷2) = 2`。
**次に境界を作る人は、真値の生成から始めなくてよい**（mpmath は二重の裏取りとして併用）。

**赤確認（2 通り）**:
1. 許容を `1e-16` に締める → **8 件が名指しで落ちる**。**メッセージは `許容 1e-16` と印字**
   （**定数を埋め込んである**）
2. スケーリングを外す（0.9.3 に戻す） → **80 件が落ち、「静かに 0」と「有限の正解を拒んだ」を
   別々に名指しする**——**直す前の内訳と一致する。**

## 5. 通常のコーパスがここに届かない理由（**「帯を広げる案」は採れない**）

`complex-000.json` の帯は `1e-6`〜`1e9`（`generate_corpus.py:1284-1285`）。
**コミット済みシャードの実測は最大 `|z| = 9.933e8`・1e9 超は 0 件**——**帯に張り付いている。**

**しかし帯を外しても届かない**——20 万本生成し、**27,046 件の除算を真値と突き合わせて
踏んだのは 0 件**（一致 26,473／有限の正解を壊した **0**／偽 Overflow **0**／
真に範囲外で正しく Overflow 573）。最大 `|z|` は `1.85e307` まで伸びる
（`sin(rad(j40577))`、虚軸の `sinh`）が、**失敗域まで 0.7 桁足りない。**

**理由は引き金の狭さ**——**分母の大きい成分が上端 1 オクターブに入る必要があり、
乱択は 2,046 ある binade の最後の 1 つを踏まない。**

**帯は残す。** 帯の役目は「途中値が溢れる形を生成の時点で捨てる」ことで、
**捨てた先を受け取る場所（この境界専用の表）と対になって初めて、捨ててよいことになる**
（0.9.2 のローン境界 golden と同じ形）。

## 6. ★ この検査がどこまで届くか（**届かない形を、次の人が読めるように**）

**`checked_div` の註は、いま起きたことを先に書いていた**——
「分母が inf になって 0 に潰れる。最終値が有限なので `finalize()` も捕まえない」。
**その対策として Smith 法が入ったのに、`d` そのものが溢れる形で戻ってきた。**
**「対策を入れた」が「その形は全部塞がった」と読まれていた。** だから範囲を先に書く。

**覆うもの**: 複素**除算 1 回**の、**分母の形 5 種 × 符号 4 種 × 大きさ 10 階級**
（`MAX`・`MAX/2` の両側・`1e308`・`1e307`・`1`・`1e-6`・正規化数の下端・`1e-320`・最小の非正規化数）
と、**真に範囲外の 12 件**。native と wasm32 の両方。

**覆わないもの（＝いま誰も見ていない）**:

- **除算以外の演算**。`checked_mul` は**各部分積が `|a||b|` で抑えられる**ので
  **真の積が有限なら中間は溢れない**——**これは論証であって実測ではない。**
- **連鎖**。`a/b/c` のように**途中の商が端に着地する**形
- **除算を内蔵する関数**。**`tan = sin/cos` はこの経路を通る**
  （`tan(1 + 710.4j)` は 0.9.3 で `Err(Overflow)`、直したあとは値が返る。**番人は別に 1 本要る**
  ——**`checked_div` を直接叩く主張とは別の主張**だから）
- **表示層**。ここは `Value` の対で測っており、`render()` を通していない
- **境界の API 越し**。wasm32 でも `Value::checked_div` を直接叩いている

**★ 呼び出し元を数えるときは、綴りではなく受け手の型で数える。**
`git grep checked_div` は **5 か所**を返すが、**f64 を通るのは 2 か所だけ**
（`scientific/mod.rs:73` の `tan`、`engine/mod.rs:265` の `BinOp::Div`）。
**残り 3 つは `Rational::checked_div`**（`convert/mod.rs:505`・`convert/currency.rs:142`・
`expr/parse.rs:113`）で、**厳密計算であって f64 を通らない**——**署名で確かめた。**
**私は綴りだけで数えて「単位換算と通貨も同じ壊れ方を受け継いでいる」と書いた。偽である。**
**同じ綴りが違う型の違う関数を指す**——このリポジトリで 3 度目
（`DISPLAY_DIGITS` が 2 か所、`1200` が 3 か所、そして `checked_div`）。
**害の一歩手前だった**——**CHANGELOG に「単位換算と通貨も直った」と書くところだった。**

## 7. 数を文言に焼いた番人（**0.9.4 では記録まで**）

**閾値が条件と文言の両方に書かれている番人が 3 件**（`.venv` の third-party は除外）。
**どれもいまは真だが、閾値を動かした日に黙って嘘になる**:

| 場所 | 焼いてある数 |
|---|---|

**この形が危ないのは、赤が出た瞬間に嘘の数を読ませるから**である
——**赤を読んでいる人は、その数を信じて次の判断をする。**
**恒久版のメッセージには定数を埋め込んだ**（`許容 {tol:e}`）。

**★ そして、この走査自体で 1 つ学んだ。**
**最初は 1 行ずつ走査して 1 件しか見つからなかった**——**複数行にまたがる `assert` を
見ていなかった**からである。**私自身の assert がまさに複数行**で、
**つまり最初の走査は「自分の事例を見つけられない走査」だった。**
窓を 4 行に広げて 3 件になった。**規律を、直前に見た穴の形にだけ合わせて作っていた。**

## 8. ★ 印字は、どこが欠けているかを先に決めてから読む

**今日 1 日で、印字の欠け方が 3 通り出た。**

| 欠け方 | 実例 |
|---|---|
| **上限で切れる** | 3d の計測が**一覧を 6 件で打ち切って**おり、**6 行を見て「8 件は…」と書きかけた** |
| **緑だと出ない** | `wasm-bindgen-test` は**通ったテストの `println!` を出さない**——**印字を読んでも数が分からない** |
| **末尾だけ読んだ** | 私が `ruff check` を `tail -1` で見て、**「1 fixable」の 1 行しか読まず、赤を緑と報告しかけた** |

**「印字は既定で切り詰められる」は知っていた。** **知らなかったのは、切り詰めが先頭からとは限らないこと**である。
**だから「全部読む」では足りない**——**読む前に「この印字はどこが欠けうるか」を決める。**

**この台帳の恒久ケースは、3 つとも設計で避けてある**:
- **件数は `assert` に載せ、印字を読んで結論しない**（**緑だと出ない**経路でも崩れない）
- **一覧は打ち切らない**（`EXPECTED_INEXACT` の失敗メッセージは 8 件全部を出す。実測で確認）
- **合計は走行が出した数から取る**（`tail` で末尾だけを見ない）

**そして数は赤確認から取る。** **緑の走行は数を教えてくれない**ので、
**`8` を `7` に変えて `left: 8` を読む**——**native でも wasm32 でも、この手で数を確かめた。**
