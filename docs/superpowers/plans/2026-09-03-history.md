## §A この計画が先に決めたこと（**spec の §13 から 2 件を降ろす**）

### A-1. `hist` の口の形 — **データが「何を」、部品が「どう」**

**採る形**: `KeyDef<T>` と `ShiftFace<T>` に **`action?: KeyAction`** を足し、
`KeypadProps<T>` に **`onAction?: (action: KeyAction) => void`** を足す。

```ts
export type KeyAction = "history";
```

**却下した形と、その理由**:

| 形 | なぜ採らないか |
|---|---|
| `ShiftFace<T>` に `onActivate: () => void` を直接持たせる | **`SCIENTIFIC_SECTIONS` はモジュール定数であり、`heavy/tests/ui/keys.ts` がデータとして歩く**。関数を入れると、あの表が「データ」でなくなる。**関数は React の state を知らないと書けない**ので、定数の側には置けない |
| `Keypad` に `onAction` だけ足し、どのキーかは `Keypad` が判断する | **盤面の定義を読んでも `hist` がどこにあるか分からなくなる。** 位置は定義側の情報である |
| `kind?: "shift"` を `kind?: "shift" \| "history"` に広げる | **`kind` は「面を切り替えるキー自身」の意味で使われている**（`types.ts` の註）。別の意味を相乗りさせると、その註が嘘になる |

**★ 既存の `kind: "shift"` の形と揃っている。** `Keypad.tsx` は既に
「データが `kind: "shift"` と言い、部品が `setShifted` を渡す」という形で書かれている。
**`action` はその 2 例目である。**

### A-2. 押したら第 2 面は降りる — **かつ、`Shift` の枝は直さない**

**`hist` を押したら `setShifted(false)` を通す。**

**理由**: `Keypad.tsx` の註が既に「**ワンショット: 1 キーで第 1 面へ戻る**」と
書いており、**`hist` は「1 キー」である**。加えて `hist` は面を離れるので、
**戻ってきたときに Shift が立ったままだと、利用者が頼んでいない状態になる。**

**★ `kind === "shift"` の枝は直さない。** spec §9.3 の最後で私は
「`kind === "shift"` の枝はトグルするだけで面を降ろさない」を宿題として挙げたが、
**あれは `Shift` キー自身の話であり、`Shift` がトグルなのは正しい。**
`action` を別の枝で扱えば問題は消える——**直す対象は無い。**
（**【訂正】** spec §9.3 の書き方は「直すべき欠陥」に読めるが、そうではない。）

### A-3. 綴りの規則 — **「キーのラベルを、押した順に」**

**規則は 3 行で全部である**:

1. **1 キーは自分の記号 1 つに綴られる**（`sin` → `sin`、`sqrt` → `√`、`mul` → `×`）
2. **数を作るキー（`0`–`9`・`dot`・`zeros3`）は前の数にくっつく。** それ以外は**前後に空白**
3. **綴らないキーが 7 つある**（下表）

**★ この規則は `echo_of` が既にやっていることと同じ形である**
（`crates/calcarc-core/src/engine/display.rs:189` の `parts.join(" ")`、
`:193` の `op_symbol`）。**新しい発明ではない。**

**綴らない 7 つ**:

| キー | なぜ綴らないか | 綴りの列に対して何をするか |
|---|---|---|
| `eq` | **1 件の終わりの合図**であって式の一部ではない | 列を閉じる |
| `ac` | 全消し | **列を空にする** |
| `del` | 1 文字消去 | **列の最後の 1 綴りを落とす** |
| `angle_toggle` | 角度モードの切替。**モードは 1 件が別の欄に持つ**（spec §3） | 何もしない |
| `eng` | 記法。**値を変えない**（spec §3 で「持たない」と裁定済み） | 何もしない |
| `polar_toggle` | 表示形式 | 何もしない |
| `dms` | 60 進表示 | 何もしない |

**残り 39 キーが綴る。**

**spec §13-3 の 5 件は、この規則で 4 件が導ける**:

| 件 | 規則からの答 | 決めることが残るか |
|---|---|---|
| `√` | **後置**（`["4","sqrt"]` → `2`。`engine_table.rs:624`）なので `4 √` | **無い** |
| `x²` | 後置なので `2 x²` | **無い** |
| 括弧 | 打った物をそのまま。閉じていなければ `2 × ( 3 + 4` | **無い** |
| `Exp` | キーのラベルどおり `1.5 Exp 3` | **無い** |
| 区切り | **規則 2 が決める**（数字はくっつく、他は空白） | **無い** |

**残るのは 1 つだけ**——**`neg` の綴りが `+/−` になること。** `2 +/−` は
読みにくい。**それでもラベルを使う**ことを推す: **例外を 1 つ作ると、
「どのキーが例外か」を覚える表が生まれ、盤面のラベルを変えたときに
静かに古くなる**。**実物の一覧で読みにくければ後で変えられる**——
規則が 3 行なので、変えるのも 1 行である。

**★ `独立:` の行は「不可能」で確定する。** 綴りは
**「盤面のキーが何と書いてあるか」という UI 側の取り決め**であり、
**数学的な事実ではない**。`reference/` の Python が別手順で同じ文字列に
到達する道は無い——**書けば写しになる**。だから **golden も置かない**
（spec §4a の【訂正】と同じ判断）。**代わりに番人を 2 つ置く**:
Task 2 の表と、**Task 3 の「綴りと盤面のラベルが一致する」parity**。

- [ ] **Step 1: 失敗する表を書く**

`crates/calcarc-core/tests/spell_table.rs`:

```rust
//! **綴りの仕様書。** キー列と式の文字列の対応を、ここが固定する。
//!
//! `engine_table.rs` が「キー列と**表示**」を固定しているのと同じ形である
//! ——あちらは電卓の挙動、こちらは履歴に残す綴りである。
//!
//! **golden は置かない。** 綴りは「盤面のキーが何と書いてあるか」という
//! 取り決めであって数学ではないので、`reference/` の Python が別手順で
//! 同じ文字列に到達する道が無い（書けば写しになる）。**表がこれの番人である。**

use calcarc_core::{Key, engine::spell::spell};

fn spell_of(tokens: &[&str]) -> String {
    let keys: Vec<Key> = tokens
        .iter()
        .map(|t| Key::from_token(t).expect("unknown token in the table"))
        .collect();
    spell(&keys)
}

#[test]
fn digits_run_together_and_everything_else_gets_a_space() {
    assert_eq!(spell_of(&["3", "0", "sin"]), "30 sin");
    assert_eq!(spell_of(&["2", "mul", "3", "add", "4"]), "2 × 3 + 4");
    assert_eq!(spell_of(&["1", "dot", "5"]), "1.5");
    assert_eq!(spell_of(&["1", "zeros3"]), "1000");
}

#[test]
fn unary_functions_are_postfix_because_that_is_how_they_are_typed() {
    // `["4","sqrt"]` は 2 を出す(engine_table.rs)。**押した順に綴る。**
    assert_eq!(spell_of(&["4", "sqrt"]), "4 √");
    assert_eq!(spell_of(&["2", "sqr"]), "2 x²");
    assert_eq!(spell_of(&["5", "n_fact"]), "5 n!");
}

#[test]
fn parentheses_are_spelled_as_typed_even_when_unbalanced() {
    assert_eq!(spell_of(&["2", "mul", "lparen", "3", "add", "4", "rparen"]), "2 × ( 3 + 4 )");
    assert_eq!(spell_of(&["2", "mul", "lparen", "3", "add", "4"]), "2 × ( 3 + 4");
}

#[test]
fn seven_keys_do_not_spell() {
    // モードの 4 つは綴りに何も残さない。**角度モードは 1 件が別の欄に持つ。**
    assert_eq!(spell_of(&["3", "0", "angle_toggle", "sin"]), "30 sin");
    assert_eq!(spell_of(&["3", "eng"]), "3");
    assert_eq!(spell_of(&["3", "polar_toggle"]), "3");
    assert_eq!(spell_of(&["3", "dms"]), "3");
    // `eq` は列を閉じるだけで、綴りに現れない。
    assert_eq!(spell_of(&["3", "add", "4", "eq"]), "3 + 4");
}

#[test]
fn del_drops_the_last_spelling_and_ac_empties_the_line() {
```

```rust
//!
//! **打った順に、キーのラベルをそのまま並べる。** 構文木を組まない
//! ——組めばそれは計算であり、参照実装に同じ手順を書くことになって
//! 照合の意味が消える（設計書 `2026-09-03-history-design.md` §4a）。
//!
//! 独立: 不可能。**綴りは「盤面のキーが何と書いてあるか」という取り決め**
//! であって数学的な事実ではないので、別手順で同じ文字列に到達する道が無い。
//! **番人は `tests/spell_table.rs` の表と、`calcarc-wasm` の

use super::key::Key;

/// 数を作るキーか。**これらだけが前の綴りにくっつく。**
fn joins_to_previous(key: Key) -> bool {
    matches!(key, Key::Digit(_) | Key::Dot | Key::Zeros3)
}

/// 1 キーの綴り。**綴らないキーは None。**
fn glyph(key: Key) -> Option<&'static str> {
    Some(match key {
        // 列に対する操作であって、綴りではない。
        Key::Eq | Key::Ac | Key::Del => return None,
        // モードの切替。**値の見せ方を変えるだけで、式には現れない。**
        Key::AngleToggle | Key::Eng | Key::PolarToggle | Key::Dms => return None,
        Key::Digit(0) => "0",
        Key::Digit(1) => "1",
        // …残りの数字も同じ形で並べる（`Key::Digit(n)` は 0..=9）
        Key::Dot => ".",
        Key::Zeros3 => "000",
        Key::Add => "+",
        Key::Sub => "−",
        Key::Mul => "×",
        Key::Div => "÷",
        Key::Sqrt => "√",
        Key::Sqr => "x²",
        // …以下、盤面のラベルと同じ綴りを 39 個すべて並べる。
        // **`label_parity.rs` が盤面と突き合わせる**ので、
        // ここを盤面と違う綴りにすると赤くなる。
        _ => return None,
    })
}

/// キー列を式の文字列に綴る。
///
/// **`del` は直前の綴りを 1 つ落とし、`ac` は列を空にする。**
/// どちらも空の列に来ても何も起きない（**panic しない**）。
pub fn spell(keys: &[Key]) -> String {
    let mut parts: Vec<String> = Vec::new();
    for &key in keys {
        match key {
            Key::Ac => parts.clear(),
            Key::Del => {
                parts.pop();
            }
            _ => {
                let Some(text) = glyph(key) else { continue };
                if joins_to_previous(key)
                    && parts.last().is_some_and(|last| {
                        last.chars().all(|c| c.is_ascii_digit() || c == '.')
                    })
                {
                    // **数は前にくっつく。** `3` `0` は `30` になる。
                    if let Some(last) = parts.last_mut() {
                        last.push_str(text);
                    }
                } else {
                    parts.push(text.to_string());
                }
            }
        }
    }
    parts.join(" ")
}
```

## §D 追加の裁定（**2026-09-03、監視役経由**）

### D-1. エラーになった計算は残す。**ただし押しても何も入らない**

`1 Exp 309 =` は `Math ERROR` を出す（`engine_table.rs:151`。**実測で確認**）。

**残す理由**: §0 の用途は診断であり、**「なぜエラーになったか」は診断そのもの**。
**押せない理由**: `Math ERROR` を入力に入れても意味が無い。

**★ この裁定は 1 件に 4 つ目の欄を要求する。** 「エラーだったか」を
**答の文字列で判定しない**——`"Math ERROR"` という綴りに依存すると、
**表示の文言を変えた日に静かに壊れる**。`HistoryEntry` に
**`error: boolean` を足す**（`DisplayState.error !== null` から作る）。

**spec §3 の表とは食い違わない。** あの表は**「一覧に出すか」**を言っており、
**`error` は一覧に出さない**——効くのは「押せるか」だけである。

**番人**: 「押しても反応しない行」という例外が 1 つ生まれるので、
Task 9 のユニットが**エラーの行を押しても `onRecall` が呼ばれないこと**を見る。

### D-2. **同じ内容の 2 件目は積まない**

**式・答・角度モードの 3 つがすべて一致したときだけ積まない。**

**★ `=` の連打は、この規則ではなく別の理由で止まる。** 実測した:

```
2 × 3 =      -> 6
2 × 3 = =    -> 6      （18 にならない）
2 × 3 = = =  -> 6
```

**この engine は直前の演算を繰り返さない**（`last_op` に相当する状態が
`engine/` に 1 つも無く、`finish`（`mod.rs:191`）は `operands` を
`clear()` して終わる）。**したがって「連打で 2 件目」という問いは無かった。**

止めるのは **Task 10 の「`eq` でキー列を空にする」**である——
2 度目の `eq` は**空の列**を綴るので式が `""` になり、
**空の式は積まない**（構造で止まる）。

**それでも D-2 の 3 つ組の比較は要る。** 同じ式を打ち直した場合
（`2 × 3 =` の後に `AC` して `2 × 3 =`）を止めるのはこちらである。
**2 つは別の場合を止めている。**

**★ 4 欄になったので、比較は 3 つのままか。** **3 つのままにする**
——`error` は式と答から決まるので、**4 つ目を比較に入れても結果は変わらない**
（同じ式・同じ答なら同じエラー状態である）。
