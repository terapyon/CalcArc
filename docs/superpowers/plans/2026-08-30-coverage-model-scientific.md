### 裁定 1: 被覆を何から数えるか — **(c) で確定**（2026-08-30、ユーザー裁定）

**10 枚のうち 9 枚に `stratum` が無い**（あるのは `associativity` の 5 層だけ）。
生成器が「どの水準を狙った行か」を記録していないので、数え方を選ぶことになる。

**選択肢は 3 つある。それぞれに「間違っていても緑になる道」がある**ので、
3 つとも書く。

#### まず、第 1 段階が実際にやっていたこと（2026-08-30 に現物で確認）

**金融は `case["input"]` から数えている**——`covered_cells_from_cases` が
`_COVERAGE_INPUT_KEYS` で欄を引き、水準表に在る値だけを数える。
**`stratum` も記録している**（`_finance_entry` が書く）が、
**両者を突き合わせる assert は 1 つも無い**（grep で確認）。

**そして金融の「ケースから数える」は推定ではない。** `input` は
`{"principal": "20000000", "rate": "1.5", "n": 12}` という**構造化された引数**で、
`input["rate"]` を読むのは**厳密な射影**である。**科学計算には `input` が無く、
在るのは `expr`（文字列）と `keys`（トークン列）**なので、そこから水準を得るのは
**解析**になる。**この 2 つを同じ「ケースから数える」で括ってはいけない。**

#### (a) `expr` / `keys` を解析して数える

- golden は 1 バイトも動かない
- **間違っていても緑になる道**: 生成器は「この水準を狙って作った」と知っており、
  解析器は「この式はこの水準だろう」と読む。**両方に同じ読み違いが入れば、
  照合は一致して緑になる**——CLAUDE.md が「参照実装を Rust の移植にしない」で
  禁じているのと**同型**であり、**機械では検出できない**

#### (b) 生成器に `stratum` を記録させ、それを数える

- **10 枚の golden が動く**（フィールドが 1 つ増える。ケースの中身は不変の見込み・実測前）
- **既存の規約に従うこと。** top-level の `strata` キーを持つシャードが 2 枚ある
  （`associativity` と `corrections`。2026-08-30 に実測）。**TypeScript 側
  （`corpus.ts`）はケース側の `stratum` しか読まない**ので、**どちらに何を書くかを
  決めてから足す**——2 か所に別々の真実を置かない
- 解析器は要らない
- **間違っていても緑になる道**: **記録は生成器の自己申告で、中身と照合されない。**
  生成器のバグで「Rad」と記録しながら `angle_toggle` を押していないケースが出ても、
  **被覆は緑**である。**「間違っていても緑」は (b) にも同じ強さで掛かる**

#### (c) 記録し、中身から数え直し、**両者の一致を assert する**（**推奨**）

- **10 枚の golden が動く**（(b) と同じ）
- **間違っていても緑になる道が、いちばん狭い**——**記録＝意図** と
  **解析＝観測** が食い違えば赤くなる。**(a) の「両方に同じ読み違い」は、
  意図と観測の突合で捕まる**
- **設計書 §15.1 の 2**（全実行ケースから被覆セルを再計算できる）を満たす
- **これは金融の実形ではない**——金融は記録も解析もしているが、
  **突き合わせていない**。**(c) は第 1 段階より 1 段強い**
- **代償**: 一致しないケースが出たときに**どちらが正しいかは決まらない**。
  **その裁定は「生成器の意図が正しい」に倒す**（記録は事実、解析は読み）——
  **一致しなければ解析器を直す**、と先に決めておく

### 裁定の結果: **(c) で確定**

**ユーザーが選んだ理由**（2026-08-30。**この計画が書いた区別がそのまま材料になった**）:

> 金融は**構造化された引数を読むだけ**で済んでいたが、**式の解析は読み違えうる**のが
> 違い。(c) は**意図と観測の突合**なので、**片方が間違えると赤くなる**。第 1 段階より
> 1 段強い。代償は「一致しないときどちらが正しいかは決まらない」ので、
> **生成器の意図に倒す（解析器を直す）**と先に決めてある。

### ★ (c) の範囲を狭める（2026-08-30、Task 3 の着手前に実物を読んで）

**判断材料にした表現が、実物より強い主張だった。** 走る前に訂正しておく。

**`build_family_shard` は関数を意図的に選んでいない。** 木を丸ごと乱択で作り
（`random_family_node`）、その中に複数の関数が入りうる——**「この水準を狙って
作った」という意図は、ケース単位には存在しない。**

**では (c) は何を突き合わせるのか。** 生成器は自分が作った木
（`Un(fn, arg)` / `Bin(op, left, right)`）を持ち、**木を歩いて中身を数えられる**。
射影は**描画されたキー列**を読む。

```
記録:  node（木）        → 水準
観測:  node → keys       → 水準       ← to_key_sequence が挟まる
```

**捕まえるのは「木 → キー」の描画と「キー → 水準」の読みであって、
木そのもののバグは捕まえない。** 正確には**「意図と観測の突合」ではなく、
「同じ木の、2 つの読み経路の突合」**である。

**ただし金融より弱いわけではない。** 金融の `covered_cells_from_cases` も
**書き出された JSON の `input`** を読んでおり、構造は同じである——
**(c) はその構造に assert を足したもの**で、**precedent + 1 段**の関係は変わらない。

**そして (c) は全軸には掛からない:**

| 軸 | (c) が成立するか |
|---|---|
| function / angle_mode / parenthesis / kind / form / zero_part / path / operator_group / shape | **成立**（記録と観測を突き合わせられる） |
| **band / grammar_class / operation / edge** | **不成立**——観測できないので**記録するしかない = (b) のまま**（自己申告、検算なし） |

**それでも (c) を採る理由**（着手前の議論より、いまのほうが根拠が強い）:

> **2 日で 3 回踏んだ読み違いは、全部この層で起きている**——`fact` の綴り
> （キーは `n_fact`、式では `!`）／**軸の並びがアルファベット順**（`Rad` の
> ケースが 2,000 件在るのに `angle_mode` の被覆が 6 中 0 になった）／
> `display/edge` の宣言漏れ。**「理屈として強い」ではなく、実際に壊れた場所を
> 覆っている。**

**順位は変わらない**——観測できる軸では (c) だけが検算を持ち、観測できない軸では
(b) と同点で (a) は覆えない。**選び直しは要らない。**

**(a) と (b) を消さない。** 選ばなかった理由が、あとから読む人の判断材料になる
——**(a) は後から直せない**（間違っていても緑で、気づく経路が無い）。
**(b) は golden が動く代償を払いながら、自己申告を誰も検算しない。**
**(c) は同じ代償で検算が付く。**

**この確定は Task 2・3 の形を決める**——Task 3 が `stratum` を記録し、
**Task 3 の中で「記録 ＝ 解析」の assert を置く。それがこの段の主番人である。**

### 裁定 2: 被覆を数える単位

**要求がシャードをまたぐ**ので、金融の「1 シャード = 1 モデル」が成り立たない。

- **(a) 要求ごとにモデルを持つ**（`coverage` を 1 枚のシャードに載せられない）
- **(b) 代表シャードに載せ、他シャードのケースも数える**（載っている場所と
  数えている範囲がずれる）

**★ どちらを採るにせよ、先に決めることが 1 つある**——**数える範囲に「9 領域の
10 枚の外」を含めるか。** `sin`/`cos`/`tan` を含むケースを持つシャードのうち、
**4 枚は 9 領域の外**である（2026-08-30 実測、`expr` の部分一致）:
`scientific-000` 1066 件 / `typed-000` 869 件 / `corrections-000` 438 件 /
`errors-000` 7 件。

- **含めると**: 被覆は実態に近づくが、**モデルの外のシャードが動いたときに
  被覆が黙って動く**（誰も予期しない依存）
- **含めないと**: `Deg × 三角` の被覆が実態より小さく出る。**「未達」と出たセルが
  「本当は別のシャードが踏んでいる」ことになり、埋める判断を誤らせる**

**私の推奨は「含めるが、どのシャードから来たかを除外の `covered_elsewhere` と
同じ形で記録する」**——金融で、**別のところで踏んでいることは補足であって
被覆ではない**、と扱ったのと同じ考え方である。

**どちらも、金融には無かった形**である。**この裁定は Task 1 の成果物**にする
——**紙の上で決めず、水準を定義したあとで、実データに当てて決める。**

### 裁定 4: 未達の門を、種類で分ける（2026-08-30、Task 4 の途中で発生・ユーザー裁定）

**規律を変える。変えた記録をここに残す。**

**金融で決めたのは「`unmet_cells > 0` は Heavy を落とす」**（設計書 §15.2）。
**科学計算では、その門をそのまま掛けると `coverage` を載せた瞬間に 7 領域が赤くなる。**

**未達 37 の内訳が違うからである:**

| 種類 | 数 | 意味 |
|---|---:|---|
| **測れない軸に起因** | **30** | 踏んでいるかもしれないが、**この経路では読めない**。「無い」ではない |
| **本当の穴** | **7** | データに無い |

**金融ではこの状況が起きなかった**——構成探索で `unmet` を 0 にしてから載せた。
**科学計算の 30 件は埋めようがない**（帯・文法クラス・演算種別・表示境界）。

**採る形**: **門を種類で分ける。測れない軸に起因する未達では落とさず、本当の穴では落とす。**

**採らなかった形と、その理由:**

- **未達 0 まで `coverage` を載せない**——**モデルが見つけたものを段 C の終わりまで
  誰にも見せないことになる。** このモデルの値打ちは**穴を可視化すること**なので、
  可視化を最後まで先送りするのは目的と逆である
- **未達を理由付き除外に振り替える**——**表は綺麗になるが嘘になる。**
  `elementary/band=zero` は**踏んでいるか分からない**だけで、覆えないわけではない
  （第 1 段階の「一律 `source_overflow`」と同じ形）
- **本当の穴も警告に留める**——**穴が緑で通るなら、このモデルを作った意味がない**

**★ 赤が始まるのは Task 5、続くのは段 B の終わりまで。**

**Task 4（`coverage` を載せる）では、まだ赤くならない**——受け入れ門は
`calls.spec.ts` から**呼び出しシャードにだけ**掛かっており、科学計算は
**値シャード**である（2026-08-30 実測）。**門を値シャードへ広げる Task 5 で、
初めて赤が出る。**

**赤い期間: Task 5 から、段 B（Task 6〜10）が本当の穴 7 件を埋めるまで。**

**止まるのはリリースであって、マージではない**（2026-08-30 に現物で確認）
——`heavy-corpus.yml` は `workflow_dispatch` と `workflow_call` だけで走り、
**毎回の CI が回すのは `heavy` の型検査・lint・vitest のみ**である。
**その代償の向きは正しい**——**「モデルが本当の穴を指しているあいだは出荷しない」**は、
`unmet > 0` の門が言いたかったことそのものである。

**★ この裁定の危険は 1 つ**——**「測れない」と宣言すれば門を通る**なら、
**宣言が「緩めれば緑になるパラメータ」になる。** 番人を置く:

- **(i) 宣言した軸が、本当に観測経路から出ないことを見る**——その軸の値を射影が
  返すケースが 1 件でもあれば落ちる。**観測できるのに「測れない」と宣言した**を捕まえる
- **(ii) 宣言の一覧を固定する**（(i) が書けない軸への保険。**弱いが、黙って増えることは防げる**）

### 裁定 5: `coverage` の載せ場所——10 枚すべてに同じブロック（2026-08-30）
