**きっかけ**: 1.0 の門 3 の判定で、**3 人が 3 つの数を出し、3 つとも正しかった**
（監視役 14 ／ 検証役 43 ／ 監視役の数え直し 288 中 43）。**割れたのは数ではなく問い**である。
**いまの規律には適用範囲が無い**——「公開関数の docstring に 1 行」とだけ書いてあり、
**どのファイルの公開関数か**を言っていない（`CONTRIBUTING.md:76-79`、`CLAUDE.md:63`）。

**利用者の裁定（2026-09-24）**: **規律の範囲を定義し直し、番人を置く。**

## §2 この設計が決めること

1. **適用範囲**——どのモジュールの、どの関数に宣言が要るか。**機械が判定できる形で。**
2. **宣言の置き場**——関数ごとか、モジュール単位でよいか。
3. **番人**——何を見て、何を見ないか。
4. **文書**——`CONTRIBUTING.md` と `CLAUDE.md` を、番人と同じことを言うように直す。

## §3 設計

### §3.0 範囲の外枠は「`reference/` の追跡下の `.py`、`tests/` を除く」（**1e の注記 1・2**）

**`scripts/` も入れる。** `generate_corpus.py` は **`mpmath` を直接 import して期待値を評価する**
（`:25`・`:2461`）、`find_convert_overflow.py` と `find_convert_half_way.py` も数の道具を持つ
（`grep` で 7 件ずつ）。**期待値に触るコードが表の外に在る——それは今回の穴そのものである。**

**数え方は `rglob("*.py")`**（`glob` では**サブパッケージができた日に数え落とす**）。
**`reference/tests/` は範囲外**——**あれは番人であって期待値ではない**（§4 にも書く）。
**いまの対象は 26 ＋ 5 ＝ 31 ファイル**（`__init__.py` を除く。`find` で数えた総数 32 と一致）。

### §3.1 範囲は「役割」で決め、**表に書く**（機械が引ける形）

**到達では絞れない**（§1）ので、**モジュールごとに役割を宣言する表**を置く。
表は `reference/src/calcarc_reference/independence.py` に持ち、**番人と人が同じ表を読む**。

| 役割 | 意味 | 宣言 |
|---|---|---|
| `expects` | **Rust と突き合わせる数（または文字列）を作る。** 期待値そのもの | **要る** |
| `builds` | **入力を組み立てる・ふるう・並べる。** 数を作らない | 要らない（**理由を表に書く**） |
| `tools` | 生成の道具（書き出し・指紋・座標）。期待値に触れない | 要らない（**理由を表に書く**） |

**初版の分類は、現物を読んで決める**（この設計書では決め切らない。§6 の「先に測る」を参照）。
**当たりは付けてある**——「数の道具（`mpmath` / `Fraction` / `Decimal` / `math.`）を使うか」で数えると、
`complex_ref`・`data_scale_ref`・`llm_ref`・`transfer_ref`・`corpus_coverage`・`corpus_opcorr` は 0 件、
`convert_ref` 56・`scientific_ref` 30・`loan_ref` 30 のように明らかな側もある。
**0 件でも `expects` はありうる**（`llm_ref` は整数の切り上げだけ、`transfer_ref` は単位の掛け算）ので、
**件数は当たりであって判定ではない。**

### §3.2 宣言はモジュール単位でよい（**関数ごとが要るのは、答えが割れるときだけ**）

**いまの規律は関数ごとを求めている。** それを**モジュールの docstring でもよい**に緩める。

- **理由**: `scientific_ref` の 15 関数は**全部同じ答え**になる（Rust は libm、こちらは mpmath 50 桁 ＝
  `独立: 別手順`）。**15 回同じ文を書かせる規律は、読む人に何も足さない**——
  **同じ文が 15 個あると、違いが在る日に気づけない。**
- **モジュール宣言には手順の対比を必ず書く**（1e の注記 4 ①）——
  「Rust は libm の f64、ここは mpmath 50 桁」の形。**対比の無い 1 行は、同じ答えを装う道具になる。**
- **混在するモジュールは 1 行にできない**（実測: 宣言を持つ 6 つのうち 3 つが既に混在。
  `loan_ref` は `一部`・`不可能`・`別手順` が並ぶ）。
- **関数側が勝つ**: モジュール宣言と違う答えを持つ関数は、**その関数の docstring に書く**
  （`loan_ref` は `不可能` と `一部` が混在している。**混在が在るモジュールは関数ごとになる**）。
- **番人はどちらでも通す**が、**印字で内訳を出す**（モジュール宣言 N 本・関数宣言 M 本）。

### §3.3 番人（pytest 1 本、`reference/tests/test_independence.py`）

1. **`independence.py` の表が、モジュールを 1 つ残らず分類している**——
   **新しいモジュールを足した日に赤くなる**（表に無い ＝ 赤）。**これが範囲の番人である。**
2. **`expects` のモジュールは、モジュール docstring か、公開関数すべてに宣言を持つ**。
3. **綴りは 4 語のどれか**（`別手順` / `不可能` / `一部` / `未確認`）。**それ以外は赤。**
4. **`builds` / `tools` に宣言が在ってもよい**（あっても害は無い）が、**理由の欄は空にできない。**
5. **表に在るがディスクに無いファイルも赤**（**両向き**。1e の注記 3）——
   **消したファイルの行が表に残ると、範囲は静かに広いまま**になる。
6. **数を印字する**——`expects` の数・モジュール宣言の数・関数宣言の数・公開関数の総数。
   **「何を数えた数か」を印字の文に書く**（0.9.6 の教訓）。
   **あわせて「モジュール宣言だけで済ませたモジュール名と、その公開関数の数」を出す**
   （1e の注記 4 ②。**15 関数を 1 行で塗ったことが、読む人の目に入る**）。

### §3.4 番人が見ないもの（**註にはっきり書く**）

**機械が見るのは、行が在ることと、綴りが 4 語のどれかであることだけである。**
**中身が正しいか**——本当に別手順か、本当に不可能か——は**見ない。読む人が見る。**
**これは CLAUDE.md の「機械では検出できない」と同じことを、番人の側から言ったもの**である。
**番人を置いたことで「独立が保証された」と読ませない**ために、この 3 行を `test_independence.py` の
docstring に置く。

### §3.5 文書

- `CONTRIBUTING.md:76-79`（「書く場所は 2 つ」）に**適用範囲の 1 段**を足し、
  **「範囲は `independence.py` の表が持つ。表に無いモジュールは番人が赤にする」**と書く。
- `CLAUDE.md:63` の 1 行は**範囲を指す形**に直す（いまは「公開関数の docstring に 1 行」だけ）。
- **設計書に節を 1 つ**という既存の要求（`CONTRIBUTING.md` の 1 つ目）は**残す**
  ——番人はコード側しか見ないので、**設計書側は人の仕事のまま**である（そう明記する）。

## §4 やらないこと

  **`builds` に宣言を書かせるのは、読む人の時間を捨てる**（同じ文が増えるだけで、違いが見えなくなる）。

- **Rust 側の宣言**。規律は参照実装の側にしか無い（いまもそう）。

## §7 未決だったもの——**2026-09-24 に全部決まった**

1. **`corpus_*.py` は 1 つずつ分類する**（監視役の裁定）。**まとめると、違いが在る日に気づけない**
   ——**§3.2 の「同じ文が 15 個あると違いが見えない」の裏返し**である。
2. **`cases.py` は `builds`**（私が現物を読んで決めた）。**公開関数 0、数を作らない**
   ——持っているのは入力の表で、**入力は Rust と共有するのが前提**である（共有しなければ
   突き合わせ自体が成り立たない）。**独立の議論の対象は「答え」であって「問い」ではない。**
3. **「Rust の実装は見ていない」の 3 つは、3 つとも `不可能`**（**私の初版の読み `未確認` は誤り**。
   1e の指摘で Rust 側を読み直した）:
   - **`llm_ref`・`transfer_ref`**: **Rust は `u128` の checked 演算**
     （`data_scale/llm.rs:4`「バイト数は Exact Integer で、u128 の checked 演算で持つ」、
     `data_scale/transfer.rs:112`「左から順に checked_mul する」）、**こちらは Python の int**。
     **どちらも厳密な整数**で、**式は仕様が固定している**——**別解が無い。**
   - **`convert_ref`**: **Rust も f64 を経由しない**（`convert/mod.rs:15`
     「**f64 を一度も経由しない——`Rational` は i128 有界の既約分数である**」）、
     こちらは `Fraction`。**式（affine 1 本）も評価（厳密有理数）も同型**なので **`不可能`**。
     **違いは有界（i128）か無界かだけ**で、**それは溢れの境目にしか出ない**
     ——**宣言の本文にその 1 文を書く**（ラベルではなく理由として）。
   **「見ていない」は書いた人の行為であって、手順が違うことの主張ではない。**
   **`未確認` にすると、実は同型であることを隠す。**

## §8 分類の読み（**現物を読んだ結果。実装でこの表を `independence.py` に置く**）

**`expects` と読んだもの（宣言が要る）**: `complex_ref`（別手順: Rust は f64 の hypot/atan2、
こちらは SymPy の厳密式を 50 桁）／`real_ref`・`eng_ref`（別手順: Rust は `{:.9e}` の文字列から
指数を読む、こちらは `Decimal` で直接）／`sexagesimal_ref`（別手順: `Fraction` で f64 の割り算を
1 度も通らない）／`data_scale_ref`（別手順: Python の int が u128 と自然に独立）／
`scientific_ref`（別手順。**ただし `pow_real` だけ `0^(y<0)` の規約を直に書いており、
ここは共有＝`一部`。モジュール 1 行＋関数 1 行になる**）／`convert_ref`・`llm_ref`・`transfer_ref`
（**不可能**。§7-3）／`currency_ref`（式は spec、`float` を一度も経由しない）／
`corpus_eval`・`corpus_complex`（別手順: 式木を数として評価する。
「**キー列を見てはならない——触った瞬間 engine の移植になる**」）／`corpus_calls`（期待値は
`*_ref` を呼ぶ）／`corpus_errors`（**別手順**: 「Rust を見ない。**種別名だけ共有**し、
どの式がどの種別かは数学的な定義域から決める」）／`corpus_entry`（**不可能**:
「**打鍵の途中の表示に数学的な定義は無い……独立に計算しない**」と自分で書いている。
**4 語のうち `不可能` がこの形である**）／`compound_ref`・`loan_ref`・`expr_ref`・
`loan_boundary`・`complex_div_boundary`・`corpus_combinatorics`（**既に宣言が在る**）。

**`builds` と読んだもの（宣言は要らない。理由を表に書く）**: `cases`（入力の表）／
