# `独立:` の規律に適用範囲を与え、番人を置く —— 設計（0.9.7）

**きっかけ**: 1.0 の門 3 の判定で、**3 人が 3 つの数を出し、3 つとも正しかった**
（監視役 14 ／ 検証役 43 ／ 監視役の数え直し 288 中 43）。**割れたのは数ではなく問い**である。
**いまの規律には適用範囲が無い**——「公開関数の docstring に 1 行」とだけ書いてあり、
**どのファイルの公開関数か**を言っていない（`CONTRIBUTING.md:76-79`、`CLAUDE.md:63`）。

**利用者の裁定（2026-09-24）**: **規律の範囲を定義し直し、番人を置く。**

---

## §1 現物（`main = 884f324`、2026-09-24 に機械で数えた）

| | 数 |
|---|---|
| `reference/src/calcarc_reference/` のモジュール（`__init__` を除く） | **26** |
| そのうち `scripts/generate.py`・`scripts/generate_corpus.py` から **import で到達する**もの | **26**（全部） |
| トップレベルの**公開関数**（`_` で始まらない `def`） | **140** |
| docstring に `独立:` を持つ公開関数 | **33** |
| 持たない公開関数 | **107** |
| **モジュールの docstring** に `独立:` を持つモジュール | **2**（`complex_div_boundary`・`corpus_combinatorics`） |

**到達では絞れない。** 26 モジュール全部がどちらかの生成器から到達する——
**「期待値を作る」と「入力を組み立てる」を、import は区別しない。**

**いま宣言を持つのは 5 モジュールだけ**（`loan_ref` 12／`compound_ref` 11／`expr_ref` 6／
`corpus_opcorr` 2／`currency_ref` 1／`loan_boundary` 1）。**残り 21 モジュールは 0 である。**

**ただし、宣言が無いモジュールが無言とは限らない。** 3 つは冒頭で**別の綴り**で言っている
（`convert_ref`・`llm_ref`・`transfer_ref` の「**Rust の実装は見ていない**」）、
`scientific_ref` は「**Rust は libm の f64、ここでは mpmath 50 桁**」と**手順の違いそのもの**を
書いている、`corpus_eval` は「**キー列を見てはならない……触った瞬間 engine の移植になる**」と
書いている。**言っていることは規律の中身だが、綴りが 4 語ではない。**

## §2 この設計が決めること

1. **適用範囲**——どのモジュールの、どの関数に宣言が要るか。**機械が判定できる形で。**
2. **宣言の置き場**——関数ごとか、モジュール単位でよいか。
3. **番人**——何を見て、何を見ないか。
4. **文書**——`CONTRIBUTING.md` と `CLAUDE.md` を、番人と同じことを言うように直す。

## §3 設計

### §3.1 範囲は「役割」で決め、**表に書く**（機械が引ける形）

**到達では絞れない**（§1）ので、**モジュールごとに役割を宣言する表**を置く。
表は `reference/src/calcarc_reference/independence.py` に持ち、**番人と人が同じ表を読む**。

| 役割 | 意味 | 宣言 |
|---|---|---|
| `expects` | **Rust と突き合わせる数（または文字列）を作る。** 期待値そのもの | **要る** |
| `builds` | **入力を組み立てる・ふるう・並べる。** 数を作らない | 要らない（**理由を表に書く**） |
| `tools` | 生成の道具（書き出し・指紋・座標）。期待値に触れない | 要らない（**理由を表に書く**） |

**初版の分類は、現物を読んで決める**（この設計書では決め切らない。§6 の「先に測る」を参照）。
**当たりは付けてある**——「数の道具（`mpmath` / `Fraction` / `Decimal` / `math.`）を使うか」で数えると、
`complex_ref`・`data_scale_ref`・`llm_ref`・`transfer_ref`・`corpus_coverage`・`corpus_opcorr` は 0 件、
`convert_ref` 56・`scientific_ref` 30・`loan_ref` 30 のように明らかな側もある。
**0 件でも `expects` はありうる**（`llm_ref` は整数の切り上げだけ、`transfer_ref` は単位の掛け算）ので、
**件数は当たりであって判定ではない。**

### §3.2 宣言はモジュール単位でよい（**関数ごとが要るのは、答えが割れるときだけ**）

**いまの規律は関数ごとを求めている。** それを**モジュールの docstring でもよい**に緩める。

- **理由**: `scientific_ref` の 15 関数は**全部同じ答え**になる（Rust は libm、こちらは mpmath 50 桁 ＝
  `独立: 別手順`）。**15 回同じ文を書かせる規律は、読む人に何も足さない**——
  **同じ文が 15 個あると、違いが在る日に気づけない。**
- **関数側が勝つ**: モジュール宣言と違う答えを持つ関数は、**その関数の docstring に書く**
  （`loan_ref` は `不可能` と `一部` が混在している。**混在が在るモジュールは関数ごとになる**）。
- **番人はどちらでも通す**が、**印字で内訳を出す**（モジュール宣言 N 本・関数宣言 M 本）。

### §3.3 番人（pytest 1 本、`reference/tests/test_independence.py`）

1. **`independence.py` の表が、モジュールを 1 つ残らず分類している**——
   **新しいモジュールを足した日に赤くなる**（表に無い ＝ 赤）。**これが範囲の番人である。**
2. **`expects` のモジュールは、モジュール docstring か、公開関数すべてに宣言を持つ**。
3. **綴りは 4 語のどれか**（`別手順` / `不可能` / `一部` / `未確認`）。**それ以外は赤。**
4. **`builds` / `tools` に宣言が在ってもよい**（あっても害は無い）が、**理由の欄は空にできない。**
5. **数を印字する**——`expects` の数・モジュール宣言の数・関数宣言の数・公開関数の総数。
   **「何を数えた数か」を印字の文に書く**（0.9.6 の教訓）。

### §3.4 番人が見ないもの（**註にはっきり書く**）

**機械が見るのは、行が在ることと、綴りが 4 語のどれかであることだけである。**
**中身が正しいか**——本当に別手順か、本当に不可能か——は**見ない。読む人が見る。**
**これは CLAUDE.md の「機械では検出できない」と同じことを、番人の側から言ったもの**である。
**番人を置いたことで「独立が保証された」と読ませない**ために、この 3 行を `test_independence.py` の
docstring に置く。

### §3.5 文書

- `CONTRIBUTING.md:76-79`（「書く場所は 2 つ」）に**適用範囲の 1 段**を足し、
  **「範囲は `independence.py` の表が持つ。表に無いモジュールは番人が赤にする」**と書く。
- `CLAUDE.md:63` の 1 行は**範囲を指す形**に直す（いまは「公開関数の docstring に 1 行」だけ）。
- **設計書に節を 1 つ**という既存の要求（`CONTRIBUTING.md` の 1 つ目）は**残す**
  ——番人はコード側しか見ないので、**設計書側は人の仕事のまま**である（そう明記する）。

## §4 やらないこと

- **107 件の穴を機械的に埋めること**。**範囲を決めたら、埋めるのは `expects` の分だけ**になる。
  **`builds` に宣言を書かせるのは、読む人の時間を捨てる**（同じ文が増えるだけで、違いが見えなくなる）。
- **中身の検査**（§3.4）。
- **Rust 側の宣言**。規律は参照実装の側にしか無い（いまもそう）。

## §5 見積り（**実測前**）

**`expects` が 15 モジュール前後、うち混在が 2〜3 モジュール**と見ている。
その場合に書く行は **モジュール宣言 12 行＋関数宣言 20 行前後**。
**107 件を全部書くことにはならない**——それが §3.2 を置く理由である。
**この数は当たりであって実測ではない**（分類を決めた日に数え直す）。

## §6 手順（**先に測る。決めるのはそのあと**）

1. **26 モジュールを読んで分類する**（`expects` / `builds` / `tools` と、その理由 1 行）。
   **読むのは docstring と公開関数の中身**で、**当たりの数（§3.1）は使わない。**
2. 分類表と番人を置き、**赤の確認 3 通り**: (a) 表から 1 モジュール消す → 赤
   (b) `expects` のモジュールから宣言を 1 行消す → 赤 (c) 綴りを 5 語目にする → 赤。
3. `expects` の穴を埋める（**中身を書く。同じ文の写しにしない**）。
4. 文書（§3.5）を同じコミットで直す。

## §7 未決（**裁定が要る**）

1. **`corpus_*.py` の扱い。** `corpus_eval` は**式木を数として評価する**——
   **期待値を作る側**に見える。一方 `corpus_expr` は木を組むだけに見える。
   **10 個の `corpus_*` を一律にせず、1 つずつ分類してよいか**（私はそうしたい）。
2. **`cases.py`（公開関数 0、入力の表）を `builds` に入れてよいか。**
   **入力の表も「Rust が読む前提」を作る**ので、**独立の議論に無関係ではない**。
   **私は `builds` に入れ、理由に「数を作らない。入力は Rust と共有するのが前提」と書くのを推す。**
3. **既存の 3 モジュールの「別の綴り」**（`convert_ref`・`llm_ref`・`transfer_ref` の
   「Rust の実装は見ていない」）を、**4 語のどれに移すか**。
   **私は `別手順` ではなく `未確認` が正しいと読む**——「見ていない」は手順が違うことの主張ではない。
   **ただし書いた人の意図は違うかもしれない**ので、裁定に上げる。
