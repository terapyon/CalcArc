# 複素数を検証する（段階 J）設計

2026-08-17

前提: [重量級検証コーパス（Layer 6）設計](2026-08-15-heavy-corpus-e2e-design.md)。

## 1. なぜやるか

未押下キーの最後の 2 個——**`j` と `polar_toggle`**——を扱う。
これで **46 キーすべてが押される**。

**この電卓は複素数を持っている。** `j` で虚数単位を打ち、四則が複素数のまま動き、
`▸∠` で極形式に切り替わる。**コーパスはそこに一度も触れていない。**

そして**独立実装が既にある**——`complex_ref.py` が **SymPy の厳密有理数**で
複素の四則と極形式変換を持つ。Rust は f64 の対で計算するので、**別物である**。

## 2. 実装の事実（コードから確認、2026-08-17）

| | |
|---|---|
| `expect` の形 | **既に `{re, im}` を持っている**。データ形式の変更が要らない |
| `j` の挙動 | バッファに桁があれば**虚実を切り替える**、無ければ虚数として始める（`engine/mod.rs:283`） |
| `polar_toggle` | 表示を `r ∠ θ` にする。**`θ` は角度モードに従う**（`format.rs:200`） |
| 極形式が出せない値 | `try_format_polar` が **`None`**（半径が無限大のとき） |
| 関数の定義域 | **関数は実数に閉じている**。`sqrt(-4)` は `DomainError` で、複素数を返さない |
| 複素数が生きる場所 | **入力・四則・表示**。`sqr` と `neg` は乗算・減算なので複素のまま |

**この最後の 1 行が設計を決める。** 複素数を作れるのは
**`j` と四則と `sqr`/`neg` だけ**で、三角関数や対数には渡せない（`DomainError`）。

## 3. 設計

### 3.1 式木に虚数の葉を足す。関数には渡さない

`Imag(text)` を足す——`j` を押してから桁を打つ形。

生成する木は **`j` を含む葉と、四則・`sqr`・`neg` だけ**で組む。
**三角関数と対数と冪は使わない**——`real_arg` が `DomainError` を返すので、
生成しても全部捨てられるだけである。**捨てられると分かっているものを
生成するのは、棄却率を上げるだけで何も確かめない。**

### 3.2 期待値は `complex_ref` から取る

`complex_ref.add` / `sub` / `mul` / `div` が **SymPy の厳密有理数**で計算する。
Rust は f64 の対なので、**アルゴリズムを共有していない。**

**`expect` は既存の `{re, im}` をそのまま使う。** データ形式の変更が要らない
——段階 F（金融）で `call` を足したときと違い、ここは**既にある器に入る**。

### 3.3 比較は虚部も見る。いまは実部しか見ていない

**現行の照合は `expect.re` しか読んでいない。** 全ケースの `im` が 0 だったので
問題にならなかったが、**複素数を入れると虚部の食い違いを見逃す**。

比較を「実部と虚部の両方」に広げる。**判定は複素平面上の距離で行う**
——`|actual − expected| / |expected|` を複素数として計算する。
実部と虚部を別々に見ると、**片方が 0 に近いときに相対誤差が定義できなくなる**
（実部 0 の純虚数など）。

**表示から複素数を読む経路が要る。** `parseDisplay` は実数専用なので、
**`parseComplexDisplay` を別に置く**——`3+j4` / `j2` / `-j2` の形を読む。
**`parseDisplay` を広げない**（段階 I と同じ理由。狭いことに価値がある）。

### 3.4 極形式は表示のトグルとして扱う

`polar_toggle` は**値を変えない**ので、段階 I の `display` ケースと同じ形にする。

```json
{"kind": "display", "keys": ["3", "add", "4", "j", "eq", "polar_toggle"],
 "expect": {"main": "5 ∠ 53.13010235"}}
```

期待値は `complex_ref.rect_to_polar` から取る。**`θ` は角度モードに従う**ので、
本段階では `Deg` に固定する（`angle_toggle` は段階 H の主題）。

### 3.5 `j2` の表示が戻ってくる

**面白い巡り合わせがある。** このブランチの初期、`sqrt(-4)` が `j2` を返すことを
実測して記録したが、その後 main で `DomainError` になり、**記録が嘘になった**
（2026-08-16 に訂正）。そのとき別セッションから
「**`j2` という表示自体は今も出る——`j` `2` と打てばよい。変わったのは
『負数の平方根の答えとして出るか』だけ**」という精度の指摘を受けた。

**この段階が、その `j2` を初めて実際に打つ。**

## 4. やらないこと

- **関数に複素数を渡さない**（§3.1）。`DomainError` になるだけ
- **`parseDisplay` を広げない**（§3.3）
- **極形式の入力**（`∠` を打って極形式で入れる）。表示のトグルだけを扱う
- **既存シャードを作り直さない**

## 5. 要件

- **R1** `Imag` を式木に足す。**`j` を含む葉と四則・`sqr`・`neg` だけで組む**
- **R2** 期待値は `complex_ref` から取る。**Rust の実装を読んで書かない**
- **R3** 比較を**虚部まで**広げる。**複素平面上の距離**で判定する
  （実部と虚部を別々に見ない）
- **R4** `parseComplexDisplay` を新設。**`parseDisplay` は広げない**
- **R5** `polar_toggle` は段階 I の `display` ケースとして扱う。
  期待値は `complex_ref.rect_to_polar` から
- **R6** **46 キーすべてが押されたこと**を、レポートが実データから示す
- **R7** 再生成一致ゲートの対象に含める

## 6. リスク

- **既存の照合が実部しか見ていない。** 広げるとき、**既存 16000 件の判定が
  変わらないことを確かめる**必要がある（全件 `im` が 0 なので変わらないはずだが、
  **「はず」で済ませない**——複素の距離が実部だけの相対誤差と一致することを
  テストで固定する）
- **`complex_ref` は SymPy を使う。** 既存のコーパスは mpmath だけで、
  **`generated_by` の素性に SymPy が入っていない**。ここは実際に SymPy が
  値に関与するので、**素性の文字列を分ける**必要がある
  （素性に嘘を書かない、という既存の規律）
- **`0` の虚部と `-0` の虚部。** `negated()` が `-0.0` を作らない工夫を engine 側が
  しているが、**参照側が `-0.0` を作ると表示が食い違う**（`∠ -180` と `∠ 180`）。
  **実装の最初に、0 近傍の極形式を実測する**
