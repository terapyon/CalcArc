## §1 形が 2 種類ある — ここが設計の入口

エンジンはキーを 2 通りに捌いている:

| | 仕組み | 例 |
|---|---|---|
| **単項** | `apply_unary(state, f)`。数を打ってから押すと、その場で現在値に適用 | `sin` `√` `x²` |
| **二項** | `push_binop(state, op)`。優先順位（`precedence()`）で括る | `+` `−` `×` `÷` |

**`n!` は単項である**——`5` `n!` で `120`。`apply_unary` にそのまま乗り、
エンジンの構造は 1 行も変わらない。

**`nPr` / `nCr` は二項演算子である**——`5` `nPr` `2` `=` で `20`。
**`BinOp` に 2 つ足し、優先順位を決める必要がある。** ここがこの spec の主題。

## §2 優先順位

いま `BinOp::precedence()` は `Add/Sub = 1`、`Mul/Div = 2`。

**`nPr` / `nCr` は `3`（`×` `÷` より先）にする。**

```
5 × 4 nCr 2 =   →  5 × (4 nCr 2)  =  5 × 6  =  30
```

理由: 一般的な関数電卓（Casio）がそうであり、`nCr` は「1 つの数」を作る演算として
読まれる。`5 × 4` を先に計算して `20 nCr 2` にする読み方は、書いた人の意図から遠い。

**同じ優先順位どうしは左結合**（既存の `>=` 比較がそうなっている）。
`5 nCr 3 nCr 2` は `(5 nCr 3) nCr 2` = `10 nCr 2` = `45`。

## §3 定義域

3 つとも**非負整数**の上でしか定義しない。

| | 定義域 | 外れたとき |
|---|---|---|
| `n!` | `n` が非負整数 | `DomainError` |
| `nPr` | `n`, `r` が非負整数、`r ≤ n` | `DomainError` |
| `nCr` | 同上 | `DomainError` |

- **非整数は `DomainError`。** `2.5!` はガンマ関数だが、S-1 の裁定（関数は実数に
  閉じる、面倒な拡張はしない）と同じ精神で入れない
- **負は `DomainError`**
- **`0! = 1`**、**`nP0 = 1`**、**`nC0 = 1`**、**`nCn = 1`**——境界は全部 1

**判定は `x.fract() == 0.0 && x >= 0.0 && x.is_finite()`。** `Value` が複素数のときは
`is_real()` が偽なので `DomainError`（S-1 の線引きと同じ）。

## §4 精度 — f64 で計算してよいのか

`Value` は `f64` である。**整数値を返す演算を f64 でやることの是非**を、
数値方針に書く必要がある。

### 事実

- `20!` = 2,432,902,008,176,640,000 は `2^53` を超えており、**f64 では既に厳密でない**
- `170!` ≈ 7.26e306 が f64 の上限。**`171!` は `Overflow`**
- しかし**表示は有効数字 10 桁**（`DISPLAY_DIGITS`）である。`20!` は
  `2.432902008e18` と出る

### 誤差の見積り

`n!` を素直に `n` 回掛けると、1 回の乗算の相対誤差は `2^-53 ≈ 1.1e-16`。
`n` 回で高々 `n × 1.1e-16`。**`n = 170` でも `1.9e-14`** であり、
**表示の 10 桁（`1e-10` 相当）より 4 桁良い。**

**したがって、表示される 10 桁はすべて正しい。** これを spec の主張とし、
golden で固定する。

### `nCr` は素直に書くと途中であふれる

`nCr = n! / (r!(n−r)!)` をそのまま計算すると、`n = 200` あたりで分子が
`Overflow` する——**答が f64 に収まるのに、途中であふれる。**

**乗除を交互にする形で書く**:

```
C(n, r) = Π[i=0..r-1] (n − i) / (i + 1)
```

各段の途中値は常に `C(n, i+1)` そのものなので、**答が収まるなら途中も収まる**。
`r` を `min(r, n−r)` に置き換えて反復回数も減らす。

`nPr = Π[i=0..r-1] (n − i)` は素直な積でよい（答より大きい途中値が出ない）。

**この「途中であふれない書き方」は spec の主張なので、golden の必須ケースに
`200 nCr 100`（≈ 9.05e58、f64 に収まる）を入れて固定する。**

## §5 Python 参照の独立軸

**ここは独立性が素直に取れる。** Python は `math.factorial` / `math.comb` /
`math.perm` で**厳密な整数**を出せる。

- Rust は f64 の逐次乗除、Python は**任意精度の整数** —— アルゴリズムが同型でない
- golden の期待値は**Python の厳密整数を 10 桁に丸めたもの**にする
- **`tolerance` は `scientific.json` の既存のものを使う**（相対誤差）。
  §4 の誤差見積り（`1.9e-14`）が tolerance に収まることを、生成時に確かめる

**`n!` が f64 の上限を超える境界**（`170!` は成功、`171!` は `Overflow`）も
Python 側で判定できる（`math.factorial(171)` の桁数を見る）。

## §6 盤面

**3 キー要る**（`n!` `nPr` `nCr`）。

**2026-08-16 時点の盤面**（S-2 で関数列が 2 段になった。S-1 §7 が正）:

```
関数列 1 段目: [Shift] [sin] [cos] [tan] [√]  [x²]  [DEG/RAD]
関数列 2 段目: [ENG]   [ln]  [log] [1/x] [eˣ] [xʸ]  [°'"]
```

**第 1 面はこれで埋まっている。** 第 2 面は S-1 が 4 つ（逆三角 3 + `e`）、
`EXP` の裏に `π`（既存）。**空いているのは数字キーと `√` `x²` `DEG/RAD` などの裏。**

**裁定: 数字キーの Shift を使う（§7）。**

| 第 1 面 | Shift |
|---|---|
| `7` | `n!` |
| `8` | `nPr` |
| `9` | `nCr` |

理由: 3 つは**同じ仲間**なので隣り合わせに置きたい。関数列の裏は S-1 が意味の対応
（`√`→`ln` など）で埋めており、そこに割り込むと対応が壊れる。数字の裏は空いていて、
**3 つ並べられる場所は他に無い**。

**懸念**: 数字キーに Shift が付くのはこのリポジトリで初めてである
（いま Shift を持つのは `sin`/`cos`/`tan`/`√`/`x²`/`EXP` だけ）。
「数字の裏に機能がある」ことを利用者が見つけられるか。§7 の裁定待ちにする。

## §7 裁定（ユーザー、2026-08-16）

| # | 論点 | 裁定 |
|---|---|---|
| 1 | `nPr` / `nCr` の優先順位 | **`×` `÷` より先（3）。** `5 × 4 nCr 2` は `5 × 6 = 30` |
| 2 | 3 キーの置き場 | **数字 `7` `8` `9` の Shift。** 3 つを隣り合わせに置ける唯一の場所（関数列 2 段目は ENG + S-1 の 5 つ + `°'"` で埋まっている）。**数字キーに Shift が付くのはこのリポジトリで初めて**なので、**発見性を E2E で確かめる**こと |
| 3 | 非整数の階乗 | **`DomainError`。** ガンマ関数は「実数に閉じる」の精神から外れる |
| 4 | 表示の桁 | **10 桁のまま。** `20!` は `2.432902008e18`。19 桁は画面に入らない |

**裁定 2 に伴う実装上の注意**: 数字キーの Shift は前例が無いので、**Shift を押したときに
数字の面が変わることが見て分かるか**をスクリーンショットで確かめる。テストでは
分からない。

## §8 検証

段ゲート: 数値方針（§4 の誤差の主張）→ Python 参照 + golden → Rust → WASM → 盤面。

**必須ケース（案）**: `0!` `1!` `20!` `170!` `171!`(Overflow) `2.5!`(DomainError)
`(-1)!`(DomainError) / `5 nPr 2` `5 nCr 2` `nC0` `nCn` `5 nCr 6`(DomainError)
`200 nCr 100`（途中であふれない証拠）/ 優先順位 `5 × 4 nCr 2`。

**赤確認**: `nCr` を「素直な `n!/(r!(n−r)!)`」に書き換えて、`200 nCr 100` が
`Overflow` になる赤を見る——§4 の主張がそこにしか無いため。
