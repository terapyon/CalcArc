**新しい節を書くときは、全節を読み直さず、この 6 行とだけ突き合わせる。**

## §1 裁定（ユーザー、2026-08-19）

1. **範囲は 4 つ**——次元数の入力方式、LLM、Data Transfer、Scale のカテゴリ選択 UI
2. **次元数は「選択」と「手入力」を切り替える。既定は選択。**
   実現は**面の入れ替え**（既存のデータ型面と同じ機構。新しい UI 部品は作らない）
3. **LLM は重み ＋ KV cache。** モデル名の諸元表は持たない（陳腐化してもテストは
   緑のままだから）
4. **KV の諸元は KV ヘッド数とヘッド次元を別々の項目にする**（`config.json` の
   `num_key_value_heads` と `head_dim` をそのまま写せる形）

## §2 いま在るもの

**Data Scale パネルは電卓である。** 件数も次元数もキーパッドで打ち、`K` / `M` / `G`
のサフィックスが押せる。`select` のフォームだったのは電卓化より前の姿である。

**【訂正 2026-08-20】四則の式は打てない。** ここには当初「**四則の式まで打てる**
（`datascale/entry.ts`、`ExprCalc`）」と書いていたが、実物に当てはまらない。
**層と盤面を取り違えた**——層は式を積めるが、盤面がそこへ配線されていない:

- **層（`web/src/datascale/entry.ts`）は積める。** `web/src/units/entry.ts` の
  `pushOperator` を再輸出しており、式を組み立てる道具は揃っている
- **キーは在る。** `web/src/ui/Keypad/dataScale.ts` の `PAD` は
  `( ) ÷ × − + =` を出している
- **盤面が受けていない。** `DataScalePanel.tsx` の押下の `switch` にあるのは
  `zeros3` / `k` / `m` / `g` / `del` / `ac` と `digit:` の枝だけで、演算子の
  トークンはどの枝にも落ちない。`grep -rn pushOperator web/src` で実際に呼んで
  いるのは `FinancePanel.tsx:497` だけである

**§2 は「いま在るもの」を数える節なので、在るのは層とキーであって、機能ではない。**
押しても何も起きない演算子キーは別件として最終 triage に送る（Ruling 19）。
将来この配線を足すときに読み直せるよう、区別を残して訂正する。

**面の入れ替えは既にある。** 項目行で「データ型」を選ぶとキーパッドが型の一覧
（`TYPE_SECTIONS`、15 セル。うち押せるのは 11）に入れ替わる。**面を入れ替えたときに
画面が伸び縮みすると、押そうとした位置がずれる**——§4 はこの規律に従う。

**【訂正 2026-08-19】枠は 4 列 × 4 行ではなく、5 列 × 5 行である。** ここには当初
`dataScale.ts` の冒頭コメント「数字面と型面は同じ 4 列 × 4 行の枠に載る」を規律の
出典として引いていたが、**その コメント自体が実物とずれている**。実物はこうである:

- `dataScale.ts` の `PAD` は `columns: 5`・25 キー（5 行）、`TYPES` は `columns: 5`・
  15 セル
- 枠を押さえているのは**コメントではなく CSS** である——
  `DataScalePanel.module.css` が両区画に `grid-template-rows: repeat(5, 1fr)` と
  `aspect-ratio: 1 / 1` を掛け、そちらのコメントは正しく「5 列 × 5 行の正方キーの
  格子」と書いている

**規律の中身は変わらない**（面を入れ替えても枠は動かない）。変わるのは**枠に入る
セル数**で、5 × 5 = 25 セル——DEL と AC を数字面と同じ位置に置いても、候補キーには
23 セル残る。`dataScale.ts` の古いコメントは実装時に直す。

**バイトの表示器は共有できる**（`data_scale/format.rs`）。`format_decimal` /
`format_binary` は「値が 1 以上になる最大の単位」を選び、小数第 1 位・
round-half-to-even で丸め、最小単位未満は `None` を返す（UI はその行を隠す）。
**設計書 §25 が言う「共通 Data Size Engine」はこれである。** 新しい 2 つも
ここに載せる——`GB` と `GiB` の扱いが 3 カテゴリで揃う。

**コーパスは wasm を直接叩いている。** `data-scale` と `finance` は call シャードで
（`corpus.ts:301`）、キーパッドを経由しない。`heavy:ui` はハーネス専用ページ直行
（U-0 §2 の実測）。**したがって、既存の `data_scale` 関数の署名さえ変えなければ、
UI をどれだけ変えてもコーパスは無傷である**（§0.0-1 はこのためにある）。

## §3 計算（公開仕様）

**この節が参照実装との契約である。** Python はこの節から書き、Rust の実装を見ない。

### 3.1 単位

内部は**すべてビット**で持ち、表示の直前にバイトへ落とす。

```text
bytes = ceil(bits / 8)
```

**切り上げる**——4 bit の重みが 1 個だけあるとき「0 バイト」と言わないためである。

**どこで効くかを先に測っておく。** `kv_bits` は `2 × … × {8,16,32} bit` なので
**常に 8 の倍数**で、**KV 側の切り上げは 1 度も発火しない**。効くのは
**`INT4` × 奇数パラメータの重み側だけ**である（他の精度は 8 の倍数）。

したがって **golden の端ケースは重み側に名指しで置く**（§7）。**KV 側の切り上げが
未検証のまま残ることは、隠さずここに書いておく**——「通っているから正しい」ではなく
「その経路は 1 度も踏まれていない」が事実である。

### 3.2 LLM の重み

```text
weight_bits = parameters × bits_per_parameter
```

`bits_per_parameter` は `FP32=32` `FP16=16` `BF16=16` `INT8=8` `INT4=4`。

**この表は定義値である**（IEEE 754 の binary32 / binary16、bfloat16 の 16 bit、
整数型のビット幅）。参照実装は Rust からではなく**この定義から**書く。

**INT4 は 4 bit = 0.5 byte の理論値を使う**（設計書 §22）。GGUF 等の実ファイルとは
一致しない——scale・zero point・メタデータ・アラインメントが載るためである。

### 3.3 KV cache

```text
kv_bits = 2 × layers × context_length × kv_heads × head_dim × bits_per_kv_element
```

先頭の `2` は **K と V の 2 本**である。**バッチサイズは 1 で固定**し、項目にしない
（§8 スコープ外）。

**`kv_heads` は KV ヘッド数であり、アテンションヘッド数ではない。** いまのモデルの
多くは GQA で、例えば 32 → 8 のように減っている。ここを取り違えると KV cache が
4 倍ずれる。**赤確認 1 はこの取り違えを変異として当てる**（§7）。

### 3.4 合計

```text
total_bytes = ceil(weight_bits / 8) + ceil(kv_bits / 8)
```

**それぞれ切り上げてから足す。** 見えている数が足し算になっていることを優先する。

**【訂正 2026-08-19】この 2 つの式は、いま使っているどのビット幅でも必ず
一致する。** ここには当初「合計を `ceil((weight_bits + kv_bits) / 8)` にすると、
画面に出ている 2 行の足し算が合計と 1 バイトずれることがある」と書いていたが、
**そのずれは起こり得ない**——§3.1 が自分で書いているとおり `kv_bits` は常に
8 の倍数だからである。

```text
kv_bits ≡ 0 (mod 8)  ⇒  ceil((w + kv)/8) = ceil(w/8) + kv/8
```

**成り立つ根拠は「ビット幅が 4 の倍数であること」である。**

```text
bits ≡ 0 (mod 4)  ⇒  2 × bits ≡ 0 (mod 8)  ⇒  kv_bits ≡ 0 (mod 8)
```

**盤面が KV に出すのは 4 つ**（FP16 / BF16 / FP32 / INT8 = 16 / 16 / 32 / 8 bit。
§4.3 の候補表。**INT4 は KV に来ない**）で、どれも 8 の倍数だから当然に満たす。
**コアは 5 つとも受ける**が（INT4 も 4 の倍数で `2 × 4 = 8`）、そちらも満たす。

**「`bits_per_kv_element` が 4 以上だから」ではない。** その言い方だと 6 bit
（`2 × 6 = 12`）を許した瞬間に、条件を満たしたまま恒等式が黙って破れる。
**この訂正がまさに戒めた壊れ方を、訂正の理由文自体がやっていた**（監視役の指摘、
2026-08-19）。「4 以上」は**下限**であって、必要なのは**割り切れること**である。

**それでも式は分けて書く**——**4 の倍数でない KV 精度を足した日**（6 bit、
2 bit、…）に初めてずれが
生まれ、そのとき黙って画面の 2 行と合計が食い違うからである。**理由が「いま
ずれるから」ではなく「足したらずれるから」であることを、ここに書いておく。**

**この訂正は §3.1 と同じ種類の告白である**——「通っているから正しい」ではなく、
「その経路はまだ 1 度も踏まれていない」が事実である。

### 3.5 Data Transfer

```text
transferred_bits = bandwidth_value × bandwidth_factor × duration_value × duration_factor
```

| 帯域幅の単位 | 係数（bit/秒） | | 時間の単位 | 係数（秒） |
|---|---|---|---|---|
| `bps` | 1 | | 秒 | 1 |
| `kbps` | 10³ | | 分 | 60 |
| `Mbps` | 10⁶ | | 時 | 3600 |
| `Gbps` | 10⁹ | | 日 | 86400 |

**帯域幅は 10 進である**（`1 Mbps = 1,000,000 bps`。`kbps` の `k` は 1024 ではない）。
**この表も定義値である**——出典は SI 接頭辞（k = 10³、M = 10⁶、G = 10⁹）と、
時間の 60 / 3600 / 86400 秒。
**入力は bit、表示は byte** で、ここが混同されやすい。

headline は設計書 §23 の例をそのまま使う: `100 Mbps × 3 時間`。**実際に計算すると
135,000,000,000 bytes = `135.0 GB` / `125.7 GiB`** で、設計書の「135 GB」と一致する
（末尾の `.0` は既存の表示器が落とさない——`format.rs` の
`trailing_zero_is_kept` がそう固定している）。

### 3.6 あふれと定義域

- どの積も u128 の `checked_mul` で行い、あふれたら `Overflow`
- 入力の桁は既存と同じ 39 桁で頭打ち（`MAX_COUNT_DIGITS`）
- 空・数字以外は `SyntaxError`（`parse_count` の既存契約）
- **0 は正当な入力である。** 文脈長 0 なら KV cache は 0 バイトで、エラーではない

## §4 盤面

### 4.1 カテゴリ選択

Scale 系統は 3 つになる:

| hash | |
|---|---|
| `#scale/data-scale` | 件数 × 次元数 × データ型（既存） |
| `#scale/llm` | 重み ＋ KV cache（新設） |
| `#scale/transfer` | 帯域幅 × 時間（新設） |

**選択はパネル最上部の `<select>`** とする——U-0 の器の裁定で承認された形
（`[ Length ▼ ]`）と同じで、縦を 1 行しか使わない。

### 4.2 次元数の面

「次元数」を選ぶとキーパッドが**候補の面**に入れ替わる。面の中に**「手入力」キー**が
あり、押すと数字面に変わる。数字面には**「選択に戻る」キー**を置く。

**既定は選択面である**（§1-2）。データ型面と同じ枠に載せる——**5 列 × 5 行**である
（§2 の【訂正 2026-08-19】）。

候補（**提案。レビューで調整可**）: `384` `512` `768` `1024` `1536` `2048` `3072` `4096`

**選択で入れた値も、手入力で打った値と同じ `Entry` になる。** 面は入り口が 2 つある
だけで、下流の計算・表示・保存は 1 本である。

### 4.3 LLM の項目行

項目は 7 つ。**4 列 × 2 段**に置く（3 列 × 3 段にすると縦を 1 段余分に食う）。

| | | | |
|---|---|---|---|
| パラメータ数 | 重みの精度 | 層数 | KV ヘッド数 |
| ヘッド次元 | 文脈長 | KV の精度 | （空き） |

選択面を持つ項目と、手入力だけの項目を分ける:

| 項目 | 既定 | 候補（提案） |
|---|---|---|
| パラメータ数 | 選択 | `1B` `3B` `7B` `8B` `14B` `27B` `32B` `70B`（`B` = 10⁹） |
| 重みの精度 | 選択のみ | `FP32` `FP16` `BF16` `INT8` `INT4` |
| 層数 | 手入力 | — |
| KV ヘッド数 | 選択 | `1` `2` `4` `8` `16` `32` |
| ヘッド次元 | 選択 | `64` `80` `96` `128` `256` |
| 文脈長 | 選択 | `2K` `4K` `8K` `16K` `32K` `128K` `1M` |
| KV の精度 | 選択のみ | `FP16` `BF16` `FP32` `INT8` |

**接尾辞の意味を明記する。同じ字が 2 つの意味を持つからである。**

| どこ | 字 | 値 | なぜ |
|---|---|---|---|
| パラメータ数 | `B` | **10⁹** | モデルカードの慣習（`27B` = 27,000,000,000） |
| 文脈長 | `K` / `M` | **1024** / **1024²** | 文脈長の慣習（`8K` = 8,192、`128K` = 131,072、`1M` = 1,048,576） |
| 帯域幅（§3.5） | `k` / `M` / `G` | **10³ / 10⁶ / 10⁹** | SI 接頭辞 |

**CalcArc に選ぶ余地は無い**——どれも外の世界で既に決まっている慣習である。
だから**黙らずに書く**。設計書 §41-5 が `GB ≠ GiB` を曖昧にしないと決めているのは、
まさにこの種の衝突のためである。

**候補キーは、ラベルと読み上げで数を分ける**——ラベルは `8K`、アクセシブルネームは
「8192」。押す前に実際の数が分かる。

**パラメータ数の手入力には接尾辞キーを置く**（`M` = 10⁶、`B` = 10⁹）。無ければ
`27000000000` を打たせることになる。**`B` は既存の `G` と係数が同じで、ラベルだけが
違う**——Data Scale の件数は `G`、LLM のパラメータ数は `B` と呼ぶ慣習だからである。
係数の解決はコアの仕事なので（`datascale/entry.ts` の「scale は持たない」）、
**新しい `unit_set` を 1 つ足す**。

### 4.4 Data Transfer の項目行

項目は 4 つ（帯域幅の値・帯域幅の単位・時間の値・時間の単位）。単位は選択面。

### 4.5 縦の予算

**悪化する可能性が高い。** カテゴリの `<select>` が 1 行増え、LLM の項目行が 2 段
になるためである。360×640 では既に Data Scale が 66px 溢れている
（`definition-of-done.md`）。

**実測して数字を残す。** 390×844 と 360×640 で 3 カテゴリすべての
`scrollHeight − innerHeight` を測り、`definition-of-done.md` の未解決項目に追記する。
**直すのはこの spec の仕事ではない**（§8）が、**どれだけ悪くしたかを黙らない。**

**【実測 2026-08-20】悪化した。** 実機ビルド（`pnpm wasm && pnpm build`）を preview で
配信し、パネルが出てから測った値（px）:

| | 390×844 | 360×640 |
|---|---|---|
| Data Scale（0.2.1 → 0.3.0） | 0 → 0 | **66 → 94** |
| LLM のメモリ | **33** | **204** |
| データ転送量 | 0 | **66** |

**予想は当たったが、当たり方が予想と違う。** この節は「カテゴリの `<select>` が 1 行
増え、LLM の項目行が 2 段になるため」と書いた。実際、**LLM は 390×844 でも 33px 溢れ、
3 カテゴリで唯一 iPhone 相当の幅に収まらない**。360×640 の 204px は
`definition-of-done.md` の表で最大である（0.2.1 の Finance 149px を超える）。

**390×844 で Data Scale が 0 のままなのは、直ったからではない**——この幅では余りが
107px あり、増分がそこに吸われている。余りが減ったことは測っても見えない。

**測定が空のページを測っていないことは、対照で確かめた。** 待たずに測ると 6 route
すべてが 0 かつ `body.innerText` が空文字になる（このタスクが警戒していた壊れ方が
実際に再現した）。上の値は、パネルの出現・ボタン数・`select.value` を確認したうえで
採り、`document.fonts.ready` の 700ms 後の再測とも全マス一致している。

**【観察 2026-08-20】§7 の「いまどちらの面に居るか」は、表示器からは分からない。**
次元数の選択面と手入力面を撮って見た結果、**表示器の文言は両面で完全に同一**である
（`次元数` / `次元数を入力中` / `10 進を主表示`）。見分けが付くのは盤面の絵柄
（候補キー ⇄ 数字キー）と、DEL が選択面で無効の見た目になることだけで、**唯一の
言葉の手掛かりである青いキーのラベル（`手入力` / `選択`）は現在地ではなく行き先の
名前である**。「`手入力` と書いてある面＝いま選択面」という反転を読む人にやらせている。
**直すかどうかは別の裁定**（§8 と同じ理由でこの spec の仕事ではない）。記録して次に渡す。

## §5 出力

`27B` `INT4` / 層数 `62` / KV ヘッド `16` / ヘッド次元 `128` / 文脈長 `8192` /
KV は `FP16` を入れたとき（**実際に計算した値である**）:

```text
重み        13,500,000,000 bytes    13.5 GB    12.6 GiB
KV cache     4,160,749,568 bytes     4.2 GB     3.9 GiB
合計        17,660,749,568 bytes    17.7 GB    16.4 GiB
```

**丸めは既存の表示器のまま**——小数第 1 位・round-half-to-even・値が 1 以上になる
最大の単位（`format.rs`）。3 桁区切りのバイト数も既存の `group_digits` である。

**注意書きを必ず出す**（設計書 §21）。ただし**設計書のリストをそのまま写さない**
——§21 は「追加で必要になるもの」に KV cache を挙げているが、**この実装は KV cache を
計算に入れている**。写すと画面が自分について嘘をつく。載せるのは残りだけである:

```text
実際に必要なメモリはこれより大きくなります。
一時バッファ・実行時のオーバーヘッド・量子化のメタデータが加わります。
```

**「理論値である」と明示する**（設計書 §20）。

## §6 境界

**WASM は追加のみ。** 既存の `data_scale(count, dimensions, dtype)` は 1 文字も
変えない（§0.0-1）。足すのは 2 本:

```rust
pub fn llm_memory(parameters, weight_precision, layers, kv_heads,
                  head_dim, context_length, kv_precision) -> JsValue
pub fn data_transfer(bandwidth, bandwidth_unit, duration, duration_unit) -> JsValue
```

戻り値は `DataScaleResult` と同じ流儀——**バイト数・3 桁区切り・10 進・2 進・エラー**を
持つ素の JS オブジェクトで、**例外は投げない**（CLAUDE.md の境界）。LLM は
重み・KV・合計の 3 組を返す。

## §7 検証

**段ゲート**（コアと golden に触るため）: 数値方針 → **Python 参照 ＋ golden** →
Rust → wasm → UI。

**参照実装は §3 から書く。** Rust の実装を見ない。既存の `data_scale_ref.py` が
先例で、その doc comment が「丸め規則と u128 の上限は、アルゴリズムではなく仕様として
固定された公開契約である——契約を知らなければ独立検証は書けない」と書いている。
**§3 がその契約にあたる。**

**golden**: `testdata/llm.json` と `testdata/transfer.json` を新設。既存の
`data_scale.json` は**不変**（1 件も変えない。変わったら §0.0-1 を破っている）。
headline は 2 つ——`27B × INT4`（§5）と `100 Mbps × 3 時間`（§3.5）。

**名指しで置くケース**（これが無いと下の赤確認が空振りする）:

| | 何を守る |
|---|---|
| **`kv_heads < attention_heads` の構成を 1 件** | GQA。導出記録に「**アテンションヘッド数で計算した対照値**」を併記し、golden と一致しないことを数で示す |
| ~~**`kv_heads ≠ head_dim` であること**~~ | **【訂正 2026-08-19】このケースは何も守らない。** 2 つは積の中で掛け合わされるだけなので、取り違えても答えが変わらない（下の赤確認 1 の【訂正】）。**値が違うこと自体に意味は無い**ので、この行は取り下げる |
| **`parameters = 1` × `INT4` → 1 byte** | 切り上げ（§3.1）。**重み側にしか無い端である** |
| **`kbps` を使う転送 1 件** | `k` が 10³ であること（§3.5） |

**GQA のケースに実在モデルの諸元を使うなら、出典を導出記録に書く。** この spec は
**モデル名を書かない**——諸元を記憶から書けば、それ自体が §1-3 で持たないと決めた
「陳腐化する表」になる。必要なのは `kv_heads < attention_heads` という**形**であって、
どのモデルかではない。

**赤確認**（変異前に一時コミット、戻すのは変異箇所の再編集）:

1. **【訂正 2026-08-19】この変異は当てられない。** ここには当初「`kv_heads` と
   `head_dim` を入れ替える——2 つの入力を取り違えていないことを見る」と書いていたが、
   **実際に入れ替えて実装が緑のままであることを確かめた**（Task 3、0 件失敗）。
   理由は算数である——`kv_heads` と `head_dim` は `kv_bits` の中で**掛け合わされる
   だけ**なので、入れ替えても積は変わらない:

   ```text
   kv_bits = 2 × layers × context_length × kv_heads × head_dim × bits
   ```

   **これは実装の弱さではなく、式の性質である。** 2 つを取り違えても答えは
   1 バイトも変わらない——利用者が 2 つの欄を入れ違えて打っても、出る数は同じである。
   **したがって「取り違えを検出する検査」は原理的に書けない。** §7 の名指しケースの
   `kv_heads ≠ head_dim` も、この理由で**何も守っていない**（下表の【訂正】を見よ）。

   **代わりに置く変異は、順序が実際に効く場所を突く**——`kv_bits` の掛ける順序で
   `layers` と `context_length` を入れ替える。積そのものは変わらないが、
   **あふれの検査は左から順に走る**ので（§3.6）、`layers = 2^127` / `context_length = 0`
   の golden が `Overflow` から `0` に変わって赤くなる。**掛け算の可換性が届かない
   のは、あふれの位置だけである。**

   **アテンションヘッド数との取り違えも、やはり変異では当てられない**——実装はその
   入力を持たないので、コードに変異点が存在しない。危険が現れるのは**利用者の入力**と
   **golden 期待値の導出**であって、実装ではない。だから golden 側に GQA の構成を
   置き（上表）、**対照値を導出記録に残す**ことでその危険に応じる。**盤面の側では、
   キーの読み上げ名とラベル**（§4.3）が「いまどちらを打っているか」を担う——
   算数が区別しない以上、区別は画面の言葉にしか無い
2. **`2 ×`（K と V）を落とす**——KV cache が半分になる
3. **`ceil` を `floor` にする**——端の 1 バイトが消える。**これが赤にならなければ、
   端の格子を 1 件も置いていない**——緑のまま何も主張していない検査になる
4. **`kbps` の係数を 1024 にする**——10 進の宣言（§3.5）が守られているか

**段付け**: コア変更なので `cargo test --workspace` は毎回。UI 段で
`pnpm wasm && pnpm test`、**ロールと面の入れ替えに触るので `pnpm e2e` も必須**。
`reference` は `uv run pytest`（`--no-config` を忘れない）。

**コーパス影響の宣言**: **無し。** `KEY_TOKENS` と `engine_table.rs` を触らず、
`data_scale` の wasm 署名を変えず、call シャードは wasm 直叩き、`heavy:ui` は
ハーネス直行。**ただし `DataScaleKeyToken` は増える**（次元数の候補キー、LLM の
項目キー）——これは Data Scale パネル固有の型で、Scientific の `KEY_TOKENS` とは
別物である。

**撮る**: 3 カテゴリ × 2 画面幅（390×844 / 360×640）。次元数の選択面と手入力面の
両方を撮り、**「いま選択面に居るのか手入力面に居るのか」が見て分かるか**を目で見る。
