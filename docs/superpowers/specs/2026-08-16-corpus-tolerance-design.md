# コーパスの許容を、表示が言えるところまで詰める（段階 3a）設計

2026-08-16

前提: [重量級検証コーパス（Layer 6）設計](2026-08-15-heavy-corpus-e2e-design.md)。
この文書はその §12 段階 3 のうち、**許容の作り直しだけ**を扱う。

## 1. なぜやるか

縦の 1 本は通ったが、成果物 `web/heavy-report.md` はこう開示している。

> 表示分解能より緩く検査されたケース: **1315**（全 4000 件中 32.9%）
> 最悪の実効相対許容: **4.15e-4**

つまり **3 分の 1 のケースが、表示が持っている情報より緩く検査されている。**
最小マグニチュード帯では有効数字 4 桁相当までしか主張できていない。表示は 10 桁出るのに。

この開示は正直だが、正直さは目的ではない。**目的は「電卓が正しい」と言えることで、
いまその主張は表示が許すより 5 桁以上弱い。** ここを詰める。

## 2. 設計書 §11 の書き方が間違っていた

前の設計書は対策を「マグニチュード依存の許容」と書いた。**これは症状を治療法と
取り違えている。**

表示は有効数字 10 桁である。最下位桁の丸め幅の半分を**相対**で見ると:

| 先頭桁 | 表示例 | 最下位桁の位置 | 半分 | 相対にすると |
|---|---|---|---|---|
| 1 | `1.234567890` | 1e-9 | 5e-10 | **4.05e-10** |
| 5 | `5.678901234` | 1e-9 | 5e-10 | 8.81e-11 |
| 9 | `9.876543210` | 1e-9 | 5e-10 | 5.06e-11 |

**相対で見た丸め幅は 5e-11 〜 5e-10 の範囲に収まり、値の大きさには依らない。**
`rel = 5e-10` という単一の相対許容が、あらゆるマグニチュードで表示の丸めをちょうど覆う。

**許容はマグニチュード依存にする必要がない。** マグニチュード依存の害を与えていたのは
`abs` の側で、`|期待値| < 1` のところで実効的な相対許容が `abs / |期待値|` に膨らんでいた。
1e-6 の値なら 5e-4 まで許してしまう——これが 4.15e-4 の正体である。

## 3. 設計

### 3.1 rel を唯一の基準にする

```
合否 = |実測 - 期待| / |期待|  ≤  rel        （期待値 ≠ 0）
合否 = |実測 - 期待|           ≤  abs        （期待値 = 0 のときだけ）
```

**OR をやめる。** `abs` は「相対が数学的に定義できない」場合の専用経路に格下げする。
`rel` は `5e-10`（表示の丸めの半分の上界）。

これで §1 の 1315 件の緩みが消える。実効的な相対許容という概念自体が不要になる
（`rel` そのものが常に実効値になる）。

### 3.2 落ちる 2 件を、名指しで、理由を書いて許す

`rel` だけにすると、いまのコーパスで **ちょうど 2 件が落ちる**（敵対的検証で実測済み）。

- `sci-000019`: `tan(rad(376 * 788²))` — rel 7.65e-10
- `sci-001332`: `cos(rad((815*412)*(747+422)))` — rel 1.34e-9

どちらも巨大角度の三角関数で、**電卓の欠陥ではない**。角度をラジアンに直した時点で
f64 の刻み幅（`sci-001332` では 9.31e-10 ラジアン）が引数そのものの不確かさになり、
結果の精度がそれを超えられない。Rust も mpmath も自分の精度の範囲で正しい。

**全体を緩めてこの 2 件を通すのではなく、この 2 件を名指しで許す。**
前者は 1315 件を巻き込む。後者は 2 件で済み、しかも**何を特別扱いしたかが数えられる**。

### 3.3 上書きは別ファイルに置く

```
corpus/
  generated/     生成器の出力そのもの。バイト単位で再生成と一致する（不変）
  overrides.json 人が書く。ケース id をキーに、緩めた許容と**理由**
  contributed/   （段階 5）
```

**`generated/` の中に上書きを書き込まない。** あそこは再生成一致ゲート
（`reference/tests/test_corpus_reproducibility.py`）が「生成器の出力とバイト単位で一致」を
毎回確かめている領域で、人の判断が混ざると、その保証が壊れる。

上書きは**人の判断**なので、人が書く場所に置く。生成器は `overrides.json` を知らない。

形:

```json
{
  "schema": 1,
  "overrides": {
    "sci-001332": {
      "rel": 2e-9,
      "expr": "cos(rad(((815 * 412) * (747 + 422))))",
      "reason": "巨大角度の三角関数。cos(392,526,820°) はラジアン換算 6.85e6 で、
                 その大きさでの f64 の刻み幅は 9.31e-10 rad。引数自体がその精度で
                 しか表現できず、結果の精度も超えられない。電卓の欠陥ではない。"
    }
  }
}
```

**`expr` は必須。** 上書きは id ではなく式に結びつく。コーパスが再生成されて式が
入れ替わったとき、id だけの結び付きだと理由がもう存在しない式を説明してしまう——
式に結びつけておけば、入れ替わりは必ず赤くなる。

**`reason` は必須。** 理由のない上書きは、名指しの体裁をした静かな緩和である。
理由が書けないなら、それは上書きすべきケースではなく、直すべきバグである。

上書きを読んで適用するのは**比較する側**（`web/tests/heavy/corpus.ts`）だけである。生成器は
`overrides.json` の存在を知らない。この非対称は意図的で、「生成は機械、例外は人」という
境界をファイルの所有者で表している。読み込み時の検証は既存の作法に揃える——未知のフィールド、
`reason` の欠落、範囲外の値は、シャード名とケース id を名指しして throw する。

### 3.4 腐った上書きは大きな声で落とす

上書きは放っておくと溜まる。溜まった上書きは、誰も見に行かないまま層の主張を削る。

**上書きが指すケースが `rel` で通るようになったら、赤にする。** 「もう要らない上書きが
ある」と名指しで言う。上書きが指す id がコーパスに存在しない場合も同様。

これは前の段階で得た教訓の適用である——**「ガードが赤くなる」なら気づくが、
「ガードは緑のまま理由が嘘になる」は誰も見に行かない**（別セッションの言葉）。
上書きも同じ形で腐るので、腐ったら赤くする。

### 3.5 レポートが上書きを数える

`web/heavy-report.md` に節を足す。

- **上書きされたケースの件数**を見出しに出す（0 なら 0 と書く）
- 各上書きについて **id / 緩めた値 / 元の rel を何倍緩めたか / 理由の全文**
- 「この結果が主張していないこと」に、上書きの分だけ主張が弱いことを明記

**外の読み手が「何件が特別扱いされ、なぜか」を数えられること**が要件である。
上書きが 2 件から 200 件に増えたら、それはこの層が壊れている兆候であり、
レポートを読めばそれが分かる形にしておく。

### 3.6 再観測できる根拠は、散文ではなく assertion で持つ

`rel = 5e-10` の根拠は「表示が有効数字 10 桁である」という**実測**で、いまそれは
`docs/corpus-measurements.md` に散文で書いてある。**散文は腐る。**

腐りかけている実例が既にある。同文書は「`sqrt(-4)` の表示は `j2`（複素表記）」と
記録しているが、別セッションが関数を実数に閉じる変更を入れると `DomainError` になる。
記録が事実でなくなっても、**この層は緑のままである**——そのケースは範囲外なので誰も見に行かない。

一般化するとこうなる。**テストは結論を守るが、結論に至った根拠は守らない。しかも
根拠の方が、次に判断する人が読む場所である**（別セッションの定式化）。

そこで、**再観測できる根拠は assertion にする。**

`web/tests/heavy/measure.spec.ts` は既に 9 つの探りを打って表示を観測しているが、
いまは件数しか assert していない（観測専用として意図的にそうした）。ここを変える:

- **有効数字の桁数**を実測して、`rel` の導出に使った 10 桁と一致することを assert する
- **指数表記の形**（小文字 `e`、`+` なし、区切りなし）を assert する
- **平坦表示の範囲**の両端を assert する

こうすると、別セッションが表示書式を変えた瞬間に**この層が赤くなり、「実測し直せ」と言う**。
散文の記録なら誰も気づかないまま `rel` の根拠だけが嘘になっていた。

**すべての根拠を assertion にはできない。** 「なぜこの 2 件を上書きしたか」は物理の説明で、
再観測できない。**再観測できるものだけを assertion に移し、残りが散文であることを
自覚的に受け入れる**——その線引き自体を文書に書いておく。

## 4. 要件

§3 の設計を、追跡できる単位に落とす。計画（`docs/superpowers/plans/2026-08-16-corpus-tolerance.md`）
はここの ID を引く。

### 4.1 合否の判定

- **R1** — 合否は**相対誤差だけ**で決める。`rel = 5e-10`（表示の丸めの半分の上界、§3.1）
- **R2** — `abs` を使うのは**期待値が厳密に 0 のときだけ**。相対誤差が数学的に定義できない
  場合の専用経路であって、`rel` の代わりではない（§3.1）
- **R3** — 許容の値は corpus の JSON から読む。テストコードに書かない（CLAUDE.md の規約）

### 4.2 例外の記録

- **R4** — 上書きは `corpus/overrides.json` に置く。**`generated/` に書き込まない**（§3.3）
- **R5** — `reason` は必須。空・欠落は throw する（§3.3）
- **R6** — 上書きを読んで適用するのは**比較する側**だけ。生成器はその存在を知らない（§3.3）
- **R7** — 不要になった上書き（上書きなしの `rel` で通るようになったもの）を赤にする（§3.4）
- **R8** — 存在しないケース id を指す上書きを赤にする（§3.4）

### 4.3 開示

- **R9** — レポートに**上書きの件数**を見出しに出す（0 なら 0 と書く、§3.5）
- **R10** — 各上書きの **id・緩めた値・元の `rel` の何倍か・理由の全文**を出す（§3.5）
- **R11** — 「この結果が主張していないこと」に、**上書きの分だけ主張が弱い**ことを書く（§3.5）

### 4.4 範囲の固定（やらないこと）

- **R12** — **ケースを 1 件も増やさない。** 複素数・エラー経路・指数表記・括弧なし式は段階 3b/3c
- **R13** — **`corpus_expr.py` の `UNARY_FNS` / `BINARY_OPS` を触らない。** あれは生成器の乱数の
  土台で、1 つ足すと同じ種でも既存 4000 件が総入れ替えになる（実測確認済み）
- **R14** — **落ちるケースが 3 件以上なら、上書きせずに報告する。** 理由が書けないものが 1 件でも
  あれば、それは電卓のバグかもしれない（§6 のリスクと対）
- **電卓の種類を増やさない**（段階 3d）
- **表示書式の実測はやり直さない。** 別セッションの関数電卓拡張は ENG を
  `12.345e3`（小文字 `e`）に留め、既定に入れない方針なので、`docs/numerical-policy.md` の
  既定の規則は動かない。動いたら実測し直す（Task 2 の手順がある）

## 5. 移行

**訂正（2026-08-16、Task 5）。** この節は当初「変わるのは `corpus/generated/*.json` の
`tolerance` フィールドの**値**で、生成器を直して再生成すれば済む」と書いていた。
**これは不正確だった。** 実装して実測すると、`{abs: 5e-10, rel: 5e-10}` という**値そのものは
変わらなかった**。変わったのは判定側の**解釈**だけである——`abs` が「OR の片側」から
「期待値が厳密に 0 のときの専用経路」に格下げされた。したがって:

- `reference/scripts/generate_corpus.py` は**無変更**
- `corpus/generated/*.json` は**1 バイトも変わっていない**（生成器の出力に触るべき変更が
  そもそも無かった）
- 再生成一致ゲート（`reference/tests/test_corpus_reproducibility.py`）は無変更のまま緑

`rel` を厳しくするとコーパスの**合否**は変わるが、それは判定コード（`web/tests/heavy/corpus.ts`
の `withinTolerance` / `classify`）の書き換えによるものであって、コーパスの JSON にも
生成器にも手を入れていない。

**この訂正自体が「根拠が腐る」形の一例である。** §3.6 が名指しした壊れ方——テストは
結論を守るが、結論に至った根拠は守らない——を、この設計書自身が計画の段階で踏んだ。
気づいたのは実装してからではなく、**設計書を書いたその日、計画（`docs/superpowers/plans/`）を
書く過程で**である。「生成器を直せば済む」という見積りは、実装する前に書いた予想であって、
実測ではなかった。

`overrides.json` は新規ファイルなので移行はない。

schema は据え置き（`1`）。ケースの形が変わらないため。

## 6. リスク

- **上書きが 2 件で済まない可能性。** `rel` を厳しくして初めて分かる。実測では 2 件だが、
  それは「abs をほぼ 0 にして rel を据え置く」条件での観測であり、実装して回すまで確定しない。
  **3 件以上出たら、それぞれ理由を確かめてから上書きする。** 理由が書けないものが 1 件でも
  あれば、それは電卓のバグかもしれないので、上書きせずに報告する
- **`abs` を期待値 0 専用に格下げした結果、期待値 0 のケースで誤差が出たときに判定が甘くなる。**
  いまの 5 件は全件が絶対誤差 0 の完全一致だが、将来 0 でない誤差が出たら、`abs` の値
  （5e-10）が唯一の基準になる。そのとき「表示が 0 と出るなら 0 とみなす」で良いのかは
  別途考える必要がある。**いまは 5 件全部が完全一致なので、判断を先送りしてよい**
- **理由の質は機械で測れない。** `reason` が必須でも、中身が薄ければ上書きは実質的に
  静かな緩和になる。レポートに全文を出すことで、外の目に晒すのが唯一の防御である。
  そこで規範を一つ置く——**理由には、読み手が再計算できる数を含めること**（ulp、導関数、
  上界、観測値）。散文だけの理由は、全文を出しても検算できない
- **申し送り（段階 3b/3c 向け）。** `report.ts` の巨大角度の段落（`renderOverrides`）は、
  いま**上書きの件数が 1 件以上なら出る**という条件になっているだけで、**中身は見ていない**。
  固定文で「上に挙がっているのは、いずれも巨大な角度を三角関数に渡したケースである」と
  **全件について断言**している。段階 3b/3c で巨大角度以外の理由の上書きが 1 件でも入ると、
  この断言は嘘になる。そのときは、この段落を条件付きにするか、理由ごとに分類すること
