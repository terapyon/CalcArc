# API 整理 — 設計

日付: 2026-08-11
対象 issue: #8 #9 #11 #12 #13 #16 #17（PR で close する）
前提: PR #18（状態遷移の強化）マージ後の main から始める

## §0 これは何か、何でないか

命名と API 形状の整理である。**挙動は 1 ビットも変えない。**
serde のフィールド名（`re`/`im`）、WASM 境界の型とトークン、表示文字列、
計算結果のすべてが変更前と一致する。変わるのはシンボルの名前・可視性・
モジュール配置と、内部の呼び出し経路だけである。

議論はすでに issue 上で終わっている。この spec は決定を書き写して固定する
ものであり、設計の再検討はしない。判断基準そのものは §4 の
`docs/api-style.md` として独立させ、以後の議論の再燃を防ぐ。

## §1 スコープ

### 1. 内部 import を再エクスポート経由に（#17 段階 1、#8 とセット）

`lib.rs` の再エクスポートを広げ、クレート内部も `use crate::Value;` の形に
寄せる。利用側（テスト・wasm・将来の #7 系ツール）から内部モジュール構成を
隠すのが目的で、モジュール自体はまだ動かさない。

### 2. 四則を `Value::checked_*` に集約（#17 段階 2）

`arith.rs` の `add`/`sub`/`mul`/`div` を `Value::checked_add` 等のメソッドに
集約する。有限性の関門 `finite()`（`arith.rs:8`。#10 は改名せず「段階 2 で
消滅するので superseded」として close 済み）は private な `finalize` に畳む。フィールドの可視性は絞れるところまで絞るが、**完全な型
保証は #6 本体の仕事**なので、ここでは深追いしない（#6 の前提づくりまで）。

### 3. `complex/` 階層の平坦化（#17 段階 3）

「種類」単位の分割（`arith.rs` / `polar.rs` / `value.rs`）をほどき、演算を
`Value` に寄せる。**From 化はしない**——変換は名前付きのまま。
`Value::to_polar` のメソッド化は rustdoc の導線改善として可（#14 は
From 化の提案だったため close 済み。名前は残る）。

### 4. 命名の修正（#9 #11 #12）

- `Buffer::pop() -> bool` → `Option` を返す形に（#9）。bool の真偽が
  「バッファが尽きたか」を意味する現状は、std の `pop` の契約と衝突している。
- `AngleMode::to_radians` の改名（#11）。`f64::to_radians` と同名で別動作
  （引数を取る）なのが名前の嘘。`from_radians` も `from_*`（コンストラクタ）
  の慣習から外れているので対で直す。
- `engine::display::display` のスタッター解消（#12）。**関数名の変更で**
  解消する。issue 当初案の `From<&EngineState> for DisplayState` は
  §4 の規約により不採用。

### 5. テスト用定数の整理（#16-4）

`TEST_EPSILON` を `pub(crate)` に絞る。`ROUNDTRIP_EPSILON` は結合テストが
使う公開定数である旨を rustdoc に明記する。

### 6. `docs/api-style.md` の新設（§4 全文）

CONTRIBUTING.md からリンクする。

### 7. `KEY_TOKENS`（TS）⇔ `Key::ALL`（Rust）の一致テスト

`web/src/calc/types.ts:21` と `crates/calcarc-core/src/engine/key.rs:113` は
同じ 30 トークンを別言語で二重管理している。未知トークンは黙って no-op に
なる設計（WASM 境界は例外を投げない）なので、ずれても**どのテストも落ちずに
キーが 1 つ死ぬ**。wasm テストか E2E で、両者の集合一致を機械検査する。

### 8. 台帳の残件: 到達しない腕の整理

`engine/mod.rs:63` の `Key::Ac => false` は `:29` の早期処理により到達しない。
match の網羅性を保ったままコメントか構造で整理する。

## §2 spec 内で判断を求められていた 1 件

**#16-1（`EngineState` に `Default` を実装するか）: 不採用。`initial()` のみを残す。**

理由: §4 の運用規則をそのまま適用した。`Default` の不在は「名前の嘘」では
ない——現状の名前はどの契約も偽っていない。一方 `initial()` は設計書 §4 が
定義した「電源投入時の状態」というドメイン語彙である。`Default` を足しても
`initial()` は消せないから生成点が 2 つになり、`mem::take` のような `Default`
を要求する使い方も現在存在しない。基準で説明できない変更は「好み」であり
現状維持、という §4 の運用そのものが最初に適用される事例になる。
（plan レビューで異論があれば覆してよい。その場合も `initial()` は残すこと。）

## §3 完了条件

1. **全テストが無変更で通る**: engine_table / golden / 網羅列挙 / proptest、
   `wasm-pack test`、vitest、E2E、Python（pytest + golden 再生成で差分なし）。
   既存テストの変更は「リネームへの追従」のみ。新規追加は §1-7 の一致テスト
   に限る。期待値・キー列・許容誤差は 1 つも変えない。
2. 挙動・serde フィールド名（`re`/`im`）・WASM 境界・表示文字列が不変。
3. `docs/api-style.md` が存在し、CONTRIBUTING.md からリンクされている。
4. §1-7 の一致テストが入っており、どちらかの言語でトークンを 1 つ消すと
   赤くなることを確認済み（このブランチの流儀: 検査は壊して赤を見てから信じる）。
5. PR で #8 #9 #11 #12 #13 #16 #17 が close される。

### 検証の役割分担について（前ブランチの教訓）

「無変更で通る」の網には役割分担がある。**同シグネチャの取り違え**（例:
リネーム中に `to_radians`/`from_radians` の中身を入れ替える）を捕まえるのは
engine_table と golden であり、網羅列挙は構造しか見ない。リファクタの安全網
として効いているのはどれかを取り違えないこと。また、等価類やキー集合を論じる
ときは**到達可能性を alphabet の見た目から論じない**——`j` のような型をまたぐ
キーが経路を作る（前ブランチ B5 の教訓）。

## §4 `docs/api-style.md` 全文

実装タスクはこの全文をそのまま配置する（体裁の調整のみ可）。

```markdown
# API スタイルガイド

命名と API 形状の判断基準。issue 単位で議論を再燃させないためにここに集約する。

## 原則

**std の慣習は「名前の嘘」を直すために採り、ドメイン語彙を消すためには採らない。**

- 名前の嘘 = 名前が std の契約や意味を偽っているもの。直す。
  例: Option を返さない `pop()`、述語に見える関門 `finite()`、
  `f64::to_radians` と同名で別動作のメソッド。
- ドメイン語彙 = 設計書・base-spec が定義した概念を指す名前。守る。
  例: `token`（境界トークン）、`sqr`（x² キー）、`CalcError`、
  `to_polar`/`from_polar`、`Buffer::text`（打鍵エコー）。

## 個別規約

- **Error 型**: クレート接頭辞付き（`CalcError`/`CalcResult`）を維持する。
  無修飾 import でも曖昧にならないことを優先する。
- **From/Into**: 「意味を持たない機械的変換」にのみ実装する。意味のある
  操作は名前付き関数にする（`to_polar` は From にしない）。
- **Display trait**: 値に正規の文字列表現が 1 つあるときだけ実装する。
  UI エコーや文脈依存の文字列化は名前付きメソッド（`text()` など）。
- **import 方針**: flat import（`format_real` を直接 use）を維持する。
  モジュール修飾呼び出しへの寄せ替え（`format::real()`）はしない。
- **述語**: `is_` / `has_` で始める。検査して返す関門は動詞で始める。
- **スタッター**: `module::module()` の形を避ける（関数名の変更で解消する。
  From 化は上の規約により不採用）。

## 運用

迷ったらこの基準で判断し、判断したらこのファイルに追記する。
基準で説明できない変更提案は「好み」であり、現状維持とする。
```
