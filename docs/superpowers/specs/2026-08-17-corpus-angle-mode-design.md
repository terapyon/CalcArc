# 角度モードを検証する（段階 H）設計

2026-08-17

前提: [重量級検証コーパス（Layer 6）設計](2026-08-15-heavy-corpus-e2e-design.md)。
先行: [打ち方と訂正（段階 G）](2026-08-17-corpus-typed-numbers-design.md)。

## 1. なぜやるか

未押下キーのうち **`angle_toggle` 1 個**を扱う。

**いまのコーパスは全 16000 件が `Deg` である。** そして
`corpus.ts` の `assertSupportedMode` が、`Deg` 以外を宣言したケースを
**その場で拒む**——理由は明快で、**harness が `angle_toggle` を押さないので、
`Rad` と書いたケースは黙って `Deg` で評価されてしまう**からである。

つまり「Rad は未検証」ではなく「**Rad と書くと嘘になるので書けない**」状態にある。
この段階はその番人を、押すことで満たす。

## 2. 実装の事実（コードから確認、2026-08-17）

| | |
|---|---|
| モードの数 | **2 つだけ**（`Deg` と `Rad`）。**`Grad` は存在しない**（`numeric/angle.rs:5`） |
| 巡回 | `toggled()` が `Deg ↔ Rad` を往復（`angle.rs:27`） |
| 押したときの効果 | **保持している値は変えない。** 表示と以後の三角関数にだけ効く（`engine/mod.rs:367`） |
| `AC` との関係 | `cleared()` は**角度モードを保つ**——利用者の設定なので |
| 三角関数 | `sin`/`cos`/`tan` は**引数**をモードで解釈。`asin`/`acos`/`atan` は**結果**をモードに変換 |

**`Grad` を書かないこと。** 私は一度レポートに「Rad と Grad」と書いて誤りを入れた
（2026-08-17 に訂正）。**2 つしかない。**

## 3. 設計

### 3.1 モードはキー列で切り替える。フィールドだけ書き換えない

ケースの `mode` を `"Rad"` にするだけでは**嘘になる**（§1）。
**キー列の先頭で `angle_toggle` を実際に押す。**

```
Rad のケース:  angle_toggle  <式のキー列>  eq
Deg のケース:  <式のキー列>  eq            （既存と同じ）
```

**`assertSupportedMode` を「押していれば `Rad` を許す」形に広げる。** 具体的には、
`mode` が `Rad` のケースは**キー列に `angle_toggle` を奇数回含むこと**を要求する
——押さずに `Rad` と名乗るケースは、いままでどおり拒む。

**偶数回押したら `Deg` に戻る**ことも、その規則が自然に扱う。

### 3.2 新しいシャードとして足す。既存は 1 件も作り直さない

`angle-mode-000.json`。生成器は独自の `random.Random(seed)` を持ち、
既存シャードの乱数に触れない（3c 設計 §3.2 の作法）。

### 3.3 参照側はモードを引数として受け取る

いま `corpus_eval.evaluate(node)` は**度を前提に固定**している——
`sin` は `value * mp.pi / 180`、逆三角は `_degrees(...)` を通す。

**`evaluate(node, mode)` に広げる。** `mode == "Rad"` なら:

- `sin`/`cos`/`tan` は引数を**そのまま**ラジアンとして渡す
- `asin`/`acos`/`atan` は結果を**度に直さない**

**既定は `Deg` にして、既存の呼び出しを 1 つも変えない**——変えれば全シャードが
再生成の対象になる。**再生成一致ゲートが、変えていないことを機械的に確かめる。**

### 3.4 Rad は「引数の帯」が変わる

度では 0〜999 の葉が現実的な角度だったが、**ラジアンでは 999 rad が
159 回転**に相当する。`sin(999)` は数学的には定義されるが、
**引数還元の精度限界に近づく**——度の巨大角度で上書きが 2 件出たのと同じ問題である。

**葉の帯を `[-2π, 2π]` の近傍に寄せる。** 具体的な帯は
**実装の最初に測ってから決める**——上書きが何件必要になるかを見てからにする
（段階 3b-A で「まず一様に測る」とした判断と同じ）。

### 3.5 Deg と Rad の同値ケースを別に作る

**`x` 度と `x·π/180` ラジアンは同じ値に着く。** これは engine の自己整合の主張で、
Python を介在させずに確かめられる:

```
左: <x のキー列> sin eq
右: angle_toggle <x·π/180 のキー列> sin eq
```

**ただし右辺の数を打つには小数点が要る**——段階 G（`dot`）が先に入っている
必要がある。**段階 G に依存する。**

## 4. やらないこと

- **`Grad`**——存在しない
- **モードを式の途中で切り替えない。** `2 sin angle_toggle 3 cos` のような列は
  engine の状態遷移の主題で、`engine_table.rs` の担当である
- **既存シャードを作り直さない**
- **`evaluate` の既定を変えない**（`Deg` のまま）

## 5. 要件

- **R1** `angle-mode-000.json` を新設。既存シャードを 1 件も作り直さない
- **R2** `Rad` のケースは**キー列に `angle_toggle` を奇数回含む**
- **R3** `assertSupportedMode` を「押していれば `Rad` を許す」形に広げる。
  **押さずに `Rad` と名乗るケースは拒み続ける**
- **R4** `evaluate(node, mode="Deg")` に広げる。**既定を変えず、既存の呼び出しを
  1 つも書き換えない**——再生成一致ゲートがそれを確かめる
- **R5** ラジアンの葉の帯は**実測してから決める**。上書きの件数を見る
- **R6** Deg と Rad の同値ケースを別に作る（段階 G の `dot` に依存）
- **R7** レポートの「Deg 以外の角度モード」の項目を**データ由来に変える**
- **R8** 再生成一致ゲートの対象に含める

## 6. リスク

- **`assertSupportedMode` を広げるとき、緩めすぎる危険がある。** いまの番人は
  「`Deg` 以外を全部拒む」で、これは強い。**「`angle_toggle` を含めば何でも許す」に
  してはいけない**——奇数回という条件まで見る
- **ラジアンの精度。** 大きなラジアン値は引数還元の限界に当たる。
  上書きが多く必要になったら、**それは許容の問題ではなく帯の問題**である
- **段階 G への依存。** §3.5 の同値ケースは `dot` が要る。**G が先**
