## §1 門 1 —— WebKit を CI に足す

### §1.1 いま（現物）

| どこ | ブラウザ |
|---|---|
| `web/playwright.config.ts` | `projects` は `mobile` の **1 つ**。390×844、`isMobile: false`、**既定の Chromium** |
| `heavy/playwright.ui.config.ts` | `devices["Desktop Chrome"]` |
| `.github/workflows/ci.yml` の `End-to-end` | `pnpm exec playwright install --with-deps chromium` のあと `pnpm exec playwright test`。時間制限 **25 分** |

**ブラウザでの検査は Chromium だけである。** 方針は「スマートフォン第一」
（`docs/base-spec.md` §42）で、**iPhone ではどのブラウザも中身は WebKit** である
——**いちばん多い利用者の環境を、CI は 1 度も通っていない。**

### §1.2 測定 —— **この作業機では WebKit が起動しない**（2026-09-10）

WebKit で `web/tests/e2e/` を全部回し、落ちた本数と理由を分類するつもりだった。
**起動の手前で止まった**（Playwright の印字そのまま）:

```
Host system is missing dependencies to run browsers.
    sudo npx playwright install-deps
Alternatively, use apt:
    sudo apt-get install libgstreamer-plugins-bad1.0-0 libavif16
```

- **足りないのは共有ライブラリ 2 つ**——`libavif.so.16`（`libavif16`）と
  `libgstcodecparsers-1.0.so.0`（`libgstreamer-plugins-bad1.0-0`）。WebKit の
  全バイナリに `ldd` を当てて、見つからないのはこの 2 つだけだった
- **ブラウザ本体は揃っている**——Playwright 1.62.1 が要求する WebKit revision 2336
  （WebKit 26.5）が `~/.cache/ms-playwright/webkit-2336` に在り、版も一致した
- **`sudo` の要る導入はしていない。** 入れるかは利用者の判断である（§4 #2）

**したがって本数も所要時間も、落ちる理由の分類も、1 つも取れていない。**
**門 1 は「CI で最初に測る」設計にする。**

### §1.3 設計

#### 足す範囲 —— **`web` の E2E を全部。`heavy:ui` は入れない**

- **`web/tests/e2e/` を全部**、WebKit でも回す。**一部に絞る根拠が無い**——どれが
  Safari で落ちるかは、回すまで分からない
- **`heavy:ui`（本物の盤面を叩く 12 分の走行）は入れない**（推し）。重量級の担当の
  持ち物で、門 3 と同じ場所を触ることになるうえ、走行時間が倍になる。
  **入れるかは §4 #3**

#### ビューポートと端末 —— **まずエンジンの差だけを見る**

WebKit の project は、**Chromium の project と同じ条件**（390×844、`isMobile: false`）
で足す（推し）。**`devices["iPhone 13"]` のような端末定義は、最初は使わない。**

**理由: 変える変数を 1 つにするため。** 端末定義にすると、エンジン（WebKit）と
端末の振る舞い（`isMobile`・タッチ・拡大率・UA）が同時に変わり、落ちたときに
**どちらのせいか分からない**。まずエンジンだけを変えて測り、端末の振る舞いは
その次に 1 つずつ足す。**iPhone の端末定義まで進めるかは §4 #4。**

#### CI の組み方 —— **別のジョブにする**

`ci.yml` に **`End-to-end (WebKit)`** を足す。中身は `End-to-end` と同じで、
違うのは `playwright install --with-deps webkit` と
`playwright test --project <webkit の project 名>` だけ。

**既存のジョブの中に足さない理由**: `ci.yml` の時間制限の表は**ジョブごとの実測**から
決めている（観測の最大の 2 倍を 5 分刻みで切り上げ、下限 10 分）。1 つのジョブで
2 つのブラウザを回すと、**`End-to-end` の実測（最大 612 秒・平均 120 秒）が
意味を失う。** 別のジョブなら、Chromium の表はそのまま生きる。

**時間制限は、まず `End-to-end` と同じ 25 分**にする（見立て）。**WebKit の実績が
1 つも無い**ので、表の規則（観測の 2 倍）を当てられない。**いちばん近いジョブの値を
借りる**のが最初の一手で、**実績が溜まったら表の規則で決め直す**——そのとき
表の注記に「最初は借りた値だった」と残す。**リリース（`release.yml`）は `ci.yml` を
`workflow_call` で呼ぶ**ので、足したジョブはリリースの走行にも自動で入る。

**CI で `--with-deps webkit` が通るか**（`ubuntu-latest` に上の 2 パッケージが
`apt` で入るか）は**未確認**である。見込みはあるが、測っていない。

#### 最初の測定の手順

1. WebKit のジョブを足した枝を push し、**その走行で初めて本数を取る**
2. 落ちたものを分類する——**(A) 本物の Safari の差**（利用者に見える違い）／
   **(B) テストの書き方の癖**（Chromium でしか成り立たない前提）／
   **(C) 環境**（CI の WebKit に固有）／**(D) 分からない**（無理に振り分けない）
3. 分類ごとに片付けて、**WebKit のジョブが緑になったら門 1 を通ったとする**

#### Safari だけで落ちる挙動が見つかったとき

| 分類 | 扱い |
|---|---|
| **(A) 本物の差** | **製品を直す**のが第一。直さないと決めるなら、**その差を利用者向けの文書に書き、テストはその差を名指しして期待値を分ける**（黙って合わせない） |
| **(B) 書き方の癖** | **テストをエンジンに依らない形に直す。** Chromium でも同じ主張をしているかを確かめる（直した結果、Chromium 側の主張が弱くなっていないこと） |
| **(C) 環境** | 理由を書き、CI 側で直せるなら直す |
| **(D) 分からない** | **調べ終わるまで門は閉じない** |

**しないこと**: **再試行で緑にしない**（`retries` を上げる・待ち時間を伸ばすだけで
通すのは、落ちた理由を消すだけで直していない）。**理由の書かれていない
`test.skip` / `test.fixme` を置かない。**

|---|---|---|

## §2 門 2 —— 保存データと URL の約束

**1.0 にすると、利用者の手元に残るものを壊しにくくなる。** 何を約束し、何を約束
しないかを、1.0 の前に決める。

### §2.1 端末に残しているもの（**現物を数えた。3 つある**）

**依頼の一覧は 2 つ（設定と履歴）だったが、数えると 3 つだった**
（`web/src` で `localStorage`・`sessionStorage`・`indexedDB`・`caches.open`・
`document.cookie` を探した。2026-09-10）:

| 置き場 | 名前 | 形 | 版 | 読めないとき |
|---|---|---|---|---|
| `localStorage` | `calcarc.settings` | `{ v: 1, scientific?, dataScale?, finance?, history? }`。**初期値と違う項目だけ**を書く | `v: 1` を書くが、**読み手は `v` を見ていない** | **項目ごとに**白リストで拾う。知らない値・欠けた項目は**その項目だけ**初期値に倒す |
| `localStorage` | `calcarc.history` | 配列。1 件は `{ expression, answer, angle, error }`、最大 50 件 | **無い**（`web/src/history/types.ts`） | **1 件ずつ**検証し、欠けた件は読み飛ばす。残りは保つ |
| IndexedDB | `calcarc-currency` / ストア `rates` / 鍵 `latest` | `{ schemaVersion: 1, set }` | `DB_VERSION` 1・`RATES_SCHEMA_VERSION` 1 | **丸ごと捨てて**「キャッシュ無し」に倒し、次の取得で入れ直す |

（アプリ本体は service worker のキャッシュにも入るが、**利用者が作ったデータでは
ない**ので、ここでは数えない。）

**★ 依頼の前提を 1 つ訂正する。**「いまの方針は『形が変わったら古い保存は捨てる』」
とあったが、**丸ごと捨てるのはレートのキャッシュだけ**である
（`web/src/currency/cache.ts` の註が「移行は書かない——レートは捨てても取り直せる。
利用者が作った値ではないので、設定とは立場が違う」と書いている）。**設定と履歴は、
読める部分を拾い、読めない部分だけを黙って落とす**——**丸ごと捨てるのではなく、
部分的に救っている。** `SETTINGS_VERSION` の註（`web/src/settings/index.ts`）が
言う「意味が変わったらキーの綴りを変える」は、**古い綴りを知らない値として
その項目だけ落とす**という意味である。

### §2.2 約束の選択肢（**利用者が決めること**）

**レートのキャッシュは「捨てる」のままでよい**（取り直せる。利用者の値ではない）。
**選ぶのは設定と履歴の扱い**である。

| 案 | 中身 | 利用者から見えること | 代償 |
|---|---|---|---|
| **(ア) 黙って落とす（いまのまま）** | 読めない項目・件は黙って初期値に戻す／読み飛ばす | 版を上げた日に、**設定の一部が初期値に戻る・履歴の一部が消える**ことがある。**知らされない** | 小さい。いまと同じ |
| **(イ) 読み続ける** | **1.0 が書いた形は、以後の版でも読める**ことを約束する。意味を変えるときは**新しい綴りを足し、古い綴りも読む**（移行を書く） | 版を上げても**設定も履歴も残る** | 形を変えるたびに古い形の読み手が要る。**番人で見張れる**（§2.4） |
| **(ウ) 落とすが知らせる** | (ア) と同じく落とすが、**落とした項目があれば 1 度だけ知らせる** | 「設定の一部を初期値に戻しました」が 1 度出る | 知らせる場所と文言が要る。縦の予算に掛かる（金融は余白が小さい） |

**この設計書の推し: 設定と履歴は (イ)、レートは捨てる。**

**理由**: **いまの読み手がすでに項目ごと・件ごとに救っている**ので、(イ) は
**新しい仕組みを要らない**——要るのは「**1.0 が書いた形を、以後の版で読めなく
しない**」という約束と、それを見張る番人だけである。(ア) のままだと、1.0 の
あとに形を変えた日に、**利用者の設定が黙って初期値に戻る**。(ウ) は知らせる
画面を要る。

### §2.3 URL の約束

**13 の画面の URL**（`#scientific`・`#convert/length` ほか。一覧は
`web/tests/e2e/screen-identity.spec.ts` の `SCREENS`）は**ブックマークと閲覧履歴に
残る。**

**いまの方針**（`web/src/route.ts`）: 知らない先頭は `#scientific` へ、知らない
カテゴリはその系統の既定へ倒す。**互換の分岐は作らない**——旧 `#data-scale` も
旧 `#loan` もこの規則で既定へ倒れている（`docs/base-spec.md` に記録がある）。
**URL が壊れて開かない、は起きない。起きるのは「別の画面が開く」である。**

**約束の案（推し）: 1.0 の 13 の URL は、以後の版でも同じ画面を開く。**
画面を足すのは自由（URL が増えるだけ）。**消す・綴りを変えるなら、古い URL を
新しい画面へ向ける分岐を足す**——「互換の分岐は作らない」という今の方針を、
**1.0 のあとは覆す**ことになる（§4 #1 と一緒に決める）。

### §2.4 門 2 の番人

| 主張 | 番人 | これを破る変異 |
|---|---|---|
| **1.0 が書いた設定が読める** | **実物の古い文字列**を固定して読む単体テスト。1.0 の `writeSettings` が書く文字列を**そのまま**置き（組み立てない）、読んだ結果を**期待値を書き写して**比べる。**置いた文字列は以後書き換えない**——形を変えたら**新しい文字列を足す** | 読み手で項目の綴りを変える |
| **1.0 が書いた履歴が読める** | 同上（`calcarc.history` の実物の文字列） | 1 件の欄を必須にする／欄の綴りを変える |
| **固定した文字列が書き換えられていない** | 固定した文字列のハッシュを別に持ち、一致を見る（**書き換えて緑にする、を止める**） | 固定した文字列を 1 字変える |
| **1.0 の 13 の URL が同じ画面を開く** | **13 の URL を字面で固定した表**（組み立てない）を持ち、`routeFromHash` がそれぞれを**既定に倒さず**その画面に解くことを見る単体テスト。**表は増やしてよいが減らせない**（件数の下限を 13 に固定） | カテゴリを 1 つ消す |

**★ いまの URL の番人には穴がある。** `screen-identity.spec.ts` は 13 の画面を回すが、
**件数を `CONVERT_CATEGORY_IDS` と `SCALE_CATEGORIES` から導いている**
（`1 + CONVERT_CATEGORY_IDS.length + SCALE_CATEGORIES.length + 1`）。**カテゴリを
消すと、表と件数が一緒に減って緑のまま**になる——**「URL が消えない」は見張って
いない。** 追加の番人は、そこを**字面の表と固定の下限**で塞ぐ。

**レートのキャッシュには番人を置かない**——捨ててよいので、守る約束が無い。

## §3 README の「ベータである」をどう書き換えるか（**案**）

**いま**（`README.md` の「現在の版」）:

> **ベータである。** 使っている人はまだ少ない。計算結果は無保証で、重要な
> 判断の根拠にしないでほしい。

**1.0 でも計算結果は無保証である。**「正式版」が**何を約束し、何を約束しないか**を
書き分ける（§2.2 で (イ)、§2.3 で推しを採った場合の案）:

> **1.0（正式版）** — 変更点は CHANGELOG.md に、リリースごとの記録は Releases にある。
>
> **正式版として約束すること:**
> - **画面の URL は変わらない。** ブックマークした URL は、以後の版でも同じ画面を開く
> - **保存した設定と履歴は、版を上げても残る**（1.0 以降に保存したもの）
> - **計算は端末内で完結し、サーバへ送信しない**
>
> **約束しないこと:**
> - **計算結果の正しさ。** 計算結果は無保証で、重要な判断の根拠にしないでほしい
> - 画面の見た目やキーの並び
> - 為替レートの値（取得元の値をそのまま使う）
>
> 気づいたことは Issue で教えてもらえると助かる。

**★ 「サーバへ送信しない」の行は、いまの README の 6 行目
（「計算は端末内で完結し、サーバへ送信しない。」）の写しである**——**新しい約束を
足さない。** 英語版も `README.en.md` の 6 行目（「Calculations complete entirely
on-device; nothing is sent to a server.」）を写す。

**★ 1 つ、裁定の前に確かめること。** 為替では**レートを取得元から取ってくる**
（`docs/base-spec.md` の為替の節。IndexedDB に 1 枚だけ置く）。**利用者の入力は
送らないが、端末から外へ通信はする。**「サーバへ送信しない」をこのまま「約束」の
欄に移すと、**通信しないと読まれうる**。いまの README がこの一文で足りているのか、
約束に格上げするなら「入力は送らない（為替のレートを取りに行く通信はする）」と
書き分けるのかは、**§4 #6 と一緒に決める。**

**英語版（`README.en.md`）も同じ構成で揃える。** 綴りは利用者の裁定を受けてから。
