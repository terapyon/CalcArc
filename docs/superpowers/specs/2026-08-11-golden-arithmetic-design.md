# 複素四則演算の言語間検証 — 設計

日付: 2026-08-11
対象 issue: #2（golden に四則演算を追加）#3（許容誤差をノルム基準に）— PR で close
前提: PR #19（API 整理）マージ後の main から始める

## §0 目的

数値的に最もトリッキーな経路——Smith 法の除算と、桁落ちを含む乗算——を
Python 独立検証の射程に入れる。現在この 2 つを守っているのは同一クレート内の
ユニットテスト（手計算の既知値）だけで、base-spec §30 が求める「同じバグが
双方に入らない」独立検証が四則演算には及んでいない。

**#3 が前提条件である。** 複素数の乗除算は成分ごとの相対精度を保証しない
（保証されるのはノルムだけ。issue #3 の実測: 恒等式 `(a*b)/b == a` 50 万件で
成分ごと最大 7.26e-12、ノルムでは 4.30e-16）。成分ごとの比較のまま #2 の
ケースを足すと、**実装が正しいのに golden が落ちる**。順序は #3 → #2。

## §1 #3: 比較をノルム基準にする

### 変更

`golden.rs` に複素数値用の比較を新設する:

```rust
/// 複素数の結果はノルムで比べる。乗除算は成分ごとの相対精度を保証しない
/// （小さい成分は大きな積の差として復元され、成分比が偏るほど桁が落ちる）。
/// 保証されるのはノルムの相対精度であり、それを検査する。
fn close_complex(actual: Value, expected_re: f64, expected_im: f64, tol: Tolerance, id: &str) {
    let diff = (actual.re - expected_re).hypot(actual.im - expected_im);
    let norm = expected_re.hypot(expected_im);
    let ok = diff <= tol.abs || diff <= tol.rel * norm;
    assert!(ok, "{id}: got ({}, {}), expected ({expected_re}, {expected_im}) \
        (norm diff {diff}, abs tol {}, rel tol {})", actual.re, actual.im, tol.abs, tol.rel);
}
```

**適用範囲: 期待値が複素数であるものすべて** — `polar_to_rect` の `(re, im)`、
新設する `add`/`sub`/`mul`/`div`、`scientific.json` の全ケース。
**`r` と `theta_deg` は現行の成分ごと `close()` のまま**——それぞれが独立に
意味を持つスカラーであり、ノルムに畳む対象ではない（issue #3 の提案どおり）。

### 変えないもの

- `tolerance` の JSON 形式（`{abs, rel}`）と値（両方 1e-12）。変わるのは
  golden.rs での**適用のしかた**であり、ファイル形式ではない。schema は 1 のまま。
- 期待値そのもの。#3 単独では testdata は 1 バイトも変わらない。

### 記録

`docs/numerical-policy.md` の「許容誤差」節に、なぜ成分ごとではなくノルムかを
issue #3 の実測値（7.26e-12 vs 4.30e-16、最悪ケースの分解）付きで書く。
同ファイルの既存の流儀（意図的な非対称を実測とともに記録する）に並べる。

**あわせて、この一様な線が add/sub については意図的な弱体化であることを
記録する（レビュー指摘）。** 加減算は成分ごとに独立に正しく丸められるため、
乗除算と違って成分ごとの相対精度を保証**できる**演算であり、成分ごと比較の
ほうが強い検査になる（例: `(1e6, 1e-8)` の加算で虚部が 100% 狂っても、
差 1e-8 < rel×ノルム 1e-6 で通ってしまう）。それでも「スカラーは成分・
複素数はノルム」の一様な線を採るのは、演算ごとに基準を分けると次に演算を
足す人が毎回この判断をやり直すことになるため。加減算の成分レベルの厳密さは
`value.rs` の単体テスト（`adds_complex_numbers` 等の完全一致）が固定して
おり、実害はない。**見落としではなく選択である**と numerical-policy.md に
理由ごと書き残す。

## §2 #2: 四則演算のケースを golden に足す

### Python 参照実装（`complex_ref.py`）

SymPy の厳密有理数で計算し、最後に 50 桁で評価して f64 に落とす——既存の
`rect_to_polar` と同じ流儀。除算は `(a_re + a_im*I) / (b_re + b_im*I)` を
厳密有理数のまま簡約するので、**Smith 法とは手法が自然に独立する**
（base-spec §30・CONTRIBUTING「参照実装を Rust の移植にしない」）。
Rust 側の分岐や規格化をいかなる形でも写さないこと。

### 入力ケース（`cases.py` に `BINARY_INPUTS: list[tuple[複素, 複素]]`）

各ペアに 4 演算すべてを生成する。設計基準:

1. **Smith 法の両分岐**: 除数が実部優勢（`|b.re| >= |b.im|`）のペアと
   虚部優勢のペアを両方含める。
2. **単体テストが守っている極端値**: 微小除数 `(1e-200, 1e-200)`（素朴な分母は
   アンダーフローで 0 に潰れ DivisionByZero になる——Smith 法でだけ通る）、
   巨大除数（素朴な分母は inf、結果が 0 に潰れる）。golden がこの 2 つを
   持てば、**Rust 側**の素朴式書き換えを捕まえる。参照側は既に厳密有理数上の
   教科書式であり「素朴式への書き換え」という退行は存在しない。参照側の
   現実的な退行（`_exact` をやめて f64 の complex に落とす等）は golden では
   原理的に捕まらない——CPython の複素除算は Smith 法なので極端値でも Rust
   と同じ答えを返す。そちらの担保は `test_division_is_exact_in_rationals` と
   CONTRIBUTING の規律である。
3. **四象限と軸上**（base-spec §33 の流儀）。
4. **成分比が極端に偏ったペア**: issue #3 の実測が示した領域
   （虚部/実部 ~1e-5 級、例 `(430.27, 0.0040323)` の類）。§3 の実証ケースを兼ねる。
5. **結果が有限であること**: 期待値が inf/nan になるペアは入れない
   （`generate.py` は `allow_nan=False` で落ちる。これは正しい挙動）。
   ゼロ除算もエラー系として golden の対象外——エラーの仕様は
   `engine_table.rs` の領域である。

### 形式

- `complex.json` に追加。`op`: `"add" | "sub" | "mul" | "div"`、
  `input`: `{"a_re", "a_im", "b_re", "b_im"}`（フラット。既存の `field()` が
  そのまま読める）、`expect`: `{"re", "im"}`、
  `id`: `"div/(a_re,a_im)/(b_re,b_im)"` の形。
- `golden.rs` に 4 つの腕を足し、`Value::checked_*` を呼んで `close_complex` で
  比べる。エラーが返ったら panic（golden は成功ケースだけを持つ、という現行の
  `unwrap_or_else` の流儀のまま）。
- `reference/` の pytest に新設関数のテストを追加する（既存の参照実装テストと
  同じ粒度。SymPy 経路の自己検証であり、Rust との突き合わせは golden の仕事）。
- op の追加は schema を bump しない（リーダーと testdata は同一コミットで
  動くため、未知 op は schema 不一致ではなく unknown op として落ちる）。

## §3 実証の規律 — 新設検査は壊して赤を見てから信じる

**#3 の主張そのもの（「成分ごとでは正しい実装でも超える」）を実測で固定する。**

1. 実装中に小さな探索（issue #3 の恒等式 `(a*b)/b` の形）で、
   **成分ごとの相対誤差が 1e-12 を超え、ノルムでは超えない具体的なペア**を
   見つけ、その f64 値を `BINARY_INPUTS` に凍結する（コメントに探索方法と
   実測値を残す）。
2. 全部が緑になった後、`close_complex` を一時的に成分ごとの比較に戻し、
   **凍結したケースが赤くなることを確認して、元に戻す**。この往復の実出力を
   実装報告に貼る。赤にできなければ、そのケースは主張を実証していない——
   別のペアを探すこと（「見つからなかったので緑のまま」は完了ではない）。
3. 前ブランチの教訓を引き継ぐ: **主張は測ってから書く**。spec のこの節も
   「実測でペアが見つかる」ことを仮定しているので、探索して見つからなければ
   それ自体を報告して止まること（成分比をさらに偏らせるか、反復乗除で
   誤差を蓄積させる形に探索を広げる判断は実装者に委ねる）。

## §4 テストの段付け（このブランチの検証段）

`test-tiering-policy`（ユーザー指示 2026-08-11）を適用する。本ブランチは
**数値・アルゴリズム段**:

- 毎タスク: `cargo fmt` + `cargo clippy --workspace --all-targets -- -D warnings`
  + `cargo test --workspace`（golden 含む、約 5 秒）。
- testdata を変えるタスクのみ: `cd reference && uv run --no-config pytest` と
  `uv run --no-config python scripts/generate.py` → コミット対象の差分として確認。
- **wasm / vitest / e2e は毎タスクでは回さない**（境界・UI・ロール意味論に
  不触のため）。ブランチ最終タスクで 1 回だけフルスイープ
  （wasm 6 / vitest 31 / e2e 14 / golden 再生成の再現性確認）を行う。
- 赤確認は §3 の実証と、新設した golden の腕（op 名の綴りを壊して
  `unknown op` で落ちること等ではなく、**期待値の突き合わせが実際に効いて
  いること**——例: 参照実装の 1 ケースの期待値を最終桁で崩して赤を見る）に絞る。

あわせて `CONTRIBUTING.md` に「テストの段付け」節（10 行程度）を追加し、
この方針をリポジトリに記録する（メモリではなくリポジトリに置くことで、
どのセッション・どのレビュアーからも見える）。
