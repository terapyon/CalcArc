## §1 60 進は 2 つの顔を持つ

`1 時間 30 分` と `1 度 30 分` は**同じ機構**である。60 で繰り上がる位取りが
2 段あるだけで、意味が違う。

```
時間:  1:30:00     = 1.5 時間
角度:  1°30'00"    = 1.5 度
```

**一般的な関数電卓（Casio）は 1 つのキー `°'"` で両方を賄う。** 値は 10 進で持ち、
表示だけ 60 進にする。だから `1.5 + 2.25 = 3.75` が `3°45'0"` とも
`3 時間 45 分` とも読める——**どちらの意味かは利用者の頭の中にしかない。**

この設計の良いところは、**四則演算を 1 つも書かなくてよい**ことである。
`1:30 + 2:45` は `1.5 + 2.75` であり、既存の加算がそのまま答える。

## §2 何を作るか — 裁定待ち（最重要）

| # | 論点 | 選択肢 |
|---|---|---|
| **Q1** | 何の 60 進か | **(a) 1 つのキーで時間と角度を兼ねる**（Casio 方式。値は 10 進） (b) 時間専用（`hh:mm:ss`） (c) 角度専用（度分秒） |
| **Q2** | 単位は何段か | (a) 3 段（時・分・秒 / 度・分・秒） (b) 2 段（時・分） |
| **Q3** | 60 進で表示するのは | **(a) 押したときだけ変換**（Casio。`=` の答に `°'"` を押すと変わる） (b) ENG と同じくモードとして残る |
| **Q4** | 日をまたぐ / 24 時間を超える | (a) 気にしない（`30:00:00` と出す） (b) 24 で割った余りにする |

**私の推奨は (a)(a)(a)(a)** である。理由:

- **Q1(a)**: 機構が同じものを 2 つ作らない。既に `AngleMode` があり Degree で計算
  できるので、**度分秒で入れた角度をそのまま `sin` に渡せる**——これは実用的な利得で、
  電気・電子分野を掲げる base-spec §9.1 と噛み合う
- **Q3(a)**: ENG（S-2）はモードにしたが、**60 進は事情が違う**。ENG は「大きな数を
  読みやすくする」ので常時効いてほしいが、60 進は**その値が時間か角度のときだけ**
  意味がある。`3.75` が常に `3°45'0"` と出ると、時間でも角度でもない計算で邪魔になる
- **Q4(a)**: 「30 時間」を出せないと経過時間の計算ができない

## §3 変えること（Q1(a) Q3(a) を採った場合）

### 入力

`°'"` キーを、**数を打っている途中に区切りとして押す**:

```
1 °'" 30 °'" 0 °'"   →  1.5
1 °'" 30 °'"         →  1.5   （秒を省略できる）
```

`Buffer`（入力中の数）に 60 進の段数を持たせる必要がある。**ここが実装の主戦場**で、
既存の `Buffer` は仮数と指数（`EXP` キー）を持っている——**3 つ目の入力モード**になる。

### 表示

`=` のあとに `°'"` を押すと、**現在値を 60 進の文字列にする**:

```
3.75  →  3°45'0"
```

**負の値**: `-3.75` → `-3°45'0"`（符号は先頭に 1 つ）。
**60 進にできない値**: 複素数、無限大、`|x|` が大きすぎて秒が丸めで 60 になる値
——`DomainError` ではなく**何もしない**（表示を変えない）のが穏当かもしれない。§8 Q5。

### 丸め

**秒の小数をどう出すか**が地味に効く。`1/3` 時間 = `0°20'0"` だが、
`0.1` 時間 = `0°6'0"`、`0.001` 時間 = `0°0'3.6"`。

**秒は小数を許す**（`3.6"`）。許さないと `0.001` 時間が表せない。
桁数は `DISPLAY_DIGITS` から逆算する——**度と分で使った桁を引いた残り**を秒に回す。

**丸めで秒が 60 になる場合**（`0°59'59.9999999999"` → `60"`）は繰り上げる。
`format_real` が `9999999999.6 → 1e10` の繰り上がりを先読みできない問題を踏んだのと
同じ形なので、**同じ手（先に丸めてから桁を決める）を使う**。

## §4 やらないこと（この設計の含意）

**「時間」という型を作らない。** 値は `f64` の 10 進のままで、60 進は**入力と表示の
形式**にすぎない。したがって:

- `1:30 × 2` は `3.0`（= `3°0'0"`）。**時間×時間**に意味を持たせない
- 時刻（`13:45` という「時点」）と経過時間（`1:30` という「長さ」）を区別しない
- 日付・曜日・タイムゾーンは扱わない

**もし「時刻の計算」（`13:45` の 3 時間後）がやりたいのなら、この設計では足りない。**
Q1 の裁定でそう言ってほしい——別の設計（時点と期間を区別する型）になる。

## §5 盤面 — 4 本ぶんの圧が限界に来る

S-1 が第 2 面を 8 つ、S-3 が 3 つ使う。**S-4 は最低 1 つ（`°'"`）要る。**

累計すると:

| 面 | 使用 |
|---|---|
| 第 1 面（32） | 満杯 + **ENG が 1 つ要求**（S-2） |
| 第 2 面 | S-1 が 8、S-3 が 3、S-4 が 1 |

**`°'"` は「押しやすくしたい」とは言われていない**ので第 2 面でよい。
残っているのは `DEG/RAD` の裏、数字 `4`〜`0` の裏、`(` `)` `DEL` `AC` の裏。

**推奨: `DEG/RAD` の Shift。** 角度の単位のキーであり、度分秒は角度の表し方なので
**意味が近い**（Q1(a) を採るなら特に）。

**ただし S-1〜S-4 を全部入れると第 2 面が 12 個埋まる。** 第 2 面が「準備中」の
空箱だったことを思えば妥当だが、**4 本を通したあとに盤面がどう見えるかは、
S-1 の実装時に一度スクリーンショットで見ておくべきである**（テストでは分からない）。

## §6 base-spec への追記

60 進は base-spec に**書かれていない**。§9.2 の MVP にも無い。

**§9 に「60 進表記」の節を足す**必要がある。Q1 の裁定次第で、それが
「角度の表し方」なのか「時間計算」なのか、あるいは両方なのかが決まる。

## §7 検証

段ゲート: base-spec と数値方針 → Python 参照 + golden → Rust → WASM → 盤面。

**Python 参照の独立軸**: 60 進の変換は `Fraction` で厳密にできる
（`3.75 = 3 + 45/60`）。**Rust は f64 の除算と剰余、Python は有理数**——
アルゴリズムが同型でない。

**必須ケース（案）**: `1.5` → `1°30'0"` / `0.001` → `0°0'3.6"` /
`-3.75` → `-3°45'0"` / `0` → `0°0'0"` / **丸めで秒が 60 になる値**（繰り上がり）/
`30.5`（24 を超える）/ 入力側の往復（`1 °'" 30 °'"` → `1.5` → `°'"` → `1°30'0"`）。

**赤確認**: 繰り上がりの検査を足したら、繰り上げ処理を外して `60"` が出る赤を見る。

## §7.1 他セッションの表示読み取りとの関係（2026-08-16 合意）

重量級検証コーパス（`feature/e2e-corpus`）は表示文字列を数に戻して比較しており、
`12°34'56"` のような書式は**拒まれる**（黙って壊れず、大きな声で落ちる作りになっている）。

**Q3 の裁定がここに効く。**

- **Q3(a)（押したときだけ変換）を採れば発火しない。** 相手のコーパスは `°'"` を
  押さないので、表示は常に十進のままである
- **Q3(b)（モードとして残る）を採ると、モードに入っている間の表示が全部 60 進になる。**
  それ自体は相手のコーパスに影響しない（押さないので）が、**「表示の書式が値に
  よらず変わりうる」という性質が増える**のは、相手が実測で書式を確定させている
  設計と相性が悪い

**推奨 (a) は、この理由でも補強される。**

いずれにせよ**実装に入る前に一声かける**——相手は `parseDisplay` と `tolerance` を
実測し直す用意があると言っている。
