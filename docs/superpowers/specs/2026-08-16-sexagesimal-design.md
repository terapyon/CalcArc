# S-4 時間計算（60 進） — 設計

日付: 2026-08-16
対象: `numeric/format.rs`、`engine/{key,state,display}.rs`、盤面、base-spec。
前提: **main（`0fd4842`）から**（複利の逆算と E2E がマージされた後）。S-2（ENG）と**表示層で隣り合う**。
**状態: 裁定すべて決着（§2、2026-08-16）。実装待ち。**

## §0 位置づけ

ユーザー発意（2026-08-16）:「**時間計算も入れていきたい。**」——**これが指示の全文
だった。** 4 本のうち最も大きく、最も情報が少なかったので、この spec は
「何を作るか」から書いた。**§2 で全部裁定が下りた。**

**結論から言うと、作るのは「経過時間の足し引き」であって「時刻の計算」ではない。**
`13:45` の 3 時間後は**この spec の範囲外**である（§4）。

## §1 60 進は 2 つの顔を持つ

`1 時間 30 分` と `1 度 30 分` は**同じ機構**である。60 で繰り上がる位取りが
2 段あるだけで、意味が違う。

```
時間:  1:30:00     = 1.5 時間
角度:  1°30'00"    = 1.5 度
```

**一般的な関数電卓（Casio）は 1 つのキー `°'"` で両方を賄う。** 値は 10 進で持ち、
表示だけ 60 進にする。だから `1.5 + 2.25 = 3.75` が `3°45'0"` とも
`3 時間 45 分` とも読める——**どちらの意味かは利用者の頭の中にしかない。**

この設計の良いところは、**四則演算を 1 つも書かなくてよい**ことである。
`1:30 + 2:45` は `1.5 + 2.75` であり、既存の加算がそのまま答える。

## §2 裁定（ユーザー、2026-08-16）

| # | 論点 | 裁定 |
|---|---|---|
| 1 | 何を作るか | **経過時間の足し引き。** `1:30 + 2:45 = 4:15`。値は 10 進の実数のままで、60 進は**入力と表示の形式**。**四則がそのまま使える** |
| 2 | 角度の度分秒と兼ねるか | **兼ねる。** 1 つの `°'"` キーで両方（Casio 方式）。**度分秒で入れた角度をそのまま `sin` に渡せる**——電気・電子分野を掲げる base-spec §9.1 と噛み合う |
| 3 | 単位は何段か | **3 段**（時・分・秒 / 度・分・秒） |
| 4 | 60 進表示の持続 | **押したときだけ変換。** ENG（S-2）はモードにしたが、**60 進は事情が違う**——ENG は「大きな数を読みやすくする」ので常時効いてほしいが、60 進は**その値が時間か角度のときだけ**意味がある。`3.75` が常に `3°45'0"` と出ると邪魔になる |
| 5 | 24 時間を超えたら | **そのまま出す**（`30:00:00`）。24 で割ると経過時間の計算ができない |
| 6 | 60 進にできない値に押したら | **何もしない**（表示を変えない）。表示の操作でエラー状態に落とすのは重い |
| 7 | 秒の小数桁 | **`DISPLAY_DIGITS` の残りを回す**（度と分で使った桁を引いた残り） |
| 8 | `°'"` の置き場 | **第 1 面の関数列 2 段目**（`[ENG] [ln] [log] [1/x] [eˣ] [xʸ] [°'"]`）。時間計算をよく使うため表に出す |

**裁定 1 の帰結——「時刻の計算」は範囲外である。** `13:45` の 3 時間後は求められない。
§4 にその含意を書いてある。**必要になったら別 spec**（時点と期間を区別する型が要る）。

## §3 変えること

### 入力

`°'"` キーを、**数を打っている途中に区切りとして押す**:

```
1 °'" 30 °'" 0 °'"   →  1.5
1 °'" 30 °'"         →  1.5   （秒を省略できる）
```

`Buffer`（入力中の数）に 60 進の段数を持たせる必要がある。**ここが実装の主戦場**で、
既存の `Buffer` は仮数と指数（`EXP` キー）を持っている——**3 つ目の入力モード**になる。

### 表示

`=` のあとに `°'"` を押すと、**現在値を 60 進の文字列にする**:

```
3.75  →  3°45'0"
```

**負の値**: `-3.75` → `-3°45'0"`（符号は先頭に 1 つ）。
**60 進にできない値**: 複素数、無限大、`|x|` が大きすぎて秒が丸めで 60 になる値
——**何もしない**（表示を変えない。裁定 6）。

### §3.1 「押したときだけ変換」の一時状態はどこに住み、何で解除されるか

**裁定 4 の「押したときだけ」を実装するには、状態が要る。** `°'"` を押してから
次のキーまでのあいだ、`render()` が「いまは 60 進で出せ」と知る必要があり、
**`EngineState` 以外に呼び出しをまたいで残る場所が無い**。

**解除規則: `°'"` 以外のあらゆるキーで解除する。**

| キー | 一時状態 |
|---|---|
| `°'"` | **入る。もう一度押すと戻る**（トグル） |
| それ以外のすべて（数字・演算子・`=`・`AC`・`DEL`・`DEG/RAD`・`▸∠`・`ENG`） | **解除** |

**例外を作らない。** 「値が変わる操作だけ解除」「表示の切り替えは保つ」といった
場合分けも考えられるが、**`▸∠` は形そのものを変え、`DEG/RAD` は角度の意味を変え、
`ENG` は同じ表示層で競合する**——どれも「60 進のまま保つ」と言いにくい。
**1 つの規則で言い切れる方が、利用者にも実装にも検査にも安い。**

利用者から見ると「**`°'"` は覗くためのキー**」になる。押して確かめ、次に何か押せば
普通の表示に戻る。

### §3.2 `STATE_SCHEMA` が上がる（`5` → `6`）

**2 つの理由で `EngineState` の直列化の形が変わる:**

1. **`Buffer` に 60 進の段が入る**（§3 の入力）。既存の `Buffer` は仮数と指数
   （`EXP` キー）を持っており、**3 つ目の入力モード**になる
2. **§3.1 の一時状態**が乗る

**S-2 が `4` → `5` を取るので、S-4 は `5` → `6`** である（実装順は S-2 §0.1 の表）。

**bump の実害**: 更新すると入力中の数が消える。既存のスキーマ変更と同じ扱いで、
`is_current()` がスキーマ不一致を見て初期状態から始める。

### 丸め

**秒の小数をどう出すか**が地味に効く。`1/3` 時間 = `0°20'0"` だが、
`0.1` 時間 = `0°6'0"`、`0.001` 時間 = `0°0'3.6"`。

**秒は小数を許す**（`3.6"`）。許さないと `0.001` 時間が表せない。
桁数は `DISPLAY_DIGITS` から逆算する——**度と分で使った桁を引いた残り**を秒に回す。

**丸めで秒が 60 になる場合**（`0°59'59.9999999999"` → `60"`）は繰り上げる。
`format_real` が `9999999999.6 → 1e10` の繰り上がりを先読みできない問題を踏んだのと
同じ形なので、**同じ手（先に丸めてから桁を決める）を使う**。

## §4 やらないこと（この設計の含意）

**「時間」という型を作らない。** 値は `f64` の 10 進のままで、60 進は**入力と表示の
形式**にすぎない。したがって:

- `1:30 × 2` は `3.0`（= `3°0'0"`）。**時間×時間**に意味を持たせない
- 時刻（`13:45` という「時点」）と経過時間（`1:30` という「長さ」）を区別しない
- 日付・曜日・タイムゾーンは扱わない

**「時刻の計算」（`13:45` の 3 時間後）は、この設計では足りない。裁定 1 でそれは
範囲外と決まった**——必要になったら別 spec（時点と期間を区別する型）にする。

## §5 盤面 — `°'"` は第 1 面に出る（裁定 8）

**S-2 で関数列が 2 段になり**（横に 8 列は 44px を割るため縦に増やした）、
**`°'"` はその 2 段目の右端に出る**。ユーザーが「時間を 6 つめに」と決めた。

```
関数列 1 段目: [Shift] [sin] [cos] [tan] [√]  [x²]  [DEG/RAD]
関数列 2 段目: [ENG]   [ln]  [log] [1/x] [eˣ] [xʸ]  [°'"]
```

**当初は `DEG/RAD` の Shift を推していた**（角度の単位のキーで意味が近いため）が、
**表に出す方が使う頻度に合う**という裁定になった。`DEG/RAD` の裏は空いたままである。

**4 本を通したあとの盤面は、S-1 の実装時に一度スクリーンショットで見ておく**
（テストでは分からない）。特に **S-3 が数字キーの裏に入る**ので、Shift を押したときに
数字の面が変わることが見て分かるかを確かめる。

## §6 base-spec への追記

60 進は base-spec に**書かれていない**。§9.2 の MVP にも無い。

**§9 に「60 進表記」の節を足す**必要がある。**裁定 1・2 により、それは
「経過時間と角度の両方を、1 つの 60 進の形式で表す」**である。時刻ではない。

## §7 検証

段ゲート: base-spec と数値方針 → Python 参照 + golden → Rust → WASM → 盤面。

**Python 参照の独立軸**: 60 進の変換は `Fraction` で厳密にできる
（`3.75 = 3 + 45/60`）。**Rust は f64 の除算と剰余、Python は有理数**——
アルゴリズムが同型でない。

**必須ケース（案）**: `1.5` → `1°30'0"` / `0.001` → `0°0'3.6"` /
`-3.75` → `-3°45'0"` / `0` → `0°0'0"` / **丸めで秒が 60 になる値**（繰り上がり）/
`30.5`（24 を超える）/ 入力側の往復（`1 °'" 30 °'"` → `1.5` → `°'"` → `1°30'0"`）。

**赤確認**: 繰り上がりの検査を足したら、繰り上げ処理を外して `60"` が出る赤を見る。

## §7.1 他セッションの表示読み取りとの関係（2026-08-16 合意）

重量級検証コーパス（`feature/e2e-corpus`）は表示文字列を数に戻して比較しており、
`12°34'56"` のような書式は**拒まれる**（黙って壊れず、大きな声で落ちる作りになっている）。

**裁定 4（押したときだけ変換）により、相手のコーパスには発火しない。** 相手は
`°'"` を押さないので、表示は常に十進のままである。

**それでも実装に入る前に一声かける**——「押さないから当たらない」は私の側の読みで、
確かめるのは相手である。前例（`STATE_SCHEMA` と関数列の 2 段化）でも、
相手が実際に確かめて「当たらない」と返してきた。**当たらないことが分かっている状態**は、
**たまたま当たらなかった状態**とは違う。
