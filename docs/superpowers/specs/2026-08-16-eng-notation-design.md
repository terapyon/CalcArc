## §2 いま在るもの

`numeric::format_real` が実数 1 つを文字列にする。**有効数字 10 桁**で、

```
|x| >= 1e10  または  |x| < 1e-9   → 指数表記（科学表記。仮数は 1 以上 10 未満）
それ以外                          → 通常の 10 進
```

したがって **`1000` はいま `1000` と出る**。ENG はこの規則を**上書きする**。

`DisplayState` は `angle`（Degree/Radian）と `form`（Rect/Polar）という
**表示の状態**を既に 2 つ持っており、どちらも `EngineState` に載って
`render()` が読む。**ENG は 3 つ目の同類**である。

## §3 変えること

### 表示の規則

```
ENG が入っているとき:
  x = 0                   → "0"
  それ以外                 → 仮数 × 10^(3の倍数)。仮数は 1 以上 1000 未満
                            （負なら絶対値がその範囲）
```

| 入力 | 通常 | ENG |
|---|---|---|
| 1000 | `1000` | `1e3` |
| 12345 | `12345` | `12.345e3` |
| 0.0022 | `0.0022` | `2.2e-3` |
| 1500000 | `1500000` | `1.5e6` |
| 999 | `999` | **`999`**（§3.1） |
| 1.5e12 | `1.5e12` | `1.5e12` |
| 1.5e11 | `1.5e11` | **`150e9`** |

### §3.1 指数 0 は書かない

`999` は工学表記だと `999e0` だが、**`e0` は書かない**。「大きな数値を 3 桁の E 表現に
する」という要望に対して `999e0` は情報を足していないし、`1 e0` のような表示は
電卓として見慣れない。**指数が 0 のときは通常の 10 進で出す。**

これは「ENG に入れたのに見た目が変わらない値がある」ことを意味する。**そういうものだ、
と spec に書いておく**——利用者が「効いていない」と誤解しないよう、§5 のインジケータで
モードに入っていること自体は見える。

### 有効数字

**10 桁のまま**（`DISPLAY_DIGITS`）。工学表記では仮数が最大 4 桁ぶん整数部を取るので、
小数部は 10 − 整数部の桁数になる。`format_real` が既にやっている数え方
（**`log10` を使わず、Rust の指数書式に 1 度整形させて指数を読む**）を踏襲する
——`log10` は 10 の冪の近くで 1 桁ずれ、丸めの繰り上がり（`999.9999…` → `1000`）を
先読みできない。

**工学表記の指数は、丸めた後の値から決める。** 先に指数を決めて丸めると、
`999.99999999e0` が `1000e0` になって仮数の範囲（1 以上 1000 未満）を破る。

## §3.2 入力中の表示は ENG にしない — 別経路である

**実測（2026-08-16）: 入力中の数は `format_real` を通っていない。**
`render()` の `main` はこう分岐している:

```rust
let main = if has_error {
    ERROR_TEXT.to_string()
} else if let Some(buffer) = &state.buffer {
    buffer.text()                      // ← 入力中。打った文字がそのまま出る
} else {
    format_rect(state.current)         // ← 確定値。ここだけが format_real を通る
};
```

**したがって ENG は入力中の表示に一切影響しない**——`1000` と打っている最中に
`1e3` に化けたりしない。**これは望ましい挙動である**（打っている途中で表示が
書き換わると、何を打ったか分からなくなる）。

**だが偶然そうなっているだけなので、spec の主張として書き、検査で固定する。**

```rust
#[test]
fn eng_does_not_touch_what_you_are_typing() {
    // 入力中は buffer.text() が出る経路で、format_real を通らない。
    // ENG に入れても、打っている数字はそのまま見える。
    // (この分岐は render() の構造に依存しているので、構造が変わったら赤くする)
}
```

**この事実はどこにも書かれていなかった。** 他セッションが表示を実測したとき、
`1e10` を打ち込んで「平坦な `10000000000` が出る、文書と食い違う」と読み、
**文書が間違っていると一瞬判断した**（実際は `eq` を押していないので入力バッファを
見ていた）。**入力中と確定後で表示の規則が違うことが、どこにも書かれていない**のが
原因である。**numerical-policy に 1 行足す。**

## §4 状態をどこに置くか

`EngineState` に `eng: bool`（または `DisplayNotation` の列挙）を足す。
`angle` / `form` と同じ扱いで、`render()` が読む。

**`STATE_SCHEMA` の bump が要る**（いま `4` → `5`）。`EngineState` は
WASM 境界を JSON で往復し、`is_current()` がスキーマ一致を見て**合わなければ初期状態から
始める**設計なので、フィールドを足したら bump しなければ**古い保存状態が新しいコードに
読まれる**。

**bump の実害は「ENG を入れたまま更新すると通常表示に戻る」だけ**——状態が初期化される。
利用者の入力中の数は消えるが、これは既存のスキーマ変更と同じ扱いである。

## §5 モードに入っていることを見せる

`angle`（DEG/RAD）と `form` が画面のどこに出ているかを plan の最初に実測し、
**同じ場所に同じ形で `ENG` を出す**。§3.1 のとおり「入れても見た目が変わらない値」が
あるので、**インジケータが無いとモードに入ったかどうか分からない**。

## §6 複素数と極形式との関係

**ENG は実数 1 つの表し方である。** 複素数と極形式は「実数を 2 つ並べたもの」なので、
**それぞれの実数に ENG を適用する**:

| 形 | 通常 | ENG |
|---|---|---|
| 直交 | `1500+j2200` | `1.5e3+j2.2e3` |
| 極 | `2500 ∠ 30` | `2.5e3 ∠ 30` |

**角度には ENG を掛けない。** 角度は度かラジアンであって工学量ではなく、
`30` を `30e0`（§3.1 で通常表示）にも `0.03e3` にもしたくない。
`format_polar` は半径にだけ ENG を通す。

## §7 盤面 — ここが唯一の難所

**「押しやすくしたい」＝ Shift の裏に置けない。** ところが**第 1 面は 32 スロット
すべて埋まっている**（関数列 7 + メイングリッド 5×5）。

```
関数列(7): [Shift] [sin] [cos] [tan] [√] [x²] [DEG/RAD]
5×5:  (   )   +/−  DEL  AC
      7   8   9    ÷    j
      4   5   6    ×    ▸∠
      1   2   3    −    EXP
      0  000  .    +    =
```

**何かを退かすか、行を増やすかしかない。** §9 の裁定待ちにする。

**私の推奨は「関数列を 8 列にする」**である。理由:

- ENG は**表示の切り替え**であり、`DEG/RAD` と `▸∠` という**同類が既に関数列と
  5 列目に居る**。関数列の右端（`DEG/RAD` の隣）が意味的に正しい置き場である
- メイングリッドの 5×5 は**3 タブで揃えてある**（`AC`/`DEL` の位置とキー寸法）。
  ここを崩すと Finance / Data Scale との一貫性が壊れる
- 関数列は**半高**なので、8 列にしても縦は増えない

### §7.1 実測: 横に広げる道は塞がっている（2026-08-16）

CSS の実値（`--key-gap: 8px`、`ScientificPanel.module.css` の `padding: 12px`）から
390px 幅で計算した:

```
7 列（現状）= (390 − 24 − 8×6) / 7 = 45.43px   OK（ぎりぎり）
8 列        = (390 − 24 − 8×7) / 8 = 38.75px   ← 44px を割る
```

**式の妥当性は確認済み**——同じ式で 6 列を出すと **54.33px** で、Finance のモード行の
実測値と一致する。

**したがって 8 列は取れない。** base-spec §43 の 44px はタッチの下限であり、関数列は
現状 45.43px で**既にぎりぎり**である。

### §7.2 裁定: 関数列を 2 段にする

**キー寸法を 1px も変えずにスロットを 7 → 14 に増やす**。

```
関数列 1 段目(7): [Shift] [sin] [cos] [tan] [√] [x²] [DEG/RAD]
関数列 2 段目(7): [ENG]   [?]   [?]   [?]   [?]  [?]  [?]
5×5 グリッド: 変更なし
```

- **キー幅 45.43px のまま**——3 タブで揃えてきた寸法の規律を崩さない
- 関数列は**半高**（`--function-row-height`）なので、縦の増分が正方キー 1 行より小さい
- **縦に収まるかは要実測**。Finance の盤面は 612.45px / 844px だったが、Scientific は
  関数列があるぶん構成が違う。**plan の最初にスクリーンショットで実測する**

**2 段目の残り 6 スロットをどうするかは S-1 の領域である**（§7.3）。

### §7.3 残り 6 スロットは S-1 が決める

ENG 以外の 6 つは、この spec では**決めない**。S-1 が 9 つの関数を第 2 面（Shift）に
置く設計になっているが、**第 1 面に 6 つ空きができたことで前提が変わる**
——`ln` や `log10` を Shift の裏に隠すのは、関数電卓として妥当かどうか。

**S-2 の実装では、2 段目は ENG 1 つ + 予約スロット 6 つで出す。** 予約スロットは
このリポジトリの既存の形（`{ token: null, label: "—", ariaLabel: "空き" }`）を使う
——Finance の周期・税の面が同じことをしている。**格子の形を崩さないため**であり、
S-1 がそこを埋める。

## §8 検証

**web 段だけで閉じる可能性がある**が、`format_real` は `calcarc-core` なので
**Rust とその golden にも触る**。

1. `numeric::format.rs` に工学表記の整形を足す（**Rust のユニットテスト**）
2. `scientific.json` に表示の golden を足すか判断する——**いまの golden が
   `format_real` を通っているかを plan の最初に確認する**。通っていないなら
   Rust のユニットテストで閉じる
3. `EngineState` の bump と `render()`
4. WASM 境界（`DisplayState` に 1 フィールド）と TS の型
5. 盤面と E2E

**赤確認**: 工学表記の検査を足したら、指数を 3 の倍数に丸める処理を外して赤を見る
（`12345` が `1.2345e4` になる）。**§3.1（指数 0 は通常表示）の検査も**、
条件を外すと `999e0` が出ることで赤になる。

**E2E**: `1000` を打って ENG を押し `1e3`、もう一度押して `1000` に戻る——
**ユーザーの言葉そのものを 1 本の E2E にする。**

## §8.1 他セッションの表示読み取りを壊さない（2026-08-16 合意）

重量級検証コーパス（`feature/e2e-corpus`）は**電卓の表示文字列を数に戻して**比較して
おり、`parseDisplay` が受ける書式は「**符号つき十進、小数点、小文字 `e` の指数**」に
限られる。それ以外は**大きな声で拒む**（黙って NaN を返すと「常に不一致」に化けるため）。

**この spec は 2 つの点でそれを守る:**

1. **書式は `12.345e3`——小文字 `e` の指数のままである。** `1.234×10³` や `1.234 k`
   のような別記法にしない。仮数が 10 以上になるだけなので、相手の `parseFloat` 系の
   読み取りはそのまま通る
2. **既定の表示を変えない。** ENG はモードだが**初期状態では入っていない**ので、
   `docs/numerical-policy.md` の「有効数字 10 桁 / `|x| >= 1e10` または
   `0 < |x| < 1e-9` で指数表記」は**既定として不変**である。相手のコーパスは
   ENG を押さないので発火しない

**numerical-policy への追記は「ENG が入っているときの規則」として書き、既定の規則の
文を書き換えない。** 書き換えると、相手が変更の判定に使っている目安が動く。

### §8.2 「既定は変わらない」を散文でなく検査で持つ

**上の 2 点は、いま散文である。散文は腐る。**

この spec は「既定の表示は変わらない」と約束しているが、**その約束を守らせるものが
何も無い**。ENG の実装で `format_real` を触るので、**うっかり既定側の分岐を動かしても
誰も気づかない**——ENG のテストは通り、既存のテストも「その値がたまたま両方で同じ」
なら通ってしまう。

**だから約束そのものを検査にする。**

```rust
#[test]
fn the_default_display_rule_does_not_move() {
    // **この spec の約束を、散文ではなくここで持つ。** ENG は既定では入らない。
    // 他レイヤー(feature/e2e-corpus)が表示書式を実測して parseDisplay を
    // 組んでおり、既定が動くと黙って壊れる側にいる。
    assert_eq!(format_real(1000.0), "1000");        // ENG なら "1e3"
    assert_eq!(format_real(12345.0), "12345");      // ENG なら "12.345e3"
    assert_eq!(format_real(1e10), "1e10");          // 指数表記の下限は動かない
    assert_eq!(format_real(9.999e9), "9999000000"); // その手前は平坦なまま
    assert_eq!(format_real(1e-9), "1e-9");
    assert_eq!(format_real(1.1e-9), "0.0000000011");
}
```

**境界の両側を置く**のが要点である（`1e10` と `9.999e9`、`1e-9` と `1.1e-9`）——
片側だけだと閾値がずれても通る。

**この形は他セッションから学んだ**（2026-08-16）:「**再観測できる根拠は、散文ではなく
assertion で持つ**。検査を書く先は相手のコードではなく自分の側で、相手が事実を
変えたときに自分が赤くなる形にする。相手に何も要求しないので、相手のセッションが
存在しなくても働く。」ここでは向きが逆で、**自分が約束を破ったときに自分が赤くなる**。

## §10 スコープ外

- **ENG の段送り**（Casio の ENG / ENG⁻¹ のように押すたび指数を 3 ずつずらす）
