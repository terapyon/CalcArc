## §1 いま何が起きているか（**すべて実行役の印字。2026-09-29、`92adf99`**）

| 入力（DEG） | `sin` | `cos` | `tan` |
|---|---|---|---|
| 0 | `0` | `1` | `0` |
| 30 | `4.9999999999999994e-1` | `8.660254037844387e-1` | `5.773502691896256e-1` |
| 90 | `1` | **`6.123233995736766e-17`** | `TrigPole` |
| 180 | **`1.2246467991473532e-16`** | `-1` | **`-1.2246467991473532e-16`** |
| 270 | `-1` | **`-1.8369701987210297e-16`** | `TrigPole` |
| 360 | **`-2.4492935982947064e-16`** | `1` | **`-2.4492935982947064e-16`** |
| −180 | **`-1.2246467991473532e-16`** | `-1` | `1.2246467991473532e-16` |
| 180.0000001 | `-1.7453290920217664e-9` | `-1` | `1.7453290920217664e-9` |

**原因は `sin` の精度ではない。** **180° を `to_rad` でラジアンに直すと `f64` の π になり、
それは本当の π より小さい**——**その差がそのまま答えになっている**
（`cos(90°)` はその半分、`sin(360°)` は 2 倍、`sin(540°)` は 3 倍。**上の表がそうなっている**）。

**★ 30° はずれているが、直す対象ではない**（`0.4999999999999994`）。**画面は `0.5` と出る**
（表示は 10 桁）。**ここで直すのは「真の値が厳密に表せる角」だけ**である（§3）。

## §2 前例——**このコアには既に「度のまま特別扱いする」判定が在る**

`scientific/mod.rs:88` の `is_tan_pole`: **`mode == Deg` かつ実数のとき、
`a >= 90 && (a - 90) % 180 == 0` で極を判定**している（**度のまま、剰余で**）。
**`tan(90°)` が `Math ERROR` になるのはこれ**である。**同じ形を `sin`・`cos` に広げる。**

## §3 直し方

**DEG のとき、実部 `x` が 90° の倍数なら、`sin x`・`cos x` を表から取る。**
**経路は 1 つで、実数はその特別な場合である**（**裁定 (a)。理由は §3.2**）。

1. `let r = x % 360.0;`（**`f64` の `%` は IEEE の `fmod` で、これは厳密**
   ——実測: `540 % 360 = 180`、`(1e10 + 180) % 360 = 100`、`(1e16 + 90) % 360 = 10`。
   **丸め誤差が入らない**ので、**大きい角でも「どの象限の角か」は正確に決まる**）
2. `r.abs()` が **0・90・180・270** のいずれかなら、**表を引く**:

| `r.abs()` | `sin` の大きさ | `cos` |
|---|---|---|
| 0 | 0 | 1 |
| 90 | 1 | 0 |
| 180 | 0 | −1 |
| 270 | −1 | 0 |

   **`sin` は奇、`cos` は偶**なので、**`sin x` は上の値に `r` の符号を掛ける**
   （**レビュー役 calcarc-1e の注記**——**7 行を 4 行と符号に畳める**。
   **`r < 0` かつ表の値が 0 のときは `-0.0` になるが、`finalize` が均す**）。
   **`cos` は `r.abs()` だけで決まる。**
3. **それ以外は、いままでどおり**（`to_rad` して `f64` の `sin`/`cos`）。

**この 2 つの値が、そのまま複素の公式に入る**:
`sin(x + iy) = sin x · cosh y + i · cos x · sinh y`、
`cos(x + iy) = cos x · cosh y − i · sin x · sinh y`。
**`y == 0` なら `cosh 0 = 1`・`sinh 0 = 0` なので、実数の答えは表の値そのもの**
——**実数のために別の分岐を書かない。**

**`tan` は何もしない。** `sin / cos` なので、**0°・180° では `0 / ±1 = 0`**（`finalize` が `-0.0` を均す）、
**90°・270° の実数は `is_tan_pole` が先に `TrigPole` を返す**。**新しい表と極の判定は衝突しない**
——**担当する `r` が重なっていない**（極は `|r|` が 90・270、`tan` が表から出るのは 0・180）。

**★ 表と `is_tan_pole` は同じ条件を 2 か所に書くことになる。**
**番人を置く**（1e の注記）——**単体で `-360.0` から `360.0` まで 0.5 刻みに走らせ、
「表の `cos` が厳密に 0」⇔「`is_tan_pole` が真」を assert する**。
**片方だけ直した日に赤くなる。**

### §3.1 **RAD は触らない**（**推し。理由を正面から**）

**利用者が【π】【sin】と打ったとき、コアに届くのは本当の π ではなく `f64` の π** である。
**その入力に対する `sin` の答えは、本当に `1.2246467991473532e-16`** であって、
**0 ではない**。**RAD で 0 を返すのは、「入力が厳密な π だった」という嘘をつくことになる。**

**DEG は逆である**——**`180` は `f64` で厳密に表せる**。**利用者が打ったのは「180 度」そのもの**で、
**その `sin` は厳密に 0**。**ずれは私たちの変換が持ち込んだもの**だから、**私たちが直す。**

**この線引きが、この設計の中心である。** **「入力が厳密なら、答えも厳密に」。**

### §3.2 **複素の引数も同じ表を通る**（**草案は逆向きだった。裁定 (a)**）

**草案はここで「`im != 0` なら触らない」と書き、理由を「実部だけ 0 に寄せると
虚部の小さい変化で答えが飛ぶ」としていた。** **逆である**——**レビュー役 calcarc-1e の指摘。**

**触らないほうが飛ぶ。** 実測（実行役、`92adf99`）:

```
sin(180)          DEG = 1.2246467991473532e-16 +0e0j
sin(180+1e-300j)  DEG = 1.2246467991473532e-16 -1.7453292519943295e-302j
```

**実部は `1e-300` の虚部を足しても `1.2246e-16` のまま**である
（**`sin x · cosh y` で、`cosh(1.7e-302) = 1.0`**）。**実数だけ表を引くと、
`im == 0` では 0、`im == 1e-300` では `1.2246e-16`** ——**そこに段差が生まれる。**
**真の値は `4.1e-43` の側**（1e の計算）なので、**残るほうが真値から遠い。**

**表を複素の公式に入れれば、段差は生まれない**——**`y → 0` で答えが連続に表の値へ寄る。**
**`is_tan_pole` が実数だけを見ているのは「極を返すか計算するか」という別の問い**
（**あれは答えを差し替えず、`Math ERROR` に分岐する**）なので、**形を写す理由は無い。**

**★ 0.9.8 のマニュアルに書いた複素の数は動かない**（実行役が実測して確かめた）——
**`sin(j)` = `0 +1.1752011936438014e0j`、`cos(j)` = `1.5430806348152437e0 +0e0j`。**
**あれは `x = 0` で、表の `sin 0 = 0`・`cos 0 = 1` は `f64` の `sin`/`cos` の答えと同じ**
だからである。**表示は `1.175201194j`・`1.543080635`・`tan(j)` は `0.761594156j` のまま。**

**動く数は在る**（**下の予測は計算で出したもの。実装後に印字で当て直す**）——
**`tan(90 + 1e-8j)`**: いま `2.0101391443809966e3 + 5.729577951307527e9j`、
**直すと実部が厳密に 0 になり、虚部は `1/sinh(1.7453292519943295e-10)` = 約 `5.729577951308232e9`**。
**実部の `2010.139…` は `cos(90°)` の `6.123233995736766e-17` が作っていた幻**である。
**この値は 0.9.8 の設計書（`2026-09-25-pdf-note-design.md` §9.2）に記録が在る**ので、
**あちらに 1 行足す**（**消さない**——**あの日に測った値は、あの日の製品では真だった**）。

### §3.3 表が引かれる角（**レビュー役 calcarc-1e の走査。実行役の測定ではない**）

- **`-90 * 200000` から `90 * 200000` までの 90 の倍数 200,001 個は、すべて `% 360` が
  厳密に 0・±90・±180・±270 に着く**（**だから表は「たまに外れる」形ではない**）。
- **`-360` は `% 360` が `-0.0` になるが、`-0.0 == 0.0` は真**なので表に着く
  （**`==` で書けば取りこぼさない。`is_sign_negative` で分けてはならない**）。
- **`1e17 + 90` は `f64` で表せない**（**`1e17` の刻みが 16 なので `90` は消える**）
  ——**そういう大きさの角は、そもそも「90 の倍数」として届かない。**
  **表が効かないのではなく、入力が別の数になっている。**

### §3.4 何を直さないか（**明示する**）

- **30°・60° のような「真の値が無理数」の角**——`0.4999999999999994` はそのまま。
  **直すには丸めの幅を決める話になり、別の裁定が要る**（`numerical-policy.md` の
  「厳密一致には厳密な入力が要る」の族）。
- **`180.0000001` のような非整数**——`r` が表に無いので、いままでどおり。
- **RAD のすべて**（§3.1）。**マニュアルに 1 行足す**（検証役の案）——
  **「角度の単位が RAD のときは、【π】で入る値が本当の π ではないので、
  `sin(π)` は 0 になりません」**。**直さないことを、利用者に伝える。**

## §9 宿題の答え——**2 つの数は、同じ入力ではなかった**

**監視役から宿題が来ていた**: 「**1e の数（`0.612 + 1e8j`）と 0.9.8 の記録
（`2,010.139144 + 5,729,577,951j`）は食い違って見える。同じ入力のはずなのに違う**」。

**違う入力である。** **単位が違う**（実行役の実測、`92adf99`）:

| 入力 | `tan` |
|---|---|
| `90 + 1e-8j` **DEG**（0.9.8 の記録） | `2.0101391443809966e3 + 5.729577951307527e9j` |
| `π/2 + 1e-8j` **RAD**（1e の数） | `6.123233995736763e-1 + 9.999999999999999e7j` |

**比は `5.729577951307527e1`。`180/π` は `5.729577951308232e1`。**
**DEG では虚部も `to_rad` を通る**ので、**`1e-8` 度 = `1.7453292519943295e-10` ラジアン**
——**極までの距離が 57.3 倍近くなり、`tan` が 57.3 倍大きく出る。**
**どちらの数も、自分の入力に対しては正しい。** **どちらかが誤りだったのではない。**

**★ 教訓**（`dont-argue-from-evidence-you-lack` の族）: **角度の値を引用するときは、
単位を数と一緒に書く。** **`1e-8` だけでは、どの空間の `1e-8` か分からない。**
