# Scientific 外装（S1）— 設計

日付: 2026-08-13
対象: base-spec §12（キー配置）・§42（スマートフォン第一）・§43（タッチと a11y）。
前提: PR #26（M6 Loan）マージ後の main から始める。

## §0 位置づけ — 4 spec のうちの 1 本目

UX 改修の要件は 11 件あり、**失敗の仕方が違う関心事**が横に並んでいた。1 本に
まとめると、盤面の CSS を触るたびに engine の網羅列挙（1,350 万遷移）を回す
ことになる。4 つに割る（順序も依存もこの順）:

| spec | 関心事 | engine への変更 |
|---|---|---|
| **S1（本 spec）** | 外装。配置・関数列・Shift・文字サイズ・部品の一般化 | **ゼロ** |
| S2 | 入力の意味論。`000`・`Exp`・後置 `j`・式エコー | あり（3 点 + 表示の導出） |
| S3 | Service Worker 更新通知トースト | ゼロ |
| L / D | Loan と Data Scale の電卓化（万/億、K/M/G） | ゼロ（UI 層） |

**本 spec の完了条件は Scientific の外装が完成すること**。L/D が同じ部品を使う
前提で一般化するが、共通化の出来は L の採用時に測る（今ここで万/億は作らない）。

## §1 変えること

1. **日本の電卓の配置慣習に寄せる**。数字は標準グリッド、右列に `÷ × − +`、
   下段に `0`・`000`・`.`、`=`。
2. **制御キー（AC・DEL）はメインエリアの右上**。上部の関数列とは別の場所。
3. **複素数まわり（`j`・`▸∠`・`π`）を左端の列へ**。現状は四則の隣（右寄り）に
   あり、四則と左右が入れ替わる形になる。
4. **関数（sin/cos/tan/√/x²）は上部の薄い行**に移す。
5. **Shift キー**を関数列に置き、関数キーの第 2 面を用意する。
6. **キーの文字を大きく**する。
7. **キーパッドと表示を部品として一般化**し、L/D が別のキー集合で使えるように
   する。

## §2 盤面

```
┌────────────────────────────────────────────┐
│ echo:                     ← S2 が埋める（場所だけ確保）│
│ main:                                  0     │
│ DEG                                   RECT   │
├────────────────────────────────────────────┤
│ [Shift][sin][cos][tan][ √ ][ x² ]  ← 関数列（半高）  │
├────────────────────────────────────────────┤
│ [ j ] [ ( ] [ ) ] [DEL] [ AC ]  ← 制御は右上        │
│ [ ▸∠] [ 7 ] [ 8 ] [ 9 ] [ ÷ ]                 │
│ [ π ] [ 4 ] [ 5 ] [ 6 ] [ × ]                 │
│ [+/−] [ 1 ] [ 2 ] [ 3 ] [ − ]                 │
│ [Exp] [ 0 ] [000] [ . ] [ + ]  ← Exp/000 は予約     │
│ [DRG] [        =        ]                     │
└────────────────────────────────────────────┘
```

**この配置は既存製品の意匠を写したものではない。** 参考にするのは電卓一般の
**配置慣習と操作感まで**であり、配色・ボタン形状・書体・ロゴ・製品名は複製
しない（base-spec §3 Non-goals、§12）。

- `=` は下段で横に伸ばす（4 セル分）。左端列の最下段は `DRG`。
- `Exp` と `000` は**このキー集合に場所だけ確保し、無効表示にする**（§5）。

### 縦の配分（390×844、スマートフォン縦持ち）

| 要素 | 高さ |
|---|---|
| ナビ 3 タブ | 44 |

| メイングリッド 6 行 | 67 × 6 + gap 8 × 5 = 442 |
| padding と safe-area | 約 58 |

## §3 関数列と Shift

- Shift は**ワンショット**。押すと第 2 面になり、関数キーを 1 つ押すと第 1 面へ
  自動で戻る。もう一度 Shift を押せば解除（何も送らない）。実機の関数電卓と
  同じ操作感で、解除忘れによる誤送信が起きない。
- **Shift は UI 層の状態**である。押下で各ボタンが送るトークンが切り替わるだけ
  で、**engine に shift の概念を持ち込まない**。engine から見れば従来どおり
  単一トークンの列であり、reducer の純度も網羅網も変わらない。
- 第 2 面は今回ほぼ空である。本命（`asin`/`acos`/`atan`/`ln` 等）は M3 後半に
  入るため、**今回作るのは面を切り替える基盤と空きスロットの見せ方**であり、
  関数そのものは足さない。空きスロットは `disabled` + `aria-disabled` で
  「そこに何か来る」ことだけ示す。
- a11y: Shift は `aria-pressed` で面の状態を伝える。第 2 面のキーは
  `aria-label` も第 2 面の名前に切り替える（見た目だけ変えて読み上げが元の
  ままにならないこと）。

## §4 寸法とタッチターゲット — 44px の線をどこに引くか

**メイングリッドは 44px を守り、関数列は割る**（約 34px 高 × 約 54px 幅）。

判断の理由: ユーザー指示は「メイングリッドをこれ以上大きくする必要はない、
関数列はもう少し小さく」であり、関数列は今後増える見込みがある。メイン
グリッドを 88px に太らせて「半分 = 44px」を成立させる案もあったが、それは
指示と逆方向に働く。

**したがって E2E の 44px 検査はメイングリッド限定に絞る。**
base-spec §43 の線を自分で下げる判断なので、根拠を spec とテストの両方に残す:

- 44px はタッチの推奨最小であり、**押し間違いの実害は誤入力の重さに比例する**。
  メイングリッド（数字・四則・AC/DEL）は誤爆が計算そのものを壊すので 44px を
  守る。関数列は誤爆しても `sin` が 1 回余計にかかるだけで、`DEL` で戻せる。
- 関数列は**横幅 54px を確保**し、縦だけを詰める（指の当たりは横に広い）。
- テスト側にも同じ理由を書く。検査を仕様に合わせて緩めるのは最終手段であり、
  理由の記録が無いと次に読む人が「うっかり緩めた」と読む。

## §5 予約スロット — S2 が埋める場所

`000`・`Exp`・エコー行・Shift の第 2 面は、**S1 で場所だけ確保する**。

理由: これらを S2 で足すときに盤面を作り替えると、E2E のセレクタと配置の検査を
二度書くことになる。場所が先に決まっていれば、S2 の変更は「無効を有効にし、
トークンを配線する」だけで済む。

- `000`・`Exp`: `disabled` + `aria-disabled="true"`。押しても何も送らない。
- エコー行: 表示部に行の場所を作るが、S1 では**常に空**（`DisplayState` には
  触れない。S1 の Rust 変更はゼロ）。
- 第 2 面の空きスロット: 同上。

## §6 キーパッドと表示の一般化

L と D が同じ部品を使うことが決まっているので、**投機ではなく発注済みの
一般化**として次を行う。

- `Keypad` は「`KeyDef[]` と列数と行の高さクラス」を受け取る汎用グリッドにする。
  関数列（6 列・半高）とメイングリッド（5 列・正方）を同じ部品の 2 つの
  インスタンスとして描く——**この spec 自身が最初の 2 利用者**になるので、
  一般化が絵に描いた餅にならない。
- `layout.ts` はモジュール別に分ける（`scientific.ts` など）。キー集合の定義と
  部品を分離する。
- 表示部（echo 行 + main + ステータス）も同様に部品化する。**engine への依存は
  持たない**（現行どおりトークンを `onPress` で返すだけ）。
- ただし**完了条件は Scientific の完成**である。L で足りないと分かった一般化は
  L の spec で足す。今ここで L/D 用のキー（万/億、K/M/G）は作らない。

## §7 検証段（tiering、ci.yml 導出）

- **Rust の変更はゼロ**。`cargo test --workspace` は既定のスイープとして回す
  （約 5 秒。網羅列挙もこの中に含まれるが、対象は不変）。
- `pnpm typecheck` / `pnpm lint` / `pnpm test`（vitest）。
- **E2E 必須**。配置変更・a11y・44px の線引きはすべて実ブラウザでしか
  確かめられない（jsdom はアクセシビリティツリーを組み立てない）。
  - 新しい配置で全キーがアクセシブルネームで引けること
  - Shift のワンショット（押下 → 第 2 面 → 1 キーで復帰、`aria-pressed`）
  - **メイングリッドの全キーが 44px 以上**であること、関数列は横 44px 以上
  - 予約スロット（`000`/`Exp`/空き）が `disabled` で、押しても何も起きないこと
  - 既存の E2E がキー配置に依存していれば、アクセシブルネーム基準に直す

## §8 スコープ外

- `000`・`Exp`・後置 `j`・式エコーの**挙動**（S2）
- Service Worker 更新通知トースト（S3）
- 万/億・K/M/G・アクティブ項目（L / D）
- 第 2 面に載せる関数そのもの（`asin`/`ln` 等。M3 後半）

## §9 完了条件

1. 盤面が §2 の配置になり、関数列と Shift が §3 のとおり動く。
2. メイングリッドの 44px が E2E で守られ、関数列を例外とした理由がテストに
   書かれている。
3. 予約スロットが場所を確保し、押しても何も起きないことが E2E で固定されて
   いる。
4. `Keypad` と表示部が関数列とメイングリッドの両方を描いており、キー集合が
   モジュール別に分かれている。
5. Rust の変更がゼロであること（`git diff --stat crates/` が空）。
