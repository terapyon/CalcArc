この文書はその §12 段階 3 のうち、**新しい関数と定数だけ**を扱う。

## 1. なぜやるか

main を取り込んだ結果、`KEY_TOKENS` は 46 個になった。**このコーパスが押しているのは
23 個で、残る 23 個は 6000 件を通して一度も押されていない**（`heavy-report.md` が
走行ごとに実データから導いている）。**電卓のキーのちょうど半分が未検証である。**

未押下の 23 個は、必要な機構で 5 つに分かれる。

| 部分系 | キー | データ形式 |
|---|---|---|
| **A 関数と定数**（本書） | `pow` `ln` `log10` `exp_e` `recip` `asin` `acos` `atan` `n_fact` `n_p_r` `n_c_r` `pi` `e` | **そのまま使える** |
| B 入力レジーム | `dot` `zeros3` `exp` `dms` | そのまま（キー列が変わるだけ）。3 つは相互排他 |
| C 訂正操作 | `ac` `del` | 同値ケースとして書ける |
| D モードと複素数 | `angle_toggle` `polar_toggle` `j` `eng` | `mode` と `expect.im` が既にある |
| E エラー経路 | （キーではない） | **`expect` の拡張が要る** |

**A を最初にやる理由は 2 つある。**

1. **23 個中 13 個を一度に埋める。** データ形式を変えずに済み、2 経路検証の機構
   （Rust が食う / Python が独立に評価する）がそのまま乗る
2. **A が E の設計に必要な実測を生む。** `ln(負)`・`asin(範囲外)`・階乗の溢れは、
   いま生成器が黙って捨てている領域である。A を入れれば**どの種類のエラーが何件
   出るかが測れる**。E をその実測の上に設計できる

## 2. 実装の事実（`crates/calcarc-core/src/scientific/mod.rs` から確認、2026-08-16）

| 関数 | 定義域 | 定義域外の返り値 | 備考 |
|---|---|---|---|
| `ln` `log10` | `x > 0` | `DomainError` | |
| `exp_e` | 全実数 | — | 溢れは `Overflow`。**`Key::Exp`（指数入力）とは別物** |
| `recip` | `x ≠ 0` | **`DivisionByZero`**（`DomainError` ではない） | |
| `asin` `acos` | `−1 ≤ x ≤ 1` | `DomainError` | **返す角度は `AngleMode` に従う** |
| `atan` | 全実数 | — | 同上 |
| `pow` | 下記 | `DomainError` / `Overflow` | 右結合・優先順位 4 |
| `n_fact` | 非負整数 | `DomainError` | 反復積。溢れは `Overflow` |
| `n_p_r` `n_c_r` | 非負整数かつ `r ≤ n` | `DomainError` | 溢れは `Overflow` |

`pow` の定義域は表に収まらないので分けて書く（`mod.rs:156`）:

- `0^0 = 1`（電卓の慣行）、`0^正 = 0`、**`0^負 = DomainError`**
- **底が負で指数が非整数は `DomainError`**（複素数になるため）
- それ以外は `powf`。`NaN` が出たら `DomainError`、溢れは `Overflow`

**`n_c_r` は「割ってから掛ける」（`acc / (i+1) * (n−i)`、`mod.rs:276`）。**
実装のコメントによれば、素直な `n!/(r!(n−r)!)` は `200 nCr 100` で落ち、
掛けてから割る形は `n = 1022`〜`1028` の中心二項係数で**答は収まるのに**落ちる。
`ncr_does_not_overflow_on_the_way_to_an_answer_that_fits`（`mod.rs:574`）が
その性質を守っている。

## 3. 設計

### 3.1 系統ごとに 3 枚のシャードを足す

`UNARY_FNS` / `BINARY_OPS` のタプルに足すと**乱数の消費列が変わり、既存 6000 件が
総入れ替えになる**（3c 設計 §3.2 で実測済みの性質）。したがって既存の生成器は触らず、
**新しい生成器と新しいシャード**として足す。

| シャード | 演算 | 定義域の性質 |
|---|---|---|
| `elementary-000.json` | `ln` `log10` `exp_e` `recip` `pow` | 引数の符号・ゼロ・溢れ |
| `inverse-trig-000.json` | `asin` `acos` `atan` | 引数が `[-1, 1]`、結果は角度 |
| `combinatorics-000.json` | `n_fact` `n_p_r` `n_c_r` | 非負整数、`r ≤ n`、溢れ |

**分ける理由は、制約が系統ごとに全く違うことである。** 1 つの生成器に 3 種類の
定義域制約を持たせると、**どの制約が何件を落としたのか分からなくなる**。
そして「どの種類が何件落ちたか」が §3.6 のとおり E の設計の入力である。
赤が出たときにどの系統かが即分かる、という利点もある。

各シャード 2000 件。既存 6000 件と合わせて **12000 件**になる。

### 3.2 定義域は「Python が独立に判定する」。engine を模倣しない

生成した木を捨てるかどうかは、**Python が mpmath と Python の整数演算で判定する**。
`scientific/mod.rs` の判定を写してはいけない——写した時点で、
**同じバグが両側に入って検証の意味がなくなる**（CLAUDE.md、および 3c で実際に踏んだ）。

具体的には、`corpus_eval` が投げた例外を `OutOfShard` として扱う:

- `ln(x)` は `x <= 0` で Python 側が落ちる
- `asin(x)` は `|x| > 1` で落ちる
- `1/x` は `x == 0` で落ちる
- 階乗・順列・組合せは Python の**厳密な整数**で計算し、`float()` に落とすときに
  `OverflowError` が出たら捨てる

**この方針の要点は組合せ論にある。** 絞る条件は**「答が f64 に収まるか」だけ**で、
engine が途中で溢れるかどうかは一切考えない。もし「engine が溢れないように」絞れば、
それは engine の実装を模倣することであり、独立性が消える。

**答が収まる限り生成し、engine が返せなければ不一致として赤くなる。** これが正しい。
`mod.rs:574` が守っている性質を、**このコーパスが規模で独立に検証する網になる。**

### 3.3 逆三角関数は角度モードを跨ぐ

`sin` は引数を `AngleMode` で解釈するが、**`asin` は結果を `AngleMode` に変換して返す**
（`mod.rs:121` の `mode.angle_of(...)`）。既存シャードは `sin(rad(x))` という形で
「引数側の変換」を式木に持たせている。逆関数はその**対称形**が要る。

木の表現: `Un("asin", child)` を Python は `deg(asin(child))` として評価する
（`mode` が `Deg` のとき）。`to_expr_text` も `deg(asin(...))` と書く。
**`mode` フィールドは既存の `Deg` を使い、この段階では動かさない**——
角度モードの切り替えそのものは部分系 D の主題である。

### 3.4 定数 `pi` と `e` は、3 枚すべてにオペランドとして混ぜる

**現行 6000 件のオペランドはすべて整数リテラルである。** つまり `current` に
**有理でない値が入ることが一度も起きていない**——丸めの経路が入力側から到達されて
いない。定数を入れると、そこが初めて踏まれる。

木の表現: `Num` の兄弟として `Const("pi")` / `Const("e")` を足す。
キー列はそれぞれ `pi` / `e` の 1 打鍵。Python は mpmath の `mp.pi` / `mp.e` を
50 桁で使う。engine は f64 の `PI` を使うので相対差は 1e-16 程度で、
表示の 10 桁（`rel = 5e-10`）に対して 6 桁の余裕がある。

**ただし増幅する式では話が別である。** §3.7 のとおり、まず一様に生成して実測する。

### 3.5 `pow` は括弧で完全に囲む。結合方向は踏まない

`xʸ` は**このプロジェクト唯一の右結合**で、優先順位も 4（既存は最大 2、`nPr`/`nCr` が 3）。
コーパスは結合方向を一度も検証していないので、ここで一緒にやりたくなる。**やらない。**

3c が「優先順位」と「結合方向」を分けた理由と同じである——**新しい関数の検証と
結合方向の検証を混ぜると、赤が出たときにどちらが原因か分からなくなる。**
このシャードの直列化は既存の `to_keys`（二項を必ず括弧で囲む）を使う。

**代償を正直に書く。** このシャードは優先順位も結合方向も検証しない。
`pow` の右結合と優先順位 4 は未検証のまま残り、レポートがそう書き続ける。
それらは独立した段階の主題である。

### 3.6 棄却の内訳を、系統ごと・理由ごとに数える

3c の Task 4 で、棄却理由の内訳（`dropped_nothing` が全試行の 53.45% など）を
実測して記録した。**同じことを、理由をエラーの種類まで割って行う。**

数えるもの: 系統ごとに、`domain`（定義域外）/ **`division_by_zero`（`recip(0)`）** /
`overflow`（f64 を超えた）/ `out_of_range`（値が `1e-6`〜`1e9` の帯の外）/
`bare`（裸のリテラル）/ `dup`。

**`division_by_zero` を `domain` と分けるのは、engine が分けているからである**
（`mod.rs:183` — 「`DomainError` は『その値には定義が無い』を言うために新設した名前で、
0 除算はそれとは別に既に名前を持っている」）。E はエラーの**名前**を検証することに
なるので、いまから区別して数えておかないと、E の設計が名前を 1 つ取りこぼす。

**これは統計のためではない。E（エラー経路）の設計の入力である。**
いま「エラー経路を検証する」と言えても、**どの種類のエラーが実際にどれだけ
出るのかを誰も知らない**。A を入れれば測れる。E はその上に設計する。

### 3.7 許容は変えない。まず一様に生成して測る

`rel = 5e-10` は「表示が有効数字 10 桁」から導いた値で、**桁に依らない**
（3a 設計 §2）。関数が増えても表示の桁数は変わらないので、**この値は動かさない。**

ただし新しい関数には**桁落ちする場所**がある——`ln(x)` は `x` が 1 に近いところ、
`asin(x)` は `x` が ±1 に近いところで、導関数が発散する。そこでは表示の丸めから
導いた許容を正当に超えうる。

**対処は 3a で作った機構をそのまま使う**: `corpus/overrides.json` に、
`expr` と数値つきの理由を書いた名前つきの上書きを置く。上限（`1e-6`）も
そのまま効く。**全体の許容を緩めることは絶対にしない。**

**「悪くなる場所を狙って測る」帯は、この段階では入れない。** 別セッションの実測で
「無作為抽出が中心二項係数を取りこぼし、格子で測ると最悪値が悪化した」という例が
あるので、狙い撃ちは有効である。しかし**いま入れると、どれだけ上書きが要るかを
知らないまま設計することになる。** まず一様に測り、その数を見てから決める。

## 4. やらないこと

- **`UNARY_FNS` / `BINARY_OPS` を触らない**（§3.1）。既存 6000 件を作り直さない
- **結合方向と優先順位を検証しない**（§3.5）。`pow` は括弧で囲む
- **角度モードを切り替えない**（§3.3）。`mode` は `Deg` のまま。部分系 D の主題
- **エラーを期待値として表現しない**（§3.6）。定義域外は捨てて数えるだけ。E の主題
- **許容の判定（`withinTolerance` / `classify`）を変えない**（§3.7）
- **UI を通らない。** 本物のボタン操作は段階 4 の主題である

## 5. 要件

### 生成

- **R1** 3 枚の新シャード `elementary-000.json` / `inverse-trig-000.json` /
  `combinatorics-000.json` を足す。**既存シャードを 1 件も作り直さない**
- **R2** 各生成器は独自の `random.Random(seed)` を持ち、既存シャードの乱数に触れない
- **R3** 定義域の判定は **Python 側の独立な計算**（mpmath と Python の整数）で行う。
  `scientific/mod.rs` の判定を写さない
- **R4** 組合せ論を絞る条件は**「答が f64 に収まるか」だけ**。engine の途中値を模倣しない
- **R5** 定数 `pi` / `e` を 3 枚すべてにオペランドとして混ぜる
- **R6** `asin` / `acos` / `atan` は結果を `AngleMode`（`Deg`）に変換したものを期待値とする
- **R7** `pow` は既存の `to_keys` で直列化する（二項を必ず括弧で囲む）
- **R8** 再生成一致ゲートの対象に含める（`corpus/generated/` の全ファイルを列挙する
  既存の仕組みに自動で乗る）

### 計測

- **R9** 棄却の内訳を**系統ごと・理由ごと**（`domain` / `overflow` / `out_of_range` /
  `bare` / `dup`）に数え、`docs/corpus-measurements.md` に実測値として記録する
- **R10** 必要になった `corpus/overrides.json` の件数と、各々の数値つきの理由を記録する。
  **全体の許容は変えない**

### レポート

- **R11** 未押下キートークンの行が **23/46 から 10/46 に減る**ことを、走行が
  データから導いて示す（手で書き換えない）
- **R12** `pow` の右結合と優先順位 4 が**未検証のまま**であることを書き続ける

## 6. リスク

- **上書きが何件必要になるか分からない。** `ln` と `asin` の桁落ちする帯がどれだけ
  引かれるかは測っていない。**多すぎたら、それは許容の問題ではなく生成の帯の問題**
  なので、帯を狭める（§3.7 の「まず一様に測る」がこのため）
- **組合せ論の棄却率が高くなりうる。** 非負整数・`r ≤ n`・答が f64 に収まる、の
  3 条件は乱択に対してきつい。3c の `dropped_nothing` が全試行の 53% だった例が
  あるので、**実装の最初に測る**。高すぎたら生成側で `n` と `r` の引き方を変える
  （分布を歪めるので、実測を見てから決める）
- **`exp_e` の引数の帯は、値の帯からほぼ一意に決まる。** f64 が溢れるのは `exp(710)`
  あたりだが、**既存の値の帯（`1e-6`〜`1e9`）のほうがずっときつい**——`exp(x)` が
  その帯に入るのは `x ∈ [-13.8, 20.7]` だけである。つまり `exp_e` は「溢れて捨てられる」
  より先に「帯の外で捨てられる」。**溢れの棄却をこの関数で観測するのは難しい**ので、
  溢れの実測は組合せ論と `pow` から取ることになる。R9 の内訳がそれを示すはず
- **`pi` / `e` が入ると `expr` の可読性が落ちる。** `expr` は人間が読むための
  文字列で検証には使っていない（上位設計書 §5 の訂正）が、投稿者が読む場所でもある。
  定数は `pi` / `e` と素直に書く
