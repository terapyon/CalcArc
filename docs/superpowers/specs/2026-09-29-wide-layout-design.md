**2026-09-29。起点は `2b478f0`（= v1.0.0）。** 利用者の裁定で、**1.1 は「広げるだけ」、
キーの並べ替え（Shift の裏を表に出す）は 1.2** に分ける。

**この文書が決めるのは 1.1 の範囲**である。1.2 の内容は §6 に置く——**1.1 の仕組みが

## 1. 測って分かったこと

**この節は実測と一次資料だけ。** 判断は §2 から。

### 1.1 キーの大きさは幅から決まる

```
キーの一辺 = (画面幅 − 56) ÷ 5
             ↑ パネルの padding 12×2 = 24、gap 8×4 = 32
```

`ScientificPanel.module.css:6` の `padding: 12px`、`tokens.css:17` の `--key-gap: 8px`、
`Keypad.module.css:9` の `repeat(var(--keypad-columns), 1fr)` から。

**390px で 66.8px** ——`panel-sizing.spec.ts:90` が実測値 **67px** を `toBe` で固定しており、
**式はその数と合う**。

### 1.2 スマホ横持ちは、広げても収まらない

Scientific の盤面の高さは `関数列 34 + 第2関数列 34 + (5 行 × キー + 4×8) + 区画の隙間 16`
（`tokens.css:60` の `--function-row-height: 34px`、`Keypad.module.css:43-45` の
`aspect-ratio: 1/1`）。

| 画面幅 | キーの一辺 | 盤面の高さ |
|---|---|---|
| 390px | 66.8px | 450px |
| 480px（いまの上限） | 84.8px | 540px |
| **44px（最小に潰した場合）** | 44px | **336px** |

**iPhone の横持ちは高さ 390px 前後**で、そこに Nav・表示欄・Footer も乗る。
**キーを床の 44px まで潰しても入らない。** **正方キーは幅に比例して縦も伸びる**ので、
**広げると悪化する。**

→ **横持ちを本当に直すのは「行を減らす＝列を増やす」**であり、**それは 1.2 の内容**である。

### 1.3 いまの棚卸し（すべて 2026-09-29 に `2b478f0` で数えた）

| 項目 | 現状 |
|---|---|
| `@media` | **2 件**（`tokens.css:73` `prefers-color-scheme` / `:105` `prefers-contrast`）。**どちらも色だけ** |
| 幅・高さ・向きの `@media` | **0 件** |
| `matchMedia` / `ResizeObserver` / `innerWidth` | **すべて 0 件**（`web/src`、テストを除く） |
| `position: sticky` | **1 件**（`ManualPage.module.css:21` の戻るリンク）。**表示欄は貼り付いていない** |
| `safe-area-inset-left` / `right` | **0 件**（`bottom` は 3 件） |
| 横位置（高さ < 幅）の E2E | **0 件**。E2E の幅は 7 種・高さは 7 種あるが、**組み合わせはすべて縦長** |
| landscape の Playwright project | **0 件**（project は `mobile` と `webkit` の 2 つ、どちらも 390×844） |

### 1.4 キー配置はデータであり、計算コアは無関係

`web/src/ui/Keypad/types.ts:49-60`:

```ts
interface KeypadSection<T> { ariaLabel: string; columns: number;
                             height: "square"|"half"|"double"; keys: KeyDef<T>[] }
```

**列はデータ**（`Keypad.tsx:64` が `--keypad-columns` に注入）。**行は「配列長 ÷ 列数」で
暗黙に決まる**——型にも CSS にも「行」は無い。**JSX に個別のキーは 1 つも無い。**

Shift の切り替えは **1 行**（`Keypad.tsx:85`）:
```ts
const face = shifted && key.shift ? key.shift : key;
```
**裏を持つのは Scientific の 10 キーだけ**（`scientific.ts` に `shift:` が 10 件。
ほかの 5 モジュールは 0 件）。

**`asin`・`acos`・`atan`・`n!`・`nPr`・`nCr`・`π`・`e` は、すでに `Key::ALL`（46 個、
`crates/calcarc-core/src/engine/key.rs:175`）に在る。** **「裏を表に出す」は新しいキーを
作る話ではない**ので、**`crates/` も `engine_table.rs` も動かない。**

## 2. 決めたこと

### 2.1 範囲

| 対象 | 1.1 で | 理由 |
|---|---|---|
| **タブレット（縦・横とも）** | **広げる** | 高さが足りるので、大きくしても収まる |
| **スマホ横持ち** | **「短い画面」として扱う**——はみ出さない・全キーに届く・**表示欄が見えている**ことだけ保証。**1 画面に収まることは約束しない** | §1.2 のとおり、**配置を変えない限り不可能** |
| **スマホ縦持ち** | **変えない**（1px も） | 回帰を 0 にする |

### 2.2 段は 1 つ。**短辺 700px**

```css
@media (min-width: 700px) and (min-height: 700px)
```

**「短辺が 700px 以上」と同じ意味**である。**スマホは横持ちでも短辺が 430px を超えない**
ので入らず、**iPad はどの向きでも入る。**

**768px にしない理由**: `iPad mini`（第 6 世代）の縦持ちの幅は **744pt** と思われるが
**測っていない**。**700px にすれば、この不確かさに答えが依存しない。**
（**利用者は mini と Pro(M1) の 2 台を持っており、実機で当てられる。**）

### 2.3 キーの大きさに**天井**を付ける

**床はすでに在る**——`Key.module.css:2-3` の `min-width/min-height: var(--touch-target-min)`
（44px）。**対になる天井を足す。**

```css
/* tokens.css */
--touch-target-max: 88px;

/* Keypad.module.css — 変更は 2 行 */
.section {
  grid-template-columns:
    repeat(var(--keypad-columns), minmax(var(--touch-target-min), var(--touch-target-max)));
  justify-content: center;
}
```

**板の幅は、画面からではなく「列数 × キー」から決まる。**

**この形を選んだ理由は 3 つ。**

1. **390px では 1px も変わらない。** いまキーは 66.8px で**天井に触らない**。
   **`panel-sizing.spec.ts` の `366px` も `67px` も緑のまま**である。
2. **1.2 が自動で乗る。** 列数は既に `--keypad-columns` として注入されている。
   **10 列ならキーの並びは `10×88 + 9×8 = 952px`、パネル込みで 976px** ——**新しい仕組みを
   足さずに数字が出る**（**ただし 1.2 では `--shell-max-width` も一緒に上げる必要がある**
   ——560px のままでは 952px のキーが入らない。§6 に書いた）。
3. **既存の考え方の対称形。** `Keypad.module.css:11-23` の註は
   「**ブレークポイントを増やさずに連続的に縮ませる**」。**天井はその逆向き。**

**88px を選んだ理由**: いまの実質最大が **84.8px**（480px 幅のとき）。
**利用者の裁定「横幅はそこまで大きくしなくて良い。間延びしないくらい」**（2026-09-29）
に従い、**いまの最大のすぐ上**に置く。

### 2.4 枠は広げるが、写しは触らない

```css
@media (min-width: 700px) and (min-height: 700px) {
  :root { --shell-max-width: 560px; }
}
```

**トークン 1 つで 13 の参照が追随する**ので、**8 つのパネル CSS の写しは触らない。**

**共通化は今回やらない。** **パネルごとに違う幅が要るとわかった日**にやる——
いまは要らない（`panel-sizing.spec.ts:48` が「**すべての電卓が同じ幅**」を守っており、
**その約束を保ちたい**）。

**560px という値の内訳**: パネルの内側は `560 − 24 = 536px`。そこに **5 列 × 88px ＋
隙間 4×8 = 472px** のキーが**中央に載る**（左右に 32px ずつ余る）。
**表示欄・Nav・Footer は 560px いっぱいまで使う。**

**12.9 インチの Pro（1024×1366）では、1.1 では左右に 230px ずつの余白が残る。**
**その余白を使うのが 1.2** である。**1.1 の目的は、余白を埋めることではなく、
1.2 が乗る仕組みと番人を用意すること**である。

### 2.5 マニュアル画面は、逆向きに手当てする

`ManualPage.module.css` に `max-width` が **0 件**で、**いま既に本文が画面幅いっぱいに
伸びている**。**タブレットでは 1 行が長くなりすぎて読みにくい。**
**本文に読みやすい幅の上限を 1 行足す。**

### 2.6 短い画面：表示欄を貼り付け、左右の安全域を足す

**表示欄が見えなくなる穴は、横持ちのために生まれるのではなく、いまも在る。**
短い画面ではスクロールして押すことになり、**そのとき答えが画面の外に出る。**

```css
@media (max-height: 500px) {
  .readout { position: sticky; top: 0; z-index: 1; }
}
```

**高さで切る**（`orientation` では切らない——**タブレットの横持ちは高さが足りる**ので
貼り付ける必要がない）。**縦持ちの 844px は影響を受けない。**

**左右の安全域は外枠 1 か所**（`App.module.css` の `.shell`）に置く。
**下端には足さない**——`ScientificPanel.module.css:7-11` が
「**下端はフッタが持つ。ここで吸うと二重になり、standalone 起動でだけ下が 44px 伸びる**」
と、**過去に踏んだ罠として書き残している。** **同じ間違いを左右で繰り返さない。**

## 6. 1.2 へ残すもの

- **JS の幅判定**（`matchMedia`）——**いまアプリに 0 件**。**「裏を表に出す」はデータの
  差し替えなので、CSS だけでは切り替えられない**
- **広い面のデータ**（Scientific の新しい `KeypadSection[]`）
- **`--shell-max-width` を、1.1 の 560px からさらに上げる**——**§2.3 のとおり 10 列の
  キーは 952px を要る**ので、**560px のままでは広い面が入らない。** **1.1 では上げない**
  （**5 列のままで 560px を超えても、余白が増えるだけで誰も得しない**）
- **`j` の裏は `action: "history"` でトークンを送らない**——**「裏を表に」すると
  そこだけ履歴ボタンが盤面に出る。** 扱いを決める
- ⚠️ **`heavy/tests/ui/keys.ts:66-73` はトークンの重複で例外を投げる。**
  **広い面に narrow と同じトークンを置くと、ここが最初に爆発しうる**（未確認・要設計）
- **`scientific.test.ts` の並び固定テスト**（`:53-64`・`:70-78`・`:91-99`・`:170-177`・
  `:181-190`）は**狭い配置を固定している**。広い面を別の定数にすれば影響しないはずだが**未確認**

**どちらにも入れないもの**: 8 つのパネル CSS の共通化／320px／**横持ちで 1 画面に収めること**。

## 7. 未確認（この文書が測っていないこと）

- **`iPad mini`（第 6 世代）の縦持ちの幅**。744pt と思われるが測っていない。
  **§2.2 の 700px は、この不確かさに依存しない値として選んだ。**
- **`panel-sizing.spec.ts:96-102` が 768×844 で緑のままか**（§4.2）
- **貼り付けた表示欄が `short-screens.spec.ts` の被り判定（`elementFromPoint`）に
  引っかかるか。** 引っかかったら、**それが正しい鳴り方かどうかを先に判断する**
- **`tools/check-boundary.mjs` の中身**（44px の見張りの実体）は読んでいない。
  **#5 を足すときに読む**
- **貼り付けが効く位置関係**。`.shell` は `display: flex` の縦並びで、
  **`position: sticky` の基準はパネル**になる。**パネルが画面から出ていくときに
  一緒に流れてしまわないか**は、実装で確かめる（**理屈では、パネルが画面の高さより
  高いので貼り付く**が、**測っていない**）
- **横持ちの表示欄の穴が、いまの短い画面（375×629）でも赤くなるか**——
  **段取り 2 で撮る**（撮れなかったら、この設計の前提が 1 つ崩れる）
