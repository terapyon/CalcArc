## 1. 測って分かったこと

**この節は実測と一次資料だけ。** 判断は §2 から。

### 1.1 キーの大きさは幅から決まる

```
キーの一辺 = (画面幅 − 56) ÷ 5
             ↑ パネルの padding 12×2 = 24、gap 8×4 = 32
```

`ScientificPanel.module.css:6` の `padding: 12px`、`tokens.css:17` の `--key-gap: 8px`、
`Keypad.module.css:9` の `repeat(var(--keypad-columns), 1fr)` から。

**390px で 66.8px** ——`panel-sizing.spec.ts:90` が実測値 **67px** を `toBe` で固定しており、
**式はその数と合う**。

### 1.2 スマホ横持ちは、広げても収まらない

Scientific の盤面の高さは `関数列 34 + 第2関数列 34 + (5 行 × キー + 4×8) + 区画の隙間 16`
（`tokens.css:60` の `--function-row-height: 34px`、`Keypad.module.css:43-45` の
`aspect-ratio: 1/1`）。

| 画面幅 | キーの一辺 | 盤面の高さ |
|---|---|---|
| 390px | 66.8px | 450px |
| 480px（いまの上限） | 84.8px | 540px |
| **44px（最小に潰した場合）** | 44px | **336px** |

**iPhone の横持ちは高さ 390px 前後**で、そこに Nav・表示欄・Footer も乗る。
**キーを床の 44px まで潰しても入らない。** **正方キーは幅に比例して縦も伸びる**ので、
**広げると悪化する。**

→ **横持ちを本当に直すのは「行を減らす＝列を増やす」**であり、**それは 1.2 の内容**である。

### 1.4 キー配置はデータであり、計算コアは無関係

`web/src/ui/Keypad/types.ts:49-60`:

```ts
interface KeypadSection<T> { ariaLabel: string; columns: number;
                             height: "square"|"half"|"double"; keys: KeyDef<T>[] }
```

**列はデータ**（`Keypad.tsx:64` が `--keypad-columns` に注入）。**行は「配列長 ÷ 列数」で

## 2. 決めたこと

### 2.1 範囲

| 対象 | 1.1 で | 理由 |
|---|---|---|
| **タブレット（縦・横とも）** | **広げる** | 高さが足りるので、大きくしても収まる |
| **スマホ横持ち** | **「短い画面」として扱う**——はみ出さない・全キーに届く・**表示欄が見えている**ことだけ保証。**1 画面に収まることは約束しない** | §1.2 のとおり、**配置を変えない限り不可能** |
| **スマホ縦持ち** | **変えない**（1px も） | 回帰を 0 にする |

### 2.2 段は 1 つ。**短辺 600px**

```css
@media (min-width: 600px) and (min-height: 600px)
```

**「短辺が 600px 以上」と同じ意味**である。**スマホは横持ちでも短辺が 440px を超えない**
ので入らない（`iPhone 16 Pro Max` の 440。**レビュー役の記憶で、未実測**）。

**★ 700px から 600px へ下げた**（2026-09-29、レビュー役の阻止 A1 を受けた監視役の裁定。
**利用者の確認待ち**）。

**理由**: **この条件が当たるのは「画面の短辺」ではなく「viewport」**である。
**Safari のタブで開くと、ツールバーの分だけ横持ちの高さが短辺より小さい。**
700px だと `iPad mini`（短辺 744 と思われる。未実測）で**余裕が 44px しかなく**、
**ツールバーがそれを超えれば、横持ちの mini がタブレットと判定されない。**
**600px なら余裕は 144px** で、**スマホ（短辺 440）はなお入らない。**

**初稿の「iPad はどの向きでも入る」は未実測の断定だったので取り下げ、§7 に移した。**

**数は 1 か所にしか書かない**（この `@media` の条件）。**実機で測ったあとに動かせる形**に
してある——**トークンにしない**のは、**トークンにすると「どこで使われているか」を
追う必要が出る**ためである。

### 2.3 キーの大きさに**天井**を付ける

**床はすでに在る**——`Key.module.css:2-3` の `min-width/min-height: var(--touch-target-min)`
（44px）。**対になる天井を足す。**

**★ 実現の仕方を差し替えた**（2026-09-29、レビュー役の条件 B1 を受けた監視役の裁定。
**利用者の確認待ち**）。**初稿は `minmax()` と `justify-content: center` で列を止める形**
だったが、**区画ごとに効くので段差ができる**——560px の枠（内側 536）では、
**正方の区画（5 列）は 472px に縮んで中央へ寄り、関数列（7 列）は `(536−48)÷7 = 69.7px`
で 536px いっぱいに広がる。** **数字の板だけが左右 32px ずつ内側に入る。**

**代わりに、枠の幅そのものを天井から導く。**

```css
/* tokens.css — 床の隣に天井を置く */
--touch-target-max: 88px;

/* tokens.css — 段の中で、枠を天井から導く */
@media (min-width: 600px) and (min-height: 600px) {
  :root {
    /* 5 列 × 88px ＋ 隙間 4 × 8px ＋ パネルの padding 12px × 2 = 496px */
    --shell-max-width: calc(5 * var(--touch-target-max) + 4 * var(--key-gap) + 24px);
  }
}
```

**`Keypad.module.css` は触らない。** **すべての区画が同じ幅のまま**なので段差が出ず、
**正方のキーはちょうど 88px に着地する**（`(496 − 24 − 32) ÷ 5 = 88`）。

**枠の幅は選ぶものではなく、キーの天井から出てくる数である**——これがこの節の主張であり、
**番人 #2（キーが 88px を超えない）はその不変条件を見ている。**

**この形を選んだ理由は 3 つ。**

1. **390px では 1px も変わらない。** **段に入らない**（390 < 600）ので `--shell-max-width` は
   480px のまま、キーは 66.8px。**`panel-sizing.spec.ts` の `366px` も `67px` も緑のまま**である。
2. **1.2 は式の `5` を変えるだけで乗る。** **10 列なら
   `10×88 + 9×8 + 24 = 976px`** ——**新しい仕組みを足さずに数字が出る。**
3. **触るファイルが 1 つで済む。** `Keypad.module.css` の grid は**いまのまま**
   （`repeat(var(--keypad-columns), 1fr)`）。**区画どうしの幅が揃うという既存の性質を壊さない。**

**88px を選んだ理由**: いまの実質最大が **84.8px**（480px 幅のとき）。
**利用者の裁定「横幅はそこまで大きくしなくて良い。間延びしないくらい」**（2026-09-29）
に従い、**いまの最大のすぐ上**に置く。

### 2.4 枠は広げるが、写しは触らない

**§2.3 の `@media` が `--shell-max-width` を 480px → 496px にする。**
**トークン 1 つで 13 の参照が追随する**ので、**8 つのパネル CSS の写しは触らない。**

**共通化は今回やらない。** **パネルごとに違う幅が要るとわかった日**にやる——
いまは要らない（`panel-sizing.spec.ts:48` が「**すべての電卓が同じ幅**」を守っており、
**その約束を保ちたい**）。

**496px の内訳**: パネルの内側は `496 − 24 = 472px`。そこに **5 列 × 88px ＋ 隙間 4×8**
がちょうど収まる。**表示欄・Nav・Footer も 496px** で、**すべてが同じ幅で揃う。**

**★ 1.1 でタブレットの見た目はほとんど変わらない**（480 → 496px、キーは 84.8 → 88px）。
**利用者に確認済み**（2026-09-29「間延びしないくらいの大きさで」「このまま進めましょう」）。
**12.9 インチの Pro（1024×1366）では、左右に 264px ずつの余白が残る。**
**その余白を使うのが 1.2** である。**1.1 の目的は、余白を埋めることではなく、
1.2 が乗る仕組みと番人を用意すること**である。

### 2.5 マニュアル画面は、逆向きに手当てする

`ManualPage.module.css` に `max-width` が **0 件**で、**いま既に本文が画面幅いっぱいに
伸びている**。**タブレットでは 1 行が長くなりすぎて読みにくい。**
**本文に読みやすい幅の上限を 1 行足す。**

### 2.6 短い画面：表示欄を貼り付け、左右の安全域を足す

**短い画面ではスクロールして押すことになり、そのとき答えが画面の外に出る。**

**★ 初稿の「この穴は横持ちのために生まれるのではなく、いまも在る」は、測ったら偽だった**
（2026-09-29、検証役の実測）。

| 寸法 | 最後のキーまで送ったときの表示欄の上端 |
|---|---|
| 390×664・390×651・375×667・375×629（**既存の 4 寸法**） | **画面の中**（4 つとも緑） |
| **844×390** | **−266.8px**（画面の外） |
| **667×375** | **−281.8px**（画面の外） |

**穴は在るが、「前から在った」のではない**——**横持ちを見るようにしたから、初めて見えた。**
**直す理由は変わらないが、理由の書き方は変わる。**

```css
/* **横持ちでは、答えが上に残る。** 最後のキーまでスクロールすると表示欄が画面の外へ出る
   ——844×390 で上端が −266.8px、667×375 で −281.8px（2026-09-29 に E2E で実測）。
   **既存の 4 寸法（高さ 629〜667）では起きていない。** */
@media (max-height: 500px) {
  .readout { position: sticky; top: 0; z-index: 1; }
}
```

**★ 500px は、測った数の間にある**（2026-09-29）。**赤は高さ 390・375、緑は 629〜667。**
**どちらの側からも 100px 以上離れている。** **レビュー役の阻止 A4 は「500px では
`SAFARI_VIEWPORTS` に効かない」だったが、実測で `SAFARI_VIEWPORTS` は効かせる必要が
無かった**——**懸念は正しく、答えは逆向きに出た。**

**条件なしにしない理由**: **緑の 4 寸法でも貼り付くことになり、いま通っている寸法の
見え方が変わる**（あそこも 127〜165px スクロールする）。**変える理由が無い所は変えない。**

**左右の安全域は外枠 1 か所**（`App.module.css` の `.shell`）に置く。
**下端には足さない**——`ScientificPanel.module.css:7-11` が
「**下端はフッタが持つ。ここで吸うと二重になり、standalone 起動でだけ下が 44px 伸びる**」
と、**過去に踏んだ罠として書き残している。** **同じ間違いを左右で繰り返さない。**

## 6. 1.2 へ残すもの

- **JS の幅判定**（`matchMedia`）——**いまアプリに 0 件**。**「裏を表に出す」はデータの
  差し替えなので、CSS だけでは切り替えられない**
- **広い面のデータ**（Scientific の新しい `KeypadSection[]`）
- **`--shell-max-width` を、1.1 の 560px からさらに上げる**——**§2.3 のとおり 10 列の
  キーは 952px を要る**ので、**560px のままでは広い面が入らない。** **1.1 では上げない**
  （**5 列のままで 560px を超えても、余白が増えるだけで誰も得しない**）
- **`j` の裏は `action: "history"` でトークンを送らない**——**「裏を表に」すると
  そこだけ履歴ボタンが盤面に出る。** 扱いを決める
- ⚠️ **`heavy/tests/ui/keys.ts:66-73` はトークンの重複で例外を投げる。**
  **広い面に narrow と同じトークンを置くと、ここが最初に爆発しうる**（未確認・要設計）
