# 打ち方と訂正を検証する（段階 G）設計

2026-08-17

前提: [重量級検証コーパス（Layer 6）設計](2026-08-15-heavy-corpus-e2e-design.md)。

## 1. なぜやるか

`KEY_TOKENS` は 46 個。**36 個は押されているが、10 個は一度も押されていない。**

この設計書は、そのうち **5 個**——`dot` `zeros3` `exp`（打ち方）と
`ac` `del`（訂正）——を扱う。残る 5 個（`j` `polar_toggle` `angle_toggle`
`eng` `dms`）は表示の形か値の型に触るので、別の段階にする。

**この 5 個を先にやる理由は、`dot` にある。**

いまの生成器はオペランドを**整数リテラル**としてしか作らない。したがって:

- **小数点を打つ経路が一度も通っていない。** 電卓には表示の規則が 2 つあり
  （`render()` の分岐）、入力中は打った文字がそのまま出て、確定した値だけが
  整形を通る。**入力側のレジームが丸ごと未検証**である
- **「結果は出るが間違っている」領域に届かない。** 実測（2026-08-16）:

  | 場面 | 相対誤差 | 表示 10 桁に出るか |
  |---|---:|---|
  | `1234567.891 − 1234567.890` | 1.639e-7 | **出る** |
  | `sqrt(1e9+1) − sqrt(1e9)` | 1.562e-7 | **出る** |
  | `ln(1.0000001)` | 5.839e-10 | **出る** |

  **どれも小数点を打たないと作れない。** エラーは自分で名乗るが、
  **もっともらしく間違った数は名乗らない**——独立実装が唯一の武器になるのは
  そこである。

`ac` / `del` を同じ段階に入れるのは、**期待値の形を変えないから**である。
どちらも同値ケースとして書ける（下記 §3.3）。

## 2. 実装の事実（`engine/state.rs` から確認、2026-08-17）

| キー | 挙動 |
|---|---|
| `dot` | 2 つ目の小数点は **`SyntaxError`**。**指数入力中は黙って無視**（打ち間違いで計算を止めない）。桁が空なら先頭に `0` を補う |
| `zeros3` | `push_digit(0)` を **3 回**。先頭ゼロの規則は仮数と共通 |
| `exp` | 指数入力を始める。**既に指数入力中なら何もしない。60 進入力中も何もしない**（入力モードは相互排他） |
| `del` | 段は **指数の桁 → `e` マーカー → 仮数の文字 → `j` マーカー** の順。バッファが尽きたら**閉じていない開き括弧**を 1 つ消す。演算子は消さない |
| `ac` | `cleared()`。**角度モード・表示形式・記法は保つ**（利用者の設定なので） |

**入力モードは 3 つで相互排他**（仮数のみ / 仮数 + 指数 / 60 進）。
本段階が触るのは前の 2 つで、60 進（`dms`）は別段階に送る。

## 3. 設計

### 3.1 葉を「整数」から「打ち方」に広げる

**`Num` は 1 文字も触らない。** あれは既存 16000 件の乱数と直列化の土台で、
振る舞いを変えれば**全シャードが総入れ替えになる**（3c 設計 §3.2 で実測済み）。
**`Typed` を新しいノード型として足し、新しいシャードだけが使う。**

`Typed` は**打鍵の列と、その厳密な値の両方を持つ**。

```python
@dataclass(frozen=True)
class Typed:
    """打った通りのキーと、その厳密な値。

    **値は文字列から Decimal で作る。** float を経由すると、
    生成の時点で丸めが入り、engine と同じ誤差を両側に持ち込むことになる。
    """
    keys: tuple[str, ...]   # 例: ("1", "dot", "5")
    text: str               # 例: "1.5"（`expr` に出る形）
```

生成する打ち方は 3 通り:

| 打ち方 | キー列の例 | 値 |
|---|---|---|
| 整数（既存） | `1` `2` `3` | 123 |
| **小数** | `1` `dot` `5` | 1.5 |
| **`000` を使う** | `5` `zeros3` | 5000 |
| **指数入力** | `1` `dot` `5` `exp` `3` | 1500 |

**`zeros3` と `exp` は既存の値の帯を変えない。** `5 zeros3` は `5000` で、
帯（`1e-6`〜`1e9`）の中に収まる。**新しいのは「同じ値への別の打ち方」**である。

### 3.2 Python は文字列から厳密に読む。float を経由しない

**これが独立性の要である。** `Typed.text` は `"1.5"` のような十進の文字列で、
参照側は `mp.mpf(text)` で読む——`float(text)` を挟むと、
**生成の時点で engine と同じ丸めが入り、両側が同じ誤差を持つ**。

指数入力の値も同様に、`"1.5e3"` を文字列のまま読む。

### 3.3 訂正は同値ケースにする。期待値を持たない

`ac` と `del` は**打った結果を巻き戻す**キーで、**値の意味を持たない**。
だから「打ち間違えて直した列」と「打ち間違えない列」が**同じ表示に着く**
ことだけを主張する——期待値が要らない。

3 つの形を作る:

| 形 | 例 | 何を確かめるか |
|---|---|---|
| **余分な桁を消す** | `1` `2` `9` `del` ≡ `1` `2` | `del` が仮数の 1 文字を消す |
| **打ち直す** | `1` `9` `del` `2` ≡ `1` `2` | 消した後に続けて打てる |
| **`ac` でやり直す** | `<でたらめな列>` `ac` `<正しい列>` ≡ `<正しい列>` | `ac` が状態を初期化する |

**`del` を注入する位置は「数を打っている最中」に限る。** バッファが空のときの
`del` は開き括弧を消しに行くので、**別の意味になる**（§2）。位置を選ばずに
注入すると、同値でない対を作ってしまう。

**`ac` の形は強い主張である。** でたらめな列が何であれ、`ac` の後は初期状態から
始まるので、右辺と一致しなければならない。**ただし角度モードなどは保たれる**
ので、でたらめな列に `angle_toggle` を含めない（本段階では押さないので自然に満たす）。

### 3.4 桁落ちを狙い撃つシャードを足す

**これが `dot` の見返りである。** 乱択では桁落ちはほとんど起きない——
近い 2 数が偶然選ばれる確率が低い。**狙って作る。**

| 形 | 例 |
|---|---|
| 近接する 2 数の減算 | `1234567.891 − 1234567.890` |
| 平方根の差 | `sqrt(1000000001) − sqrt(1000000000)` |
| 1 に近い対数 | `ln(1.0000001)` |
| 大小の吸収 | `1000000000 + 0.000001` |
| 極の近傍 | `tan(89.9999)` |

**このシャードは「赤くなること」を目的にしない。** 目的は
**「表示された答が真の値と違う件数を測ること」**である。出たら
**発見として報告する**——許容の緩和で黙らせない（設計書 3a の規律）。

**engine のバグではない場合が多い。** f64 の性質であって実装の欠陥ではない。
しかし**利用者が見る表示が真の値と違う**ことに変わりはなく、
**このコーパスが言えるのは「表示された答えが間違っている」**である。
その区別を保ったまま件数と分布を報告する。

### 3.5 レポートの整理を同じ段階で行う

ユーザ指摘（2026-08-17）: **過去の経緯の言い訳と、初見の読み手が追えない
内部参照が本文に混ざっている。**

- 本文は**「何を確かめて、結果はどうだったか」だけ**にする
- 内部参照（設計書の節番号、`.rs` / `.spec.ts` のファイル名）は**付録に落とす**。
  消さない——検算したい人には要る
- 過去の誤りへの言及は原則消す。**例外は「いま現に測っている限界」**
  （巨大角度の三角関数の上書き 2 件など）で、それは経緯ではなく現在の事実
- 骨格は **判定表・検出力の表・踏んでいない領域** の 3 つ

## 4. やらないこと

- **`j` `polar_toggle` `angle_toggle` `eng` `dms`**——表示の形か値の型に触る。別段階
- **60 進の入力モード**（`dms`）。入力モードは 3 つで相互排他だが、本段階は 2 つ
- **既存シャードを作り直さない。** 新しいシャードとして足す
- **許容を変えない。** 桁落ちで超えたら**発見として報告する**

## 5. 要件

- **R1** `Typed` を足し、**打鍵の列と厳密な十進文字列の両方**を持つ
- **R2** 参照側は `mp.mpf(text)` で**文字列から読む**。`float()` を経由しない
- **R3** 打ち方は 4 通り（整数 / 小数 / `zeros3` / 指数入力）を生成する
- **R3a** **`zeros3` は先頭に置かない。** 空のバッファに打つと先頭ゼロの規則で
  `"0"` に潰れる（実測、§6）。**0 でない桁を 1 つ以上打った後にだけ使う**
- **R3b** **`Num` を変更しない。** `Typed` は新しいノード型として足し、
  新しいシャードだけが使う。既存 16000 件は 1 件も作り直さない
- **R4** 訂正は**同値ケース**で書く。期待値を持たない
- **R5** `del` の注入位置は**数を打っている最中**に限る
- **R6** 桁落ちを狙うシャードを別に足す。**許容を緩めない**
- **R7** レポート本文から経緯と内部参照を落とす（§3.5）
- **R8** 未押下キーが **10 → 5** に減ることを、レポートが実データから示す
- **R9** 再生成一致ゲートの対象に含める

## 6. リスク

- **`dot` の `SyntaxError`（2 つ目の小数点）を踏むと、値ケースが作れない。**
  生成器は 1 つの数に小数点を 2 つ打たないので自然に避けるが、
  **訂正の同値ケースで `del` を打つ位置によっては踏みうる**。位置の制約（R5）で防ぐ
- ~~**`zeros3` の先頭ゼロの規則が未確認。**~~ **実測した（2026-08-17、`state.rs:269`）。**
  先頭ゼロの規則は `digits == "0"` なら消してから足す形なので、
  **空のバッファに `zeros3` を打つと `"000"` ではなく `"0"` になる**
  （3 回とも同じ枝を通る）。`5 zeros3` は正しく `5000`。
  → **要件にした（R3a）。** 推測のままなら期待値が食い違っていた
- **桁落ちのシャードは赤くなりうる。** それは失敗ではなく発見だが、
  **`pnpm heavy` が赤いとワークフロー全体が落ちる**。
  件数を測ってから、このシャードを別のテストに分けるか判断する
- **レポートの整理でテストが赤くなる。** 文言に依存したテストが複数ある。
  **それは仕掛けが働いている証拠**なので、テスト側も一緒に直す
