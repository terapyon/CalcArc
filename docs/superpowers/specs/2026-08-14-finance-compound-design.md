## §0 位置づけ — 何を作るか、なぜ今できるか

M6（Loan）が作った資産——分数の `Rate`、各行 floor の厳密整数ループ、
逆算の二分探索、Python 独立実装と `finance.json`、免責表示——は
**ほぼそのまま複利に使える**。ローンは「借りた金が減っていく表」、複利は
「預けた金が増えていく表」で、1 期あたりの演算は同じ
`floor(残高 × 分子 / 分母)` である。

loan-design §11 のロードマップでは複利・積立は「第 4 モジュール」として
**変動金利（北極星）の後**に置かれていた。しかし**依存関係としては独立**で、
`schedule.rs` 本体を触らずに `Rate` + 新しいループで足りる。今回の要望は
この先取りに相当する（§13 Q4 の判断材料）。

**製品方針は M6 と同じ「決定的概算」を引き継ぐ**: 実額一致は非目標
（金融機関ごとに付利単位・丸め・利払日が違う）、同じ入力は常に同じ答、
計算方法は本 spec に明文化して Python 独立実装で検証、UI に免責を常設。

**このゲートを spec の構造そのものに組み込む。** plan のタスク順序を次に固定し、

## §2 スコープ（Q5）— 3 つの選択肢

| | 内容 | 入力 | 出力 |
|---|---|---|---|
| (a) | **一括預入の複利** | 元本・年利・期間・複利周期 | 満期元利合計・利息・（税オプションで手取り） |
| (b) | **毎月積立** | 毎月の積立額・年利・期間・積立タイミング | 満期の資産額・元本合計・運用収益 |
| (c) | **両方** | 上の合併 | 上の合併 |

**Fable/実装側の推奨は (c)**。理由: (a) と (b) は**同じ 1 期ループの上に載る**
——(b) は各期の頭または末に一定額を足すだけで、コアの追加は数行である。
別々の spec に割ると §1 のゲート（数値方針・Python 参照・golden）を 2 回
踏むことになり、そちらのコストの方が大きい。

**(c) を採った場合の完了条件案**（§14 に再掲）:
- 一括・積立の両方が golden 完全一致
- 丸め方式（§4）の裁定が両方に一貫して適用されている
- 積立の逆算（目標額から必要積立額）は**スコープ外**（§12）

**(a) だけを採った場合**: 完了条件から積立関連を落とす。UI のモードは
「複利」1 つ。**(b) だけ**は勧めない——資産形成の主題は積立だが、
一括のケースは積立ループの `m=0` として自然に落ちるので、除外しても
実装が減らない。

## §3 数値経路 — M6 の規律をそのまま引く

**答は厳密整数ループが出す。f64 は逆算の候補にしか使わない。**

M6 の numerical-policy「第 3 の分類」がそのまま適用される:

- **1 期の演算**: `bal += floor(bal × 分子 / 分母)`（`Rate::monthly_interest_floor`
  がこの関数そのものである。u128 中間、u64 残高）。
- **積立**: 期末型なら利息計算の**後**に積立額を足す（§5）。
- **f64 の居場所**: 「目標額に到達する期数」「目標額に必要な月額」のような
  逆算の**候補**を閉形式で出すときだけ。**答は候補の近傍を厳密ループで
  歩いて確定する**——M6 の逆算で 167 円の系統差を実測した経験がここに効く
  （閉形式の答と厳密表の答は一致しない。表が正である）。
- **`pow_1p` の抽出**: `(1+r)^n − 1` は素朴に計算せず `expm1(n·log1p(r))` で
  評価する。**この式は現在 3 箇所に重複している**（実測: `closed_form.rs` に
  2 箇所（`x_n` と `x_m`）、`inverse.rs:99` に 1 箇所。調査メモの「2 箇所」は
  過少）。さらに年金現価 `(x/(x+1))/r` も `closed_form.rs` と `inverse.rs:100`
  の 2 箇所に重複している。**`pow_1p(r, n)` と `annuity(r, n)` の 2 つを
  抽出する**（重複解消を同乗させ、新規の重複を作らない）。
  `inverse.rs:64` の `−ln_1p(−ratio)/ln_1p(r)`（期間逆算）は別の式なので
  抽出対象外。

**オーバーフロー**: 複利は単調増加なので、u64 の上限（約 1.8×10^19 円）に
到達しうる。到達したら `Overflow`（base-spec §25）。ローンは残高が減るので
この経路が無かった——**新設のエラー経路であり、golden にケースが要る**。

## §4 丸め方式の二者 — 本 spec の心臓部

**同じ入力に対して 2 つの正解がある。** これが複利計算の最大の設計判断で、
ローンには存在しなかった論点である。

| | 銀行方式 | シミュレータ方式 |
|---|---|---|
| 各期の利息 | **円未満切り捨てて元本組入**（付利単位 1 円） | 丸めない |
| 表示時 | そのまま | 最後に 1 回だけ丸める |
| 実装 | 厳密整数ループ | 高精度の閉形式 or 有理数 |
| 既存規律との親和 | **高い**（M6 と同型） | 低い（f64/Decimal が答を出す） |

### 実測: 差は無視できる大きさではない

100 万円・年 1%・5 年・半年複利（§9 の種 ①）:

```
銀行方式（各半期 floor して元本組入）: 1,051,136 円
シミュレータ方式（1,000,000×1.005^10 を最後に切捨）: 1,051,140 円
差: 4 円
```

**この種は調査時に「銀行の公開例と一致」として採録されたが、一致していたのは
シミュレータ方式の値の方である**（1,051,140）。つまり**銀行が公開している
試算例が各期切り捨てを実演しているとは限らない**。「銀行方式」という呼称は
慣行の名前であって、特定の銀行の公開値の裏付けではない——spec にこう
書いておかないと、後で「銀行の例と合わない」と誤って直される。

税額はさらに 2 円ずれる（利息が 4 円違うため）:

```
銀行方式    : 利息 51,136 → 国税 7,831 + 地方税 2,556 = 10,387
シミュレータ: 利息 51,140 → 国税 7,832 + 地方税 2,557 = 10,389
```

### floor の意味が反転する（根拠文の書き換えが要る）

M6 の numerical-policy は「全金銭計算、円未満切り捨て」を 1 語で決めており、
その**根拠は「切り捨ては安全な向き」**だった——ローンでは月額が理論値を
下回るぶん残高が高めに残り、端数は最終回が吸収する。借主に不利な方向へは
倒れない。

**積立・預金では向きが反転する。** 各期の利息を切り捨てるのは
**受取を減らす向き**であり、利用者に不利である。「切り捨て = 安全」という
根拠文はここでは成り立たない。

**それでも切り捨てを採る根拠は別にある**: 実際の金融機関が付利単位 1 円で
切り捨てるので、**切り捨てた方が実際に受け取る額に近い**。つまり根拠が
「安全な向き」から「**慣行の再現**」に変わる。numerical-policy にはこの
違いを明記する——同じ 1 語（切り捨て）でも、なぜそうするかが分野で
違うことを残さないと、後から「利用者に不利だから直そう」という誤った
修正が入る。

### 選択肢（§13 で裁定）

- **(A) 銀行方式のみ**: 最も単純。既存規律と一直線。
- **(B) 両方式をモードとして持つ**: 利用者が「銀行の通帳と合わせたい」と
  「よくあるシミュレータと合わせたい」の両方を選べる。**golden は別系統に
  なる**（同じ入力で期待値が 2 組）。
- **(B′) 方式をモードに固定で紐付ける**（検討して捨てた案）: 一括預入は
  銀行方式、積立はシミュレータ方式と決め打ちし、利用者にオプションを
  見せない。各分野の慣行に沿う点は魅力だが、**golden が 2 系統になるのは
  (B) と同じ**で、コスト論は変わらない。加えて「同じアプリの中で 2 つの
  丸め規律が黙って共存する」ことになり、numerical-policy の 1 語で
  説明できなくなる。
- **(C) シミュレータ方式のみ**: 資産形成の文脈では多数派だが、
  **f64/Decimal が答を出す形になり §3 の規律と衝突する**。採るなら
  numerical-policy に例外を書く必要がある。

**推奨は (A)**。理由: §3 の規律を曲げず、ローンと一貫し、golden が 1 系統で
済む。(B) は魅力的だが、**丸め方式は「オプション」ではなく「別の計算」**で
あり、全ケースの期待値が倍になる。まず (A) で出し、要望が出たら (B) を
別 spec で足す方が安い。

## §5 複利周期と月利換算 — 2 方式が実在する

### 周期

調査（2026-08-14）の結果:

- 投資・積立シミュレータ: **月次複利**
- 銀行預金（スーパー定期の複利型）: **半年複利**が業界標準
- 年複利: FP 教育の世界

→ **周期はパラメータ化する**（月 / 半年 / 年）。`Rate::from_percent` は現在
**分母に月次（×12）がハードコード**されているので、頻度を受ける形に変える。
`half_year()` が既にあるので、`yearly()` を足すのは 3 行である。

### 月利換算は 2 方式あり、金融庁が乗り換えた

| 方式 | 式 | 使う所 |
|---|---|---|
| 名目 | `r/12` | M6 のローン、旧・金融庁つみたてシミュレーター |
| 実効 | `(1+r)^(1/12) − 1` | 新・金融庁つみたてシミュレーター（2025 年に変更） |

**差の実測**（毎月 3 万円・期末積立・30 年）:

| 年利 | `r/12` | `(1+r)^(1/12)−1` | 差 |
|---|---|---|---|
| 1% | 12,588,846 | 12,579,852 | 0.07% |
| 3% | 17,482,106 | 17,361,391 | 0.70% |
| 5% | 24,967,759 | 24,461,277 | 2.07% |
| 7% | 36,599,129 | 35,083,578 | 4.32% |

**調査メモにあった「30 年で約 4.3% 差」は年 7% の場合の数字**である。
低金利帯では 0.1% を切る。spec には「率に強く依存する」と書き、
単一の数字で語らない。

**注意**: 金融庁つみたてシミュレーターの**公式仕様は非公開**で、上記は
第三者解析に依拠している。**golden の種にするなら実機突き合わせが必要**
——「金融庁と一致」を完了条件に書いてはならない（検証不能な目標になる）。

### 積立タイミング

**既定は期末**（月末）。明記しているシミュレータは期末型が多数派で
（三菱UFJ AM・野村が明記）、Excel の `FV` の既定も期末である。
式は年金終価 `((1+r)^n − 1)/r`。期首型はオプション（§12 でスコープ外に
するかは Q5 と連動）。

## §6 税

**既定はタックスフリー**（NISA 前提）。投資系シミュレータの標準であり、
資産形成の主用途に合う。

**オプションで源泉分離課税 20.315%**。ここが他のシミュレータとの差別化に
なりうる。実装の要点:

- **国税 15.315% と地方税 5% を別々に円未満切り捨て**（国税庁 タックスアンサー
  No.1310）。合算して 20.315% を掛けて 1 回切り捨てるのとは**結果が違う**。
- 課税対象は利息（元本を除く）。
- **税の逆算は一意でない**: 「税引後 1,000 円」になる額面は **1,253 円と
  1,254 円の 2 つある**（実測）。

  ```
  1,253 → 国税 191 + 地方税 62 → 手取り 1,000
  1,254 → 国税 192 + 地方税 62 → 手取り 1,000
  ```

  これは M6 の残価逆算で踏んだ「**階段関数の像に目標がある場合、逆像が
  区間になる**」問題と同型である（`residual_target` の対策がそのまま使える）。
  逆算をスコープに入れるなら**どちらを返すかを決めて spec に書く**
  （推奨: 小さい方 = 利用者が余計に払わない向き）。

## §7 実装方針

### モジュール構造

M6 は `crates/calcarc-core/src/loan/` に置いた。複利をどこに置くかで
**F0 の §1（内部名を改名しない）の前提が動く**:

- **(i) `finance/` を新設し `finance::{loan, compound}` に再配置** ——
  base-spec:189 の空き枠に合う。`loan` の移動は機械的だが、
  `calcarc_core::loan::*` を参照する wasm/テストに波及する。
- **(ii) `compound/` を `loan/` と並べる** —— 移動ゼロ。ただし木の上では
  ローンと複利が同列に見え、`finance` の枠は空いたまま。

**推奨は (i)**。F1 は本体が大きいので、ここで構造を整えないと
`loan::compound`（= 名前の嘘）に落ちる。ただし**再配置は独立のコミットに
分ける**（API 整理 PR #19 と同じ方式。移動と機能追加を同じ diff に混ぜない）。

### 再利用できるもの（調査済み）

| 資産 | 使い方 |
|---|---|
| `Rate`（分数） | そのまま。ただし `from_percent` の**分母の月次ハードコードを頻度パラメータ化** |
| `monthly_interest_floor` | **1 期の利息そのもの**。複利 1 期は `bal += rate.interest_floor(bal)?` |
| `parse_yen` | そのまま |
| `inverse.rs` の二分探索 | 必要積立額・必要年数の逆算に流用 |
| `residual_target` の像対策 | 目標額逆算・税逆算で同じ問題が起きる（§6） |
| WASM 境界 / TS ラッパー / golden エンベロープ | パターンをそのまま踏襲 |

### 落とし穴（調査で判明）

1. **`schedule.rs` のコメント「利率列を受けられる形」は未実装**。変動金利は
   シグネチャ変更で全 caller に波及する。F1 では触らない。
2. **f64 の `(1+r)^n` を答に使うのは既存規律違反**（§3）。
3. **floor の向きの意味が反転**（§4）。根拠文の書き換えが要る。

## §8 Python 参照の独立軸（base-spec §30）

**ここが本 spec で最も難しい設計判断である。**

各期 floor の複利を Python で書くと `int` ループになり、**Rust と同型の
アルゴリズムになる**——base-spec §30（逐語的に実装しない）に抵触する。
同じ実装バグが両方に入れば検証の意味が消える。

M6 は「月額導出は Decimal 閉形式 / 償還表は int で愚直に」の二層で解いた。
その先例に沿った選択肢:

- **(a) Decimal 閉形式との差を検証に使う**（推奨）: Python は
  `P × (1+r)^n` を高精度 Decimal で評価し、**厳密整数ループとの差が
  期数 × 1 円以内**であることを確認する。さらに **golden の期待値自体は
  int ループが出す**が、閉形式が独立の番人として横に立つ。
- **(b) `Fraction` で厳密有理数の閉形式**: リポジトリ初使用。厳密だが、
  各期 floor が入ると閉形式が存在しないので、**丸めなし方式（§4 の C）
  にしか使えない**。
- **(c) 何もしない**（int ループのみ）: §30 に抵触。採らない。

**推奨 (a)**。ただし**「同じ丸め契約は共有する」**ことを明記する——
「各期の利息 = `floor(残高 × 分子 / 分母)`」は M6 と同じく**両者共通の公開契約**
であり、アルゴリズムの共有ではない（契約を知らなければ独立検証は書けない）。

**境界近接ガードは Python 生成側が担う**（M6 と同じ）: 理論値が円境界の
`max(1e-6, |値|·1e-9)` 以内に来るケースは golden に入れない。

## §9 golden（`testdata/finance.json` に op 追加）

**新ファイルを作らない。** base-spec 855 行の 4 ファイル列挙（`scientific` /
`complex` / `data_scale` / `finance`）を動かさずに済み、`finance.json` は
tolerance なし・`Input` が既に合併型なので、**op を足すのが素直な線**である。

### ハーネスの一般化（同時に必要）

`crates/calcarc-core/tests/finance_golden.rs` は現在 loan の 3 op に固定
されている。必要な変更:

- `Input` に複利用フィールドを追加（`monthly_deposit` / `periods_per_year` /
  `tax` など。すべて `#[serde(default)] Option<_>`）。
- `run(op, input)` の `match` に新 op を追加（`other => panic!` はそのまま
  ——未知 op が黙って通らないのは良い性質）。
- **id 重複チェックはリスト結合後に直す**（ケースが 2 系統になるため）。

### 必須ケース（案）

- **§4 の種 ①**（100 万・年 1%・5 年・半年複利）を**採用する丸め方式で**
- **一括**: 周期 3 種（月/半年/年）× 金利 0%（利息ゼロの退化）
- **積立**: 期末・毎月 3 万・年 3%・20 年（`r/12` で 9,849,059 — 実測済み）
- **月利換算 2 方式の差**を固定するケース（§5 の表から 1 組）
- **u64 オーバーフロー**（§3。新設のエラー経路）
- **積立額 0 = 一括の退化恒等式**（(c) を採る場合）
- **税**: §6 の 2 例（別切り捨てが合算切り捨てと違うことを示す組）
- **1 期だけ**、**最長期間**、**元本 0**（`SyntaxError`）

### 赤確認（案。新設検査は壊して赤を見てから信じる）

1. 各期 floor を「最後に 1 回 floor」に変える → §4 の 4 円差で赤
2. 税を合算 20.315% の 1 回切り捨てに変える → §6 の例で赤
3. 積立を期首に変える → 積立ケースで赤
4. 月利換算を他方に変える → §5 のケースで赤

**M6 の教訓**: 赤確認は**実際に赤になることを実出力で確かめる**。多層防御が
効いていて赤にならない場合は、**そのことを正直に報告し、等価な強さの変異に
差し替える**（M6 の【訂正 2c】が先例）。

## §10 UI（この spec の主戦場ではない）

**本 spec は計算コアと検証を主戦場とする。** UI の詳細は実装 spec を分ける。

方向だけ決めておく:

- **Finance タブの中のモード追加**。L が作った「求めるもの」のモード行が
  そのまま器になる（`LoanKeyToken` の `mode:*` と同じ形）。
- モードは `ローン` / `複利` / `積立`（§2 の裁定による）。
- 入力項目はモードごとに開閉する——L の `fieldEnabledIn(field, mode)` が
  先例（**モードを引数に取る**こと。L のレビューで「モード切替時に無効項目が
  active に残る」バグを踏んでいる）。
- **免責の常設**は M6 と同じ（「実際の利息は金融機関の計算方法により
  異なります」の趣旨）。**税オプションを出すなら税務上の助言ではない旨も
  要る**。

## §14 完了条件

§13 の裁定を Q5=(c)・Q6=(A)・Q7=(a) と仮定した場合:

1. **§1 の段順が守られている**（数値方針 → Python 参照 → golden → Rust）。
   `docs/numerical-policy.md` に複利の節があり、**floor の根拠が「安全な向き」
   から「慣行の再現」に変わったこと**（§4）が明記されている。
2. 一括・積立の両方が `testdata/finance.json` の golden と**完全一致**
   （tolerance なし）。
3. 赤確認 4 種（§9）の**実出力**がある。赤にならないものは正直に報告し、
   等価な変異に差し替えてある。
