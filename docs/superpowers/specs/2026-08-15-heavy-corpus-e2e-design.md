# 重量級検証コーパス（Layer 6）設計

2026-08-15

## 1. 目的

「この電卓は計算が正しい」を、**普段の開発とは別の軸から、桁違いの件数で**確かめる。
そして、その確認を**外部の人間が見て納得でき、外部の人間が件数を増やせる**形にする。

既存のテスト階層（base-spec §31 の Layer 1〜5）は、開発の速度を守るために意図的に小さい。
`testdata/*.json` は 28〜85 件で、これは毎 PR で再生成して一致を確認するための規模であって、
「数多く試した」と言える規模ではない。本設計はその上に、普段は回さない層を一つ足す。

## 2. 非目標

- **既存のテストを置き換えない。** Layer 1〜5 は今のまま、今の速度で回り続ける。
- **UI の見た目・操作性を検証しない。** それは既存の `web/tests/e2e/` の担当。
- **未知のバグを探索しない。** コーパスは固定で、毎回同じものを回す。乱数探索は本設計の範囲外。
- **表示精度より深い数値精度を検証しない。** 理由は §6.3。

## 3. 位置づけと呼び名

新しい層を **Layer 6** と呼ぶ。

なお現状、層番号は二箇所で食い違っている。base-spec §31 は
「1 Unit / 2 Property / 3 WASM / 4 Python Reference / 5 Browser E2E」、
`ci.yml` のコメントは「1-4 が cargo test / 5 が wasm-pack / 6 が playwright」。
本設計では base-spec §31 を正とし、`ci.yml` のコメントを実装時に合わせて直す。

## 4. コーパス

### 4.1 置き場所

トップレベルに `corpus/` を新設する。

```
corpus/
  generated/     scientific-000.json … 生成物。手で編集しない
  contributed/   *.json               人が書く。ジェネレータは絶対に触らない
```

**`testdata/` の下に置いてはならない。** `ci.yml` の `reference` ジョブは
`uv run python scripts/generate.py` を実行したあと `git diff --exit-code testdata/` で
「コミット済み golden は再生成と一致すること」を検査している。数万件のコーパスをここに
置くと、毎 PR で SymPy による大量再生成が走り、CI が実用的な時間で終わらなくなる。
性格も違う——`testdata/` は毎 PR で再生成一致を確認する小さい golden、`corpus/` は
リリース時にだけ再生成する大きい固定資産である。

`generated/` と `contributed/` をディレクトリで分けるのは事故防止のため。ジェネレータは
`generated/` を丸ごと上書きしてよいが、`contributed/` を上書きしたら投稿が消える。
ディレクトリ境界で分けておけば、この事故が仕組みとして起きない。

### 4.2 ファイル分割

「電卓の種類 × シャード番号」で分割し、1 ファイル 2000 件程度に収める。

```
corpus/generated/scientific-000.json
corpus/generated/scientific-001.json
corpus/generated/complex-000.json
...
```

1 ファイルに数万件入れると `git diff` もレビューも成立しない。分割しておくと、
失敗したときに「どのシャードか」で原因が絞れ、並列実行の単位もそのまま取れる。

### 4.3 ファイルの形

トップレベルの形は既存 `testdata/*.json` に揃える。

```json
{
  "schema": 1,
  "generated_by": "mpmath 1.3.0 (50 dps), Python 3.14",
  "tolerance": { "abs": 1e-9, "rel": 1e-9 },
  "cases": [ ... ]
}
```

`schema` が整数、`generated_by` が生成器の版という形は `reference/scripts/generate.py` の
既存の書き方に合わせたものである。`tolerance` も同スクリプトと同じ `abs` / `rel` の対にする。

`tolerance` はファイル単位である。**許容誤差をテストコードに書かない**という CLAUDE.md の
規約は、これで守られる。

上の `1e-9` は書式を示すための例である。**実測して確定した値は `{"abs": 5e-10, "rel": 5e-10}`**
（表示の有効数字 10 桁の最下位桁の丸め幅の半分。`docs/corpus-measurements.md`）。

**訂正（実装後）。** 当初この節は「必要なケースだけ個別に上書きできる」と書いていたが、
**ケース単位の上書きは実装されていない。** しかも書いても警告なく黙って無視される状態だった
（投稿者の視点からの検証で実測）。段階 3 のマグニチュード依存の許容と同じ機構になるので、
そこで一緒に実装する。それまでは、ケースに `tolerance` を書いたら**大きな声で拒む**。

**訂正（2026-08-16、段階 3a）。** 上の「段階 3 のマグニチュード依存の許容と同じ機構になるので、
そこで一緒に実装する」は**行き先を誤って指していた**。マグニチュード依存は段階 3a が明示的に
否定している（[段階 3a 設計](2026-08-16-corpus-tolerance-design.md) §2 — 実効的な相対許容を
膨らませていた真犯人は `abs` の床であって `rel` ではなかった）。ケース単位の緩和は
**`corpus/overrides.json` として実装済み**である（同 §3.3）。シャードのケースに `tolerance` を
書くことは**将来も許さない**——`corpus/generated/` は再生成一致ゲートが守る領域で、人の判断を
混ぜるとその保証が壊れる。生成は機械、例外は人。
（実装済み: `web/tests/heavy/corpus.ts` の `assertNoCaseTolerance()` が、シャード名・ケース id・
書かれていた値を名指しして throw する。この一文が書かれてから実装されるまでの間、`{abs: 1e30,
rel: 1e30}` を 1 件に足しても 43 passed / EXIT=0 で無警告だった——**設計書が約束したことを実装が
守っていない状態**が実在した。）

**合否基準がデータ側にあることの帰結。** 許容をテストコードから追い出した結果、シャードの
`tolerance` を書き換えれば何でも通る状態が一度生まれた（敵対的検証で実証）。塞ぎ方は二つで、
どちらも入れている——(1) 読み込んだ `tolerance` に正気の範囲を課す（閾値を決めるのではなく、
明らかに異常な値を弾く）、(2) §7.1 の再生成一致ゲートで、コミット済みシャードが生成器の
出力と一致することを毎回確かめる。

### 4.4 ケースの二種類

**値ケース (`kind: "value"`)** — 期待値を持つ。Python 参照実装が審判する。

```json
{
  "kind": "value",
  "id": "sci-004213",
  "mode": "Deg",
  "keys": ["3", "0", "sin", "add", "2", "sqrt", "="],
  "expr": "sin(rad(30)) + sqrt(2)",
  "expect": { "re": 1.914213562, "im": 0.0 }
}
```

**同値ケース (`kind: "equivalence"`)** — 期待値を持たない。二つのキー列の最終表示が
一致することだけを主張する。

```json
{
  "kind": "equivalence",
  "id": "eqv-000123",
  "mode": "Deg",
  "left":  ["2", "sqrt", "sqr", "="],
  "right": ["2", "="]
}
```

同値ケースは「往復して戻る」「別経路で同じ値に着く」「符号を二度反転すると元に戻る」を
すべて同じ一つの形で書ける。期待値が不要なので Python 参照が介在せず、投稿者にとっても
一番書きやすい。恒等式による検算はこの形に集約する。

なお Rust 側には既に property test（base-spec §31 Layer 2）がある。役割は重ならない——
あちらは `calcarc-core` を Rust から叩き、こちらは**出荷する wasm をブラウザで**叩く。

## 5. オラクル：二重表現

値ケースは**互いを知らない二つの経路**で同じ数に到達する。

- **Rust 経路** — `keys` を engine が順に食べ、表示を出す。
- **Python 経路** — 同じ式木を mpmath が 50 桁で評価する。

アルゴリズムを共有していないので、片方のバグがもう片方に伝染しない。CLAUDE.md の
「参照実装を Rust の移植にしない」は、この分離によって守られる。

**訂正（実装後）。** 当初この節は「Python 経路は `expr` を SymPy が解釈し mpmath が評価する」
と書いていた。実装は違う——Python 側は**式木を直接** mpmath で評価しており、SymPy は評価経路に
いない。二経路が独立であるという主張自体は変わらない（Rust はキー列を歩き、Python は式木を歩く）。

その帰結として、**`expr` は誰にも検証されない人間向けの説明文字列である。** 生成器が式木から
描き出すだけで、読んで値を出す経路がどこにも無い。これは §7.2 と §7.3 に直接効く（後述）。

**Python にキー列を渡してはならない。** 押した順の意味論（保留演算、括弧、モード切替）を
Python 側に実装した瞬間、それは engine の移植になり、検証の意味が消える。Python が見るのは
`expr` だけである。

### 5.1 残る結合（既知の弱点）

式木から `keys[]` を作る直列化は、「sin は数を入れてから押す」といった**記法の約束**を
知っている必要がある。これは計算ではなく表記なので移植には当たらないが、engine の記法が
変われば直列化も直す必要がある、という結合は残る。キー列と表示の対応は
`crates/calcarc-core/tests/engine_table.rs` が仕様なので、直列化はそれに従う。

## 6. 実行

### 6.1 二つの経路、一つのコーパス

```
corpus/**  ──┬── core 経路: 全件（数万件）
             └── ui   経路: 同じコーパスから抽出した代表 200 件
```

UI 側は別データではなく**同じデータの部分集合**なので、「UI 側だけ古い」というズレが
構造的に起きない。

抽出は **id のハッシュ順で決定的に**行う。シャードの先頭から取ると生成順の偏り（式木の
深さが浅いものが先に並ぶ、など）をそのまま拾ってしまう。ハッシュ順なら分布を保ったまま
決定的に選べる。

### 6.2 置き場所と設定

```
web/tests/heavy/            重い spec。既存の web/tests/e2e/ とは別ディレクトリ
web/playwright.heavy.config.ts
```

既存 `playwright.config.ts` の `testDir` は `./tests/e2e` なので、別ディレクトリに置けば
**既存 CI は構造的に拾わない**。「今の実装に影響しない」がコメントではなく仕組みで担保される。

`playwright.heavy.config.ts` は既存設定を踏襲する。特にポート **4179**（Vite 既定の 4173
ではない）は必ず維持する——4173 は他プロジェクトの preview を掴む事故が実際に起きている。
重い方は別ポート（4180、`--strictPort`）を使い、既存 E2E と同時に走っても衝突しないようにする。

### 6.3 core 経路が検証できる範囲

`web/src/calc` の公開 API は `initial()` と `dispatch(state, key)` だけで、結果は
`DisplayState.main` という**整形済みの文字列**である。数値をそのまま取り出す口はない。

したがって **Layer 6 が検証できるのは表示精度までである。** それより深い精度は Layer 1〜4 の
担当であり、本層は踏み込まない。`tolerance` は「コアの精度」ではなく「表示の桁数」に律速される
値として、シャードごとに設定する。実装時に実際の表示桁数を測って決める。

比較は「表示文字列を数値に戻して `tolerance` 内か」で行う。文字列の逆整形はテスト側に置くが、
許容誤差そのものはコーパスの JSON から読む。

### 6.4 ハーネスページ

core 経路は DOM を経由せず `calc.dispatch` を直接回すが、本番バンドルは `src/calc` を
グローバルに露出していないので、`page.evaluate` から素直には呼べない。

そこで **ハーネスページを 1 枚追加する**。`web/heavy-harness.html` とその入口が
`src/calc` を読み込み、`window.__calcarc` に露出する。

ビルドは既存 `vite.config.ts` を触らず、**`web/vite.heavy.config.ts` を別に持つ**。
既存設定に入口を足すと VitePWA の workbox がハーネスを precache に巻き込み、配信物の
Service Worker が変わってしまう。重い方の設定は PWA も React も持たない最小構成
（`wasm()` と `topLevelAwait()` のみ）にする。`deploy.yml` が作る配信物には入らない。

**正直に書いておく。** これにより「出荷するものそのもので確かめた」は厳密には成り立たない。
ただし差分はエントリ HTML が 1 枚多いことだけで、`src/calc` と wasm のバイナリは同一である。
UI 経路（§6.1）の方は本物のアプリを操作するので、そちらが出荷物そのものを踏む役を担う。

## 7. 生成と投稿

### 7.1 生成

`reference/scripts/generate_corpus.py` を新設する。

```
種を固定して式木を大量生成
  ├─ 式木 → keys[]                    （トークンへの直列化）
  ├─ 式木 → mpmath で 50 桁評価 → expect
  ├─ 式木 → expr                      （人が読むための描画。検証には使われない）
  └─ corpus/generated/*.json
```

**`generate.py` からは呼ばない。** 呼ぶと毎 PR の再生成一致チェック（§4.1）が数万件を
背負うことになる。再生成が一致することの確認は、重いワークフローの中でリリース時にだけ行う。

種を固定するので、同じ入力から常に同じコーパスが出る（固定コーパス）。

### 7.2 投稿

一般ユーザは `corpus/contributed/` にファイルを 1 つ足す PR を出す。

値ケースの `expect` は**必須**とする。書かせないと「電卓がこう言うならそうなんでしょう」に
なり、人間側の主張が記録されず、食い違いを検出する力が一つ減る。手計算が面倒な場合のために、
ローカルで参照実装に埋めさせるスクリプトを用意する。

書き方は `docs/corpus.md` に置く。`KEY_TOKENS` の 32 個の一覧、`expr` の記法、ローカルでの
回し方、値ケースと同値ケースの使い分け。

### 7.3 審判

投稿 PR には**軽い関門**が付く。差分にある値ケースだけを Python 参照にかけ、`expect` と
食い違えば赤。数秒で終わる。

これが「みんなで信憑性を確認する」の実体であり、レビュアーの目には依存しない。
人・Python・Rust の三者のうち、どれが外れているかが機械的に切り分けられる。

### 7.4 段階 5 に必要な実装（実装後に判明した見積り）

投稿の受け口は、ワークフローの YAML を書けば済む話ではない。縦の 1 本を通したあとに
投稿者の視点で検証した結果、§7.2 と §7.3 は次の実装を前提にしている。

- **`expr` テキストを値に戻すパーサ。** §7.3 の審判は投稿された `expr` を Python に評価させる
  もので、§5 の「Python にキー列を渡してはならない」がある以上、Python の入力は `expr` で
  なければならない。しかし現在あるのは式木 → テキストの**片方向**だけで、逆はどこにも無い。
  これを新規に書く工数を段階 5 の見積りに入れること。
- **期待値を埋めるローカルスクリプト（§7.2）。** 存在しない。上のパーサができれば書ける。
- **`loadShards()` の拡張。** 現在は `corpus/generated/` 固定なので、`contributed/` を
  作っただけでは投稿されたケースが一件も拾われない。
- **投稿の実行時検証。** 未知の `kind`・欠けたフィールド・壊れた JSON を**拒む**こと。
  縦の 1 本の実装では、未知の `kind` を持つケースが警告も出さずに消え、報告書の総件数からも
  外れる状態が一度生まれた（実証済み）。投稿を「無視する」のではなく「拒否してエラーにする」
  のでなければ、§7.3 の審判の前提が壊れる。JSON の構文エラーは**どのファイルが壊れているかを
  名指しし**、他の投稿を巻き込まないこと。
- **`docs/corpus.md` に `expr` の記法を明文化する。** 現在その規則は `to_expr_text` の
  実装が唯一の定義で、投稿者はコードを読まないと書けない。

## 8. 報告

数万件をバッチで回す以上、Playwright の標準レポート（1 test = 1 行）では何が落ちたか読めない。

- **core 経路は 1 シャード = 1 test。** `page.evaluate` は「不一致だったケースの配列」を返す。
  test は「不一致 0 件」を assert し、不一致があれば先頭 20 件を失敗メッセージに出し、
  全件を JSON に落とす。20 件は「端末で読める量」として選んだ上限で、全件は必ず JSON に残る。
- **実行後に `heavy-report.md` を生成する。** 総件数、シャード別内訳、値ケース／同値ケースの
  件数、観測された最大誤差、失敗一覧。
- この Markdown を artifact として upload する。タグ実行時はリリースにも添付する。

**この成果物が「他の人が見てこれなら大丈夫だと分かる」の実体である。** 緑のチェックマークは
「何を何件どこまでの精度で確かめたか」を答えない。

## 9. CI

**既存の `ci.yml` と `deploy.yml` は編集しない**（§3 の層番号コメント修正を除く）。
ワークフローを 2 本新設する。

### 9.1 `corpus-gate.yml` — 投稿の関門

```yaml
on:
  pull_request:
    paths: ['corpus/**']
```

`paths` フィルタにより、コーパスに触らない PR では**そもそも起動しない**。
Python 参照で差分のケースを検算する。数秒。

### 9.2 `heavy-e2e.yml` — 重い実行

```yaml
on:
  push:
    tags: ['v*']
  workflow_dispatch:
```

現状 `v*` タグを引き金にするワークフローは存在しないので、これが最初になる。
`deploy.yml` は `main` への push で走るため、タグとは干渉しない。

ジョブは wasm ビルド → ハーネス込みビルド → `playwright.heavy.config.ts` で実行 →
レポート生成 → artifact upload。シャード単位で matrix 並列にできる。

再生成一致の確認（§7.1）もここに入れる。

## 10. 既存への非干渉

「今の実装に影響しない」を、以下の**構造**で担保する。宣言や運用規約には頼らない。

| 干渉しうる経路 | 遮断の仕組み |
|---|---|
| 既存 E2E が重い spec を拾う | `testDir` が別（`tests/e2e` と `tests/heavy`） |
| 毎 PR の golden 再生成が重くなる | コーパスは `testdata/` の外（`corpus/`） |
| `generate.py` が数万件を背負う | 生成スクリプトが別ファイルで、呼び出し関係がない |
| 関係ない PR で重いジョブが起動する | `paths` フィルタと、タグ／手動のみのトリガ |
| 配信物にハーネスが混入する | ハーネスのエントリは重い実行用ビルドだけが含む |
| preview のポート衝突 | 既存 4179 と別の 4180、`--strictPort` |

## 11. リスクと未解決

- **表示精度の壁（§6.3）。** この層が言えるのは「表示される桁まで正しい」であって
  「倍精度の最後の桁まで正しい」ではない。報告書にこの但し書きを必ず載せる。
- **SymPy の生成時間という前提は実測で反証された。** `generate_corpus.py` は式の評価に
  `mpmath` しか使わず、SymPy は `_provenance()` の版文字列取得にしか登場しない
  (評価経路から SymPy の import ごと落ちている)。実測(docs/corpus-measurements.md)は
  生成 0.06ms/件、ブラウザでの実行 0.2ms/件(2000 件で 425ms)。**コーパスの上限を決める
  のは実行時間でも生成時間でもなく、式木が作れる形の空間の多様性の方である**(下記の
  「式木の分布」の項を参照)。段階 3 で SymPy を評価経路に使うジェネレータ(記号的簡約に
  よる同値対の生成など)を足すなら、そのときは本節と同じ手順で改めて実測すること。
- **式木の分布。** 乱択の設計次第で「大量に試した」が「同じような式を大量に試した」に
  なりうる。演算子の深さ、極値近傍（0、π/2、極）、複素数の分岐（負数の平方根など）を
  意図的に配分する。分布そのものを報告書に載せて、外から検証可能にする。
- **同値ケースの自明化。** 両辺が同じ経路に落ちると常に緑になる。生成器が自明な対を
  出さないことを、生成器自身のテストで確認する。
- **`contributed/` の増加。** 投稿が増えたときの重複・命名・レビュー方針は未定。
  最初の投稿が来るまで決めない。
- **決定性は共有された選択肢プールに対して脆い(段階 3 への申し送り)。**
  `corpus_expr.py` の `UNARY_FNS` / `BINARY_OPS` は生成器が `random_node` の中で
  `rng.choice()` で引いている。段階 3 でここに関数や演算子を 1 つ足すと、同じ種を
  与えても乱数の消費列が最初の呼び出しから変わり、既存シャードを再生成しただけで
  中身が総入れ替えになる(複数の種で実測確認済み)。既存シャードを凍結資産として
  扱うなら、新しいジェネレータは独立した定数プール(`rng.choice()` の対象が既存と
  別)を持つか、新しいファイル名だけを追加する運用にすること。
- **段階 5 の投稿受け口には、想定より多くの実装が要る(段階 3 以降への申し送り)。**
  (a) `loadShards()` は `generated/` 固定なので `contributed/` を作っただけでは
  拾われない。(b) §4.3 の「ケース単位の tolerance 上書き」は、**シャードに書く形では
  実装しない**(段階 3a の訂正を見よ)。人の判断による緩和は `corpus/overrides.json`
  にあり、投稿の受け口もそちらに繋ぐこと。(c) §7.2 の
  「期待値を埋めるローカルスクリプト」は存在しない。(d) §7.3 の審判には `expr`
  テキストを値に戻すパーサが新規に要る——現状 `to_expr_text` は式木からテキストへの
  片方向しかなく、逆方向(テキストの構文解析)は無い。YAML やコーパス形式を書けば
  済む話ではなく、これらを段階 5 の作業項目として見積もっておくこと。
- **~~段階 3 で極値近傍を入れるなら、マグニチュード依存の tolerance を先に入れること。~~**
  ~~現状の `MIN_ABS = 1e-6` の床を下げた瞬間、絶対誤差 `tolerance.abs`(`5e-10`)の
  実効的な相対許容は値が小さいほど際限なく緩くなる(例: `abs = 5e-10` の値が
  `1e-8` なら実効相対誤差は 5%)。極値近傍(0、π/2、極)を広げる作業とマグニチュード
  依存の tolerance 設計には順序の依存関係があるので、後者を先に決めてから前者に
  着手すること。~~

  **訂正(2026-08-16、段階 3a)。この項は対策を誤って名指ししていた。** 実効的な相対許容を
  膨らませていた真犯人は**`abs` の床**であって、`rel` ではない。合否を `rel` だけで判定する
  ようにした時点で、`abs / |期待値|` という膨らみ方は経路ごと消えた——**表示の丸め幅は相対で
  見ると 5e-11〜5e-10 に収まり、値の大きさに依らない**ので、単一の相対許容があらゆる
  マグニチュードで表示の丸めをちょうど覆う([段階 3a 設計](2026-08-16-corpus-tolerance-design.md)
  §2)。**マグニチュード依存の tolerance は入れないこと。** 極値近傍を広げる作業に、この
  順序の依存関係はもう無い。個別に緩める必要が出たケースは、`corpus/overrides.json` に理由を
  添えて名指しで書く(同 §3.3。上限・腐り検出・全文開示が付く)。この段階で 4000 件中 1315 件
  あった「表示分解能より緩い検査」は 2 件になった。

## 12. 段階

未知が二つある——表示精度（§6.3）と生成時間（§11）。この二つは目標件数と
`tolerance` を決めてしまうので、**作り切る前に測る**。

1. **測る。** 1000 件の小さいコーパスを作り、表示桁数を実測して `tolerance` を確定し、
   生成時間を計る。ここで目標件数が決まる。

**実測後の訂正。** 段階 1 の二つの未知のうち、時間の方は空振りだった。表示精度は
有効数字 10 桁で `tolerance` を決めたが、**生成時間も実行時間も目標件数を縛らなかった**
（§11）。件数を縛るのは式木の空間の多様性の方である。段階 3 の計画を書くときは、
「何件回せるか」ではなく「何件目から同じような式ばかりになるか」を先に測ること。
2. **縦に 1 本通す。** 1 シャードだけで、生成 → コーパス → ハーネス → core 経路 →
   レポートまでを繋ぐ。件数は増やさない。
3. **横に広げる。** 電卓の種類ごとにジェネレータを足し、シャードを増やす。
4. **UI 経路を足す。** 抽出 200 件を本物のボタン操作で回す。
5. **外向きを整える。** `corpus-gate.yml`、`docs/corpus.md`、報告書の書式。

段階 1 の結果次第で §11 の目標件数が変わりうる。変わったらこの設計書を直す。
