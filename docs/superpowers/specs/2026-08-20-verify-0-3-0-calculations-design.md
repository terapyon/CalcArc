# 0.3.0 の計算の検証（Convert 7 カテゴリ・LLM メモリ・データ転送量）— 設計書（草案）

**前提の main: `f1fdc2e`**（`Merge pull request #60`、0.3.0 のアプリ + 重量級の検証インフラが入った地点）。
この後 main には fix ブランチと 0.3.1（通貨）が入る予定なので、**この文書の実測値はすべて `f1fdc2e`
で数えたもの**である。数字が合わなくなったら、まず SHA を疑うこと。

**この文書はユーザーのレビュー待ちの草案である。** §7 の未決 4 件が決まるまで実装に入らない。

---

## 1. 何のための検証か

0.3.0 で 3 つの計算が入った——**単位換算（7 カテゴリ 63 単位）**、**LLM のメモリ見積り**、
**データ転送量**。どれも u128 と有理数の厳密計算で、関数電卓のような超越関数も、
金融のような丸め慣行も持たない。

**ユーザーの言葉:「難しい計算はしていないので、関数電卓や金融電卓のような網羅的テストは不要。」**
この設計書はその節度を守る。**足すのは件数ではない。**

## 2. 非目標（スコープの節度）

- **網羅的な生成コーパスを作らない。** 63 単位 × 63 単位の総当たりも、カテゴリごとの
  数万件も作らない。**Scientific（20,000 件）や Finance（3,500 件）と同じ規模にしない。**
- **誤差帯を設計しない。** 厳密計算なので「厳密一致」枠で足りる（§4）。
- **表示の規則を作り直さない。** 既存の `format` は golden が表示文字列まで固定している（§3）。
- **0.3.1（通貨）を含めない。** 別の spec の領分である。

## 3. 既にあるもの（`f1fdc2e` で実測。数えてから足す）

| 層 | Convert | data_scale / LLM / transfer |
|---|---|---|
| Rust 単体テスト | **39**（`convert/mod.rs` 27・`convert/format.rs` 12） | **30**（`mod.rs` 6・`llm.rs` 8・`transfer.rs` 8・`format.rs` 8） |
| 言語間 golden | **`convert.json` 55 件** + `tests/convert_golden.rs` | **`data_scale.json` 28 / `llm.json` 18 / `transfer.json` 11** + 各 `*_golden.rs` |
| Python 独立実装 | `test_convert_ref.py` | `test_data_scale_ref.py` / `test_llm_ref.py` / `test_transfer_ref.py` |

**覆いは、見た目より良い:**

- **`Unit::ALL` の 63 単位は、golden が全部 1 度以上触っている**（未訪問の単位は 0 個）。
  当初「7 カテゴリで 55 件は薄い」と見立てたが、**単位の覆いは穴が無い**。
- **`llm.json` と `transfer.json` の期待値は表示文字列まで持つ**——`"3.9 GiB"`、
  `"4,160,749,568"`（桁区切り）、二進と十進の別。**表示層は golden が既に降りている。**
- 未知の単位も 1 件ある（`convert/length/1kmtofurlong` → `SyntaxError`）。エラー期待は計 4 件。

**それでも薄い場所が 2 つある（実測）:**

1. **63 単位のうち 45 単位は、golden に 1 度しか現れない。** つまりその単位の係数を
   縛っている等式は**1 本だけ**で、しかも**片方向**である。
2. **ケース数はカテゴリで偏る**——length 20 / volume 10 / area 6 / temperature 6 /
   data-size 6 / mass 5 / **speed 2**。

## 4. 本当の穴は「件数」ではなく「検出力が測られていないこと」

**実測（`f1fdc2e`）: 重量級の 18 枚のシャードに、convert・llm・transfer は 1 枚も無い**
（`data-scale-000.json` は `data_scale` op のみ）。**変異 18 種のうち、`convert/` と
`data_scale/` を触るものは 0 件**（内訳: `finance/loan/rate.rs` 4・`numeric/format.rs` 3・
`compound_inverse` 2・`compound` 2・`value` 1・`scientific` 1・`polar` 1・`tax` 1・
`schedule` 1・`engine/state` 1・`engine/mod` 1）。

**つまり: 上の 69 本の単体テストと 84 件の golden が、欠陥を実際に捕まえるかを誰も測っていない**
（84 = convert 55 + llm 18 + transfer 11。**`data_scale.json` の 28 件は 0.2.x から在る兄弟**で、
`llm.rs` / `transfer.rs` と同じモジュールに同居しているだけなので、0.3.0 の数には入れない。
ただし変異 1 と 4 は `data_scale/format.rs` を壊すので、**その 28 件も測定の対象にはなる**）。
0.2.x の教訓がそのまま当てはまる——**「緑である」と「壊したら赤くなる」は別の主張**である。

**この spec の芯は、件数を増やすことではなく、いま在る検査の検出力を測ることである。**
測った結果、赤くならない帯が見つかったときにだけ、そこへケースを足す。

## 5. やること（3 段、この順）

### 段 1: 変異を注入して、既存の検査が赤くなるかを測る

`web/scripts/detection-power.mjs` の枠組みをそのまま使う（`from`/`to` の文字列置換 +
`expectShards` + `minRate`）。**ただし期待するのはシャードではなく、既存の検査である**
——この 3 つの計算には生成コーパスが無いので、**`expectShards` の代わりに
「どのテスト集合が赤くなるべきか」を宣言する枠が要る**（§7 の未決 2）。

変異の候補（**係数表を写さず、意味の違う壊し方を選ぶ**）:

| # | 何を壊す | 捕まえるべきもの |
|---|---|---|
| 1 | `data_scale` の基数 1024 と 1000 を取り違える | 二進と十進の別。**表示にも計算にも効く** |
| 2 | Convert の温度のオフセットを落とす（`degf` の 32） | アフィン変換の平行移動。比だけの単位では起きない壊れ方 |
| 3 | Convert の係数を 1 つだけ 1000 倍ずらす（例: `um`） | **1 度しか現れない 45 単位の代表**。1 本の等式で足りるかを測る |
| 4 | 表示の丸めを half-even から half-up に変える | 既存の `format` の丸め規則（Convert・data_scale の両方） |
| 5 | LLM の kv キャッシュの係数を 1 段ずらす | 合成された計算（`llm.rs`）が独立実装と食い違うか |

**赤確認の作法は 0.2.x と同じ**: 変異ごとに「**何本が赤くなったか**」だけでなく
「**どの検査が赤くしたか**」まで見る。**戻しは再編集**（`git checkout` を使わない）。

### 段 2: 暗い帯にだけケースを足す

段 1 で**赤くならなかった変異**があれば、そこが暗い帯である。**そこにだけ** golden を足す
（Python 参照側で生成 → `testdata/*.json` を再生成 → Rust が突き合わせる、既存の経路）。

**足す前に段 1 の実測を記録する。** 「足したから安全になった」ではなく
「**この変異が捕まらなかったから足した**」と言えるようにする。

### 段 3: 盤面から打てるかを 1 度だけ確かめる（任意。§7 の未決 3）

**実測（2026-08-20、§8.5 の走行）: `heavy:ui` は `/`（科学計算）と `#finance` しか開かない。**
Convert と Scale のパネルは**盤面経路の検査を 1 度も通っていない**。
0.3.0 の画面で `heavy:ui` が 36 passed・46 トークン全押下だったのは**科学計算と金融の話**である。

やるなら**軽く**——各カテゴリ 1 件ずつ（Convert 7 + LLM 1 + transfer 1 = 9 件）を
実画面から打ち、**値が core まで届いて表示に戻ること**だけを見る。
**U-1 の教訓（「計算できる」と「打てる」は別の問い）**がここに掛かる。

## 6. 検証の枠（厳密一致）

3 つとも **u128 / 有理数の厳密計算**なので、**`tolerance` を持たない「厳密一致」枠**で扱う。
実測: `convert.json` / `llm.json` / `transfer.json` / `data_scale.json` は **4 枚とも
`tolerance` キーを持たない**（`scientific.json` と `complex.json` だけが持つ）。
**この spec で誤差帯を新設しない。**

## 7. 未決（ユーザーの裁定待ち）

1. **段 3（盤面経路）をこの spec に含めるか。** 含めると `heavy:ui` の走行時間が伸びる
   （現状 11.9 分）。含めないなら「Convert と Scale は盤面経路を通っていない」ことを
   レポートに明記して残す。**推奨: 含める**（9 件なら 1 分未満の増分。U-1 で「打てるか」を
   落として実機で気づいた前例がある）。
2. **`detection-power.mjs` の期待の枠をどう広げるか。** いまは「シャードが反応したか」しか
   見られない。**推奨: `expectTests`（赤くなるべきテストファイル名）を足す**——`expectShards`
   と排他にし、既存 18 種は 1 行も変えない。
3. **段 2 で足す golden の上限。** 際限なく足さないための数を先に決める。
   **推奨: 変異 1 件につき最大 5 件、合計 20 件まで。**超えるなら設計を見直す合図とする。
4. **speed の 2 件（`kmh`/`mph`/`mps`/`kn` の 4 単位に対し 2 ケース）を先に足すか。**
   段 1 の測定を待たずに足すのは「測る前に足す」ことになる。**推奨: 待つ。**
