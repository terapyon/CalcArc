## §0 なぜ今これを書くか

`docs/base-spec.md` §40（`1001` 行）は、ブラウザ側に保存できるものとして

**★ 履歴はそこが変わる。** 履歴は**計算した内容そのもの**を保存する。
**この 1 点が、この設計書の全部の論点に効いている**——置き場も、無効化も、
上限も、プライバシーの節も、そこから出てくる。

## §1 「履歴」という言葉が、いま 2 つの別のものを指している

**★ 議論の最初に、どちらの話かを決める必要がある。** コードの註に、
既に 2 つが別々に現れている。

| | 現物 | 何を指しているか |
|---|---|---|
| **(A) 打鍵の履歴**（打った通り） | `crates/calcarc-core/src/engine/display.rs`（`echo_of` の docstring） | 「**打鍵履歴ではなくスタックの形**を見せる。後置関数は押した瞬間に値へ畳まれ（`30 sin` は `0.5`）、優先順位でも畳まれる（`2 × 3 +` は `6 +`）。**打った通りを見せるには状態に履歴が要る**」 |
| **(B) undo のための履歴** | `crates/calcarc-core/src/engine/mod.rs`（`delete_one` の docstring） | 「**undo は状態に履歴スタックを要求し**、EngineState が毎打鍵で WASM 境界を往復する設計（D7）に正面から効く」 |
| **(C) 計算の履歴**（この設計書の主題） | 未着手 | **終わった計算を並べて、あとから見る／呼び戻す** |

**(A) と (B) は「1 回の計算の途中」の話**で、**(C) は「終わった計算の一覧」**である。
**base-spec §40 が言っているのは (C)** だが、**「履歴を付けよう」の一言は
3 つのどれにも読める。**

**★ 未決 1: この設計書は (C) だけを扱ってよいか。** (A)（打った通りの表示）や
(B)（undo）を同じ版に含めるなら、**規模が別物**になる——どちらも
`EngineState` に手を入れ、**WASM 境界を毎打鍵で往復する物が太る**。

**私の推し: (C) だけ。** 理由は 2 つ。**(A) と (B) は core の内側の設計変更**で、
**engine_table.rs（電卓の挙動の仕様書）が全面的に動く**。**(C) は、選び方に
よっては core を 1 行も触らずに作れる**（§2 の案 2）。**小さく出せる案が
在る側から始めたい。**

## §2 どこに置くか——**履歴は計算か、表示か**

**CLAUDE.md の第 1 の規律に正面から触る**:

> **計算ロジックは `calcarc-core` に置く。** `calcarc-wasm` と `web` に計算を書かない。

**★ 「履歴」はこの規律のどちら側か。** 履歴の中身は計算の結果だが、
**履歴を持つこと自体は計算ではない**——**そこが割れる。**

### 案 1: `calcarc-core` の状態に持つ

`EngineState` に履歴を足し、`reduce` が積む。

| | |
|---|---|
| 良い所 | **すべての盤面が同じ仕組みを共有する。** 「呼び戻したら式が再現される」（§4）が**自然にできる**——core は式を持っているので |
| 代償 | **`EngineState` が毎打鍵で WASM 境界を往復する**（設計 D7）。履歴が n 件あれば、**n 件が毎打鍵でシリアライズされる** |
| 代償 | **`STATE_SCHEMA` が変わり、WASM 境界に出る。** 0.6.0 で境界を `Outcome<T>` にしたばかりの所である |
| 代償 | **`engine_table.rs` が仕様書**なので、**表を先に赤くしてから実装する**。表の行数が増える |
| 検査 | `engine_table.rs`（キー列と表示）＋ `cargo test` ＋ 境界の parity |

### 案 2: `web` 側の永続化に持つ（**前例が 2 つある**）

`web/src/history/`（新設）が持ち、エンジンは何も知らない。

**前例 2 つは、どちらも「掴むのは 1 ファイルだけ」という規律で書かれている:**

- **設定** — `web/src/settings/` は **Storage を引数で受け取る純粋なモジュール**で、
  **`window.localStorage` を掴むのは `web/src/ui/useSetting.ts` だけ**
  （そのファイルの docstring に「**localStorage を掴むのはこのファイルだけである**」と書いてある）
- **通貨レートのキャッシュ** — `web/src/currency/cache.ts` の docstring に
  「**IndexedDB を掴むのはこのファイルだけ**——`localStorage` を掴むのが
  `useSetting.ts` だけなのと同じ形」

| | |
|---|---|
| 良い所 | **core を 1 行も触らない。** `EngineState` も `STATE_SCHEMA` も WASM 境界も動かない |
| 良い所 | **無効化（§5）が素直に書ける。** 保存するかどうかは web 側の判断で完結する |
| 代償 | **「呼び戻したら式が再現される」が難しい**（§4）——web は式を持っていない。**表示文字列は持てるが、式の内部形は持てない** |
| 代償 | **盤面ごとに「1 件」の意味が違う**（§3）ので、**盤面ごとに詰め方を決めることになる** |
| 検査 | vitest（純粋なモジュール）＋ E2E（**jsdom はアクセシビリティツリーを組まないので、ロールの意味論は E2E**） |

### 案 3: 折衷——core は「1 件の形」だけを持ち、貯めるのは web

core が「終わった計算 1 件」を返す口を持ち、**貯める・捨てる・呼び戻すは web**。

| | |
|---|---|
| 良い所 | **`EngineState` は太らない**（1 件は毎打鍵で往復しない） |
| 良い所 | **式の再現に必要な情報を core が決められる** |
| 代償 | **口が 1 つ増える。** 境界の関数が増え、parity の対象になる |

**★ 未決 2: 案 1 / 2 / 3 のどれか。**

**私の推し: 案 2。** 理由: **`EngineState` が毎打鍵で往復する設計に、
件数に比例して太る物を載せたくない**。**そして §40 の「無効化できる」は
保存の話であり、保存は既に web の仕事**である。**ただし §4 の「式の再現」を
採るなら案 3 になる**——**そこは §4 の裁定に従属する。**

## §3 何を 1 件とするか

**★ 盤面ごとに意味が違う。** 同じ形にならない。

| 盤面 | 1 回の計算とは | 素直な「1 件」 |
|---|---|---|
| **Scientific** | 式を打って `=` | **式と答**（`2 × 3 + 4` → `10`） |
| **Convert** | 値・変換元・変換先 | **値と 2 つの単位と答**（`1 km` → `0.621… mi`） |
| **Data Scale / LLM / Transfer** | 項目を選んで数を入れる | **項目の組と答**。式ではない |
| **Finance** | 7 項目を入れて計算 | **項目の組と答**。**1 件が大きい** |

3 つの案:

| 案 | 1 件の中身 | 何が良くて、何が困るか |
|---|---|---|
| **(a) 打鍵の列** | `["7","×","6","="]` | **全盤面で同じ形になる**。呼び戻しは replay（**設定の復元が既にこの形**——前例 spec §4「Scientific — キーを replay する」）。困るのは**読めないこと**（一覧に「7×6=」と出すには、結局どこかで組み立てる） |
| **(b) 式と答** | `{ expr, value }` | **Scientific には自然**。**Finance / Scale には式が無い**ので、そこだけ別の形になる |
| **(c) 表示文字列** | `{ main, sub }` | **全盤面で作れる**（表示は全盤面が持っている）。**呼び戻しが弱い**——文字列からは式に戻れない。**答だけ入れる**（§4 の (i)）なら足りる |

**★ 未決 3: (a) / (b) / (c) のどれか。盤面ごとに変えるのか。**

**★ 未決 4: 全盤面に持たせるのか、Scientific だけか。**
**Scientific だけなら規模が一段小さい**——**1 件の形が 1 つで済み**、
**§3 の表がまるごと消える。** ただし「Finance の計算を見返したい」は
**むしろ Finance のほうが要望として自然**である（金額を並べて比べるので）。

**私の推し: まず Scientific だけ、形は (c) 表示文字列 ＋ 呼び戻しは答だけ。**
理由: **一番小さく、一番早く「要るかどうか」が分かる**。**要ると分かってから
広げる**ほうが、**7 項目の Finance を最初に設計するより安い。**
**ただしこれは「小さく出す」を優先した推しであって、要望の形とは別**である。

## §4 呼び戻したとき何が起きるか

| 案 | 何が起きる | 何が要る |
|---|---|---|
| **(i) 答だけ入る** | 履歴の答が、いまの入力位置に数として入る | **一番小さい。** 表示文字列でも足りる |
| **(ii) 式が再現される** | `2 × 3 + 4` を打ち直した状態になる | **式の内部形が要る**（案 1 か 3）。または**打鍵列の replay**（§3 の (a)） |
| **(iii) 見るだけ** | 一覧に出るが、押しても何も入らない | **一番小さい。** ただし「呼び戻せない履歴」に価値があるかは別の問い |

**★ AC との関係。** この作業台の記録に
**「AC で表示状態は戻らない」**（角度モード・記法・表示形式は AC を越えて残る）
という実測がある。**履歴も「AC を越えて残る」側**だと考えるのが自然だが、
**それは「AC は入力を消すが、履歴は消さない」と明示して初めて成り立つ**。

**★ 未決 5: 呼び戻しは (i) / (ii) / (iii) のどれか。**
**★ 未決 6: `AC` は履歴を消すか。** 消さないなら、**履歴を消す手段が別に要る**
（§5 の無効化とは別の操作である——「切る」と「消す」は違う）。

**私の推し: (i) 答だけ ＋ AC では消えない。** 理由: **(ii) は §2 の案を
1 と 3 に狭める**——**呼び戻しの形が置き場を決めてしまう**ので、
**最初の版で決め切りたくない。**

## §5 無効化（base-spec §40 の要求）

> 履歴保存はユーザーが無効化できる設計を検討する。

**これは「検討する」と書かれた要求**であって、**やり方は決まっていない。**

**★ 未決 7: 既定は入か切か。**

| | 良い所 | 困る所 |
|---|---|---|
| **既定は入** | 使われる。設定を触らなくても機能する | **既定で計算内容が端末に残る。** base-spec の「**入力した数値そのものを収集しない**」（`1075` 行）が言っているのは**収集**の話だが、**保存も説明が要る**（§8） |
| **既定は切** | **何も残らないのが既定。** 説明が要らない | **機能が既定で無い**——「履歴が無い」と読まれる |

**★ 切ったとき、既存の履歴はどうなるか。** これも別の裁定である:

- **消す** — 「切る」が「消す」を兼ねる。**分かりやすいが、戻せない**
- **残すが読まない** — 入れ直せば戻る。**「切ったのに残っている」と読まれうる**

**私の推し: 既定は入、切ったら消す。** 理由: **「切る」を押した人が期待するのは
「残っていない」ことだと思う**（**これは推測であって、実測ではない**）。
**ただし既定を切にする判断も十分に成り立つ**——**この電卓の Privacy の書き方は
かなり強い調子**なので、そこに合わせる選択は一貫している。

## §6 上限——何件で、溢れたら何を捨てるか

**★ 未決 8: 件数か容量か。**

| | |
|---|---|
| **件数** | 「50 件」。**分かりやすい。** ただし **1 件の大きさが盤面で違う**（Finance の 1 件は Scientific の数倍） |
| **容量** | 「100 KB」。**溢れにくいが、利用者に説明できない**（「何件入るか」が言えない） |

**溢れたら古いものから捨てる**が自然だが、**「捨てた」ことを見せるかどうか**は別の話。

**★ `localStorage` と IndexedDB の選択**（§2 の案 2 を採ったとき）:

| | 前例 | 向き不向き |
|---|---|---|
| **`localStorage`** | 設定（`useSetting.ts`） | **同期で読める。** 容量が小さい（一般に数 MB）。**件数の上限を置くなら十分** |
| **IndexedDB** | 通貨レートのキャッシュ（`currency/cache.ts`） | **非同期。** 容量が大きい。**前例が既に在り、掴むファイルが 1 つに閉じている** |

**私の推し: `localStorage` ＋ 件数の上限。** 理由: **履歴は起動時に一覧を出す**ので、
**同期で読めるほうが素直**である。**非同期にすると「まだ読めていない」状態が
1 つ増える。**

## §7 盤面にキーが増えるか——**増えると重量級が動く**

**★ ここは選択肢ごとに答が違う。**

| 出し方 | 盤面のキー | 重量級への影響 |
|---|---|---|
| **キーを 1 つ足す**（履歴を開く） | **増える** | **押下台帳が動く。** `heavy/tests/ui/reachability.spec.ts` の **4 本**が「盤面が主張するキーは全部押せる」「Shift の裏は Shift のあとにだけ出る」を見張っており、**キーが増えれば `BUTTON_FOR` に足すことになる** |
| **盤面の外に出す**（表示の周り、または別の面） | **増えない** | **押下台帳は動かない**（見立て。**実測前**） |
| **既存のキーの長押し** | 増えない | **長押しの仕組みが無い。** `Key.tsx` は `onClick` だけである（実測） |

**直近の走行の実測値**（`docs/corpus-measurements.md`、0.7.0 の走行）:
**37 テスト / 押下 19,960 / 打鍵ケース 1,279 / 指摘 0 / 46 トークン全押下**。
**これは走行の記録であって、テストが埋め込んでいる数ではない**
——`reachability.spec.ts` は `BUTTON_FOR` を回すので、**キーを足せば
台帳の数は自然に動く。**

**★ この論点は「設計の副作用」ではなく「設計の入力」である。**
**盤面を触らずに済む出し方が在るなら、そちらのほうが 1 版ぶん安い。**

**★ 議論の材料として 1 つ**: **「端末に残る」と「外へ出る」は別**であり、
**この電卓はこれまで後者だけを約束してきた**。**履歴は前者を初めて増やす**ので、

——文言の話であって、設計の分岐ではないため**）。

## §10 まだ測っていないこと（**この草案の弱い所**）

- **要望の形を聞いていない。** 「履歴が欲しい」が **(A)(B)(C) のどれ**で、
  **どの盤面**で、**何のため**（見返す／打ち直す手間を省く／間違いを確かめる）かを
  聞いていない。**§9 の推しは全部、そこを聞く前の推しである**
- **規模を測っていない。** どの案も**行数・触るファイルの実測が無い**
  （**§2 のファイル一覧は案ごとに変わるので、裁定の後でないと数えられない**）
