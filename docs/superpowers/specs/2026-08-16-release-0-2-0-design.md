## 2.1 このリリースが発火させる記録済み条件（`#loan` 互換）

F0 設計書（`2026-08-14-finance-rename-design.md`）§3 は、判断が変わる条件を
書き残している。

> **この判断が変わる条件を書いておく**: 第三者が使い始めたら（公開告知・
> リポジトリの公開・URL の共有）、`#loan` を指すブックマークが本人の手の
> 届かない所に生まれる。**その時点で互換分岐を足す**——ただしそのときは
> 「今いる利用者を壊さない」ためであって、本 spec の判断の誤りではない。

同じ条件は `web/src/App.tsx:9-12` のコメントにも書かれている
（「第三者が使い始めたら足す」）。

**0.2.0 のアナウンスはこの「公開告知」にあたる。条件は発火する。**

### 分析

条件の**目的**は「本人の手の届かない所にある `#loan` ブックマークの保護」で
ある。したがって問うべきは「告知したか」ではなく「**保護対象が存在するか**」
である。

確かめられた事実:

- 公開 URL（`calc.terapyon.net` も `calcarc.pages.dev` も）は
  **リポジトリのどこにも書かれていない**（§11 の grep、0 件）。リポジトリが
  public であっても、そこから動くサイトには辿り着けない
- したがって `#loan` 時代（〜2026-08-15）にアプリへ到達した第三者がいるなら、
  **ユーザー本人が URL を直接渡した場合に限られる**
- 告知後に来る人は `#finance` しか知らない

残る 1 つ——本人が `#loan` 時代に URL を誰かへ直接渡したか——は本人しか
知らない。**2026-08-16、ユーザー本人が「誰にも渡していない」と回答した。**

### 処置: 互換分岐は足さない

**条件は発火したが、保護対象が存在しない。**

`#loan` を指すブックマークを持ちうるのは、改名（2026-08-15）より前にアプリへ
到達した第三者だけである。到達経路は「リポジトリ経由」と「本人が URL を渡す」の
2 つしかなく、前者は公開 URL がリポジトリに 1 度も書かれていないため成立せず、
後者は本人が否定した。**したがって集合は空である。**

F0 §3 が守ろうとしたのは「今いる利用者を壊さない」ことであって、`#loan` という
綴りそのものではない。壊れる利用者が居ないので、処置は不要である。

**ただし記録は残す**——書かなければ、F0 を読んだ将来の誰かが「条件が発火したのに
無視された」と読む。次の 2 箇所に接続する。

1. **F0 設計書 §3 に訂正印**（発火した / 保護対象が空だった / 根拠）
2. **`web/src/App.tsx:9-12` のコメント**（「第三者が使い始めたら足す」の現況を追記）

**条件そのものは生かしておく。** 今後 URL を第三者に渡す場面が来れば、そのときは
また別の話になる。

## 3. 切り方 — PR 2 本

**1 本目「画面」**: C-1・C-2・C-3・C-4・C-8・C-9・C-10・C-11 + 版数 0.2.0
**2 本目「公開物」**: C-5・C-6・C-7 + 古い記述の修正 + OGP + CHANGELOG

**性質で 3 本に切らない理由**は縦方向の競合である。C-1（フッタ）は画面の縦を

決めきる。**

**1 本にまとめない理由**は、CSS・パネル・キーパッド・Rust の版数・README 2 本・
CHANGELOG・OGP が同じ差分に入ると、どこか 1 つの差し戻しで全部が止まるためである。

順序は **画面 → 公開物**。README のスクリーンショットと OGP 画像は、直したあとの
画面から撮る。

# 第 1 部 — 画面

## 4. 版数の出所（C-3）

### 現状と、それが使えない理由

いまの版数表示は `web/src/ui/ScientificPanel.tsx:70-71` の 1 箇所だけで、
WASM の `core_version()`（= Cargo ワークスペースの版数）を `calcarc-core 0.1.0`
と出している。

**この経路はフッタには使えない。** フッタはシェル（`App.tsx`）が持つが、
**シェルは WASM を読み込まない** — 読むのは各パネルで、しかも非同期である。
シェルに置くと、読み込みが終わるまで版数が空になり、タブによって出方が変わる。

### 決め

| | |
|---|---|
| 表示する値 | `web/package.json` の `version` を Vite の `define` でビルド時に埋める |
| 更新の手順 | `Cargo.toml`（workspace）と `web/package.json` の **2 箇所**を書き換える |
| 漏れの防止 | `web/scripts/check-version.mjs` を新設し、2 つの `version` が一致しなければ非 0 で終わる。`pnpm check:version` として CI に足す |

意味の上でもこちらが正しい。`CalcArc 0.2.0` は**アプリの版**であって、計算コアの
版ではない。コアの版をアプリの版として出していた今の形は、たまたま一致していた
だけである。

`check:sw` と同じ流儀（`web/scripts/` に検査スクリプトを置き、`pnpm` から呼び、
CI が回す）に揃える。

### `core_version()` は残す

web から参照されなくなるが、**WASM 境界のテストが「境界が生きていること」を
版数の往復で確かめており**、コアの版を返す関数としては正しいままである。
今後使う可能性もある（ユーザー裁定）。

## 5. フッタ（C-1・C-2・C-4）

3 回書くと、片方だけ直す事故が起きる。`ScientificPanel.tsx:70-71` の既存表示と
`.version` の CSS は削除する。

新しい部品は `web/src/ui/Footer/{Footer.tsx, Footer.module.css}`。

### 中身


- **1 行目まるごとを 1 つのリンク**にし、`https://github.com/terapyon/CalcArc`
  へ飛ばす。`CalcArc` と `@terapyon` を別リンクに割ると、フッタの小さい文字で
  隣り合う 2 つのタップ標的ができて押し分けられない

**【訂正 2026-08-16】フッタは 2 行ではなく 1 行になった。** 実装後に 390×844 で

## 6. 表示エリアの高さ固定（C-8）

### 原因

**盤面を押し下げているのは `Readout` だけである。** Finance の内訳
（`FinancePanel.tsx:794`）も Data Scale の結果（`DataScalePanel.tsx:245`）も
`<Keypad>` の**下**にあるので、答えが出ても盤面は動かない。原因は 2 つ。

1. **`Readout.tsx:54` の `{active && ...}`** — いま打っている行が、打っていない
   ときは要素ごと消える。この行は `--key-font-size`（22px）なので、出現・消滅で
   約 28px 動く。**これが主犯である**
2. **`.entriesDone` の `flex-wrap: wrap`** — 入力済みの項目が増えると 1 行から
   2 行に伸びる。項目の多い Finance で効く

`.status` は `min-height` を持ち中身も短いので原因ではない。

**【訂正 2026-08-16】** 当初ここには「`.main` は `white-space: nowrap` +
`overflow-x: auto` なので高さは一定」と書いていた。**誤りである。**中身が
ある場合しか見ておらず、**空のときに 0px になる**ことを見落としていた。
Scientific は常に `0` などが入るので踏まないが、**Finance は答えが出るまで
空**で、計算が走った瞬間に 1 行ぶん(実測 45px)伸びて盤面ごと押し下げる。
実装中に E2E が捕まえた。`.main` にも同じ規則(`min-height` と固定
`line-height`)を当てて解決した。

### 決め

`Readout.module.css` が既に `.entriesDone` に対して採っている方針
（「空でも 1 行ぶんの場所を残す」）を、**`.entryActive` にも同じく適用する**。

- `.entryActive` を**常に描画**する。中身が無ければ空のまま場所だけ残す
  （`Readout.tsx` の条件付きレンダリングをやめる）
- `.echo` に「打っている行 1 行 + 入力済み 2 行」ぶんの `min-height` を置く
- **`height` ではなく `min-height`** を使う。それを超える内容が来たときだけ伸びる
  ——「表示できない場合だけずれを許容する」というユーザー指示がそのまま形になる

### 2 つの変更は独立に観測できない

`.entryActive` を常に描画する変更と `.echo` の `min-height` は、**どちらも
正しいが、盤面の位置では区別できない**。`min-height` が子の有無を吸収する
ためで、条件付き描画に戻しても盤面は動かない（実装中に実測）。

だから**測る対象を分ける**。盤面が動かないことは E2E が Y 座標で、打っている
行が常に場所を占めることは E2E が**その要素の箱**で、要素が存在することは
vitest が、それぞれ測る。

`min-height` があるなら常時描画は要らない、とはしない。**入力済みが 3 行に
なった瞬間に差が出る**——そのとき条件付き描画だと、はみ出しぶんに加えて
22px が乗る。いまの内容では届かないが、届いたときに壊れ方が小さいほうを取る。

### 高さは全パネル共通

パネルごとに最適な高さを与えると、**タブを切り替えるたびに盤面の位置が変わる**。
それは今回直そうとしているのと同じ種類の不快さである。

## 8. Finance の行の高さ（C-10）

### 原因（当初の見立ての訂正を含む）

`Keypad/finance.ts:91` は `label: "借入\n可能"` と明示的に改行を入れており、
**`FinancePanel.module.css` が区画名で `white-space: pre-line` を当てているので、
固定改行は効いている**。原因は単純に、**2 行になるのに行の高さが半高
（`--function-row-height: 34px`）のままで、2 行分（約 36px）が入らない**ことである。

### 決め

`KeypadSection.height` に **3 つ目の値**を足す（いまは `"square"` / `"half"`）。
`--function-row-height` の 2 倍を持ち、**文字サイズは `"half"` と同じ
`--key-font-size-function`** とする。

Finance の 6 列半高セクションは**定義が 3 つ**ある。すべて `"double"` にする。

| セクション | 区画名 | 長いラベル |
|---|---|---|
| `MODES` | `計算の種類` | 借入可能 / 必要積立 / 必要年数 |
| `FIELDS` | `入力する項目` | ボーナス |
| `COMPOUND_FIELDS` | `入力する項目` | （2 文字以下だが行の高さは揃える） |

逆算 2 モードの項目行（`DEPOSIT_FOR_FIELDS` / `PERIODS_FOR_FIELDS`）は
`fieldsWith()`（`finance.ts:231-245`）が `COMPOUND_FIELDS` をスプレッドして
作っているので、**自動的に追随する**。個別に直す必要はない。

**両方を 2 倍にするのはユーザー裁定である。** `FinancePanel.module.css` は
項目行だけフォントを 0.75rem（12px）に落として「収めるために読みやすさを削った」
状態にあり、器を広げるならそこも戻すのが筋である。**この 0.75rem の特例は削除し、
他の半高行と同じ `--key-font-size-function`（0.9375rem）に戻す。**

`計算の種類` への `white-space: pre-line` は**残す**（固定改行は引き続き必要）。

### 副産物: この 2 行は 44px 例外でなくなる

半高の関数列は `--touch-target-min`（44px）を縦だけ割る、というのが既存の
裁定である（`--function-row-height: 34px`。誤爆しても DEL で戻せる軽さに
見合わせたもの）。**器を倍にすると 68px になり、この 2 行はその例外から
外れる。**

`web/tests/e2e/loan-keypad.spec.ts` の「モード行と項目行は半高である」という
検査は、**主張ごと反転させる**——`toBeLessThan(44)` から
`toBeGreaterThanOrEqual(44)` へ。半高であることを守っていた検査を残すと、
今回の変更で落ちるだけでなく、**守るべきでないものを守り続ける**。

## 10. 縦の予算

| フッタ | +40px 前後 |
| 合計 | **+150px 前後** |

いまのレイアウトは普通の文書フローなので、収まらなければページがスクロールする。
壊れはしないが、**電卓でキーがスクロールの下に隠れるのは実用上まずい**。

**実装時に iPhone の寸法で撮って確認する。** 収まらなかったときに何を削るか
（正方キーの縦を少し詰める、など）はそこで相談する——測る前に決めない。

**【訂正 2026-08-16】測った結果と、そこで決めたこと。**

実測（390×844、`scrollHeight − innerHeight`）は Scientific 0px / Data Scale 0px /
**Finance +3px はみ出し**だった。差の 68px は、モード行と項目行を 34px から
倍にした分そのものである。

**はみ出しよりも重い問題が同時に見つかった**——盤面の高さがタブごとに違うので
（450 / 408 / 518px）、**ページ全体の高さもフッタの位置もタブで変わっていた**。
切り替えるたびに縦が動く。ユーザー指示は「余裕を持って同じ高さにして、縦方向の
揺らぎをなくして欲しい」。

決めたこと:

1. **シェルを `100dvh` の縦 flex にする**（`web/src/ui/App.module.css` を新設）。
   `<main>` が `flex: 1` で余りを吸い、フッタは常に一番下・3 タブで同じ位置に来る。
   **`100vh` ではなく `100dvh`**——`100vh` はモバイルのブラウザ UI の出入りを
   見ないので実機で下がはみ出す
2. **フッタを 2 行から 1 行にして返した**（§5 の訂正）
3. **パネルの `safe-area-inset-bottom` を外した。** 下端はフッタが持つので二重に
   なっていた——standalone 起動でだけ 44px 伸びる状態だった

結果、Finance の空き（`<main>` の高さ − パネルの高さ）は **22.31px**。

**「盤面の下端とフッタの上端の距離」で余裕を測ろうとして失敗した**ことも記録して
おく。あの距離は盤面を 4 倍・8 倍にしても縮まなかった——`100dvh` では伸びた分が
画面の外へ出るためで、**主張していた性質を一度も測っていなかった**。測るべきは
`<main>` とパネルの高さの差である。
