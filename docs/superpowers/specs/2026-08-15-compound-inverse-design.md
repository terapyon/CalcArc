# 複利の逆算（必要積立額・必要年数）— 設計

日付: 2026-08-15
対象: `crates/calcarc-core/src/finance/compound_inverse.rs`（新設）、golden 2 op、
Python 参照、WASM 境界、Finance タブのモード 2 つ。
前提: main（PR #40 マージ後 = `549ac14`）から。
**状態: ユーザー裁定済み（§1）。Fable レビュー済み。**

## §0 位置づけ

F1 設計（`2026-08-14-finance-compound-design.md`）§12 が「**目標額からの逆算は
`inverse.rs` のテンプレで書けるが、§6 の『像が区間になる』問題を別途裁定する
必要がある。次の spec**」としてスコープ外に置いたもの。その spec がこれである。

**F1 が懸念した「像が区間になる」問題は、問いの立て方で消える。** 「目標額
**ちょうど**にする積立額」を求めると逆像が区間になるが、「**目標額以上になる
最小の積立額**」なら答は一意に決まる（§1 の裁定 4）。ローンの `term_for`
（完済する最小の n）と同じ形である。

**代わりに、F1 が想定していなかった問題が出た**——§3。

## §1 スコープと裁定（ユーザー、2026-08-15）

| # | 論点 | 裁定 |
|---|---|---|
| 1 | 逆算の種類 | **必要積立額と必要年数の 2 つ**。必要元本・必要利回りは入れない |
| 2 | 税 ON のときの目標額 | **手取り（税引後）**。A の裁定 Q5「税ありは手取りを一番大きく出す」と揃える |
| 3 | 盤面 | **モードを 2 つ増やす**（4 → 6）。ローンと同じ「求めるものごとにモード」 |
| 4 | 端の選び方 | **目標を下回らない最小を返す** |

**裁定 4 の重み**（実測、§15 の A）: 元本 0・年 3%・月次・240 期・目標 1,000 万円で

```
積立 30,461 円 → 10,000,251 円   ← 答（目標を 251 円上回る）
積立 30,460 円 →  9,999,906 円   ← 目標に 94 円足りない
```

**積立 1 円の差が残高 345 円の差になる**ので、目標ちょうどには基本的に着地しない。
「超えない側」を選ぶと**目標に届かない額を答として出す**ことになる。貯金の問いと
しては届く側が答である。

## §2 目的関数 `reached()` — 1 つの契約

**両方の逆算が、この 1 つの値だけを見る。**

```rust
/// 目標と比べる値。税 ON なら手取り、OFF なら残高。
fn reached(g: &Growth, taxed: bool) -> CalcResult<u64> {
    if !taxed {
        return Ok(g.final_balance);
    }
    let (national, local) = tax::withholding(g.interest)?;
    g.final_balance
        .checked_sub(national + local)
        .ok_or(CalcError::Overflow)
}
```

税は `tax::withholding`（F1 で作った国税 15.315% / 地方税 5% の**別々切り捨て**）を
そのまま呼ぶ。**この spec は税の計算を 1 行も書かない。**

`reached` は Python 参照と共有する**公開契約**である（F1 §8 の契約 1〜4 に
「**目標と比べる値は手取り、税 OFF なら残高**」を 1 項足す）。契約の共有は
アルゴリズムの共有ではない——契約を知らなければ独立検証を書けない。

## §3 手取りは期数について単調でない — 本 spec の心臓部

**総当たりで反例が出た**（§15 の探索範囲）。元本 999 円・年 1.5%・月次・積立なし:

| n | 残高 | 利息 | 国税 | 地方税 | 手取り |
|---|---|---|---|---|---|
| 18 | 1,017 | 18 | 2 | 0 | 1,015 |
| 19 | 1,018 | 19 | 2 | 0 | **1,016** |
| 20 | 1,019 | 20 | 3 | 1 | **1,015** ← 減る |
| 21 | 1,020 | 21 | 3 | 1 | 1,016 |

**残高が 1 円増える間に、税が 2 円増えている。** 利息 20 円が
`0.15315 × 20 = 3.063` と `0.05 × 20 = 1.00` の**両方の閾値を同時に跨ぐ**ためで、
2 つの floor が同じ期に跳ぶ。年 0.0001% の 100 万円でも同じ形が出る——起きるのは
「利息が小さく、残高の伸びも小さい」領域である。

### 帰結 1: 必要年数に二分探索を使ってはならない

二分探索は単調性を前提にする。反例があるので、**静かに間違った答を返しうる**。

### 帰結 2: 「届いた直後にまた下回る期」がある — これは仕様である

目標 1,016 円（手取り）の必要年数は **19 期**だが、**20 期では 1,015 円で目標を
下回り、21 期で戻る**。利用者が「19 期で届くと言われたのに 20 期の表示が下回って
いる」を見たとき、それが税の階段の性質であって不具合ではないと読める記録が要る。

**§7 の golden がこの 2 つを対にして固定する**——「必要年数 = 19」と「20 期の
手取り = 1,015」の両方を載せ、注記が本当であることを golden 自身に語らせる。

### 積立額については単調である（証明）

積立を 1 円増やすと、残高は `S ≥ n` 増える（各期末の 1 円が最低でもそのまま残る）。
投入合計は `n` 増えるので、利息は `S − n` 増える。税の増分は 2 つの floor の
合計なので `0.20315(S − n) + 2` を超えない。したがって

```
手取りの増分 ≥ S − (0.20315(S − n) + 2) = 0.79685·S + 0.20315·n − 2 ≥ n − 2
```

`n ≥ 3` で正。`n = 1` は積立が期末に入るので利息に影響せず税が動かない（増分は
ちょうど +1）。`n = 2` は利息の増分が 0 か 1 で、1 のとき税の増分は最大 2、残高の
増分は 3 なので +1 以上。**よって全域で単調非減少。**

**この証明があるので、必要積立額は二分探索でよい。**

## §4 2 つのアルゴリズム

**f64 を 1 つも使わない。** ローンが f64 の種を要ったのは、期間が数万回になりうる
うえ償還表が高価だったからである。複利は期数が `MAX_PERIODS = 1200` で頭打ちで、
1 回の `grow` が最大 1200 期の乗算にすぎない。**出すべき候補が無い。**

### 必要積立額 — 二分探索

```
probe(d) := reached(grow(principal, d, rate, periods), taxed) >= target
```

1. `probe(0)` が真なら **0**（積立をしなくても届く）。
2. そうでなければ `low = 0`（届かない側）、`high = 1` から**倍々**で `probe(high)`
   が真になるまで伸ばす。
3. `high − low > 1` の間、中点で挟む。答は `high`（= 届く側の最小）。

**Overflow は「届く側」として扱う**——探索を u64 の定義域で閉じるためで、ローンの
`probe` が「u64 に収まらない元本は完済しない側」としたのと同じ形（向きは逆）。
`high` は必ず `u64::MAX` までに真になる（そこで Overflow するため）ので、
**探索は必ず停止する**。答が確定したら最後にもう一度 `grow` を走らせ、そこで
Overflow するなら `Overflow` を返す。

歩数は最大 64 + 64 probe。1 probe が最大 1200 期なので、最悪 15 万反復。

### 必要年数 — 前進 1 本

**探索しない。** 残高を持ち回りながら 1 期ずつ進め、**最初に届いた期で止める**。

```rust
let mut balance = principal;
let mut principal_total = principal;
for n in 1..=MAX_PERIODS {
    balance = balance
        .checked_add(rate.interest_floor(balance)?)
        .and_then(|b| b.checked_add(deposit))
        .ok_or(CalcError::Overflow)?;
    principal_total = principal_total.checked_add(deposit).ok_or(CalcError::Overflow)?;
    let interest = balance - principal_total;   // 利率は非負なので下回らない
    if reached_from(balance, interest, taxed)? >= target {
        return Ok(/* n とその期の内訳 */);
    }
}
Err(CalcError::SyntaxError)   // 1200 期でも届かない = 事実上の発散
```

**単調性に依存しない**——「最初に届いた期」を定義どおり前から探すので、その後に
下回る期があっても答は変わらない。計 1200 反復で、二分探索（11 probe × 最大 1200 期
= 13,200 反復）より**安い**。

### 結果の型 — 1 つ

```rust
/// 逆算の答と、その答における全体像。
pub struct Solution {
    /// 積立額。必要積立額では答、必要年数では入力そのまま。
    pub deposit: u64,
    /// 期数。必要年数では答、必要積立額では入力そのまま。
    pub periods: u32,
    pub growth: Growth,
    /// 税 OFF なら 0。
    pub national_tax: u64,
    pub local_tax: u64,
    /// 税 OFF なら `growth.final_balance` と同じ。
    pub net: u64,
}
```

2 つの逆算で同じ型を返す。**答の数値だけでなく「その積立額・期数で実際にいくらに
なるか」を持つ**のは、盤面が内訳を出すためと、§3 の帰結 2 を利用者が画面で
確かめられるようにするためである（ローンの `TermResult` が総支払と最終回を
抱えているのと同じ理由）。

## §5 エラー表

| 入力 | 結果 | 理由 |
|---|---|---|
| `target == 0` | `SyntaxError` | 目標 0 は入力が足りていない（`grow` の「入れた金がゼロ」と同じ流儀） |
| `periods == 0` / `> MAX_PERIODS`（必要積立額） | `SyntaxError` | `grow` の定義域 |
| `principal == 0 && deposit == 0`（必要年数） | `SyntaxError` | 増える源が無い |
| 1,200 期でも届かない（必要年数） | `SyntaxError` | 事実上の発散。ローンの `term_for` と同じ扱い |
| 途中で u64 を超える | `Overflow` | |
| 必要積立額が u64 に収まらない | `Overflow` | 上記の「最後にもう一度 `grow`」で出る |

**目標が元本以下のとき**（必要年数）はエラーにしない。**1 を返す**——
`net ≥ principal` が常に成り立つ（税は利息の一部でしかない）ので、1 期目で既に
届いている。実測: 元本 100 万・目標 50 万 → **1 期**。

**必要積立額が 0 になる場合**もエラーにしない。「積立をしなくても届く」は答である。

## §6 `numerical-policy.md` への追記

§3 をそのまま節にする。書くのは 3 つ:

1. **手取りは期数について単調でない**——反例（999 円・年 1.5%・月次の 19→20 期）と
   機構（2 つの floor が同じ期に跳ぶ）。
2. **だから必要年数は前進 1 本で解く**。二分探索は使わない。
3. **手取りは積立額については単調**——§3 の証明と、総当たりの探索範囲（§15）。

「切り捨てに揃える」の 1 語は動かない。動くのは**探索の正当化がどこから来るか**の
記述である。

## §8 Python 参照の独立軸（base-spec §30）

**逆算では Decimal 閉形式が番人になれない。** 各期 floor があるので年金終価の
逆関数が存在せず、税を入れると閉形式そのものが書けない。F1 の (a) は使えない。

**代わりに Python は証明書検査（certificate check）をする。** Rust が探索して答を
出し、Python は**その答が定義を満たすかだけを見る。探索を一切しない。**

```python
def check_deposit_certificate(d, principal, num, den, periods, target, taxed):
    """単調側。答の両隣 2 点で足りる（§3 の証明があるため）。"""
    assert reached(principal, d, num, den, periods, taxed) >= target
    if d > 0:
        assert reached(principal, d - 1, num, den, periods, taxed) < target


def check_periods_certificate(n, principal, deposit, num, den, target, taxed):
    """非単調側。1..n−1 の全数を見る——「最初に届く」の定義そのもの。

    残高を持ち回る 1 本の走査で全接頭辞を評価する（O(n)）。**これは探索ではない**
    ——打ち切りの判定を持たず、n まで必ず走り切って全接頭辞の述語を確かめる。
    """
```

**非対称は意図である。** 積立側は単調性の証明があるので 1 点、期数側は単調でない
ので全数——**検査の構造が、証明の依存関係を写している。**

**§30 に抵触しない根拠**: Rust は二分探索と前進ループ、Python は述語の評価。同じ
アルゴリズムを 2 回書いていない。独立性の境界は「**Rust の答の出し方（二分探索・
打ち切り判定）を写さないこと**」にあり、契約部分（各期 floor の形）が同じなのは
M6 以来の設計どおりである。

**golden の期待値の出所も Rust から独立する**——生成スクリプトが `k = 1, 2, ...` と
回して最初に届いた `k` を出す。

### 証明書は常時効かせる

**生成時 1 回だと「golden を作った日に正しかった」で終わる。** 3 点で効かせる:

1. **生成時**——`generate.py` が期待値を出した直後に検査する。
2. **pytest**——新設 `reference/tests/test_compound_inverse_certificate.py` が
   `testdata/finance.json` を読み、逆算 2 op の**全ケース**に証明書検査を掛ける。
3. **golden 突き合わせ**——`finance_golden.rs` が Rust の実装と付き合わせる。

**2 はこのリポジトリで初めての形である。** `reference/tests/` の 6 本はどれも参照
実装の健全性テストで、`testdata/*.json` を読むものが 1 つも無い（`test_loan_ref.py`
の 1 行目が「突き合わせ本番は golden の仕事」と明言している）。**分業を変えるので
明示する**: pytest が担うのは突き合わせではなく**定義検査**である（Rust の答を
見に行かない）。`cargo test` を回さずとも `uv run pytest` だけで、golden に載った
逆算の答が定義を満たしていることが分かる状態にする。

## §9 赤確認（新設検査は壊して赤を見てから信じる）

| # | 新設する検査 | 壊し方（実装か golden を変異させる） | 期待する赤 |
|---|---|---|---|
| 1 | 必要年数の前進ループ | **二分探索に差し替える** | **ケース #4 が赤。これが §3 の存在理由そのもの** |
| 2 | 証明書検査（pytest、期数側） | golden の #4 の答を 19 → **21** に書き換える | `1..n−1` の走査が `k=19` で `reached ≥ target` を見つけて赤 |
| 3 | 証明書検査（積立側） | golden の #1 の答を 30,461 → **30,462** に書き換える | `d − 1` 側の検査が赤 |
| 4 | 必要積立額の二分探索 | 答を `high` ではなく `low` にする（超えない側の端） | ケース #1 が 30,460 になって赤。裁定 4 を実装が守っていることの検査 |
| 5 | カバレッジ検査の 2 行 | golden から逆算ケースを全部消す | `no golden case for compound_deposit_for` |

**#1 を実際に見るのが、この spec で最も重要な赤確認である。** 赤にならないなら、
非単調性を捕まえる golden が足りていないということなので、golden を足してから進む。

**#2 の変異が 21 であることには理由がある。全数走査が要る根拠そのものだからである。**

期数側の証明書検査を「`n − 1` の 1 点だけ見る」形に弱めて、2 つの変異を比べる:

| 変異 | 1 点検査（`k = n−1` のみ） | 全数検査（`k = 1..n−1`） |
|---|---|---|
| 19 → **20** | `reached(19) = 1,016 ≥ 1,016` で**赤** | 赤 |
| 19 → **21** | `reached(20) = 1,015 < 1,016` で**通ってしまう** | `k = 19` で**赤** |

**20 期が目標を下回るせいで、1 点検査は「21 が最初に届いた期」を信じる。** §3 の
非単調性が、そのまま検査の穴になっている。**この 2 行を実際に走らせて表のとおりに
なることを確かめる**のが、§8 の非対称（期数側だけ全数）の正当化である。

表のとおりにならなかったら、非対称の根拠が別のところにあるということなので、
**§8 を書き直してから実装に進む。**

```
│    │能    │    │    │積立  │年数  │

```

項目行はモードで差し替える（既存の `COMPOUND_FIELD_SECTION` の仕組みをそのまま使う）:

| モード | 項目行 |
|---|---|
| 複利 | 元本・積立・年利・期間・周期・税 |
| 必要積立 | 元本・**目標**・年利・期間・周期・税 |
| 必要年数 | 元本・積立・年利・**目標**・周期・税 |

**求める項目が消えて、代わりに目標が出る**——既存の `SOLVED_FOR` がそのまま使える。
`FinanceKeyToken` に `mode:deposit-for` `mode:periods-for` `field:target` を足す。

**値の入れ物は複利と共有しない**——F1 が「ローンの値を持ち回らない」と決めたのと
同じ理由で、`compound:` 接頭辞と別の接頭辞にする。ただし**目標額だけは 2 つの逆算で
共有してよい**（同じ意味の欄である）。

**この節は方針まで。** 盤面の詳細（答の出し方、内訳の並び、`=` を置かない既存の
規律との整合）は plan で詰める。

## §15 この spec が依拠した実測と、その範囲

すべて 2026-08-15 に、コアの整数演算を写した使い捨てスクリプトで測った。

**単調性の総当たり範囲**（「反例が無かった」の範囲を書かずに単調性を主張しない）:

| 軸 | 範囲 |
|---|---|
| 年利 | 0 / 0.0001 / 0.01 / 0.5 / 1 / 1.5 / 3 / 7 / 20 / 100 % |
| 周期 | 1・2・12 |
| 期数 | 1〜12・24・60・120・360・1200（積立側）、1〜399（期数側） |
| 元本 | 0・1・999・1,000,000・123,456,789 |
| 積立 | 0〜199 と 9,900〜10,099（積立側）、0・1・7・30,000（期数側） |

**結果**: 積立側の反例 **0 件**（§3 の証明と整合）。期数側の反例 **10 件**——すべて
「利息が小さく残高の伸びも小さい」領域で、2 つの税の floor が同じ期に跳ぶ形。

**§7 の期待値**はすべてこのスクリプトが出したもので、**実装前に spec に載っている**。
実装がこの値に合わないなら、合わない理由を先に説明すること。
