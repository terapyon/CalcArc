# S-1 関数を実数に閉じ、MVP を埋める — 設計

日付: 2026-08-16
対象: `crates/calcarc-core/src/scientific/`、`engine/key.rs`、golden、Scientific の盤面。
前提: main（`f9cac72`）から。
**状態: ユーザー裁定済み（§1）。まとめレビュー待ち。**

## §0 位置づけ

base-spec §9.2 が MVP として挙げた関数のうち、**8 つが未実装**である。この spec が
それを埋める。あわせて、**関数の定義域を実数に閉じる**——ユーザー裁定（2026-08-16）。

これは 4 本に分けた spec の 1 本目である（S-2 ENG / S-3 確率 / S-4 時間計算）。
**盤面のキー数は 4 本で奪い合う**ので、§7 で全体の割り当てを示す。

## §1 裁定（ユーザー、2026-08-16）

| # | 論点 | 裁定 |
|---|---|---|
| 1 | 関数が複素数を返しうるとき | **エラーにする。** `sqrt(-4)` も**エラーに落とす**（既存挙動の変更） |
| 2 | 複素数そのもの | **やめない。** 四則と極座標変換は今までどおり複素数を扱う |

**線引きはこうなる: 四則と座標変換は複素、関数は実数。**

「その方が一貫性があるし、普段あまりやらない計算だと思うので」（ユーザー）。

## §2 いま在るもの

```
Key: Digit Dot Zeros3 Exp Pi Add Sub Mul Div Eq LParen RParen
     J PolarToggle Sqrt Sqr Sin Cos Tan Neg Ac Del AngleToggle
```

`scientific/mod.rs`（168 行）に `sqrt` / `sqr` / `neg` と三角関数。`Value { re, im }`
は複素数で、`sqrt` は**負の実数を虚軸に載せて返す**:

```rust
// 現状
if v.re >= 0.0 { Value::real(v.re.sqrt()) } else { Value::imag((-v.re).sqrt()) }
```

**この分岐が裁定 1 で消える。** 負の実数は `CalcError::DomainError` になる。

## §3 足すもの — base-spec §9.2 の残り 8 つ

| キー | 意味 | 実数の定義域 | 外れたとき |
|---|---|---|---|
| `xʸ` | べき乗 | §4 参照（一番込み入る） | `DomainError` |
| `exp` | e^x | 全実数 | Overflow のみ |
| `ln` | 自然対数 | `x > 0` | `DomainError` |
| `log10` | 常用対数 | `x > 0` | `DomainError` |
| `asin` | 逆正弦 | `−1 ≤ x ≤ 1` | `DomainError` |
| `acos` | 逆余弦 | `−1 ≤ x ≤ 1` | `DomainError` |
| `atan` | 逆正接 | 全実数 | — |
| `e` | 自然対数の底 | 定数 | — |

**`exp` の名前が紛らわしい。** 既存の `Key::Exp` は**指数入力**（EE。仮数と指数を
分けるキー）であって e^x ではない。**新しいキーは `Key::Exp` を再利用せず、
`Key::ExpE`（トークン `exp_e`、表示 `eˣ`）として足す。** 既存の `Exp` は名前を
変えない——公開トークンの変更は境界の変更であり、この spec の主題ではない。

**逆三角の返す角度は `AngleMode` に従う**（Degree なら度、Radian ならラジアン）。
`sin` などが `AngleMode` で引数を解釈しているのと対称である。

## §4 `xʸ` の定義域 — ここが唯一難しい

`x^y` は実数の範囲でも場合分けが要る。**すべて `DomainError` に倒すのではなく、
実数の答が一意に決まるものは返す。**

| `x` | `y` | 答 | 理由 |
|---|---|---|---|
| `x > 0` | 任意 | `exp(y·ln x)` | 一意 |
| `x = 0` | `y > 0` | `0` | |
| `x = 0` | `y = 0` | **`1`** | §4.1 |
| `x = 0` | `y < 0` | `DomainError` | 0 除算 |
| `x < 0` | **整数** | `x` を `y` 回掛けた符号つきの値 | 実数で一意 |
| `x < 0` | 非整数 | **`DomainError`** | 複素数になる。裁定 1 |

**`x < 0` かつ整数の `y` は許す。** `(-2)^3 = -8` は実数で一意であり、これをエラーに
すると「普段やる計算」が落ちる。判定は `y.fract() == 0.0 && y.is_finite()`。

**実装は `f64::powf` に丸投げしない。** `powf` は `(-8.0).powf(1.0/3.0)` を `NaN` に
するが、`(-2.0).powf(3.0)` は `-8` を返す——**定義域の判定を先に自分で書き、
`powf` は判定を通ったものにだけ使う。** `NaN` が出たら `DomainError` にする最後の
網も置く（判定漏れを黙って通さない）。

### §4.1 `0^0 = 1` にする

数学的には不定形だが、**電卓は 1 を返すのが慣行**である（IEEE 754 の `pow` も
`powf` も 1）。`DomainError` にすると `x^0` の一様性（どんな `x` でも 1）が
`x = 0` で崩れ、利用者には理由が見えない。

## §5 `sqrt(-4)` を落とす — 既存挙動の変更

**この spec で唯一、動いているものを壊す変更である。**

- `scientific::sqrt` の虚軸分岐を消し、`v.re < 0.0` を `DomainError` にする
- **複素数の入力（`v.is_real()` が偽）も `DomainError`** にする——裁定 1 の
  「関数は実数」を素直に読むとこうなる。`sqrt(3+j4)` は現状 極形式経由で答えるが、
  それも落とす
- `sqr`（x²）は**そのまま**——複素数の 2 乗は乗算であり、四則の側である
- `neg`（符号反転）も**そのまま**——同じ理由

### §5.1 `engine_table.rs` の既存行を書き換える — 順序が決まっている

**実測済み。書き換える行はここである**（`crates/calcarc-core/tests/engine_table.rs:354`）:

```rust
#[test]
fn square_root_of_a_negative_gives_an_imaginary_result() {
    // 従来機が Math ERROR を返す入力に、複素数対応の電卓は答えられる。
    assert_eq!(main_of(&["4", "neg", "sqrt"]), "j2");
}
```

**このリポジトリが意識して作った挙動である**——コメントが「従来機が Math ERROR を
返す入力に、複素数対応の電卓は答えられる」と誇っている。裁定 1 はそれを**逆に倒す**。

CLAUDE.md が定める規律に従う: **「電卓の挙動は `engine_table.rs` が仕様書。
キー列と表示の対応を先に変えてから実装を直す。」**

したがって plan の順序は:

1. **先にこの行を書き換える**（テスト名も `..._is_a_domain_error` に）。**赤を見る**
   ——実装がまだ `j2` を返すので落ちる。これが「仕様を先に動かした」証拠になる
2. そのあとで `scientific::sqrt` を直す

**コメントも書き換える。** 「複素数対応の電卓は答えられる」を残したまま
`DomainError` にすると、**文書が実装と逆のことを言う**——このリポジトリで既に
2 度踏んだ形である。「関数は実数に閉じる。複素数は入力と四則と表示の機能であって、
関数の値域ではない」と書き直す。

### §5.2 影響の実測（plan の最初の段）

`sqrt` の複素経路を覆っているテストと golden を数える。`complex.json` の 77 件は
`add/sub/mul/div` と `rect_to_polar` / `polar_to_rect` なので**触れないはず**だが、
`scientific.json`（29 件）は要確認。

## §5.3 他セッションとの約束（2026-08-16、`feature/e2e-corpus` 担当と合意）

重量級検証コーパス（4,000 件）が**キー列の綴り**で電卓を叩いており、この spec の
実装がその足元を動かしうる。**確認して合意した制約:**

- **`KEY_TOKENS` は足すだけ。既存トークンの綴りを変えない・消さない。**
  1 文字変えると 4,000 件が全部「未知のキー」になる。§3 で `Key::Exp` を改名しないと
  決めているのは、この意味でも正しい
- **`reference/src/calcarc_reference/corpus_expr.py` の `UNARY_FNS` / `BINARY_OPS`
  に触らない。** あそこは相手の生成器の乱数の土台で、1 つ足すと同じ種でも
  4,000 件が総入れ替えになる。**関数を増やすのは `calcarc-core` と
  `web/src/calc/types.ts` の側だけ**
- **`engine_table.rs` の既存行を書き換えるのは §5.1 の 1 行だけ。** 相手の直列化は
  あの表を仕様として従う設計なので、**実装に入る前に、書き換える行を名指しで
  伝える**（伝達済み）

**base-spec の訂正が要る。** §9.2 の一覧に定義域の但し書きを足し、§10/§11
（複素数と極座標は重要な基本機能）との関係を書く——**「複素数は入力と四則と表示の
機能であって、関数の値域ではない」**という 1 行が要る。

## §6 エラーの種類

`CalcError` にいま何があるかを plan の最初に確認する。**`DomainError` が無ければ
足す**——`SyntaxError` に混ぜない。「打ち方が悪い」と「その値には定義が無い」は
利用者にとって別の話で、`ln(-1)` を `SyntaxError` と言われても直しようがない。

WASM 境界と TS の型に 1 つ増えるので、`CalcErrorCode` の合併型も広がる。

## §7 盤面 — 4 本の spec でキーを奪い合う

**第 1 面は 32 スロットすべて埋まっている**（関数列 7 + メイングリッド 5×5）。
一方 **第 2 面（Shift）は空である**——`ariaLabel: "第2面（準備中）"` の
`EMPTY_FACE` が `sin` / `cos` / `tan` / `√` / `x²` に刺さっている。

**S-1 は第 2 面だけを使う。** 第 1 面は 1 キーも動かさない。

| 第 1 面 | Shift（第 2 面） |
|---|---|
| `sin` | `asin` |
| `cos` | `acos` |
| `tan` | `atan` |
| `√` | `ln` |
| `x²` | `xʸ` |
| `EXP` | `π`（既存） |
| `j` | `log10` |
| `▸∠` | `eˣ` |
| `+/−` | `e` |

**`√`→`ln` と `x²`→`xʸ` の対応は形が近い**（どちらも逆・拡張の関係）。
`j` と `▸∠` の Shift は複素数のキーなので、**第 2 面で実数の関数を置くのは
一貫していない**——ここは §9 の裁定待ちにする。

**`+/−` の Shift に `e`** は据わりが悪い。数の定数なので `EXP`（`π` が居る）の
近くが良いが、`EXP` の Shift は埋まっている。

## §8 検証

段ゲート（base-spec §49 は金融計算の規定だが、**コアと golden に触るので同じ順で
進める**）:

1. `CalcError::DomainError` の追加と `sqrt` の変更（**既存テストが赤になるところから**）
2. Python 参照 + golden（`scientific.json` に op 追加）
3. Rust のコア
4. WASM 境界と TS
5. 盤面（第 2 面）

**Python 参照の独立軸**: `mpmath` で高精度に評価し、`f64` の結果との相対誤差が
`tolerance` 内であることを見る（`scientific.json` は既に tolerance を持つ）。
**定義域の境界は golden の必須ケースにする**——`ln(0)` `ln(-1)` `asin(1)` `asin(1.0000001)`
`0^0` `(-2)^3` `(-2)^0.5` `sqrt(-4)`。

**赤確認**: `sqrt(-4)` がエラーになることを確かめる検査を足したら、**虚軸分岐を
戻して赤を見る**。
