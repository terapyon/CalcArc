## §0 位置づけ

base-spec §9.2 が MVP として挙げた関数のうち、**8 つが未実装**である。この spec が
それを埋め、あわせて**ユーザー要望の `1/x` を足す**（計 9 つ。§3.0）。さらに、**関数の定義域を実数に閉じる**——ユーザー裁定（2026-08-16）。

これは 4 本に分けた spec の 1 本目である（S-2 ENG / S-3 確率 / S-4 時間計算）。
**盤面のキー数は 4 本で奪い合う**ので、§7 で全体の割り当てを示す。

## §1 裁定（ユーザー、2026-08-16）

| # | 論点 | 裁定 |
|---|---|---|
| 1 | 関数が複素数を返しうるとき | **エラーにする。** `sqrt(-4)` も**エラーに落とす**（既存挙動の変更） |
| 2 | 複素数そのもの | **やめない。** 四則と極座標変換は今までどおり複素数を扱う |
| 3 | `xʸ` の結合方向（旧 Q4。§3.1 §3.2） | **右結合を実装する。** `2 xʸ 3 xʸ 2 = 512`。`push_binop` の比較 1 行に手を入れる |
| 4 | 複素数を関数に入れたとき（旧 Q3） | **`DomainError`。** 実部だけ使う案は**黙って別の計算をする**ので採らない |

**線引きはこうなる: 四則と座標変換は複素、関数は実数。**

「その方が一貫性があるし、普段あまりやらない計算だと思うので」（ユーザー）。

## §2 いま在るもの

```
Key: Digit Dot Zeros3 Exp Pi Add Sub Mul Div Eq LParen RParen
     J PolarToggle Sqrt Sqr Sin Cos Tan Neg Ac Del AngleToggle
```

`scientific/mod.rs`（168 行）に `sqrt` / `sqr` / `neg` と三角関数。`Value { re, im }`
は複素数で、`sqrt` は**負の実数を虚軸に載せて返す**:

```rust
// 現状
if v.re >= 0.0 { Value::real(v.re.sqrt()) } else { Value::imag((-v.re).sqrt()) }
```

**この分岐が裁定 1 で消える。** 負の実数は `CalcError::DomainError` になる。

## §3 足すもの — MVP の残り 8 つ + `1/x`

**9 つのうち 8 つは単項、`xʸ` だけ二項である**（§3.1）。表では分けて書く。

**単項 7 つ**——数を打ってから押すと現在値に適用される（`apply_unary`）。
エンジンの構造は 1 行も変わらない。

| キー | 意味 | 実数の定義域 | 外れたとき |
|---|---|---|---|
| `exp` | e^x | 全実数 | Overflow のみ |
| `ln` | 自然対数 | `x > 0` | `DomainError` |
| `log10` | 常用対数 | `x > 0` | `DomainError` |
| `asin` | 逆正弦 | `−1 ≤ x ≤ 1` | `DomainError` |
| `acos` | 逆余弦 | `−1 ≤ x ≤ 1` | `DomainError` |
| `atan` | 逆正接 | 全実数 | — |
| `1/x` | 逆数 | `x ≠ 0` | **`DivisionByZero`**（§3.0） |

**定数 1 つ**: `e`（自然対数の底）。`π` と同じ扱い。

### §3.0 `1/x` はユーザー追加（2026-08-16）

base-spec §9.2 の MVP には無いが、**ユーザー要望で足す**（「関数の機能に、逆数の
ボタンが欲しい」）。当初この spec は §10 でスコープ外に置いていた。

**`apply_unary` にそのまま乗る**ので、エンジンの構造は動かない。

**`x = 0` は `DomainError` ではなく `DivisionByZero` にする。** `CalcError` に既にある
分類であり、**利用者にとってそれはまさに 0 除算である**——`5 ÷ 0` と `0` `1/x` が
違うエラーを返す理由が無い。`DomainError` を新設するのは「その値には定義が無い」を
言うためで、0 除算はそれとは別に既に名前を持っている。

**複素数は `DomainError`**（裁定 1。ほかの関数と同じ）。`1/(3+j4)` は四則で
`1 ÷ (3+j4)` と書けるので、機能が失われるわけではない。

### §3.1 `xʸ` は二項演算子である — エンジンに手が入る

**当初この spec は `xʸ` を他の 7 つと並べて「関数」として書いていた。誤りである。**
`2 xʸ 10 =` は `+` と同じ**二項演算子**で、`apply_unary` には乗らない。

**`BinOp` に `Pow` を足し、優先順位と結合方向を決める必要がある。**
これは S-3（`nPr` / `nCr`）と同じ種類の変更で、**S-1 の中で唯一エンジンの構造を動かす**。

**優先順位**: `×` `÷`（2）より先。S-3 が `nPr` / `nCr` を 3 に置くので、
**`Pow` は 4** にする（`2 × 3 xʸ 2` = `2 × 9` = `18`）。

**結合方向がここだけ他と違う。** 数学の慣行では**右結合**である:

```
2 xʸ 3 xʸ 2  =  2^(3^2)  =  2^9  =  512      （右結合）
                (2^3)^2   =  64              （左結合）
```

**いまのエンジンは全演算子が左結合である**——`push_binop` が
`top.precedence() >= op.precedence()` で畳んでいる（`>=` が左結合を作る）。
右結合にするには、**その演算子のときだけ `>` にする**必要がある。

```rust
// いま（全部左結合）
Some(OpToken::Op(top)) if top.precedence() >= op.precedence()

// 右結合を入れるなら
Some(OpToken::Op(top)) if top.precedence() > op.precedence()
    || (top.precedence() == op.precedence() && !op.is_right_associative())
```

**これは既存の論理の書き換えである。** 他の演算子の挙動が変わらないことを、
`engine_table.rs` の既存の行が守る（`1 add 2 sub 3` などが左結合のままであること）。

**裁定 3（右結合）に伴って、plan は次を守る:**

- **左結合を守る行を足す。ただし「1 つも無い」は誤りだった**
  （**【訂正 2026-08-16】** 当初この項は「実測したところ 1 つも無い」と書いていた。
  `feature/e2e-corpus` 担当セッションの指摘を受けて測り直したところ、**半分は在った**）。

  `reduces_same_precedence_left_to_right` の**1 行目**（`["2","add","3","add"]` → `"5"`）
  が結合方向を捕まえる。`push_binop` の比較を `>=` から `>` に素朴に変えると 2 つ目の
  `+` で畳まれなくなり、`state.current` が 3 のままになって **`"3"` が出る。この行は
  赤くなる**（実測。落ちるのはこの 1 件だけ）。

  **在るのは「途中の表示」の守りであって、「答え」の守りではない。** 同じ test の
  2 行目 `2 + 3 + 4 = 9` は、加算が結合的なので**どちらの結合でも 9** であり区別しない。
  `10 − 3 − 2` が 5 か 9 か、`100 ÷ 5 ÷ 2` が 10 か 40 か——**答えの側で結合方向を
  主張する行が無かった**。足すべきはそれである。

  **この区別には使い道がある**（相手の指摘）: `xʸ` だけを右結合にする実装なら、
  **既存の行は緑のままのはず**である。赤くなったら他の演算子まで巻き込んでいる証拠になる。
  **既存の行が、変更の範囲を測る道具になる。**

  ```rust
  // 足す。**答えの側で結合方向を主張する行が無いまま push_binop の比較を
  // 書き換えるのは、守りの片側だけを見て崩すことになる。**
  assert_eq!(main_of(&["1", "0", "sub", "3", "sub", "2", "eq"]), "5");   // 左結合(9 でない)
  assert_eq!(main_of(&["1", "0", "0", "div", "5", "div", "2", "eq"]), "10"); // 左結合(40 でない)
  ```

  **順序が決まっている**: 比較を触る**前に**この 2 行を足し、**緑であることを見る**。
  そのあとで比較を書き換え、**まだ緑であること**を確かめる
- **右結合の行を足す**: `2 xʸ 3 xʸ 2 eq` → `512`。**`64` にならないことがこの裁定の
  全内容である**
- **赤確認**: 比較を `>=` に戻して `512` の行が赤になることを見る。
  同時に**左結合の行が緑のままであること**も見る（片方だけ動いたのでは意味がない）

**この 1 か所が、`sqrt` の行に続く 2 つ目の「既存に手を入れる」箇所である。**
（**裁定 3 で右結合に決着**。§3.2 は、その裁定に至った検討の記録として残す。）

### §3.2 ただし左結合はタダではない（2026-08-16、`feature/e2e-corpus` 担当の指摘）

**左結合を選ぶと、独立検証層と恒久的に食い違う。** 相手の二経路はこうなっている:

- **Rust 経路**: キー列 `2 xʸ 3 xʸ 2 eq` を engine が食べる。左結合なら `(2^3)^2 = 64`
- **Python 経路**: 同じ式木を **mpmath** が評価する。**mpmath は数学の慣行に従う**ので
  `2^(3^2) = 512`

**Python 側に「engine は左結合だから左結合で評価しろ」と教えることはできない。**
それは engine の意味論の移植であり、CLAUDE.md の「**参照実装を Rust の移植にしない。
同じアルゴリズムを両方に書くと、同じバグが両方に入って検証の意味がなくなる**」に
真正面から当たる。

したがって**左結合を選ぶなら、選び方は 3 つある**（相手の整理）:

| | やり方 | 代償 |
|---|---|---|
| 1 | **右結合を実装する** | `push_binop` の比較に手が入る |
| 2 | 左結合のまま、`xʸ` を括弧省略の対象から外す | 相手の層が結合方向を見なくなる。**「慣行と違う」という事実が誰にも検出されないまま残る** |
| 3 | 左結合のまま、**慣行との差を理由つきで記録する** | 赤にはならないが、相手のレポートに理由の全文が出る。外の読み手が「この電卓は `2^3^2` を 64 と答える」と読める |

**相手の推奨は 3**（「妥協した」ことを消さずに残せるのが 3 番だけだから）。
**私の推奨は 1** ——`push_binop` の変更は 1 行の条件式であり、既存の演算子の挙動が
変わらないことは `engine_table.rs` の既存の行が守る。**恒久的な食い違いを抱えるより
安い**と見る。

**この論点は、独立した検証層が実装前に設計判断を動かした事例である**——
「独立性を保ったまま自動検出できるか」が、結合方向の選び方の判断材料になった。

**`exp` の名前が紛らわしい。** 既存の `Key::Exp` は**指数入力**（EE。仮数と指数を
分けるキー）であって e^x ではない。**新しいキーは `Key::Exp` を再利用せず、
`Key::ExpE`（トークン `exp_e`、表示 `eˣ`）として足す。** 既存の `Exp` は名前を
変えない——公開トークンの変更は境界の変更であり、この spec の主題ではない。

**逆三角の返す角度は `AngleMode` に従う**（Degree なら度、Radian ならラジアン）。
`sin` などが `AngleMode` で引数を解釈しているのと対称である。

## §4 `xʸ` の定義域 — ここが唯一難しい

`x^y` は実数の範囲でも場合分けが要る。**すべて `DomainError` に倒すのではなく、
実数の答が一意に決まるものは返す。**

| `x` | `y` | 答 | 理由 |
|---|---|---|---|
| `x > 0` | 任意 | `exp(y·ln x)` | 一意 |
| `x = 0` | `y > 0` | `0` | |
| `x = 0` | `y = 0` | **`1`** | §4.1 |
| `x = 0` | `y < 0` | `DomainError` | 0 除算 |
| `x < 0` | **整数** | `x` を `y` 回掛けた符号つきの値 | 実数で一意 |
| `x < 0` | 非整数 | **`DomainError`** | 複素数になる。裁定 1 |

**`x < 0` かつ整数の `y` は許す。** `(-2)^3 = -8` は実数で一意であり、これをエラーに
すると「普段やる計算」が落ちる。判定は `y.fract() == 0.0 && y.is_finite()`。

**実装は `f64::powf` に丸投げしない。** `powf` は `(-8.0).powf(1.0/3.0)` を `NaN` に
するが、`(-2.0).powf(3.0)` は `-8` を返す——**定義域の判定を先に自分で書き、
`powf` は判定を通ったものにだけ使う。** `NaN` が出たら `DomainError` にする最後の
網も置く（判定漏れを黙って通さない）。

### §4.1 `0^0 = 1` にする

数学的には不定形だが、**電卓は 1 を返すのが慣行**である（IEEE 754 の `pow` も
`powf` も 1）。`DomainError` にすると `x^0` の一様性（どんな `x` でも 1）が
`x = 0` で崩れ、利用者には理由が見えない。

## §5 `sqrt(-4)` を落とす — 既存挙動の変更

**この spec で唯一、動いているものを壊す変更である。**

- `scientific::sqrt` の虚軸分岐を消し、`v.re < 0.0` を `DomainError` にする
- **複素数の入力（`v.is_real()` が偽）も `DomainError`** にする——裁定 1 の
  「関数は実数」を素直に読むとこうなる。`sqrt(3+j4)` は現状 極形式経由で答えるが、
  それも落とす
- `sqr`（x²）は**そのまま**——複素数の 2 乗は乗算であり、四則の側である
- `neg`（符号反転）も**そのまま**——同じ理由

### §5.1 `engine_table.rs` の既存行を書き換える — 順序が決まっている

**実測済み。書き換える行はここである**（`crates/calcarc-core/tests/engine_table.rs:354`）:

```rust
#[test]
fn square_root_of_a_negative_gives_an_imaginary_result() {
    // 従来機が Math ERROR を返す入力に、複素数対応の電卓は答えられる。
    assert_eq!(main_of(&["4", "neg", "sqrt"]), "j2");
}
```

**このリポジトリが意識して作った挙動である**——コメントが「従来機が Math ERROR を
返す入力に、複素数対応の電卓は答えられる」と誇っている。裁定 1 はそれを**逆に倒す**。

CLAUDE.md が定める規律に従う: **「電卓の挙動は `engine_table.rs` が仕様書。
キー列と表示の対応を先に変えてから実装を直す。」**

したがって plan の順序は:

1. **先にこの行を書き換える**（テスト名も `..._is_a_domain_error` に）。**赤を見る**
   ——実装がまだ `j2` を返すので落ちる。これが「仕様を先に動かした」証拠になる
2. そのあとで `scientific::sqrt` を直す

**コメントも書き換える。** 「複素数対応の電卓は答えられる」を残したまま
`DomainError` にすると、**文書が実装と逆のことを言う**——このリポジトリで既に
2 度踏んだ形である。「関数は実数に閉じる。複素数は入力と四則と表示の機能であって、
関数の値域ではない」と書き直す。

`sqrt` の複素経路を覆っているテストと golden を数える。`complex.json` の 77 件は

## §5.3 他セッションとの約束（2026-08-16、`feature/e2e-corpus` 担当と合意）

**守るのは「行」ではなく「記法の約束」だと相手が明示した。** 相手の直列化が
依存しているのは 3 つだけで、**特定の行ではない**:

1. **単項は後置**——数を入れてから `sqrt` / `sqr` / `sin` / `cos` / `tan` / `neg` を押す
2. **二項は必ず括弧で囲む**——`lparen … add … rparen`。**優先順位に一切依存しない**
3. **式の終わりは `eq`**

**この 3 つを壊さない。** 特に 1 番が変わると 4,000 件が一斉に別の式になる。

**4 本の spec はどれも 1〜3 を守る**: S-1 の単項 6 つは `apply_unary`（後置）に乗り、
`xʸ`（§3.1）と S-3 の `nPr` / `nCr` は二項として足すだけである。**優先順位の階層が
2 段→4 段になっても、相手が括弧で囲んでいる限り当たらない**（相手も確認済み）。

**行への依存は相手の段階 3c（括弧を省いたキー列）から生まれる。** そのとき読む行の
一覧を相手が送ってくれる。**いま渡すと実態より広い「触ってはいけない範囲」になる**
ので出さない、という相手の判断は正しい。


重量級検証コーパス（4,000 件）が**キー列の綴り**で電卓を叩いており、この spec の
実装がその足元を動かしうる。**確認して合意した制約:**

- **`KEY_TOKENS` は足すだけ。既存トークンの綴りを変えない・消さない。**
  1 文字変えると 4,000 件が全部「未知のキー」になる。§3 で `Key::Exp` を改名しないと
  決めているのは、この意味でも正しい
- **`reference/src/calcarc_reference/corpus_expr.py` の `UNARY_FNS` / `BINARY_OPS`
  に触らない。** あそこは相手の生成器の乱数の土台で、1 つ足すと同じ種でも
  4,000 件が総入れ替えになる。**関数を増やすのは `calcarc-core` と
  `web/src/calc/types.ts` の側だけ**
- **`engine_table.rs` の既存行を書き換えるのは §5.1 の 1 行だけ。** 相手の直列化は
  あの表を仕様として従う設計なので、**実装に入る前に、書き換える行を名指しで
  伝える**（伝達済み）

**相手が 4,000 件を全件走査して確認済み（2026-08-16）**: `["4","neg","sqrt"]` は
**0 件**、`neg` の直後に `sqrt` が来る形も**部分列として 0 件**。`sqrt` を含む 993 件は
すべて引数が非負である（生成器が負数の平方根を `OutOfShard` で捨てるため、
キー列に組み上がる前に消えている）。**したがってタイミングを合わせる必要は無い。**

**ただし相手の文書がこの変更で古くなる。** `docs/corpus-measurements.md` に
「`sqrt(-4)` の表示は `"j2"`（複素表記）」という**実測記録**があり、事実でなくなる。
ガード自体は正しいまま（範囲外であることは変わらない）で、変わるのは**理由**
——「読めない複素表記だから外す」から「エラー経路だから外す」へ。

**→ 完了条件に入れる: 実装したら `feature/e2e-corpus` の担当セッションに伝える。**
相手が実測し直して記録を更新する。**これは「実装が動いたときに、なぜエラーなのかの
記録が腐る」という一般的な形の一例であり、独立した検証層がそれを先に見つけた事例
である。**

**base-spec の訂正が要る。** §9.2 の一覧に定義域の但し書きを足し、§10/§11
（複素数と極座標は重要な基本機能）との関係を書く——**「複素数は入力と四則と表示の
機能であって、関数の値域ではない」**という 1 行が要る。

## §6 エラーの種類

`CalcError` にいま何があるかを plan の最初に確認する。**`DomainError` が無ければ
足す**——`SyntaxError` に混ぜない。「打ち方が悪い」と「その値には定義が無い」は
利用者にとって別の話で、`ln(-1)` を `SyntaxError` と言われても直しようがない。

WASM 境界と TS の型に 1 つ増えるので、`CalcErrorCode` の合併型も広がる。

**第 1 面は 32 スロットすべて埋まっている**（関数列 7 + メイングリッド 5×5）。
一方 **第 2 面（Shift）は空である**——`ariaLabel: "第2面（準備中）"` の
`EMPTY_FACE` が `sin` / `cos` / `tan` / `√` / `x²` に刺さっている。

## §7 盤面 — 確定（2026-08-16、ユーザー裁定）

**関数列が 2 段になった**（S-2 の裁定。7 列 × 2、キー幅 45.43px のまま）。
**第 1 面に 7 スロット増えた**ので、**よく使う関数は表に出す**——関数電卓で `ln` や
`log10` が Shift の裏なのは不便であり、空きを予約スロットで埋めたまま隠すのは
本末転倒である。

### 第 1 面

```
関数列 1 段目: [Shift] [sin] [cos] [tan] [√]  [x²]  [DEG/RAD]
関数列 2 段目: [ENG]   [ln]  [log] [1/x] [eˣ] [xʸ]  [°'"]
5×5 グリッド:  (  )  +/−  DEL  AC / 7 8 9 ÷ j / 4 5 6 × ▸∠ / 1 2 3 − EXP / 0 000 . + =
```

**2 段目は S-1 が 5 つ、S-2 が 1 つ（ENG）、S-4 が 1 つ（`°'"`）である。**
`°'"` を表に出すのはユーザー裁定（時間計算をよく使うため）。

**5×5 グリッドは 1 キーも動かさない**——3 タブで揃えた `AC` / `DEL` の位置と寸法。

### 第 2 面（Shift）

| 第 1 面 | Shift | 備考 |
|---|---|---|
| `sin` | `asin` | |
| `cos` | `acos` | |
| `tan` | `atan` | |
| **`eˣ`** | **`e`** | **同じ e。`eˣ` を Shift すると底そのものが出る**（ユーザー質問への答え） |
| `EXP` | `π` | 既存。変更なし |

**逆三角を Shift に置く**のは、使用頻度が低く、`sin`/`cos`/`tan` の裏という対応が
自然だからである。

**S-3 は数字 `7` `8` `9` の Shift を使う**（`n!` `nPr` `nCr`）。S-3 §6 のとおり。

**残る Shift の空き**: `√` `x²` `DEG/RAD` `ENG` `ln` `log` `1/x` `xʸ` `°'"` と
グリッドの大半。**将来の余地は十分にある**（双曲線関数、メモリ、`Ans` など）。

### 旧案（空きが無かった前提。記録として残す）

以下は関数列が 1 段だった時点の割り当てで、**もう採らない**。

| 第 1 面 | Shift（第 2 面） |
|---|---|
| `sin` | `asin` |
| `cos` | `acos` |
| `tan` | `atan` |
| `√` | `ln` |
| `x²` | `xʸ` |
| `EXP` | `π`（既存） |
| `j` | `log10` |
| `▸∠` | `eˣ` |
| `+/−` | `e` |
| `÷` | **`1/x`** |

**`÷` の裏に `1/x`** は意味の対応が良い（除算と逆数）。`√`→`ln`、`x²`→`xʸ` と同じ
「第 1 面のキーと第 2 面のキーが関係している」という並べ方に乗る。

**`√`→`ln` と `x²`→`xʸ` の対応は形が近い**（どちらも逆・拡張の関係）。
`j` と `▸∠` の Shift は複素数のキーなので、**第 2 面で実数の関数を置くのは
一貫していない**——ここは §9 の裁定待ちにする。

**`+/−` の Shift に `e`** は据わりが悪い。数の定数なので `EXP`（`π` が居る）の
近くが良いが、`EXP` の Shift は埋まっている。

## §8 検証

段ゲート（base-spec §49 は金融計算の規定だが、**コアと golden に触るので同じ順で
進める**）:

1. `CalcError::DomainError` の追加と `sqrt` の変更（**既存テストが赤になるところから**）
2. Python 参照 + golden（`scientific.json` に op 追加）
3. Rust のコア
4. WASM 境界と TS
5. 盤面（第 2 面）

**Python 参照の独立軸**: `mpmath` で高精度に評価し、`f64` の結果との相対誤差が
`tolerance` 内であることを見る（`scientific.json` は既に tolerance を持つ）。
**定義域の境界は golden の必須ケースにする**——`ln(0)` `ln(-1)` `asin(1)` `asin(1.0000001)`
`0^0` `(-2)^3` `(-2)^0.5` `sqrt(-4)`。

**赤確認**: `sqrt(-4)` がエラーになることを確かめる検査を足したら、**虚軸分岐を
戻して赤を見る**。
