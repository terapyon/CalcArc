# 括弧を省いたキー列（段階 3c）設計

2026-08-16

前提: [重量級検証コーパス（Layer 6）設計](2026-08-15-heavy-corpus-e2e-design.md)。
この文書はその §12 段階 3 のうち、**括弧を省いたキー列だけ**を扱う。

## 1. なぜやるか

成果物 `web/heavy-report.md` の「まだ一度も踏んでいない領域」に、こう書いてある。

> **括弧を省いた式。** キー列は二項演算を必ず括弧で囲む。したがって演算子の優先順位と
> 保留演算の意味論（`1 + 2 * 3` が 7 か 9 か）を一度も踏んでいない。

**電卓として、これが最大の未検証領域である。** 4000 件すべてが構造を括弧で明示しているので、
engine の `push_binop` の畳み込みループ——**保留中の `+` を抱えたまま `×` を先に畳む機構**——を
一度も通っていない。

## 2. 実装の事実（コードから確認、2026-08-16）

| | |
|---|---|
| 優先順位 | **2 段**。`crates/calcarc-core/src/engine/state.rs:46` で `Add`/`Sub` = 1、`Mul`/`Div` = 2 |
| 結合方向 | **全部左結合**。`engine/mod.rs:142` の `top.precedence() >= op.precedence()` |
| 表が守っているもの | `engine_table.rs:216` の `main_of(&["2","add","3","add"]) == "5"`。**途中の表示**で結合方向を捕まえる |
| 表が守っていないもの | **答えの側で結合方向を主張する行**（`10 - 3 - 2` が 5 か 9 か） |

## 3. 設計

### 3.1 省くのは、子の優先順位が真に大きいときだけ

| 式木 | キー列 | |
|---|---|---|
| `1 + (2 × 3)` | `1 add 2 mul 3 eq` | **省く**（子 2 > 親 1） |
| `(1 + 2) × 3` | `lparen 1 add 2 rparen mul 3 eq` | 残す（子 1 < 親 2） |
| `(10 − 3) − 2` | `lparen 10 sub 3 rparen sub 2 eq` | **残す**（同順位） |

3 行目が要点である。`(10−3)−2` の括弧を省いて `10 − 3 − 2` にできるのは**左結合だから**で、
省いた瞬間に直列化が結合方向を知ることになる。**同順位の入れ子は括弧を残す**——これで
結合方向を一切知らずに済む。

規則を一文にすると: **子が二項で、その優先順位が親より真に大きいときだけ、子の括弧を省く。**

**代償を正直に書く。** このコーパスは結合方向を検証しない。同順位の入れ子は常に括弧つきで
生成されるので、`10 − 3 − 2` のような列が一件も出ない。結合方向は `engine_table.rs` の
担当のままである（§2 のとおり、いまは途中の表示だけが守っている）。

### 3.2 新しいシャードとして足す。既存 4000 件は 1 件も作り直さない

式木に「括弧を省ける」性質を持たせて `random_node` を変えると、**乱数の消費列が変わり、
同じ種でも既存 4000 件が総入れ替えになる**（保守者レビューが複数の種で実測した性質。
上位設計書 §11 にも記載）。しかも上書き 2 件は `expr` で結び付いているので、入れ替われば
正しく赤くなるが、無用に赤くする理由がない。

**`corpus/generated/precedence-000.json` を新設する。** 生成器は独自の `random.Random(seed)` を
持つ（`build_shard` / `build_equivalences` と同じ作法）ので、既存シャードの乱数に触れない。

ファイル名が §4.2 の「電卓の種類 × シャード番号」の慣行から外れるのは意図的である。
これは新しい**電卓の種類**ではなく、同じ式の**別の直列化**なので、名前でそう分かる方がよい。

### 3.3 省ける括弧が 1 つも無い木は捨てる

省くものが無ければキー列が括弧つきの形と同一になり、**新しいことを何も試さないケース**が
混ざる。段階 2 で「裸のリテラル 529 件」を捨てたのと同じ理屈である。

**新シャードの全件が、必ず優先順位を踏む。**

### 3.4 レポートの領域判定を、キー列から導く

いまの「まだ一度も踏んでいない領域」の当該項目は**手書きの固定文**である。3c が入れば
部分的に嘘になり、そして手書きのままでは次に領域が埋まったときまた腐る。

**キー列から機械的に導く。** 判定はこうである——**同じ括弧の組の中に、優先順位の異なる二項
演算子が 2 つ以上現れる列は、定義上、優先順位が無ければ正しく解釈できない。** その件数を
実データから数える。

**「組」であって「深さ」ではない。** 初稿はここを「同じ括弧の深さ」と書いていたが、
それは誤りだった。深さが同じでも別々の括弧の中なら、その 2 つの演算子は同じ式に
並んでいない。実測した反例（`scientific-000.json` の `sci-000025`）:

    377 - ((553 / 982) / (189 - 996))
    lparen 3 7 7 sub lparen lparen 5 5 3 div 9 8 2 rparen div lparen 1 8 9 sub 9 9 6 rparen rparen rparen

`div`(2) と `sub`(1) がどちらも深さ 3 にあるが、`(553/982)` と `(189-996)` という
**別の組**である。構造は括弧が完全に決めており、優先順位は一切要らない。

深さで数えると、全二項を括弧で囲んでいる既存 2 シャードから **311 件の偽陽性**が出る
（`scientific` 191 件 + `equivalence` 4000 キー列中 120 件）。組で数えると**どちらも 0 件**
になり、`precedence-000.json` は 2000/2000 のまま。実装は `lparen` で新しい組を push する
スタックで行う。

この誤りの見つかり方も記録しておく。実装者は TS と Python の双子を 3 シャードで
突き合わせ、**完全に一致した**と報告した。それでも両方とも間違っていた——**両方が
この設計書の規則を実装していたから**である。CLAUDE.md の「同じアルゴリズムを両方に
書くと、同じバグが両方に入って検証の意味がなくなる」が、検証の道具そのもので起きた。
**突き合わせは、由来が独立でなければ何も保証しない。**

- 0 件 → 「一度も踏んでいない」
- 1 件以上 → 「N 件が踏んでいる。**ただし結合方向は踏んでいない**」

結合方向の方は踏んでいないままなので、そう書き続ける。**踏んだ / 踏んでいないの両方を、
同じ機構から出す。**

## 4. やらないこと

- **結合方向を検証しない**（§3.1 の代償）。同順位の入れ子は括弧を残す
- **既存シャードを作り直さない**（§3.2）
- **`corpus_expr.py` の `UNARY_FNS` / `BINARY_OPS` を触らない。** 新しい関数を足すだけ——
  あのタプルは生成器の乱数の土台で、要素が増えると既存 4000 件が総入れ替えになる
- **判定（`withinTolerance` / `classify`）を変えない。** 段階 3a で締めたものをそのまま使う
- **UI を通らない。** 本物のボタン操作は段階 4 の主題である

## 5. 要件

### 直列化

- **R1** 子が二項で、その優先順位が親より**真に大きい**ときだけ、子の括弧を省く
- **R2** 同順位の入れ子は括弧を残す（結合方向を知らずに済ませるため）
- **R3** 単項の後置と末尾の `eq` は従来どおり

### コーパス

- **R4** 新しいシャード `corpus/generated/precedence-000.json` に置く。既存シャードを作り直さない
- **R5** 生成器は独自の `random.Random(seed)` を持ち、既存シャードの乱数に触れない
- **R6** 省ける括弧が 1 つも無い木は捨てる。**全件が優先順位を踏む**
- **R7** 期待値は従来どおり mpmath が式木を評価したもの。**キー列の直列化とは独立**
- **R8** 再生成一致ゲートの対象に含める（`corpus/generated/` の全ファイルを列挙する既存の仕組みに自動で乗る）

### レポート

- **R9** 「優先順位を踏んだケース」の件数を**キー列から導く**（同じ括弧の**組**に優先順位の異なる二項演算子が 2 つ以上。深さではない——§3.4 の反例を参照）
- **R10** 0 件なら「一度も踏んでいない」、1 件以上なら「N 件が踏んでいる」と書き分ける
- **R11** **結合方向は踏んでいない**ことを明記し続ける

## 6. リスク

- **省ける括弧を持つ木の割合が低い可能性。** 深さ 3 の乱択で、優先順位の異なる二項が
  入れ子になる確率は測っていない。棄却率が高すぎれば分布の設計に跳ね返る。
  **実装の最初に測る。** 高すぎたら生成器に「異なる優先順位を優先して選ぶ」偏りを入れる
  判断があるが、それは分布を歪めるので、実測を見てから決める
- **`to_keys` と新しい直列化の二本立てになる。** どちらかだけ直す事故が起きうる。
  **同じ式木から両方を出し、括弧を除いた文字列が一致することをテストで固定する**——
  片方だけ変えれば赤くなる
- **結合方向を踏まないことが、レポートで誤読されうる。** 「括弧なし式を踏んだ」とだけ
  書くと、読み手は優先順位も結合方向も試されたと受け取る。§3.4 の書き分けが唯一の防御である
