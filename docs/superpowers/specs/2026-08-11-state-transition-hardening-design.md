# 状態遷移バグの系統的な潰し込み 設計書

対象: `calcarc-core` の電卓状態機械（`engine`）
前提文書: [docs/base-spec.md](../../base-spec.md)、[2026-08-11-vertical-slice-design.md](2026-08-11-vertical-slice-design.md)
作成日: 2026-08-11

---

## 1. なぜこれをやるか

Vertical Slice で見つかった実バグは、**キー列に偏っていた**。

| バグ | 種類 | 見つけた工程 |
|---|---|---|
| 連続した演算子で誤った計算（`3 + + 4 =` が 10） | キー列 | 全体レビュー |
| no-op キーを挟むと上記が復活（`3 + DEL + 4 =` が 10） | キー列 | 修正の再レビュー |
| DEL が虚数入力の `j` を捨てる（`3 + j4 DEL 5 =` が 8） | キー列 | 外部レビュー |
| リスナー再アタッチ中の打鍵取りこぼし | キー列 | CI |
| 除算の桁溢れ、有効数字、−0.0 | 数値 | golden 検証・個別レビュー |

数値側は golden 検証とタスクごとのレビューが捕まえた。一方**キー列側は 92 件のテストと proptest をすり抜けた**。proptest が `no-panic` しか検査していなかったためである。

この spec はその穴を埋める。新機能は足さない。

## 2. 検査できるものの限界

網羅列挙もランダム探索も、**オラクルを持たない**。したがって検査できるのは不変条件だけであり、**不変条件の質がこの spec のすべて**になる。

Python 側に素朴なオラクル電卓を書いて差分テストする案は検討したが、状態機械をもう一度書くことになり規模が一段大きくなるため、今回は採らない。

**成立していない性質を不変条件として書かない。** 成立しないものは「バグ」か「期待が違う」かのどちらかであり、仕分けずに書くとバグでないものが落ちるテストができる。本 spec に載せる不変条件はすべて、現在の実装に対して実測で成立を確認した。

## 3. 不変条件

### 3.1 採用するもの

| # | 不変条件 | 根拠 |
|---|---|---|
| I1 | `reduce` は panic せず、常に有効な状態を返す | 既存 |
| I2 | 被演算数の数 ＝ 保留中の二項演算子の数（エラー時を除く） | 既存 |
| I3 | **実数を入れれば実数が出る。** 実数のみで構成された入力に対し、出力の虚部は厳密に `0.0`。**ただし負の実数の `sqrt` を除く**（下記） | 実測。実数 28 種 × 全単項関数 × 両角度モード ＋ 四則 3,360 件、および乱数 20 万件 × 9 演算で漏れ 0 件 |
| I3b | **負の実数の `sqrt` は純虚数を返す。** 実部が厳密に `0.0` である | 実測。`4` `+/−` `√` は `j2`。極形式を経由する実装では実部に 1.2e-16 が残る |
| I4 | **二項演算子の連続打鍵は、最後の 1 つを押したのと同値。** 同種・異種を問わず、また表示だけを変えるキーを挟んでも成り立つ | 実測。`3 + + 4 =` `3 + × 4 =` `3 + DEL + 4 =` `3 + DRG + 4 =` |
| I5 | **エラー中は AC 以外のどのキーでも状態が変わらない** | 実測。`Key::ALL` の AC を除く 29 キーすべてで状態不変 |
| I6 | **AC はどんな状態からも初期状態に戻す。** 角度モードと表示形式だけは保つ | 既存 |

**I3 の例外は 1 つだけで、意図されたものである。** 虚軸への入口は `j` キーと「負の実数の `sqrt`」の 2 つしかない。前者は入力なので I3 の前提（実数のみの入力）に入らない。後者は `sqrt(-4) = j2` を返すという設計上の機能であり（Vertical Slice 設計書 §4.1）、従来機が `Math ERROR` を返す入力にこの電卓が答えられることの根拠でもある。

したがって I3 を「例外なし」と書くと、網羅列挙が `+/−` `√` を踏んだ瞬間に**バグでないものが落ちるテスト**になる。§2 で自ら戒めた形そのものなので、例外を明示し、対になる性質を I3b として分けて固定する。I3 と I3b を合わせて「実軸は演算で閉じており、虚軸への出口は 1 つだけ」を表す。

I4 についても範囲を明示する。**実際に起きたバグは同種の連打ではなかった。** `3 + × 4 =` は異種の連続で最後が勝つ形、`3 + DEL + 4 =` は消すもののない DEL を挟んだ形で、後者は一度修正をすり抜けている。検査関数はこの 2 形を含む。

I3 は現在、個々の関数の実装詳細に依存して成立している。`mul` の虚部が `a.re*b.im + a.im*b.re` で両虚部が 0 なら厳密に 0 になること、`div` が `b.im == 0` のとき第 1 分岐で `t = 0` になること、`sin`/`cos` の `sinh(0)` を `finite()` の負ゼロ均しが吸収すること、`tan` が実数どうしの `div` に帰着すること。**どこにも明文化されておらず、守るテストもない。**

`ln` / `exp` / `asin` / `acos` / `atan` / `xʸ` を追加するとこの性質は自明でなくなる。とくに極形式を経由する実装は実部・虚部の両方に誤差を撒く。`sqrt` が負の実数のために専用経路を持つのはまさにこの理由である。**壊れる前に固定する**ことに価値がある。

### 3.2 採用しないもの

**「DEL は直前の打鍵 1 つを取り消す」は成立しない。** 実測:

```
3 + 4 DEL     → 3      直前の 4 が取り消された     ✓
3 + DEL       → 3      直前の + は取り消されない   ✗
3 + 4 = DEL   → 7      直前の = は取り消されない   ✗
30 sin DEL    → 0.5    直前の sin は取り消されない ✗
```

DEL は**入力中の文字を消すバックスペース**であって、打鍵の取り消しではない。設計書 §4.3 もそう定めており、CASIO の DEL も同じである。この性質を不変条件として書くのは、仕様の取り違えになる。

## 4. DEL の仕様変更

現在 `3` `(` `DEL` は `0` を表示し、**括弧の深さ 1 が残る**。`(` が入力中の 3 を捨て、DEL は消すものが無いため何もしないためである。利用者には「3 が消えたうえ、閉じていない括弧だけが残った」と見える。

DEL が**閉じられていない開き括弧も消せる**ようにする。

```
3 ( DEL          →  0、深さ 0
3 + ( DEL 4 =    →  7          括弧の押し間違いが綺麗に戻る
3 + ( 5 DEL DEL  →  5 を消し、次に括弧を消す
```

**演算子は消せない。** 境界の根拠は「その打鍵がまだ計算を起こしていないか」である。`(` は何も計算しないが、`+` は入力を確定させて被演算数を積み、場合によっては畳み込みも行う。演算子を消せるようにすると、消えた入力を復元する必要が生じ、それは undo になる。undo は状態に履歴スタックを要求し、`EngineState` が毎打鍵で WASM 境界を往復する設計（D7）に正面から効く。独立した機能として、それ自体の検討に値する。

この変更に伴う不変条件を 1 つ足す。

| # | 不変条件 |
|---|---|
| I7 | DEL は次の優先順位で 1 つだけ消す。**数字 → `j` マーカー → 閉じられていない開き括弧。** どれも無ければ状態を変えない |

**3 段であることが要点である。** 素の `j`（数字を伴わない虚数入力、表示は `j`）は文字列としては空だが、消す対象としては存在する。2 段で書くと `3 + ( j DEL` で `j` と括弧のどちらが消えるか読めない。

3 段すべてを通る例は、虚数入力を括弧の中で打った場合である。

```
3 + ( j 4 DEL DEL DEL
            │   │   └ 3 段目: 開き括弧が消える
            │   └──── 2 段目: j マーカーが消える
            └──────── 1 段目: 数字の 4 が消える（表示は j になる）

3 + ( 5 DEL DEL       →  5 を消し、次に括弧を消す（2 段目は通らない）
3 + ( j DEL           →  j が消える。括弧は残る
j DEL                 →  j が消える
```

### 4.1 DEL と `operator_pending`

DEL で**演算子の直後に戻った**とき、次に押した演算子は差し替えでなければならない。`3 × 4 DEL × 5 =` は 15、`3 × ( DEL × 4 =` は 12 である。実装は当初どちらも取りこぼしており（45 と 0）、既存の表テストが加算経路しか持っていなかったため表からも見えていなかった。加算では `3 + 3 + 4` も `3 + 4` も 7 になるので、**この種の穴を塞ぐ固定テストは乗算で書く**こと。

直し方の要点は、`operator_pending` の意味を「**直前のキーが二項演算子だったか**」から「**いま演算子の直後に居るか**」に読み替えることである。入力中の文字も `(` も居場所を動かさない。DEL で消せば元の場所に戻るのだから、そのあいだ旗を落とす理由がない。落とすキーは値を確定させるもの（`=` `)` `π` 後置関数 `AC`）だけで、差し替えてよいかどうかは `push_binop` が旗と「入力中のバッファが無い」「スタックの先頭が演算子である」を併せて判断する。

**採らなかった案: DEL 後の状態から構造的に導出する**（バッファが無く、演算子スタックの先頭が `Op` なら真とする）。これだと `3 + ( 4 ) 5 DEL + 6 =` が 13 ではなく 9 になる。`)` の直後は演算子の直後ではないのに、状態としては `3 + 4 DEL` と見分けがつかないためである。

```
3 + 4 DEL         →  buffer なし、operands [3]、operators [+]、current 3
3 + ( 3 ) DEL     →  buffer なし、operands [3]、operators [+]、current 3
```

**この 2 つは観測可能な状態が完全に一致し、次の `+` に対して違う答えを出さなければならない。** だから「演算子の直後か」は状態から導出できず、旗が運ぶしかない。同時にこれは、`engine_robustness.rs` のどんな観測ベースの不変条件もこの区別を固定できないということでもある。**この 2 行を守るのは `engine_table.rs` だけである。**

## 5. 網羅列挙

### 5.1 なぜ網羅か

見つかったキー列バグの長さは、いずれも 7 以内だった。

```
3 + + 4 =        長さ 5
3 + DEL + 4 =    長さ 6
3 + j 4 DEL 5 =  長さ 7
```

ランダム探索はこの領域を「たまたま」しか踏まない。網羅なら**短い列にバグが無いことを保証できる**。

### 5.2 等価類とキーの畳み込み

30 種のキーをそのまま列挙すると長さ 7 で 10^10 通りになり成立しない。構造的に等価なキーを代表 1 つに畳む。**畳んでよいかの根拠は「状態機械に対する作用が同じか」であり、表示上の違いではない。**

| 等価類 | キー | 代表 | 根拠 |
|---|---|---|---|
| 数字 | `1`–`9` | `3` | いずれも入力バッファに 1 文字追加する |
| ゼロ | `0` | `0` | 先頭の 0 を置き換える分岐を持つので数字と分けない |
| 小数点 | `.` | `.` | 重複で `SyntaxError` になる唯一のキー |
| 虚数 | `j` | `j` | 虚数入力を開始する。虚軸への 2 つの入口の一方 |
| 低優先の二項演算 | `+` `−` | `−` | 優先順位 1。畳み込みの条件が同じ |
| 高優先の二項演算 | `×` `÷` | `÷` | 優先順位 2。同上 |
| 確定 | `=` | `=` | 保留中をすべて畳む |
| 括弧 | `(` `)` | 両方 | 対で意味を持つので畳めない |
| 後置関数 | `√` `x²` `+/−` `sin` `cos` `tan` | `√` | 入力を確定してから現在値に即時適用する。作用の形が同じ |
| 定数 | `π` | `π` | **入力バッファを破棄して定数で置き換える唯一のキー。** 数字（追加する）とも `(`（破棄して括弧を積む）とも異なる |
| 表示トグル | `DRG` `▸∠` | `▸∠` | どちらも `angle` / `form` しか変えず、`buffer` `current` `operands` `operators` に触れない。`operator_pending` の扱いも同一 |
| 消去 | `DEL` `AC` | 両方 | 作用がまったく違うので畳めない |

`√` を後置関数の代表にするのは、`sqrt` が負の実数のために専用経路を持ち（I3b）、他の単項関数と異なる分岐を通るためである。この分岐を網に含めておきたい。

**等価類の中から選ぶ代表は「作用が同じなら何でもよい」ではない。射程の広いほうを選ぶ。** 当初は `+` `×` `DRG` を代表にしていたが、3 つとも自分の等価類でいちばん射程の狭いキーだった。

- **`+` `×` には負の数への直接の経路がない。** 初期値 0 から `+` `×` `√` `π` と数字 3 / 0 だけで閉じた集合は非負にとどまる。`−` なら `− 3 = √`（長さ 4）で I3b に届く。実測: `sqrt` の負実数の専用経路を潰して極形式経由に戻す退行を入れると、`−` の網は `3 . − π − √` で I3b が赤くなる。到達回数は `+` `×` の 685 回に対し `−` `÷` で 2606 回。

  **ただし「`+` `×` の網は I3b に一度も到達しない」は誤りである。** レビューの初期にそう書いたが、実測で否定された。`j` があるため `j × =` が −1 を返し（長さ 3）、`j × = √` で I3b に届く（長さ 4）。虚数どうしの積という、実数の演算子だけを見ていては気づかない経路である。**`−` の価値は「唯一の到達手段」ではなく「直接の経路を足して到達回数を 4 倍に広げること」**であり、代表を戻してよい理由にはならない。到達可能性を alphabet の見た目から論じると、`j` のような型をまたぐキーを見落とす。
- **`÷` は畳み込みの途中で失敗できる唯一の二項演算子である。** `reduce_top` が演算子と被演算数 2 つをスタックから降ろした後に `DivisionByZero` を返すため、**被演算数を消費しきった形のエラー状態**が生まれる。`×` の網ではこの形に一度も入らない。実測: 網が触れるエラーの種類は `+` `×` では `SyntaxError` だけ（構造 1,112,444 件）、`−` `÷` では `DivisionByZero` が構造で 366,364 件・全等価類で 219,517 件加わる。
- **`DRG` はこの網では何も変えないキーになる。** `angle` が効くのは三角関数と極形式の角度表示だけで、網は単項関数を `√` に畳んでいる。`▸∠` なら `form` が効いて極形式の描画が網の全域で走り、I1 がそれを見る。実測: `try_format_polar` が `r = 0` で空文字列を返す退行を入れると、`▸∠` の網は `3 3 3 3 ( ▸∠` で「display is empty」を出し、`DRG` の網は緑のまま通る。

**採らなかった案: 畳まずに `+` と `−`、`×` と `÷`、`DRG` と `▸∠` を両方入れる。** 列数はキー数の長さ乗で効く。構造の網を 10 キーから 11 キーにすると長さ 7 で 1.95 倍、全等価類の網を 14 キーから 15 キーにすると長さ 6 で 1.5 倍になり、どちらも単独で §5.4 の予算（壁時計 6 秒）を超える。代表の差し替えならキー数も列数も時間も変わらないまま、上の 3 つの分岐が全部入る。**射程の広い代表を選ぶことは、等価類を畳むことの費用を払い直さずに済ませる唯一の方法である。**

畳み込みは**構造を保つ**。`3 + j 4 DEL 5 =` は代表キーでは `3 + j 3 DEL 3 =` になるが、DEL が `j` を捨てるバグは値に依存しないため同じように露見する。一方、値に依存するバグ（先頭の 0 の扱いなど）は畳み込みで見えなくなる。そのため `0` を代表キーに残すが、**残すのは §5.4 の「全等価類」の網だけ**である。構造の網に足すと長さ 7 の列数が跳ね上がるのに対し、先頭の 0 の扱いは長さ 6 で足りるためである。

### 5.3 枝刈り

エラー状態に落ちた列は、以降 AC 以外のキーが無効である（I5）。したがって**続きを辿っても新しい状態に届かない**ので枝刈りする。

刈るのは**降下だけ**である。遷移そのものは必ず検査する。枝刈りの根拠が I5 である以上、I5 を検査せずに刈っては循環で、しかも I5 だけが網羅から漏れる。実装で一度この誤りを踏み、構造の網で 553,212、全等価類の網で 369,785、合わせて 92 万遷移——ちょうど I5 の定義域全体——が未検査になっていた。

降下の枝刈りで、辿る遷移は 1,111 万から 723 万（構造、35% 減）、811 万から 625 万（全等価類、23% 減）になる。

### 5.4 2 つの網

1 つの列挙で全部を覆おうとすると重くなる。対象に必要なだけの網を張る。

| 列挙 | 代表キー | 長さ | 列数 | 時間 |
|---|---|---|---|---|
| 構造 | `3` `.` `j` `−` `÷` `=` `(` `)` `DEL` `AC` | 7 | 723 万 | 3.7s |
| 全等価類 | 上記 ＋ `0` `▸∠` `√` `π` | 6 | 625 万 | 4.2s |

**壁時計で 4.3 秒**（debug、CI が使う構成での実測）。cargo は既定でテストを並列に走らせるので、2 本の合計 7.9 秒ではなく長いほうに揃う。表の秒数は 1 本ずつ逐次で測った実費である。**この 2 つを混同しないこと**——実装中に逐次の和を壁時計と取り違え、予算超過だと誤って報告したことがある。完了条件（§8）が言う 6 秒はすべて壁時計である。

計測は網 2 本だけを走らせた値であることに注意する。CI の `cargo test --workspace` では同じバイナリ内で proptest 3 本が同時に走るため実測は伸びる（手元で 4.7 秒）。コア数の少ない runner ではさらに逐次に近づく。

不変条件 1 回あたりの費用は `display` が支配する。**検査は `reduce` が返した `DisplayState` に対して掛け、`display(次の状態)` を組み直さない。** 組み直すと毎遷移で `display` が 2 回になり、全等価類の網が 4.2s から 6.7s に伸びる。返り値を使えば I1 がそのまま「WASM 境界に渡る値」の検査になるので、費用と射程の両方で有利である。返り値が `display(次の状態)` と一致すること自体は `reduce` の最終行 1 行の性質でしかないため、**乱択 2 本だけが検査する**（採らなかった案: 網羅列挙でも毎遷移で検査する。2.4 秒に見合うものが無い）。

分ける理由は実測にある。13 キーで長さ 7 まで回すと **35 秒**かかり、現在 25 秒の Rust ジョブを倍以上にしてしまう。一方で必要な長さは対象ごとに違う。`3 + j 4 DEL 5 =` は長さ 7 だがトグルを使わないので構造の網で踏める。`3 + DRG + 4 =` は長さ 6 なので全等価類の網で踏める。

長さ 8 は 51 秒かかるため採らない。

（35 秒と 51 秒は、不変条件を持たない試作で測った 20.8 秒・29.8 秒を、構造の網の実測比 3.1s→5.26s で割り戻した見積りである。実測ではない。試作は構造しか見ておらず、本番の不変条件は毎遷移 `display` で文字列を組むぶん重い。）

## 6. ランダム探索の強化

網羅が届かない長い列を担当する。現在の生成器は 30 キー一様・長さ 0〜40 で、**約 74% の列が途中で `SyntaxError` へ落ちる**。対応しない `)` を 1 キーあたり 1/30 の確率で引き、40 打鍵のあいだに一度も引かない確率が `(29/30)^40 ≈ 0.26` だからである。落ちた後は AC 以外が無効なので、列の後半が探索に寄与しない。

2 点変える。

- **重みを寄せる。** 演算子と括弧の比率を上げ、深い入れ子と長い畳み込みに届かせる
- **エラーから復帰させる。** エラーに落ちたら AC を挟んで継続し、列の後半を使い切る

**この 2 点の役割を取り違えないこと。列が生き延びるのは復帰のおかげであって、重みのおかげではない。** 重みを寄せた後の `)` は合計 20 のうち 2、すなわち 10% で、一様な 3.3% の**3 倍多い**。列の 9 割近くが途中で一度はエラーに落ちる（長さ 0〜120 に伸ばしたぶん、割合はむしろ上がっている）。重みが効くのは深さのほうで、それも絶対値ではなく `(` 15% 対 `)` 10% という比が効いている。「`)` を薄くすれば列が死ななくなる」と読むと、重みを触ったときに深さだけが静かに消える。到達距離を表明するテスト（`the_weighted_search_still_reaches_deep_states`）が測っているのはその深さである。

`crates/calcarc-core/tests/engine_robustness.rs` に集約する。

## 8. 完了条件

## 9. スコープに含まないもの

- 複素四則演算の golden 検証。別 spec（A1）で扱う
- 表示フォーマッタの言語間検証
