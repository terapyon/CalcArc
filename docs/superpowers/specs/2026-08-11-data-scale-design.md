# Data Scale Calculator（M4）— 設計

日付: 2026-08-11
対象: base-spec §14〜§17・§47 M4 の MVP スコープ。issue #7 をこの PR で close
前提: PR #20（golden-arithmetic）マージ後の main から始める

## §0 目的

count × dimensions × datatype からバイト数を求め、10 進（KB/MB/GB/TB）と
2 進（KiB/MiB/GiB/TiB）の両方で表示する（§17「両者を混同しない」）。

基準例（§49 M4）: `100M × 768 × float32` → バイト数 307,200,000,000、
表示 **307.2 GB / 286.1 GiB**。

これは 2 つ目の Calculator モジュールであり、**プラットフォーム化（§8）の
最初の一歩**——初のモジュール切替ナビゲーションが入る。

## §1 #7 の正式化: 数値型は抽象しない

**決定: Data Scale は Scientific と数値型を共有しない。** `data_scale` は
モジュール専用の値型とロジック（u128 ベース）を持ち、`Value{f64,f64}` と
`engine` には触れない。共有するのは次の 3 つだけ（§8）:

1. **エラー分類**: `CalcError`（`error.rs`）。オーバーフローは既存の
   `CalcError::Overflow` を使う。新しいエラー型は作らない。
2. **表示の原則**: 内部値と表示の分離（§26）、丸めは round-half-to-even
   （`numerical-policy.md` の既定。ただし実装は共有しない——f64 の書式化
   関数は u128 に流用できないため、§3 の整数丸めを専用に持つ）。
3. **UI プラットフォーム**: ナビゲーション・デザイントークン・a11y の流儀。

理由: バイト数は Exact Integer（§24）であり、f64 に載せた瞬間に 2^53 超で
嘘になる。逆に複素数は整数に載らない。両者を覆う抽象は「どちらにも最適で
ない共通型」にしかならず、§25（暗黙のオーバーフロー禁止）と §24（可能な
限り整数演算）を同時に満たす最短の道は**分離**である。この記録をもって
#7 を close する（将来 Loan/Finance が Decimal を要するときも同じ原則:
モジュール専用型 + 共有はエラー分類と表示原則のみ）。

## §2 計算コア（`crates/calcarc-core/src/data_scale/`）

- **`DataType`**: §16 の 9 種（int8 / uint8 / int16 / float16 / bfloat16 /
  int32 / float32 / int64 / float64）。`bytes_per_element()` は 1/1/2/2/2/4/4/8/8。
  境界トークン（`from_token`/`token`、小文字そのまま）を `Key` と同じ流儀で持つ。
- **計算**: `count × dimensions × bytes_per_element` を **u128 の checked 演算**
  で行い、あふれたら `Err(CalcError::Overflow)`（§25。u128 は同節の第一候補）。
  count/dimensions の入力は 10 進数字列として受け、u128 に checked でパース
  する（先頭ゼロ可、空・非数字・u128 超は `SyntaxError`）。0 は正当な入力
  （結果 0 bytes）。
- **panic しない**: 既存の deny 属性の下に入る。`unwrap`/`expect` 禁止。
- engine/`reduce` には一切触れない。キーストローク状態機械ではない。

## §3 表示: 厳密整数と表示丸めの分離（§26 の整数版）

- **バイト数は厳密整数のまま持ち、そのまま表示する**（3 桁区切り。例:
  `307,200,000,000 bytes`）。表示丸めした値を再計算に使う経路は作らない。
- **単位表示は自動スケール**: 10 進は KB/MB/GB/TB から、2 進は KiB/MiB/GiB/TiB
  から、値が 1 以上になる最大の単位を選ぶ（1000 bytes 未満は bytes のみ）。
  §15 の列挙は候補単位の集合であり、MVP は各系 1 行ずつ表示する。
- **丸めは小数第 1 位、round-half-to-even**（基準例 286.102294921875 → 286.1
  と整合。既定の丸め規則に一致）。
- **丸めで表示値が 1000.0（2 進は 1024.0）に達したら、単位を再選択する。**
  例: 999,999,999,999 bytes は単位選択時点では GB だが、小数第 1 位への丸めで
  1000.0 に繰り上がるので **1.0 TB** と表示する（`1000.0 GB` とは出さない）。
  2 進側（1023.95 GiB → 1.0 TiB）も同様。判断は**丸めた後の値**で行う——
  `format_real` の指数表記切替（丸めで 1e10 に繰り上がる値は指数表記）と
  同じ設計思想であり、このプロジェクトで 3 度目の同一クラスなので明文で固定
  する。**上位の単位が無いとき（TB/TiB）だけは再選択せず、そのまま出す**
  （1000 TB 以上は通常表示でも `1234.5 TB` の形になるため、`1000.0 TB` は
  異常ではなく連続的な表示である）。
- **換算経路に f64 を使わない**: 商 `q = bytes / D` と剰余 `r = bytes % D`
  （D は 1000^k または 1024^k）から、小数第 1 位を `10 × r / D` の整数丸め
  （half-to-even は剰余の比較で判定）で得る。`10 × r` は r < D ≤ 2^40 なので
  あふれない。u128 の全域で厳密。
- 表示文字列の形は `"307.2 GB"` / `"286.1 GiB"`（数値・空白・単位）。`.0` も
  省略しない（`"5.0 KB"`）——桁の見た目が揃い、パースも一意になる。

## §4 WASM 境界: reducer ではなく純関数

**決定: `data_scale` の境界は 1 つの純関数にする。** Scientific の
`reduce(state, key)` はキーストローク状態機械だから状態の受け渡しが要るが、
Data Scale は**フォーム → 即計算**であり、保持すべき状態がない。状態機械を
輸入するとフォームの値が二重管理になる。

```rust
#[wasm_bindgen]
pub fn data_scale(count: &str, dimensions: &str, dtype: &str) -> JsValue
```

- **入力は文字列**。JS の number は 2^53 超で精度を失うため、u128 の定義域を
  境界で殺さないには文字列しかない。パースは Rust 側（§2）。
- 戻り値は `{ bytes: string | null, bytesGrouped, decimal, binary,
  error: CalcErrorCode | null }` の 1 オブジェクト。**bytes も文字列**
  （JSON/JS number の 2^53 制限。testdata も同じ理由で文字列にする——§5）。
- 例外は投げない。エラーは戻り値の一部（既存の境界規約のまま）。
- 計算ロジックは持たない（既存の adapter 規約のまま）。

## §5 検証: `testdata/data_scale.json` の新設（§35）

- **Python 参照は組み込み int**（§29）。任意精度なので u128 と自然に手法が
  独立する。単位換算も `divmod` の整数演算で書く（f64 を経由しない点だけが
  共有される「約束」であり、アルゴリズムの共有ではない）。
- **比較は完全一致**。バイト数（文字列）と表示文字列（`"307.2 GB"` 等）を
  文字列等値で突き合わせる。**`tolerance` フィールドは持たない**——整数と
  決定的な丸めに許容誤差は存在しない。float の golden と混ぜない。
  新スキーマ（`schema: 1`、data_scale.json 独自）。
- **エラーケースも golden に含める**: `expect: {"error": "Overflow"}` の形。
  Python 側は「積が 2^128 以上なら Overflow」と判定する。これは Rust の
  アルゴリズムの写しではなく、§25 が定めた **u128 という公開契約**の検査で
  ある（contract を知らなければ独立検証は書けない）。
- ケース設計: 基準例（100000000 × 768 × float32）、§25 の例
  （1000000000 × 65536 × 8 バイト型）、9 データ型の各 1 件、0 件・1 件の
  境界、u128 上限近傍の成功ケース（積 < 2^128 ぎりぎり）、上限超の
  Overflow ケース、単位の切り替わり境界（999 / 1000 / 1024 bytes 等）、
  丸めが half ちょうどになるケース（half-to-even の実証。10 進・2 進の両方）、
  **丸め繰り上がりが単位境界を越えるケース**（§3 の再選択規則の実証。
  999,999,999,999 bytes → `1.0 TB` の類と、その 2 進版。10 進・2 進の両方）。
- **表示丸めのアルゴリズムは Rust と Python で実質同型になるが、これは
  §30 違反ではない**: 丸め規則（小数第 1 位・half-to-even・繰り上がり時の
  単位再選択）は仕様として固定された**公開契約**であり、u128 の上限と同じ
  位置づけである。契約を知らなければ独立検証は書けない。アルゴリズムの
  独立性が意味を持つのは「答えの求め方」（積の計算そのもの）であり、
  そちらは u128 checked と任意精度 int で分かれている。
- **新設検査の赤確認**（house rule）: Rust 側の換算を意図的に 1000↔1024 で
  取り違える一時変更で、10 進/2 進の混同が golden で赤になることを確認して
  戻す（§17 の「混同しない」を検査が実際に守っている証拠）。half-to-even
  ケースも half-up に一時変更して赤を確認する。

## §6 UI とナビゲーション（プラットフォーム化の設計判断）

- **ナビゲーション**: 画面上部のタブ 2 つ（Scientific / Data Scale）。
  - 実装は React の状態 + **URL ハッシュ**（`#scientific` / `#data-scale`）。
    リロード・共有・ブラウザ履歴に耐え、ルーターライブラリは入れない
    （2 モジュールに対して依存を足す理由がない。Loan が入る M6 で再評価）。
  - a11y: `<nav>` ランドマーク + `aria-current="page"`。タブごとに
    アクセシブルネーム。切替でフォーカスが迷子にならないこと。
  - モバイル第一（§42）: タッチターゲット 44px 以上（既存の e2e 基準に従う）。
- **Data Scale のフォーム**: count・dimensions のテキスト入力（inputmode
  numeric、`<label>` で結線）+ データ型の `<select>`（9 種）。入力のたびに
  即計算（ボタンなし）。エラーは結果領域に表示（既存の Math ERROR の流儀）。
  結果領域は `role="status"`（既存の Display と同じ）。
  **未入力とエラーを区別する**: フィールドが空のあいだは中立表示
  （結果を出さないだけ。エラーではない）。不正な文字列（数字以外・u128 超）
  のときだけエラー表示。区別しないと初期状態と入力途中でエラーが点滅する。
  この区別は UI 層の責務であり、コアの `SyntaxError`（§2）は「空文字列を
  渡されたら」の契約として変えない——UI が空のとき呼ばなければよい。
- **層の分離は既存の規約のまま**: `web/src/datascale/`（仮称）に framework
  非依存のラッパー（React import 禁止）、`web/src/ui/` に React コンポーネント。
  Scientific の `web/src/calc/` には触れない。

## §8 スコープ外

- SI プレフィクス表示、単位の手動選択、KB=1024 の俗用互換。
- Loan / Finance（M6）、PWA（M5）。
- Scientific 側の変更一切（`calc/`・`engine`・キーマップ不触。ただし
  App のルートにナビが入るぶんの組み込み変更は含む）。
- 履歴・設定などのプラットフォーム共通機能（§8 の将来分）。
