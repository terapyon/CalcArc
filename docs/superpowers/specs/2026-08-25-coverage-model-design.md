## 1. 背景

CalcArcのHeavyテストは、Rust/Wasmの計算結果をPythonの独立参照実装と照合し、実ブラウザ上で数万件を検証している。

基準runでは次の結果を得ている。

| 項目 | 基準値 |
|---|---:|
| 全ケース | 33,567 |
| 外部参照と照合したケース | 28,239 |
| 金融ケース | 3,500 |
| 金融の正常ケース | 3,139 |
| 金融の期待エラーケース | 361 |
| 金融の不一致 | 0 |
| 金融変異 | 10種類すべて検出 |
| 参照実装が答えを出せず棄却した金融候補 | 7 |

金融コーパスには、すでに次の仕組みがある。

- 金利・期間・複利周期・税有無の水準定義
- 正常境界・異常境界の名指し層
- ペアワイズによる組合せ生成
- 層別最低件数
- 17種類の入力エラー経路
- 参照実装の限界理由の型による分類
- 未分類の参照実装エラーで生成器を停止する処理
- 既知欠陥を注入する変異テスト

一方、現在のHeavyレポートでは次が十分に見えない。

1. 何を必須のテスト空間として定義したか。
2. 必須セルのうち、実際に何セルを検証したか。
3. 生成前に除外した組合せと、その理由。
4. 参照実装の限界で検証できなかった入力。
5. 乱択候補の棄却と、テスト空間からの除外の違い。
6. `loan_term`のように、入力構成用の水準と実際の結果が一致しないケース。

本仕様は、現在のテストを大きく作り直さず、オムロンの事例にある「試験空間と、試験しない範囲・理由を説明可能にする」という考え方を部分的に導入する。

## 2. 目的

本仕様の目的は、Heavyテストの結果から、次の問いに機械的かつ人間にも読める形で答えられるようにすることである。

- どの入力因子と水準を検証対象にしたか。
- どの組合せを必須としたか。
- 必須組合せのうち、何を実行したか。
- 実行しなかった組合せは何か。
- 実行しなかった理由は、安全な重複排除か、構成不能か、参照実装の限界か。
- 未説明の未実行セルが残っていないか。
- 前回のrunから、網羅範囲や除外理由が意図せず変化していないか。

## 4. 用語

### 4.1 因子

計算結果へ影響する入力上の軸。例: 金利、期間、複利周期、税有無。

### 4.2 水準

因子を代表させる値または同値クラス。例: 金利 `0`、`0.0001`、`100`、期間 `1`、`12`、`1200`。

### 4.3 要求セル

テスト空間モデルが「検証対象」と定めた一つの水準、境界、または水準の組合せ。

### 4.4 被覆セル

実行されたケースにより、要求どおり検証できた要求セル。

### 4.5 除外セル

要求セルとして数え上げられたが、理由を明示して実行対象から除外したセル。

### 4.6 未達セル

要求セルであるにもかかわらず、被覆も理由付き除外もされていないセル。未達セルはテスト設計上の不足である。

### 4.7 生成候補棄却

乱択生成の途中で作られた候補を、定義域外、重複、Overflowなどの理由で捨てた回数。これは乱数生成の効率を示すテレメトリであり、テスト空間のセル数ではない。

### 4.8 期待エラー

`SyntaxError`や`Overflow`になることを期待値として持ち、実際に照合したケース。これは除外ではなく、実行済みの正常なテスト結果である。

### 4.9 オラクル限界

製品側ではなく参照実装側の探索・境界判定などの都合により、期待値を作れず検証できなかった入力。

## 5. 全体設計

テスト空間に関する情報を、次の3層へ分離する。

1. **モデル**: 必須の因子、水準、境界、被覆強度を定義する。
2. **実測**: 生成済みコーパスが被覆したセルを数える。
3. **説明**: 未実行セルと生成候補棄却を、理由別に記録・表示する。

モデルと実測は同じ生成処理から機械的に算出する。Heavyレポートへ手書きの実測値を埋め込んではならない。

## 6. 導入段階

### 6.1 第1段階: 金融モデルの正式化と可視化

第1段階は必須とする。

- 生成前の除外を理由付きで記録する。
- 参照実装が答えられなかった候補を「未検証」として表示する。
- Heavyレポートに簡潔な網羅表を追加する。
- `loan_term`の構成用目標期間と実際の結果のずれを明示する。

### 6.2 第2段階: 科学計算の部分モデル

第2段階は第1段階の完了後に実施する。

- 現在のシャードを実験ブロックとして利用する。
- 各シャードに少数の要求軸と最低件数を定義する。
- 既存の生成候補棄却をレポートへ表示する。
- 連続値の完全列挙や全直積は行わない。

## 7. 金融テスト空間モデル `finance-v1`

### 7.1 既存の基本水準

次の既存水準をモデルの一次資料とする。レポート側へ写しを作ってはならない。

#### 金利

正常水準:

`0`, `0.0001`, `0.001`, `0.01`, `0.1`, `1.5`, `2.7125`, `20`, `99.9999`, `100`

異常水準:

`100.0001`、空文字列、非数字、負数、小数5桁以上など。

#### 期間

`0`, `1`, `2`, `5`, `6`, `7`, `11`, `12`, `13`, `479`, `480`, `599`, `600`, `1199`, `1200`, `1201`

操作により `1201` の意味が異なることを維持する。ローン入力では許容され、複利入力ではエラーとなる。

#### 複利周期

正常水準: `1`, `2`, `12`

異常水準: `0`, `4`, `13`

#### 税

`false`, `true`

### 7.2 被覆強度

| 操作群 | 因子 | 被覆規則 |
|---|---|---|
| `loan_forward` | 金利 × 期間 | 全組合せ |
| `loan_principal` | 金利 × 期間 | 全組合せ |
| `loan_bonus_forward` | 金利 × 期間 | 全組合せ |
| `loan_bonus_principal` | 金利 × 期間 | 全組合せ |
| `loan_term` | 金利 × 目標期間 | 全組合せを要求として数え、構成可否と結果一致を記録 |
| `compound_grow` | 金利・期間・周期・税 | 2因子間ペアワイズ |
| `compound_deposit_for` | 金利・期間・周期・税 | 操作単体の2因子間ペアワイズ |
| `compound_periods_for` | 金利・周期・税 | 2因子間ペアワイズ |

「別の操作で同じ因子ペアを踏んでいる」は、操作単体の被覆を満たしたことにはしない。ただし、除外理由の補足として「同じ因子ペアを別操作で検証済み」と表示してよい。

### 7.3 境界層

現在の名指し境界層を維持する。少なくとも次を含む。

- 残価0
- 残価=元本、残価>元本
- ボーナス0
- ボーナスが元本の50%を超える
- 元本・積立0
- 金利0、0.1%未満、小数4桁、100%、100%超
- 期間0、1、2、5/6/7、11/12/13、上限近傍
- `u64` 境界およびOverflow
- 税の国税・地方税それぞれの切り捨て境界
- 税引後残高の非単調な谷
- 逆算結果が480、600、1200付近になるケース
- 返済額が初回利息以下になるケース
- 残価へ届く前に完済するケース
- 目標未達・探索上限へ達するケース

### 7.4 エラー経路

現在列挙されている17種類のエラー経路を維持する。

各経路について次を満たすこと。

1. 少なくとも一つの名指し層へ対応づいている。
2. 対応するケースが生成済みコーパスに存在する。
3. 期待エラー種別が参照実装の実測と一致する。
4. 表示上の `Math ERROR` だけでなく、内部エラー種別まで照合する。

## 8. `loan_term` の扱い

### 8.1 現状の問題

現在は、金利と目標期間 `target_n` から正算で月額を作り、その月額を `loan_term` へ入力している。

基準コーパスのペアワイズ133件を確認すると、結果は次のとおりである。

| 結果 | 件数 |
|---|---:|
| `actual_n == target_n` | 74 |
| `actual_n == target_n + 1` | 47 |
| `SyntaxError`で期間なし | 11 |
| `actual_n == target_n - 1` | 1 |

このずれは、円単位に丸めた月額を逆算へ戻すことによって起こり得る。製品不具合であるとは限らないが、目標期間セルを被覆したことにはならない。

### 8.2 必須変更

`loan_term` の各ペアワイズ候補は、次の情報を内部的に保持する。

- `rate_level`
- `target_n`
- 構成した `principal`
- 構成した `payment`
- 参照実装が返した `actual_n` またはエラー種別
- セルの状態

セルの状態は次のいずれかとする。

- `covered`: `actual_n == target_n`
- `excluded`: 決定的な候補探索を行っても目標期間を構成できない
- `unmet`: ケースは作れたが、目標期間を満たしていない

`actual_n != target_n` のケースを計算照合用ケースとして残してもよい。ただし、`target_n` セルの被覆には数えない。

### 8.3 構成探索

目標期間を満たすケースを作る場合、元本または月額を決定的な候補列で調整してよい。

- 乱数へ依存しない。
- 候補順が固定されている。
- 試行上限を持つ。
- 成功時は `actual_n == target_n` をassertする。
- 失敗時は `inverse_target_unconstructible` として、対象セルを理由付き除外へ入れる。

すべての水準で構成可能であることは要求しない。しかし、構成不能を黙って別の期間のケースへ置き換えてはならない。

## 9. `compound_deposit_for` の扱い

### 9.1 操作単体での被覆

`compound_grow` が同じ因子ペアを被覆していても、`compound_deposit_for` の被覆には数えない。

基準コーパスでは、元の140行から122行が生成され、266要求ペア中246ペアを被覆している。残る20ペアは、被覆または理由付き除外へ分類する。

### 9.2 代替構成

正算で目標値を構成できない場合、次を決定的な候補として試してよい。

- 元本
- 積立額
- 目標値を作るための基準期間

代替値はテスト対象の因子水準を変えてはならない。

### 9.3 一つのケースによる複数セルの被覆

同一の `(op, input)` が複数の要求セルを満たす場合、ケースを重複生成してはならない。

代わりに、一つのケースが複数の `coverage_cell_id` を被覆できる集計構造を持たせる。既存の `stratum` はケースの生成目的を表す値として維持してよい。

これにより、重複ケースを削除しても要求セルが未達として残る問題を防ぐ。

## 10. 除外理由モデル

### 10.1 除外の分類

除外記録は、理由コードと判断区分を分けて持つ。

#### 理由コード

最低限、次を使用する。

| 理由コード | 意味 |
|---|---|
| `duplicate_equivalent` | 同一の `(op, input)` を既存ケースがすでに検証する |
| `not_applicable` | その操作には因子または水準が意味を持たない |
| `inverse_target_unconstructible` | 逆算用入力を決定的に構成できない |
| `source_overflow` | 正算側がOverflowし、逆算の目標値を作れない |
| `oracle_near_yen_boundary` | 参照実装の円境界ガードにより期待値を作れない |
| `oracle_search_limit` | 参照実装が探索上限へ達した |
| `candidate_domain` | 乱択候補が定義域外だった |
| `candidate_out_of_range` | 乱択候補が対象シャードの値域外だった |
| `candidate_overflow` | 乱択候補がOverflowした |
| `candidate_duplicate` | 乱択候補が生成済みケースと重複した |

未分類理由を `other` として通してはならない。未知の例外または未知の理由コードは生成失敗とする。

#### 判断区分

| 判断区分 | 意味 |
|---|---|
| `safe` | 同一ケースで同じ主張を検証済みなど、情報を失わない除外 |
| `reasonable` | 対象操作では構成不能だが、理由が仕様または数学上説明できる除外 |
| `accepted_risk` | オラクル限界など、未検証であることを承知して受容する除外 |

`accepted_risk` は「安全」を意味しない。Heavyレポートでは必ず「未検証」と表示する。

### 10.2 除外セルの必須フィールド

各除外セルは、最低限次を持つ。

```json
{
  "cell_id": "loan_term/rate=20,target_n=1200",
  "scope": "loan_term",
  "reason": "inverse_target_unconstructible",
  "disposition": "reasonable",
  "detail": "forward result cannot produce a valid inverse input after deterministic candidates",
  "covered_elsewhere": [
    "loan_forward/rate=20,n=1200"
  ]
}
```

- `cell_id` は安定した順序・綴りで生成する。
- `detail` は固定文または決定的に生成される文とする。
- `covered_elsewhere` は補足であり、元セルを被覆済みに変えない。
- 全除外セルを機械可読データに残す。
- Heavyレポートには理由別件数と最大3例を表示する。

### 10.3 生成候補棄却との分離

次の二つを同じ合計へ混ぜない。

1. `coverage.excluded_cells`: 有限に定義した要求セルの除外。
2. `generation_rejections`: 乱択候補を捨てた試行回数。

生成候補棄却には網羅率の分母を表示しない。次のように明示する。

> この件数は乱択候補の試行回数であり、未検証空間の大きさではない。

### 10.4 オラクル限界

`reference_gave_up` は期待値を作れなかった入力であり、成功ケースにも期待エラーケースにも含めない。

最低限、次を記録する。

- 理由別件数
- 対象操作
- 入力値
- 最初の最大3例
- 前回のコミット済みコーパスからの増減

基準runでは次を起点とする。

| 理由 | 基準件数 | 扱い |
|---|---:|---|
| `near_yen_boundary` | 7 | `accepted_risk`、警告 |
| `compound_deposit_search_limit` | 0 | 1件以上で失敗 |
| 未分類 | 0 | 1件以上で生成失敗 |

`near_yen_boundary` の7件を永続的な許容上限としてハードコードしない。固定コーパスの再現性検査により、入力や件数の変化を差分として検出する。

## 11. コーパスの機械可読形式

### 11.1 方針

既存15シャードが共有する `schema` を一律に変更しない。新しいトップレベル要素として `coverage` を追加し、その中に独立した `schema` を持たせる。

第1段階では `finance-000.json` のみ必須とする。

### 11.2 形式例

```json
{
  "schema": 1,
  "generated_by": "...",
  "coverage": {
    "schema": 1,
    "model": "finance-v1",
    "requirements": [
      {
        "id": "compound_grow/rate-periods-ppy-tax/pairwise",
        "scope": "compound_grow",
        "strength": "pairwise",
        "required_cells": 266,
        "covered_cells": 266,
        "excluded_cells": 0,
        "unmet_cells": 0,
        "status": "complete"
      }
    ],
    "excluded_cells": [],
    "generation_rejections": {
      "candidate_duplicate": 0,
      "oracle_near_yen_boundary": 7,
      "oracle_search_limit": 0
    }
  },
  "cases": []
}
```

### 11.3 状態

`requirements[].status` は次のいずれかとする。

| 状態 | 条件 |
|---|---|
| `complete` | 全要求セルを実行済み |
| `accounted_with_exclusions` | 未達は0だが、理由付き除外がある |
| `incomplete` | 未達セルが1件以上ある |
| `not_measured` | 必要な集計データを生成できなかった |

整合条件:

```text
required_cells
= covered_cells
+ excluded_cells
+ unmet_cells
```

この等式を生成側と読取側の両方で検証する。

## 12. Heavyレポート

### 12.1 追加位置

既存の「関数呼び出しの内訳」内、金融の正常・エラー件数表の直後へ、次の順で追加する。

1. テスト空間の網羅表
2. 理由付き除外
3. 生成候補棄却

既存の判定表、変異表、許容誤差表は変更しない。

### 12.2 網羅表

表示例:

```markdown
#### 金融テスト空間 `finance-v1`

| 対象 | 被覆規則 | 必須セル | 実行 | 理由付き除外 | 未達 | 状態 |
|---|---|---:|---:|---:|---:|---|
| loan_forward | 金利×期間 全組合せ | 150 | 150 | 0 | 0 | 完全網羅 |
| loan_term | 金利×目標期間 全組合せ | 150 | 74 | 17 | 59 | 不足 |
| compound_grow | 4因子ペアワイズ | 266 | 266 | 0 | 0 | 完全網羅 |
| compound_deposit_for | 4因子ペアワイズ | 266 | 246 | 20 | 0 | 理由付き未実行あり |
| compound_periods_for | 3因子ペアワイズ | 56 | 56 | 0 | 0 | 完全網羅 |
```

上記の数値は基準コーパスから得た説明例である。実装では生成済みデータから算出し、文字列へハードコードしない。

### 12.3 状態の日本語表記

| 内部状態 | レポート表記 |
|---|---|
| `complete` | 完全網羅 |
| `accounted_with_exclusions` | 理由付き未実行あり |
| `incomplete` | 不足 |
| `not_measured` | 測定していない |

「理由付き未実行あり」を「完全網羅」と表示してはならない。

### 12.4 除外の表示

表示例:

```markdown
#### 理由付き除外

| 理由 | 判断 | 対象数 | 単位 | 例 |
|---|---|---:|---|---|
| 逆算用入力を構成できない | reasonable | 自動集計 | 要求セル | rate=20, target_n=1200 |
| 正算がOverflowして目標を作れない | reasonable | 自動集計 | 要求セル | rate=100, periods=1200 |
| 同一入力で検証済み | safe | 自動集計 | 要求セル | ... |
| 参照実装の円境界限界 | accepted_risk | 7 | 生成候補 | ... |
```

要求セルの除外件数と、オラクル限界による生成候補棄却件数は、表または注記で明確に区別する。

ペアワイズの「構成行」と「要求セル」は同じ単位ではない。一つの構成行が複数の2因子セルを被覆するため、除外した構成行数を、そのまま除外セル数として表示してはならない。

### 12.5 レポート上の注意文

次を自動生成する。

> 完全網羅は、ここで定義した有限の因子・水準・組合せに対する表現であり、金融入力全体を数学的に全列挙したことを意味しない。

> 生成候補棄却の件数は乱択試行の回数であり、未検証空間の大きさではない。

## 13. 合否規則

### 13.1 生成器を失敗させる条件

- 未知の除外理由が発生した。
- `other` として未分類のまま継続しようとした。
- 必須セルが、被覆・除外・未達のどれにも分類されない。
- 同じセルが被覆と除外の両方へ入った。
- 整合式が成立しない。
- 名指し層が宣言した最低件数を満たさない。
- `oracle_search_limit` が1件以上発生した。
- `coverage.schema` または `coverage.model` が読み手の対応外である。

### 13.2 Heavyを失敗させる条件

- `unmet_cells > 0`
- `status == incomplete`
- `status == not_measured`
- コーパスに `coverage` が無いにもかかわらず、`finance-v1` 対象として実行された。
- 読取側で件数整合が取れない。
- 除外理由を表示できない。

### 13.3 警告に留める条件

- `accepted_risk` の除外が存在する。
- `near_yen_boundary` が存在する。
- `accounted_with_exclusions` である。
- 生成候補棄却率が大きく変化したが、理由コードと固定コーパスは再現可能である。

警告は成功ケースへ数えない。

## 14. 科学計算の部分モデル

### 14.1 基本方針

科学計算では実数・複素数が連続であり、全入力の有限列挙はできない。そのため、既存シャードをリスク別の実験ブロックとし、代表水準と最低件数だけを定義する。

### 14.2 初期モデル

| シャード・領域 | 要求軸 | 初期の被覆規則 |
|---|---|---|
| elementary | 関数種別 × 定義域帯 | 各水準1件以上、境界近傍は名指し |
| inverse-trig | 関数種別 × 角度モード × 境界帯 | 1-way必須、重要ペアを選択 |
| angle-mode | Deg/Rad × 三角関数 | 各組合せ1件以上 |
| precedence | 優先順位関係 × 括弧有無 | 各文法クラスに最低件数 |
| associativity | 演算子群 × 平坦/括弧対照 | 既存層の最低件数を維持 |
| cancellation | 相殺形式 × 桁落ち強度帯 | 各帯に最低件数 |
| combinatorics | nPr/nCr × 正常/定義域/Overflow近傍 | 各経路に最低件数 |
| display | ENG/DMS × 表示境界 | 名指し境界と最低件数 |
| complex | 演算種別 × 表示形式 × ゼロ成分 | 各重要クラスに最低件数 |

全軸の直積は作らない。ペアワイズを採用する場合も、相互作用リスクがある軸に限定する。

**【追記 2026-08-30】上の表は軸を挙げるが、水準を 1 つも定義していない。**
水準は `reference/src/calcarc_reference/corpus_science.py` の `SCIENCE_FACTORS`
が持ち、**どこから起こしたかを軸ごとに docstring に書いてある**——
仕様が名指しする境界（`numerical-policy.md` の定義域表、ENG の「指数は 3 の倍数」、
有効数字 10 桁）、生成器が名前で選んでいる定数（相殺の形・演算子群）、
そして**私が選んだもの**（`Overflow 近傍` の下限・優先順位の対の取り方）である。
**最後の種類には「私が選んだ」と印が付いている。**

`SPEC_AXES` が**この表の 9 行をそのまま写している**——因子表の取りこぼしは
**同じ因子表から列挙するテストには原理的に見えない**ので、**人が並べて読む**
ためである。

### 14.2a 科学モデルが `coverage` に足す 4 欄（2026-08-30）

**§11.2 の形式例は金融モデルのものである。** 科学モデル（`scientific-v1`）は
**同じ形に 4 つの欄を足す**。**どれも追加であり、既存の欄の意味は変えない。**

| 欄 | 何を言うか | なぜ要るか |
|---|---|---|
| `not_measured_axes` | **測る経路が無い軸**（scope・axis・理由） | 「未達」には**データに無い**と**読めない**の 2 種類があり、**混ぜると埋める判断を誤る** |
| `requirements[].unmet_from_unmeasured_axes` | 未達のうち、上の軸に起因する数 | **読み手の門はこれを引いてから落とす**（裁定 4）。**領域単位で見逃すと、両方を持つ領域の穴が緑で通る** |
| `requirements[].unmet_real_cells` | **本当の穴の `cell_id` 一覧** | 数だけでは**報告書がどこが空かを言えない**。**穴の可視化がこのモデルの値打ちである** |
| `covered_outside_model` | モデルの範囲外が踏んでいるセル | **除外ではない**（裁定 2 の B は「外は数えない」）。**判断材料として別欄で見せる** |

**`coverage.schema` は 1 のままにする。** 理由:

- **4 欄はすべて追加**であり、**schema 1 の読み手は自分が知る欄をすべて読める**
- **知らない読み手は安全側に倒れる**——`unmet_from_unmeasured_axes` を
  読まない実装は既定 0 として扱い、**未達を全部「本当の穴」と見なして落ちる。**
  **緩む方向には壊れない**
- **消費者はこのリポジトリの `heavy/tests/corpus/corpus.ts` 1 つだけ**であり、
  **同じコミットで追随している**
- §11.1 が `coverage` に独立した `schema` を持たせたのは
  **既存シャードの `schema` を churn させないため**である。
  **追加のたびに上げると、その churn を内側へ移すだけになる**

**破壊的な変更（欄の削除・意味の変更）が起きたときに上げる。**

**★ この設計には、読み手だけでは埋まらない穴が 1 つある。**

**TypeScript の門は `unmet_from_unmeasured_axes` を「シャードの申告」として
そのまま信じる**（`corpus.ts` に「数はシャードが宣言する（読み手は数え直さない）」
と書いてある）。**数え直しているのは Python 側**——
`test_unmet_splits_into_unobservable_and_real_holes` が要求セルを走査し、
`test_all_ten_shards_carry_the_same_block_and_it_matches_a_fresh_count` が
**源と写しの一致**を見る。

**つまり、誰かが JSON を手で直して `unmet_from_unmeasured_axes` を増やせば、
`pnpm heavy` は緑のまま通る。** 止めるのは **`reference` の pytest**であり、
**CI は両方を回す**ので経路としては塞がっているが、
**「`pnpm heavy` が緑」は「会計が正しい」を意味しない。**

**読み手側で数え直さないのは意図した設計である**——数え直すには
**因子表と水準の定義を TypeScript 側にも持つ**ことになり、
**2 つの実装がずれた日に、どちらが正しいか誰も言えなくなる。**
**代わりに、生成器の側に数え直しを置いた。**

### 14.3 科学系の生成候補棄却

既存JSONが持つ `domain`、`division_by_zero`、`overflow`、`out_of_range`、`bare`、`dup` を、生成テレメトリとして表示する。

次を守る。

- これらを未検証セル数と呼ばない。
- これらから網羅率を算出しない。
- 新しい理由コードが出た場合は生成器またはテストを失敗させる。
- 定義域エラーを専用エラーシャードで検証している場合、その件数を別に表示する。

## 15. テスト要件

### 15.1 Python生成器テスト

最低限、次を追加する。

1. 全要求セルが一意に列挙される。
2. 全実行ケースから被覆セルを再計算できる。
3. `required = covered + excluded + unmet` が成立する。
4. 未分類理由で生成器が失敗する。
5. 一つの要求セルを意図的に落とすと `unmet` になる。
6. 一つの除外理由を削除すると生成器が失敗する。
7. 一つのケースが複数セルを被覆できる。
8. `loan_term` は `actual_n == target_n` の場合だけ目標期間セルを被覆する。
9. `compound_deposit_for` の被覆は同操作のケースだけから計算する。
10. 生成を2回行うと `coverage` を含めてバイト一致する。

「本当に赤くなるか」を確認する反証可能性テストを最低1本含める。

### 15.2 TypeScript読取テスト

最低限、次を追加する。

- 未知の `coverage.schema` を拒否する。
- 未知の `model` を拒否する。
- 件数整合の不一致を拒否する。
- `excluded_cells` の未知理由を拒否する。
- `unmet_cells > 0` をHeavy失敗にする。
- `not_measured` をHeavy失敗にする。
- `accepted_risk` を警告として保持し、成功ケースへ加算しない。

### 15.3 レポートテスト

最低限、次の状態を個別に固定する。

1. 全セル被覆・除外0
2. 安全な重複除外あり
3. reasonable除外あり
4. accepted riskあり
5. 未達あり
6. 測定記録なし
7. 未知理由あり
8. 要求・被覆・除外・未達の合計不一致
9. 候補棄却0
10. 候補棄却あり

レポートテストは固定した架空データと、実物の `finance-000.json` の両方を使用する。

### 15.4 変異テストとの関係

既存の金融変異10種を維持する。

- テスト空間セル数と変異検出件数を足し合わせない。
- 変異表は現在どおり、どの壊れ方を何件検出したかを表示する。
- 新しいモデルの実装により変異検出件数が変わった場合、意図した被覆変更かを記録する。
- 網羅表が完全でも変異を検出できなければ、網羅水準またはオラクルが弱いと判断する。

## 19. 完了後にレポートから判断できること

実装完了後、Heavyレポートは次を同時に示す。

1. 実行した計算が独立参照実装と一致したか。
2. 既知の壊れ方をテストが検出できるか。
3. 定義した有限のテスト空間をどこまで被覆したか。
