# リリースをキーにした本番展開と、証拠の保存 設計書

- 文書状態: 実装仕様
- 作成日: 2026-08-25
- 決定者: ユーザー（2026-08-25、3 択 × 3 で裁定）

## 1. いまどうなっているか（実測）

| ワークフロー | 起動 | テストとの関係 | 残るもの |
|---|---|---|---|
| `ci.yml` | main への push・PR・手動 | — | `wasm-pkg`（ジョブ間）・`playwright-report` |
| `deploy.yml` | **main への push**・手動 | **CI の成功を待たない**（`docs/deploy.md` が「独立ワークフローである」と明記） | **無し** |
| `heavy-corpus.yml` | **タグ `v*`**・手動 | 版数ゲート → コーパス | `heavy-report`（90 日） |

**つまり本番は「main に push した瞬間」に出ており、タグは重量級を回すだけで展開に関与
していない。リリースされた物がどの検査を通ったかは、どこにも残っていない。**

## 2. 決めたこと

| 問い | 決定 |
|---|---|
| 本番展開の契機 | **`v*` タグだけ。** main への push では出さない |
| 展開の条件 | **CI 全部（Rust・WASM・web・E2E・Python 参照）＋ 重量級コーパス**の成功 |
| 証拠の置き場 | **GitHub Release に添付**（ワークフローが Release も作る） |

**この決定は 2026-08-25 の「Heavy テスト空間モデル」設計書 §3 の非目的
「Heavy をリリース前の必須ゲートにはしない」を撤回する。** 撤回したことを、
あちらの文書にも書く（理由だけが静かに嘘になるのを避けるため）。

## 3. 変えるかたち

```
v0.5.0 のタグを打つ
  └─ Release ワークフロー（新規 release.yml）
       1. 版数ゲート    版数 5 箇所がタグ名と一致し、CHANGELOG に日付がある
       2. CI            ci.yml を workflow_call で呼ぶ（テストの定義は 1 つだけ）
       3. 重量級        heavy-corpus.yml を workflow_call で呼ぶ（35〜41 分）
       4. 本番展開      deploy.yml を workflow_call で呼ぶ（Cloudflare Pages + スモーク 3 本）
       5. 証拠と Release  各ジョブの結論・配った物・重量級レポートを添えて Release を作る
```

**テストの定義を写さない。** `release.yml` が `ci.yml` と `heavy-corpus.yml` を
**呼ぶ**（`workflow_call`）。写しを作ると、片方だけ直された日に「リリース前に通した検査」と
「毎回の CI」が別物になる。

### 3.1 各ワークフローの役割

| ファイル | 変更 |
|---|---|
| `ci.yml` | `on:` に `workflow_call:` を足すだけ。**ジョブの中身は 1 行も変えない** |
| `heavy-corpus.yml` | `on:` に `workflow_call:` を足し、**`push: tags` を外す**（タグからは `release.yml` 経由でだけ走る。二重に走らせない） |
| `deploy.yml` | `on:` を `workflow_call:` ＋ `workflow_dispatch:` にする。**main への push では走らない。** ガードを「main からのみ」から「`v*` タグ、または緊急の手動」に書き換える |
| `release.yml`（新規） | タグで走り、上の 5 段を順に回す |

### 3.2 concurrency の穴（先に塞ぐ）

呼ばれる側の `concurrency.group` に `${{ github.workflow }}` を使うと、**呼び出し元の
ワークフロー名**が入る。`cancel-in-progress: true` と組み合わさると、**呼ばれた CI が
呼び出し元の走行を自分で打ち切る**。各ファイルの group にファイル固有の接頭辞
（`ci-` / `heavy-` / `deploy-` / `release-`）を付けて、群を分ける。

## 4. 証拠（Release に添付するもの）

| 添付物 | 何を示すか |
|---|---|
| `release-evidence.md` | タグ・コミット SHA・版数・**各必須ジョブの結論**（GitHub API から取得。人手の転記をしない）・重量級の主要な数 |
| `heavy-report.md` | 重量級の走行が出した報告書そのもの |
| `calcarc-<tag>-dist.tar.gz` | **実際に配った物**。`build-info.json`（commit と時刻の刻印）を含む |

**結論はワークフローが `gh api` で自分の走行から読む。** ステップの出力を人が写すと、
「緑だったと書いてあるが実は落ちていた」が作れてしまう。

**証拠は Release の本文にも載せる**（2026-08-26 追記。v0.4.1 で穴が見つかった）。
添付とジョブのサマリーだけに置くと、**読む人が最初に見る場所**に結論が出ない。
「Release が既に在る」は例外ではなく**通常経路**である——GitHub の UI で Release を
作る操作がタグを push し、この走行を起こす。v0.4.1 では Release の公開が走行開始の
**2 秒前**で、`create` 側は一度も走らなかった。自動生成の "What's Changed" は消さず、
目印（`<!-- release-evidence -->`）より後ろを貼り直すので、再走行で二重に積まない。

`release-evidence.md` には、この文書が言えることの範囲も書く——**「この SHA が、
この一覧の検査を通ってから配信された」**であって、検査していない性質については何も
言わない。

## 5. ロールバック（手順が変わる）

いまの `docs/deploy.md` は「**main に revert コミットを積む**」と書いている。main への
push が配信しなくなるので、**この手順は成立しなくなる**。新しい手順:

1. **通常のロールバック**: revert を main に積み、**新しいパッチ版のタグを打つ**
   （例 `v0.5.1`）。版数 5 箇所と CHANGELOG も揃える——版数ゲートが見張っている。
2. **緊急のロールバック**: `deploy.yml` を**古いタグの ref で手動起動**する。
   これは**検査を通さない経路**なので、`docs/deploy.md` に「緊急時のみ・
   何を配ったかを Release に書き足すこと」と明記する。

**「main の先頭 = 配信物」という不変条件は失われる。** 代わりに
**「最新の `v*` タグ = 配信物」**が不変条件になる。両方の文書を書き換える。

## 6. 非目的

- CI のジョブの中身を変えない（速くも遅くもしない）。
- 重量級の内容・所要時間を変えない。
- デプロイ先（Cloudflare Pages・`--branch=main`）とスモーク 3 本を変えない。
- プレビュー環境を作らない（main への push は**どこにも配らない**）。
- 証拠に検査していない性質の主張を書かない。

## 8. 確認できること／できないこと

- **手元で確認できる**: YAML の構文、`workflow_call` の入出力、ガードの分岐、
  証拠ファイルを組み立てるスクリプトの出力（走行の JSON を食わせて確かめる）。
- **実タグを打つまで分からない**: 呼び出しの連結が実際に通ること、`gh api` の
  権限（`contents: write` が Release 作成に要る）、Release への添付。
  **これは（未確認）と明記し、次のリリースで確かめる。**
