## §2 入力の見せ方

### 症状 1: いま打っている数字が小さすぎる（実測）

`web/src/ui/Readout/Readout.module.css` の `.echo` は

```css
  color: var(--display-status-fg);
  font-size: var(--display-size-status);   /* 0.75rem = 12px */
```

**status 行と同じ扱い**になっている。

原因は**役割の取り違え**である。**Scientific では echo は副次表示**だ——答が
`main` に出ていて、echo は「いま何を打ったか」の控え。小さくて薄くてよい。

**Loan と Data Scale では echo が入力の主表示**である。`main` に出るのは
**答**で、**利用者がいま打っている数字は echo にしかない**。

### 症状 2: 項目を切り替えると、前に入れた値が画面から消える

```
借入額を選んで 3000万 と打つ  → echo: 借入額 3000万
年利に切り替える              → echo: 年利          ← 3000万 が消える
```

**答だけがあって根拠が見えない画面**は、金融計算では特に危うい——桁を 1 つ
間違えたまま答を読んでも気付けない。項目が 6 つある Loan と複利で悪化する。

### 直し方【裁定: `Readout` を `entries[]` に構造化】

```
┌──────────────────────────────────────┐
│                          年利 1.5     │  ← アクティブ（大きく・濃く）
│  借入額 3000万 · 期間 35年             │  ← 入力済み（小さく・薄く）
│  月額を求める            年利を入力中   │  ← status（既存）
│                            91,855     │  ← main（答）
└──────────────────────────────────────┘
```

```ts
export interface ReadoutEntry {
  /** 項目名。Scientific のように名前が無い入力では空文字。 */
  label: string;
  /** 表示用に整形済みの値。**Readout は整形しない**（既存の規律）。 */
  value: string;
  active?: boolean;
}
```

`echo: string` を `entries: ReadoutEntry[]` に置き換える。**Scientific は
「名前なしの 1 件」を渡す**ので、見た目も意味も変わらない。

- **未入力の項目は出さない**（空の `残価` や `ボーナス` で埋めない）。
- **アクティブが未入力なら、ラベルだけを大きく出す**。
- 並び順は**項目行の並び**に合わせる。
- **アクティブかどうかは入力の事実であって、装飾の指定ではない**——だから
  `echoRole` のような見た目の prop を持たない。

**大きさの具体値は plan で決める。** 目安はアクティブが `--key-font-size`
（1.375rem）級・色は `--display-fg`、入力済みが `--display-size-status`
（0.75rem）級・色は `--display-status-fg`。

### 縦に伸びるとき【裁定: 折り返して伸ばす】

値が見えることが目的なので隠さない。**キーパッドの 44px を割らないことを
実機で確かめる**。足りなければ削る順序は
**入力済みの文字を詰める → `Readout` の余白 →（キーの寸法は最後）**。

## §3 `000` を直す

### 実測（2026-08-15、jsdom で再現）

`月々の返済額` モードで「借入額」を選び、`3` → `000` と押した結果:

| 項目 | 打鍵 | 出た値 | 期待 |
|---|---|---|---|
| 借入額（金額） | `3` `000` | **`30円`** | `3000円` |
| 返済期間 | `1` `000` | `1000か月` | `1000か月` ✓ |
| 年利 | — | キーが無効 | 無効（設計どおり） |

### 原因

`LoanPanel.tsx` の `zeros3` は 1 打鍵を 3 回の数字入力に展開する:

```ts
      case "zeros3":
        for (const _ of [0, 1, 2]) pressDigit("0");
```

`pressDigit` は項目の種類で分岐し、**金額だけが「いまの値」をレンダー時の
クロージャから読む**:

```ts
    if (MONEY_FIELDS.includes(active)) {
      setEntry(active, pushDigit(entryOf(active), digit));   // ← 値を先に計算する
      return;
    }
    if (active === "rate") {
      setRate((previous) => ...);                            // ← 関数型更新
    }
    setMonths((previous) => ...);                            // ← 関数型更新
```

同じイベントの中で 3 回呼んでも 3 回とも同じ値を読み、React がまとめて反映する
とき**最後の 1 回だけが残る**。年利と期間が無事なのは、関数型更新が**直前の
結果**を受け取るからである。

**Data Scale は正しい**——ローカルで畳んでから 1 回だけ書く。

### 検査の穴（記録）

**L には「`000` を押した結果」を見る検査が 1 つも無い。**

```bash
$ grep -rn "3桁のゼロ" web/src/ui/Loan/LoanPanel.test.tsx web/tests/e2e/loan*.spec.ts
LoanPanel.test.tsx:152:  expect(...{ name: "3桁のゼロ" })).toBeDisabled();     # 年利で無効
LoanPanel.test.tsx:157:  expect(...{ name: "3桁のゼロ" })).toBeEnabled();      # 金額で有効
loan-keypad.spec.ts:62:   const zeros = ...{ name: "3桁のゼロ" };              # 可否のみ
```

**押せるかどうかしか見ていない。** キーが何もしなくても全部緑になる。
**Data Scale にも同じ穴がある**（押下結果の検査は 0 件。実装は正しいが、
正しさは検査に支えられていない）。

**実装側の自己レビューでも、読みの完了レビューでも捕まらなかった。**
可否表を丁寧に作ったことが「このキーは検査済み」という錯覚を生んだ——
**可否は入口の検査であって、出口の検査ではない。** これは 1 つのキーの話では
なく**「状態を持たないキーは検査を忘れる」という型**である。

### 【裁定: 直して残す】

Data Scale と同じローカル畳み込みにする。あわせて:

- **出口の検査を L と D の両方に足す**（`3` `000` → `3000`）。
- **同じイベントで複数回状態を更新する経路が他に無いか、`press` 全体を走査する**
  ——`000` は症状であって、原因は「クロージャから読んで書く」形である。

## §4 盤面を Scientific に揃える【裁定: 5 列にする】

### いまズレている（実測）

| | Scientific | Loan / Data Scale |
|---|---|---|
| 列数 | **5** | 4 |
| キーの寸法（390px 幅） | **約 67px 角** | 約 86px 角 |
| `DEL` の位置 | 最上段の右から 2 番目 | 右上 |
| `AC` の位置 | 最上段の右端 | `DEL` の**下** |

**タブを行き来すると `AC` の場所が変わる。** 消去は取り返しが効くが、
**`AC` を押すつもりで別のキーを押す**のは入力のやり直しに直結する。

### 5 列にすると位置も寸法も同時に揃う

```
Scientific（現状）        Loan（5×5）              Data Scale（5×5）
(  )  +/− DEL AC         (  )  ░  DEL AC          (  )  ░  DEL AC
7  8  9   ÷   j          7  8  9   ÷   万          7  8  9   ÷   K
4  5  6   ×   ▸∠         4  5  6   ×   億          4  5  6   ×   M
1  2  3   −   Exp        1  2  3   −   ░          1  2  3   −   G
0 000 .   +   =          0 000 .   +   =          0 000 ░   +   =
```

- **`DEL` と `AC` が最上段に並ぶ**（Scientific と同じ）。
- **キーは約 67px 角**になり、3 つのタブで同じ寸法になる。44px は余裕で守る。
- **5 列目がモジュール固有の列**、**4 列目が演算の列**。
- `(` `)` は式（§8）で生きる。`+/−` は金額・件数に負の値が無いので置かない。

**キーが小さくなることは後退ではない。** 44px の線を割らず、
**位置の一貫性の方が誤爆を減らす**。

### 余ったセル【裁定: 無効なボタンを描く（予約スロット）】

`░` は**無効なボタンとして描く**（S1 の予約スロットと同じ）。
何も描かない案ではなくこちらを採る——**格子の形が崩れないので、
キーの位置が視覚的に安定する**。

**無効に見えることが条件**である。S1 で「予約スロットが有効なキーと同じ
見た目だった」欠陥を踏んでいるので、**computed style を読む検査で固定する**
（背景色か不透明度が通常キーと異なること）。

### 波及（見落としやすい）

- **L と D の vitest・E2E がキーの位置と 44px を見ている**箇所は書き換わる。
- **D の型面も 5 列になる**（数字面と同じ枠に載る、が D の不変条件）。
  9 つの型 + `DEL` + `AC` を 5×5 に置き直す。
- **`000` は残る**（§3）ので、`000` 由来の空きセルは生じない。

## §5 単位キーは項目に従う

### 万/億 の 2 セルは半分の時間だけ働いている

`万`・`億` が有効なのは金額の項目だけで、期間や年利を打っているあいだは
**押せないボタンとして場所を占めている**。一方**期間には単位が要る**——
いまは「か月」固定で、35 年のローンを `420` と打っている（**利用者が頭の中で
12 を掛けている**）。

### 【裁定: 期間に `年`/`月` を入れる】

```
借入額のとき      期間のとき       年利のとき
   ... 万            ... 年           ... ░
   ... 億            ... 月           ... ░
```

**`units/entry.ts` の文法がそのまま使える。** 値は
`Σ セグメントの数字 × scale + 末尾の数字` で、**10 の冪を前提にしていない**:

```
3 5 年      → 35×12        = 420 か月
3 年 6      → 3×12 + 6     = 42 か月
3 年 6 月   → 3×12 + 6×1   = 42 か月
```

「単位は下る向きにしか置けない」「DEL は 1 段ずつ解く」「数字が無いと単位を
置けない」——**万/億 と同じ規則が共有される。新しい文法を書かない。**

`units/entry.ts` の冒頭「小数や単位を持たない値（年利、期間、次元数）は
ここを通らない」は**訂正する**。

### 複利の期間は周期に従う

| 周期 | 上の単位 | 下の単位 |
|---|---|---|
| 月次 | `年`（scale 12） | `月`（scale 1） |
| 半年 | `年`（scale 2） | `半期`（scale 1） |
| 年 | `年`（scale 1） | —（1 期 = 1 年） |

**上の単位はいつでも `年` で、scale が「1 年あたりの期数」になる。**
どの周期でも**割り切れる**ので端数の期が生まれない。利用者は「10 年間」と
打てばよく、期数への換算は盤面がやる。

**周期を変えても期間の値は保持する**（L の「打った値は消さない」）。
`10年` のまま周期を変えれば期数が変わる——期間は 10 年のままで、複利の刻みが
変わっているので正しい。

### 桁の上限は「合成後の値」に効かせる（L の教訓）

L の `MAX_MONTHS_LEN = 4` は**桁数ではなく定義域**のガードだった——10 桁を
超える月数は WASM 境界の `u32` 変換で折り返し、コアの 1200 上限を**すり抜けて
もっともらしい誤答を出す**（4,294,968,496 か月が 1,200 か月として計算される）。

**セグメント入力にすると、この上限は打鍵の桁数では効かない。** `9999年9999` は
打鍵としては 4 桁ずつでも、合成すると 129,987 か月になる。

- `pushDigit` の `maxDigits` は**入力中の数字**にしか効かない。
- **それとは別に、合成後の値（`digits(entry)`）が定義域に収まるかを見る。**
  期間は `u32` かつ 1200——**どちらも実装しないという選択は無い。**
- **式（§8）が入ると、この検査は式の結果にも掛かる。**

## §6 複利を 1 つのモードにする

F1 のコアは `grow(principal, deposit, rate, periods_per_year, periods, tax)` の
**1 本**で、一括預入は `deposit = 0`、毎月積立は `principal = 0` の退化である。
**盤面もその形をそのまま写す**——「一括」と「積立」を別モードにすると、
**モードが違うのに計算が同じ**になる。

### モード行【裁定: 1 段 4 キー + ラベル短縮】

区画名を `求めるもの` → **`計算の種類`** に変える（複利は「求めるもの」では
ない）。390px で 4 列だと 1 キー ≈ 87px なので**ラベルを詰める**
（`月額` / `借入可能` / `期間` / `複利`）。**読み上げ名はいまのまま**
（`月々の返済額を求める` など）残す。

**区画名の変更は L の E2E のセレクタを動かす**（`loan.spec.ts`・
`loan-keypad.spec.ts`）。plan の最初のタスクで扱う。

### 項目行（複利のとき）

| 項目 | 種類 | 備考 |
|---|---|---|
| 元本 | 金額 | 一括預入ぶん。空なら 0 |
| 積立額 | 金額 | 毎期の積立。空なら 0 |
| 年利 | 数（小数可） | ローンと同じ入口 |
| 期間 | 数 | 単位は周期に従う（§5） |
| 周期 | 選択 | 月 / 半年 / 年 |
| 税 | 選択 | なし / あり（20.315%） |

- 複利モードでは**すべての項目が有効**。ローン固有の項目は出さない。
- **元本と積立額が両方とも空**なら計算しない（画面は中立のまま）。
- **モードを切り替えたら、アクティブ項目を新しいモードで有効な先頭へ移す。**
  L の完了レビューで見つかった状態整合バグ（無効になった項目に居座る）の
  再演を防ぐ。**ローン ⇄ 複利は L の実装時に存在しなかった経路**なので、
  `fieldEnabledIn(field, forMode)` のようにモードを引数で受ける形を守る。

## §7 周期と税の置き方

どちらも数字ではなく選択である。既存の前例は 2 つ:

| 前例 | 置き方 | 性質 |
|---|---|---|
| Data Scale の**データ型** | 項目タブを押すと**盤面の面が入れ替わる** | 計算に入る |
| Data Scale の**主表示トグル** | 盤面の外のトグル | **表示の読み方だけ** |

**規律: 計算に入るものは盤面の中、表示の読み方だけが盤面の外。**

周期も税も計算に入る（周期は分母を変え、税は出力を増やす）ので、
**どちらも「面が入れ替わる項目」**にする。周期は 3 キー（`月`/`半年`/`年`）、
税は 2 キー（`なし`/`あり`）。**面の高さは 5 行ぶんを保つ**（D で確立した機構）。

## §8 有理数の式評価器（新しいコア）

**裁定 4 点がここに集まる**: 優先順位あり / 除算は切り捨て / **丸めは着地の
1 回だけ** / **年利でも使える** / 単位と混ぜられる。

### 4 つの裁定が 1 つの機構に収束する

「途中を正確に保ち、最後に 1 回だけ丸める」と「年利（小数）でも使える」は、
**どちらも有理数で評価すれば同時に満たせる**。

```
100万 ÷ 3 × 3   →  (1000000/1) ÷ (3/1) × (3/1) = 1000000/1  →  1,000,000
100万 ÷ 3       →  1000000/3                                 →    333,333（floor）
年利 1.5 + 0.25 →  (15/10) + (25/100) = 175/100              →  1.75
```

**評価器は 1 つ、着地が項目ごとに違う。** これが設計の骨である。

### 値の表現【裁定: 分子・分母とも `u128` の既約分数】

- Data Scale の件数は 10 進 39 桁（u128）まで受ける。**f64 は 2^53 で壊れる**
  ので使えない。
- Scientific の engine（複素数 f64）は**流用できない**。同じ理由である。
- 分母は常に正、符号は分子が持つ。

**Rust の標準ライブラリに多倍長整数は無い。** 多倍長のクレートを足す案と
自前で書く案があったが、**どちらも採らない**——ユーザー裁定は
「無理するところじゃない」で、**依存ゼロと実装の小ささを優先する**。
`calcarc-core` の依存は `serde` だけのままである。

#### 角: 中間値が u128 を超えたらエラー（仕様として明記する）

**分子か分母が u128 に収まらなくなった時点で `Overflow` を返す。**
その結果、**数学的には定義域に戻る式もエラーになる**:

```
39桁 ÷ 3        → OK（分子は動かない）
100万 ÷ 3 × 3   → OK（約分で分母が消える）
39桁 × 2 ÷ 2    → Overflow（× の時点で分子が u128 を超える）
```

**これは実装の都合ではなく、仕様である。** 実用の式——`100M × 768`、
`3000万 × 2`、`100万 ÷ 3`、`1億6000万 − 500万`——はすべて収まる。
超えるのは u128 の端に張り付いた値をさらに掛ける場合だけで、
そこを通すために多倍長を抱える価値は無い、という判断である。

#### 約分は最適化ではなく正しさの一部

**各演算のあとに必ず約分する。** 多倍長なら約分は「桁が爆発しないための
最適化」だが、**u128 有界では「収まるかどうか」を左右する**。
`100万 ÷ 3 × 3` が通るのは、約分によって分母の 3 が消えるからである。
約分をやめると、この式は分子 300 万で通るものの、より長い式では
**予期しない `Overflow`** になる。

### 文法

```
式    := 項 (("+" | "−") 項)*
項    := 因子 (("×" | "÷") 因子)*
因子  := 数 | "(" 式 ")"
数    := 位取り入力（units/entry.ts の文法。単位は数の後置修飾）
```

**優先順位あり・括弧あり**（Scientific と同じ規則。同じアプリの中で 2 つの
規則が共存しない）。

**単位は数リテラルの後置修飾**として扱う——`3000万` は 1 つの数であって、
`3000` と `万` の演算ではない。したがって `100万 + 50万` は
`1000000 + 500000` になる。**位取り文法（セグメント列）はそのまま数リテラルの
中で働く**（`1億6000万` は 1 つの数）。

### 着地（項目の定義域へ）

| 項目 | 定義域 | 着地の規則 |
|---|---|---|
| 金額（借入額・残価・ボーナス・元本・積立額） | u64 円 | **floor** して整数。超えたら `Overflow` |
| 件数・次元数 | u128 | **floor**。超えたら `Overflow` |
| 期間 | u32 かつ ≤1200（複利は `MAX_PERIODS`） | **floor**。超えたら `SyntaxError`（§5） |
| 年利 | 小数 4 桁以内・0〜100% | **4 桁に収まらなければ `SyntaxError`** |
| **式の途中** | 分子・分母とも u128 | 超えた時点で **`Overflow`**（上の角） |

**年利の 4 桁制限は新しい規則ではない。** いまも `1.23456` は入口で
`SyntaxError` になる（`Rate::from_percent`）。**計算で出た値にも同じ線を
引く**——`1 ÷ 3` % は 4 桁で表せないので拒否する。これは「表示できない値を
黙って丸めない」という既存の規律と一致する。

### エラー

| エラー | 条件 |
|---|---|
| `DivisionByZero` | 除数が 0（既存の分類にある） |
| `Overflow` | 着地先の定義域を超える |
| `SyntaxError` | 括弧の不整合、演算子の連続、年利が 4 桁に収まらない |

**計算コアは panic しない**（既存の規律）。

### `=` の意味

**アクティブな項目の式を評価して、その項目の値にする。** 項目をまたぐ式は
書けない（`借入額 = 年利 × 2` のようなことはしない）。

式を打っている途中は**その項目が未確定**として扱い、**モジュールの計算
（月額・データ量・複利）は走らせない**——中途半端な式から答を出さない。

### Python 参照の独立軸（base-spec §30）

**Python は標準ライブラリの `fractions.Fraction` で評価する。**
Rust は自前の有理数を実装するので、**手法が違う**（base-spec §30 の
「既存の数学ライブラリや別手法を利用する」にそのまま当たる）。
Python の `int` は多倍長なので u128 の定義域を自然に持てる。

**共有する公開契約**（アルゴリズムの共有ではない）:

1. 優先順位と結合（左結合）。
2. **丸めは着地の 1 回だけ**、向きは floor。
3. 単位は数リテラルの後置修飾。
4. 各項目の定義域と、超えたときのエラー種別。
5. **中間値も u128 に収まること。** Python の `Fraction` は多倍長なので
   放っておくと通ってしまう——**各演算のあとに分子・分母が u128 に収まるかを
   検査し、超えたら `Overflow` にする**。ここを入れないと、Python が Rust
   より広い定義域を持ち、golden が「Rust では出せない答」を持つ。

### golden

`testdata/` に**式の op を足す**。置き場所は plan で決める（`finance.json` に
足すか、`expr.json` を新設するか——base-spec 855 行の 4 ファイル列挙を
動かすかどうかの判断）。

必須ケース（案）:

- **`100万 ÷ 3 × 3` = 1,000,000**（丸めが着地の 1 回だけであることの証明。
  各演算で丸めるなら 999,999 になる）
- `100万 ÷ 3` = 333,333（floor の向き）
- `(3000 + 500) × 2` と `3000 + 500 × 2`（優先順位と括弧）
- `100万 + 50万` = 1,500,000、`1億6000万 − 500万` = 155,000,000（単位の同居）
- **39 桁 × 2** → **`Overflow` が正解**（着地の u128 を超える。f64 なら
  黙って壊れる値が出る）
- **`39桁 × 2 ÷ 2` → `Overflow`**（**中間**オーバーフロー。数学的には戻るが
  仕様としてエラー。上の角を固定するケース）
- `÷ 0` → `DivisionByZero`
- 着地の境界: u64 ちょうど / 超え、期間 1200 / 1201
- **年利 `1.5 + 0.25` = 1.75**、**`1 ÷ 3` → `SyntaxError`**（4 桁の線）

赤確認（案）:

1. 各演算で floor する → `100万÷3×3` が 999,999 で赤
2. 優先順位を左結合に落とす → `3000 + 500 × 2` で赤
3. **約分をやめる** → `100万 ÷ 3 × 3` が `Overflow` になって赤。
   u128 有界では約分が正しさの一部なので、**多倍長のときより判別力が高い**
   （多倍長なら「遅くなるだけ」で赤にならない可能性があった）
4. 年利の 4 桁検査を外す → `1 ÷ 3` が通ってしまい赤

## §14 この spec の大きさについて（実装前の注意）

**A は当初の想定より大きい。** UI の作り直し（表示・盤面 5 列化・複利の項目）と
**新しい計算コア**（有理数の式評価器 + Python 参照 + golden）が 1 本に入る。

入る**——ここを飛ばすと、独立検証の意味が消える。

別ブランチに切り出す**——コア（段 1〜3）は盤面が無くても完結し、golden で
検証できるからである。この判断は plan の段階か、遅くとも段 3 の完了時点で行う。
