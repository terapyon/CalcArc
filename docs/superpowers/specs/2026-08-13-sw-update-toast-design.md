# Service Worker 更新通知トースト（S3）— 設計

日付: 2026-08-13
対象: base-spec §40 前後（PWA とオフライン）、M5 の PWA 設計
（[2026-08-12-pwa-design.md](2026-08-12-pwa-design.md)）。
前提: M5 の `registerType: "prompt"` を**変えない**。本 spec は、その prompt の
本来の使い方をようやく配線するものである。

## §0 なぜ今か — 見送った機能のコストが実測された

M5 は「UI は配線しない」を意図的に選んだ（`main.tsx` の `registerSW()` に
コールバックを渡さない）。新しい SW は waiting に留まり、**全タブを閉じて
再訪したとき**に切り替わる。予告なくページの下で世代がすり替わらないための
設計であり、`autoUpdate` を避けた理由でもある。

その代償が M6 のデプロイ後に**実際に起きた**: 利用者の iPhone / Safari で
「新版が届いているのに表示が変わらない」。Safari のタブが旧 SW のクライアント
として残り続けたためである。

設計判断そのものは正しかった（勝手に世代を替えない）。足りなかったのは
**利用者に選ばせる出口**である。本 spec はそれだけを足す。

## §1 やること

1. `registerSW({ onNeedRefresh })` を配線し、waiting の SW を検知する。
2. **トーストを出す**——「新しいバージョンがあります」+「再読み込み」。
3. **利用者が押したときだけ** `SKIP_WAITING` を送り、`controllerchange` を待って
   `location.reload()` する。
4. 押さなければ何も起きない。トーストは閉じられる（次回の検知でまた出る）。

**`skipWaiting` を自動で呼ばない**という M5 の原則は維持する。変わるのは
「利用者が押せば今すぐ切り替わる」経路が増えることだけである。

## §2 トーストの形

- 位置: 画面下部、シェルの上に重ねる。`--shell-max-width` の中に収める。
- 役割: **`role="status"`**（`alert` にしない）。更新は事故ではないので、
  読み上げを割り込ませない。
- 中身: 文言 + 「再読み込み」ボタン + 「閉じる」ボタン。ボタンは 44px を守る。
- **文言に「入力中の内容は消えます」を含める**。リロードで `EngineState` は
  失われる。状態の永続化は base-spec §40 の別の話であり、ここでは扱わない
  （トーストは揮発でよい——保存を始めるなら schema と復元規則の設計が要る）。
- フォーカス: トーストが出ても**フォーカスを奪わない**（打鍵中に奪うと計算が
  中断する）。Tab で到達でき、Esc で閉じられる。
- **Esc は計算に届かせない**（追記 2026-08-13、plan レビュー）。物理キーボードの
  `Escape` は `AC` に割り当てられている（`useKeyboard.ts` の `KEYBOARD_MAP`）。
  トーストが Esc を bubble まで通すと、**閉じた瞬間に計算が全部消える**——
  「押さなければ何も起きない」に反する。トーストは capture 段で受けて止める。

## §3 更新の流れ

```
registerSW({ onNeedRefresh })      ← waiting の SW を検知
        ↓ トーストを出す
利用者が「再読み込み」を押す
        ↓ updateSW()（= SKIP_WAITING を送る）
controllerchange
        ↓
location.reload()
```

- `virtual:pwa-register` の `registerSW` は `updateSW` 関数を返す。押下時に
  それを呼ぶだけでよく、`SKIP_WAITING` の送信と `controllerchange` の購読は
  プラグインが持っている。**自前で postMessage を書かない**（sw.js 側の
  ガードは workbox が生成し、`check:sw` が存在を検査している）。
- 検知の契機は `registerSW` の既定（登録時と、ブラウザが行う更新チェック）に
  従う。**自前の定期 `update()` ポーリングは足さない**——電池と通信を使う割に、
  タブを開き直せば同じことが起きる。

## §4 検証 — 実 SW の世代交代を自動テストで再現しない

M5 で踏んだ罠を繰り返さない: **SW は本番ビルドでしか本物にならない**。
E2E で「新しい版をデプロイして waiting にする」を再現するには 2 回ビルドして
配り替える必要があり、費用と不安定さに見合わない。

段を分ける:

| 何を | どこで |
|---|---|
| トーストが出て、押すと更新関数が呼ばれ、reload が走る配線 | **vitest**（`registerSW` をモックし、`onNeedRefresh` を発火させる） |
| トーストの役割・フォーカス・タッチターゲット | **E2E**（トーストを強制表示するテスト用の入口を 1 つ設ける） |
| sw.js が prompt の形をしていること（`SKIP_WAITING` ガード） | **`check:sw`**（既存。そのまま有効） |
| 実際の世代交代（旧タブ → トースト → 新版） | **手動確認**（デプロイ後、`docs/deploy.md` のチェックリストに 1 項目追加） |

E2E 用の入口は「テストのためだけの分岐」になるので、**本番の挙動を変えない
形**（クエリパラメータでトーストの表示状態だけを立てる等）にし、その旨を
コードにも書く。ここを曖昧にすると、テストのための穴が本番の経路になる。

**`check:sw` に検査を 1 つ足すか**は実装時に判断する。候補は「`main.tsx` が
`onNeedRefresh` を配線していること」の静的検査だが、`check:sw` は成果物
（`dist`）の番人であり、ソースの検査は vitest の担当という切り分けのほうが
きれいである——実装時に理由ごと決める。

## §5 スコープ外

- `EngineState` の永続化（base-spec §40。リロードで入力が消えることの解決は
  トーストの仕事ではない）
- 定期的な更新チェック（ポーリング）
- `registerType` の変更、`autoUpdate` への移行
- Scientific の盤面・入力意味論（S1 / S2）

## §6 完了条件

1. 新しい SW が waiting になったときトーストが出て、押すと更新して reload する。
   押さなければ何も起きない。
2. トーストが `role="status"` で、フォーカスを奪わず、44px を守っている
   （E2E で固定）。
3. 配線が vitest で検査されている（`onNeedRefresh` 発火 → 表示 → 押下 → 更新
   関数の呼び出し）。
4. `check:sw` が引き続き緑。
5. `docs/deploy.md` の実機チェックリストに「旧タブでトーストが出て、押すと
   新版になる」が 1 行加わっている。
