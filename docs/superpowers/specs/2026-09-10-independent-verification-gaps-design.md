## §2 `spell()` — 独立は「不可能」で確定し、守りを「写しの残り」へ向ける

### §2.1 裁定案 1: `独立: 不可能` を確定させる（「実測前」を外す）

理由は 3 つある。

1. **綴りは取り決めである。** 演算子・関数・括弧の字面は「盤面のキーに何と
   書いてあるか」で、数学的な事実ではない。別手順で同じ文字列に着く道が無い
   （`spell.rs` の宣言のとおり）。
2. **数の部分は、設計として engine そのものである。** `58995ec` 以降、`spell` は
   本物の `Buffer` を歩かせ、値を `Buffer::text()` で綴る。Python に独立実装を書く
   とは **`Buffer` をもう 1 つ手で写すこと**であり、それは**この族を 5 回生んだ
   作業そのもの**である（写しは 16 の振る舞いのうち 13 を取りこぼしていた）。
3. **この族の欠陥は「`spell` が値を間違える」ではなく「`spell` が engine から
   ずれる」である。** 前者の oracle は独立実装だが、**後者の oracle は engine
   自身である。** 独立な Python と照合しても、ずれたのが Rust の写しなのか Python
   の写しなのかが言えない。

**`独立:` の宣言は 3 か所とも「不可能」のまま据え置き、「実測前」の但し書きを
外して、代わりに何が守るか（§2.4）を書き足す。** CONTRIBUTING の「宣言は 2 か所」
（設計書の節と公開関数の docstring）はこの節と `spell.rs` で満たす。

### §2.2 独立な golden は、7 回を捕まえられたか——正直な見積もり

**捕まえられなかった、と見立てる。** 確実に捕まえたと言えるものは **0 件**。

| # | 独立な golden（Python が期待値を作る） | 理由 |
|---|---|---|
| 1–5 | **運しだい。確実なものは 0 件** | golden は**誰かが並べた列**しか見ない。**5 件とも、並べる人が思いつかなかった角**だった——`spell` の作者も、表を書いた人も踏まず、探針が初めて踏んだ。**実装を独立にしても、列の選び方は独立にならない。** さらに Python 側で `Buffer` を写すことになるので、同じ角を同じように取りこぼす見込みが高い |
| 6, 7 | **捕まえられない（構造上）** | core の golden は web のコードを 1 行も走らせない |

**裏付けが 1 つある。** `58995ec` の前に `Buffer` を読んで振る舞いを全部数え、
表の行に起こしたところ、**13 行のうち 11 行が実際にずれていた**
（`history-HANDOFF.md` §0）。**行を並べさえすれば、表は捕まえた。**
足りなかったのは oracle の独立性ではなく、**列を並べ尽くすこと**である。

**だから守りは「独立な期待値」ではなく「列を人に並べさせない突き合わせ」にする。**
探針がやっていたこと（`spell` と engine を直接比べる）を、**人が選んだ列ではなく、
網羅と乱択が作る列**に掛ける。これが §2.4 である。

（この節は**見立て**である。書かれなかった golden は測れない。測れるのは §2.4 の
守りのほうで、§2.6 で過去の欠陥版に当てる。）

### §2.3 残っている写し——キーの行き先の振り分け

`58995ec` で数の綴りは本物になったが、**写しは 1 つ残っている。** `spell` の
`match` の各アームは、キーが「バッファを開く／伸ばす」「確定する」「捨てる」の
どれかを、**`engine/mod.rs` の `apply()` を読んで手で振り分けたもの**である
（`spell.rs` の docstring が「`apply()` をそのまま辿った」と書いている）。

**次にこの族が入るならここである**——engine にキーが増えた、あるいは `apply()` の
振り分けが変わった日に、`spell` の `match` は追随しない（既定のアーム `_ =>` は
「確定して字形を足す」に倒れる）。

### §2.4 代わりの守り A——入力中は、綴りの末尾が engine の表示と一致する

**不変条件 A.** 打鍵列のどの prefix でも、**engine が入力中の数を持っている
（バッファが開いている）とき、`spell(prefix)` の最後の語は engine の
`render(...).main` と一致する。**

- **逆写像を要らない。** 綴りを打鍵に戻す関数（§2.5 の案 B）を書かないので、
  **新しい写しが増えない。**
- **振り分けのずれを捕まえる。** `spell` が「確定」に振ったキーを engine が
  「伸ばす」に振れば（逆も）、次の数字で `spell` は新しい語を始め、engine は
  書き足す——**最後の語と表示が食い違う。**
- **偽の赤が出にくい。** 比べるのは engine 自身の表示だけで、`000` と `0` 3 回の
  等価性（上限を跨ぐと等価でない）のような解釈を持ち込まない。

**どこで回すか——網羅と乱択の 2 本。どちらも core のテストに置く。**

1. **網羅の歩き**（`crates/calcarc-core/tests/engine_robustness.rs` の
   `walk_from_the_start` と同じ形）。**ただし同値類に `Zeros3` と `Neg` を足す。**
   いまの `ALL_CLASSES`（`:482`、17 個）には**この 2 つが無い**——欠陥 1（`000` の
   `del`）と 5（指数の符号）の鍵である。`Exp` と `Dms` は在る。
2. **入力に寄せた乱択**（proptest）。**既存の `weighted_key`（`:683` 付近）は
   そのまま使えない**——`Zeros3`・`Exp`・`Dms` を 1 つも引かない。字数上限
   （欠陥 5）には長い数が要るので、数字・`000`・`.`・`Exp`・`Neg`・`j`・`dms`・
   `del` に寄せた生成器を別に持つ。

**置き場を重量級でなく core にする理由。** core のテストは**毎回の PR**で走る
（`Rust core`、制限 10 分、実績最大 93 秒）。重量級はリリースと手動起動でしか
走らない。**この族は PR の中で入る**ので、PR で止める。WASM 境界は `spell` を
素通しで出すだけで、字形は `label_parity.rs` が見ている——**重量級で同じことを
もう 1 度回す理由が無い。**

**A が捕まえないもの（書いておく）。**

- **字形の側のずれ**——欠陥 2（`3 + DEL 4`）。`DEL` の直後は engine に開いた
  バッファが無いので A は何も言わず、次の `4` では両方が `4` を示す。**これは
  `spell_table.rs:211` の既存の行**（`spell_of(&["3", "add", "del", "4"]) == "3 + 4"`。
  `5d6b9ba` が足したもの）が持ち続ける。
- **web の 2 件**（欠陥 6・7）。core のテストは web を走らせない。守りは既存の
  `carried_value_parity.rs` と web の単体・E2E（`history-HANDOFF.md` §0 の番人の表）。
- **捨てるべき数を確定した**形（`3 (` の `3` を綴りに残す）。表示にも答にも
  現れない（`(` がバッファを捨てるので）。**綴りの見た目だけの違い**で、族の
  定義（式が自分の答を生まない）には当たらない。

### §2.5 採らなかった案 B——答の往復

**B.** `engine(再生(spell(keys))) == engine(keys)`。欠陥 2 も捕まえる。

**採らない。** 理由は 3 つ。

1. **「再生」は `spell` の逆写像を手で書くことである。** 字形→キー、数の文字列→
   キー列——**新しい写し**であり、この族を生んだ形そのものである。
2. **偽の赤が構造的に出る。** `000` を `0` 3 回で再生すると字数上限の手前で振る舞いが
   変わる（`Buffer` の「`000` の上限跨ぎ」）。受け入れ済みの残差
   **`3 × ( DEL =`**（綴りが答 `0` を説明しない。`history-HANDOFF.md` §0「残した
   論点」）も赤になる。どれも除外の一覧を持つことになり、**その一覧がまた腐る。**
3. 欠陥 2 は**既に表の行が持っている**。B の追加分は「表に無い字形のずれ」だけで、
   それを取りに行く代価が 1 と 2 である。

（裁定で B も欲しいとなれば、§7 の 2 番。）

## §3 到達性——「すべてのボタン」を本当にする

### §3.1 現物

- `heavy/tests/ui/keys.ts` の `build()` は、`SCIENTIFIC_SECTIONS` の面を

- `reachability.spec.ts:51` の **`every button the keypad claims can actually be
  pressed`** は `BUTTON_FOR` を回す。**名前は「すべてのボタン」だが、実装は
  「トークンを持つボタン」**である。
- 関数電卓の `token: null` は 2 つ——**Shift**（`scientific.ts:18`、`kind: "shift"`。
  `keys.ts` の `SHIFT_ARIA_LABEL` が別に持つ）と **`hist`**（`:214`、

  （金融の盤面には在る——`FinancePanel.tsx` の `"空き"`）。
- `hist` の到達は **web の E2E が見ている**（`history.spec.ts`「the history key is
  reachable behind Shift…」）。**守られていないのは `hist` ではなく、重量級の

### §3.2 裁定案 2: 盤面の面を 3 種に分類し、分類できない面で落ちる

**`keys.ts` が、`SCIENTIFIC_SECTIONS` のすべての面（第 1 面・第 2 面）を次の
どれか 1 つに分ける。** どれにも当たらない面を見つけたら**例外で落ちる。**

| 種 | 条件 | 行き先 |
|---|---|---|
| トークン | `token !== null` | `BUTTON_FOR`（今のまま） |
| 操作 | `action !== undefined`（`token` は null） | **新設 `ACTION_BUTTONS: ReadonlyMap<KeyAction, ButtonFor>`** |
| Shift | `kind === "shift"` | 今のまま（`SHIFT_ARIA_LABEL`） |

**これが構造の穴を閉じる。** 今日の実害は `hist` 1 つだが、**形としては
「トークンを持たないキーという種類が製品に増えたのに、重量級のモデルが表現できない」**
である。分類が網羅であることを要求すれば、**次に種類が増えた日に、この表が赤くなって
決めさせる**（予約の空き枠が関数電卓に来た日も同じ）。

**`reachability.spec.ts` の変更:**

- `:51` は第 1 面の**トークン ∪ 操作**を回す（今日、第 1 面の操作は 0 個——`hist` は
  第 2 面なので次の項へ）。名前はそのまま、**主張を名前に合わせる**。
- `:88` の「Shift の裏のキーは Shift を押してから現れる」に**第 2 面の操作を足す**。
  `hist` は Shift のあと**ちょうど 1 つ在り、有効である**ことを見る。
- **`hist` は押さない。** 押すと履歴の画面へ移り、以降のテストの盤面が変わる。
  到達（在る・有効）までが重量級の持ち分で、**押した先は web の E2E が持っている。**

| 分類が空で緑を返さない | 同じテストに下限——**操作 ≥ 1、トークン ≥ 1**（数は盤面から導き、46 などを書き写さない） | 同上 |
| `hist` は Shift の裏に 1 つ在り有効 | `reachability.spec.ts:88` | **`heavy:ui`＝CI だけ**（この作業機では走らない） |

**赤の確かめ方（名指しの前に）:** (1) 単体——トークンも操作も `kind` も持たない面を
1 つ差し込むと赤、(2) `heavy:ui`——`hist` を無効にすると赤。**(2) は手元で回せない**
ので、CI の `Heavy corpus` を枝で手動起動して確かめる。

## §4 期首を重量級に入れる

### §4.1 現物

- **harness** は複利の 3 op に `"end"` を固定で渡す（`heavy-harness.ts:161-190`）。
  註に「重量級を期首へ広げるのは、期末/期首を足した枝の範囲外」とある。
- **境界証明書**（`certificates.ts`）の `compoundDepositForProbes` と
  `compoundPeriodsForProbes` は、正算 `compound_grow` の入力 `base` を
  **principal・rate・periods_per_year・periods（または deposit）・tax から組み、
  timing を入れない。** harness の既定は `"end"` なので、**期首の逆算ケースを
  入れると、その答を期末の腕で検算してしまう。**
- **コーパス**は `finance-000.json` の 1 枚（`generate_corpus.py:2433`
  `FINANCE_COUNT = 3500`、`:2466` で seed `20260821`）。複利の層に timing は無い。
  試験空間モデルは `finance-v1`（`corpus_calls.py:3036`）、複利 3 op は
  2 因子間ペアワイズ（`:3080` 以降の 3 つの `Requirement`）。
- **検出力**: `step()` の期首の腕 2 本は重量級から見て**空白**である。
  harness が `"end"` しか渡さないので、そこに置いた変異は原理的に捕まらない。
- **golden** は期首を持つ（`cases.py:747-836`）。**「積立 0 は 1 通りに畳んである」**
  （`:754`）——積立が 0 なら期首と期末は同じ答を返すので、**期首の腕の違いを
  見るケースは積立 > 0 でなければならない。**
- **`heavy:ui`** の金融の面は周期と税を「打つのではなく選ぶもの」
  （`finance-cases.ts` の `CHOSEN_NOT_TYPED`）として chip で押す。**期首の chip は
  押していない。** 盤面の期首キーは `timing:start`、アクセシブルネーム
  「**積立を期首に行う**」（`web/src/ui/Keypad/finance.ts:388-392`）。

### §4.2 裁定案 3: 期首は新しいシャード `finance-start-000.json` に置く

**`finance-000.json` は 1 バイトも変えない。**

| | 案 1: 新しいシャード（推す） | 案 2: `finance-000.json` に足す |
|---|---|---|
| 既存 3,500 件 | **不変**（再現性の検査がそのまま通る） | 件数が変わる。層に軸を足せば `cell_id` の綴りも変わる（`corpus_coverage.py:92` 「並べ替えると `cell_id` の綴りが変わる」） |
| 読み方の表（868 / 315 / 2,317） | **そのまま使える** | 作り直し |
| v0.8.0 / 0.9.0 の検出率との比較 | **そのまま比べられる** | **また比べられなくなる**（09-10 に 1 本ほどいたばかりの形） |
| 既存変異の `minRate` | 鍵（シャード名）が変わらない | 分母が変わる |
| 手数 | `ALL_SHARDS` に 1 行（`detection-power.mjs`）。**定数の註は腐っている**——いまも「正当に 19 枚目を足す日には…」と書くが、`ALL_SHARDS` は**すでに 19 個**を持つ。期首のシャードは **20 枚目**で、**註もこの PR で直す** | 少ない |

**案 1 を推す。** 手数の差より、**比べられることの値打ちが大きい。**

### §4.3 生成（`reference/`）

- **別の seed** で作る（例: `20260910`）。`finance-000.json` の乱数列をずらさない
  （`corpus_calls.py` の既存の流儀——「無関係な `compound_grow` の乱数列をずらさない」）。
- **op は複利の 3 つだけ**。すべて `timing: "start"`。**`timing: "end"` の明示は
  入れない**（それは `finance-000.json` と golden の `cases.py:785-796` が持つ）。
- **積立 > 0 を要求する**（§4.1 の `cases.py:754`）。積立 0 のケースは期首の腕の
  違いを 1 度も見ないので、**入れても検出力にならず、件数だけを水増しする。**
- **非単調な谷**（`compound_periods_for/non_monotone_net`、`corpus_calls.py:1886`）は
  期首で**探し直す**。谷は timing に依存する。探索の上限内で見つからなければ、
  **試験空間の「測れない軸」の宣言**で書く（既存の仕組み）。
- **試験空間モデルは `finance-start-v1` を新しく名乗る。** 因子表は
  `PAIRWISE_COMPOUND_*_FACTORS` を**参照し、写さない**（`corpus_calls.py:3015` の
  「ここに水準を書き写さない」）。`finance-v1` の意味は変えない。
- **件数（実測前）。** まず `finance-000.json` の複利の比率（437 / 431 / 315＝1,183）に
  揃え、**被覆の門が要求するセル数で下限を決める。**
- **公開する参照関数は増えない。** 期待値は既存の `compound_ref.grow` /
  `deposit_for` / `periods_for`（`timing` 引数あり）から取る。CONTRIBUTING の
  「独立」の宣言は既存のものがそのまま効く——**`grow` は `独立: 不可能`（Rust と
  同じ 1 期ごとの floor のループ）**である。したがって**このシャードが確かめるのは
  「Rust の期首の腕と Python の期首の腕が同じ手順で同じ答を出すか」**であり、
  **別手順の検算は `closed_form`（`独立: 別手順`、期首を持つ）が参照側の
  テストで持つ。** そう読めるように、シャードの `generated_by` の説明に書く。

### §4.4 harness と境界証明書

- **harness**: 複利 3 op は `input.timing` を読み、**無ければ `"end"`**。
  `"end"` / `"start"` 以外は**例外で落とす**（黙って既定へ倒さない）。
  `finance-000.json` は `timing` を持たないので**振る舞いは変わらない。**
- **境界証明書（必須）**: `compoundDepositForProbes` / `compoundPeriodsForProbes` の
  `base` に **`timing` を運ぶ。** これを落とすと、期首の逆算ケースの証明が
  **期末の腕で行われる**——答が合っていれば赤くなって誤警報、**運悪く期末でも
  境界に当たれば黙って緑**になる。**このシャードを入れる同じコミットで直す。**
- **証明書の番人**: 期首のケースだけを 1 件入れた単体で、`base` が `timing` を
  持つことを見る（`heavy/tests/unit/`、純関数の側）。

### §4.5 検出力（`heavy:power`）

- **新しい変異 `compound-start-deposit-at-end`**: 期首の腕を期末の腕と同じにする
  （積立を利息の後へ）。**期首の腕 2 本を同時に動かす**——片方だけだと「積立が
  消える」別の、はるかに大きい壊れ方になる（09-10 の当て直しで確かめた教訓と同じ）。
  `expectShards` は **`finance-start-000.json (calls)` だけ。**
- **既存の `compound-deposit-at-start` は `finance-000.json` だけを期待したまま**
  にする。これは期末の腕しか動かさないので、**期首のシャードでは 0 件であるべき**
  ——`detection-power.mjs` は「捕まらないはずの変異が捕まっても失敗」とする。
  **2 本で腕の独立を両方向から確かめる**ことになる。
- **`compound-round-once-at-maturity` と `periods-for-binary-search`** は期首の
  シャードにも届く（前者は `grow_with_timing` のループ、後者は `periods_for` の
  ループに在り、どちらも timing を問わず通る）。**`finance-000.json` の件数は
  612 / 1 のまま変わらないこと**を回帰として見る。新しいシャードの件数は新しい行として
  報告書に出る。
- **`minRate`**: 新しい変異と新しいシャードの分は、**最初の CI の実測から決める。**
  それまでの版は下限 1（`minRate` 未指定＝`verdictFor` の `max(1, …)`）とし、
  **註に「未測定」と書く**。実測したら値を入れ、註を実測に置き換える。

### §4.6 `heavy:ui`（実画面）

- `timing` を `CHOSEN_NOT_TYPED` に足し、`TIMING_KEY = { end: "積立を期末に行う",
  start: "積立を期首に行う" }` を持つ（**アクセシブルネームは実装の日に
  `finance.ts` から当て直す**）。期首のケースは、方式の面で期首の chip を押してから
  打つ。
- 標本は新しいシャードからも引く。**押下台帳は動く**——台帳は盤面の不変量ではなく
  コーパスの関数である（2026-08-30 実測。記憶 `heavy-corpus-next-steps`）。
  **動いた量を報告書で読める形で残す。**
- **この作業機では走らない**（segfault）。確かめは CI の `Heavy corpus` の手動起動で行う。

### §4.7 読み方の表——何が変わり、何が変わらないか

**`finance-000.json (calls)` の表は変わらない:**

```
compound_grow 437 / compound_deposit_for 431 / compound_periods_for 315 / loan_* 2,317   計 3,500
```

**新しい表が 1 つ増える（件数は実測前）:**

```
finance-start-000.json (calls)   すべて複利・すべて期首・積立 > 0
  compound_grow / compound_deposit_for / compound_periods_for   （loan_* は 0 件）
```

報告書の検出の表では、**変異ごとの「赤くなったシャード」欄に新しいシャードが
並ぶ**。読むときの注意は 09-10 と同じ——**太字の「件数」は捕まえた数の合計で、
分母ではない。** 率はシャードごとに、そのシャードの件数で割って出す。

### §4.8 受け入れ

- `finance-000.json` の digest が**変わっていない**（再現性の検査）

  - `compound-round-once-at-maturity` の `finance-000.json` が **612**、`periods-for-binary-search` が **1**
  - `Corpus vs reference` の所要時間（**実測前**。いまの 85 分の制限の内側であること）
