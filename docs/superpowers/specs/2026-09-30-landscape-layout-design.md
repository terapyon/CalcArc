# 横向きの配置 — 表示欄と関数を左へ、5×5 を右へ（1.1.0）

**2026-09-30。起点は `fc57633`（版数は既に 1.1.0、タグ未）。**

**利用者の裁定**: **「メインの 5×5 はそのままにして、表示エリアとファンクションを左側に持ってくる」**
／**「`j` や `Exp` などの重要なボタンは表から消さない」**／**「CSS だけでできるほうがよさそう」**
（2026-09-30）。

**★ 前の設計書（`2026-09-30` の 1 つ前、`2026-09-29-wide-layout-design.md`）は
「配置の変更は 1.2」と書いているが、それは監視役の取り違えである**——**利用者が最初に選んだ絵は
すでに「関数を左に寄せた配置」だった。** **選ばれた絵の名前（「Shift の裏を表に出す」）だけを
受け取り、絵の中身を読まなかった。** あちらにも訂正の印を入れた。

---

## 1. 測って分かったこと

### 1.1 いまの横向きは、中身が画面の 2 倍ある

**横向き（幅 667/844）でページ全体の高さは 831px、画面は 390px**
（2026-09-29、検証役の実測）。**441px 溢れている。**

### 1.2 溢れの主犯は「正方形のキー」である

`Keypad.module.css` の `.square > button { aspect-ratio: 1 / 1 }`。
**5 行の正方キーは、幅 480px の枠で `5 × 84.8 + 32 = 456px`** を占める。
**横向きは「幅は余るが高さが無い」**ので、**正方形はいちばん相性が悪い。**

### 1.3 `j` と `Exp` は 5×5 の中に在る

`scientific.ts` の `MAIN_GRID`（`:148`、`columns: 5`、25 キー）——
**`j` は `:205`、`exp` は `:239`。** **どちらもこの区画の中である。**

**→ 5×5 の配列に手を入れなければ、表から消えることは構造上ありえない。**

### 1.4 `.keypad` はランドマークではない

区画は `<fieldset aria-label={…}>`（`Keypad.tsx:59-64`）で、**`aria` は区画側に付いている。**
**`.keypad` はそれらを縦に並べるだけの入れ物**である。

**→ `.keypad` を箱から外しても、読み上げのランドマークには触らない**
（**`<main>` を外す案は採らない**——あちらはランドマークで、**箱から外すと読み上げの木から
消えるおそれがある**。**確かめていない。**§6）。

## 2. 決めたこと

**★ §2 は 2026-09-30 に組み直した。** **初稿の数（Nav 48・Footer 41・キー 47px）は
監視役の逆算で、外れていた**——**レビュー役が `fc57633` のビルドを Playwright で直接測った。**

### 2.0 実測（844×390、ページ全体 831.3px）

| 部品 | 初稿の数 | **実測** |
|---|---|---|
| Nav | 48 | **68**（`.nav` の padding 12×2 ＋ タブの `min-height: 44`） |
| Footer | 41 | **33** |
| 表示欄 | 154 | 154.2（y = 80） |
| 関数列 ×2 | 76 | 34 ＋ 8 ＋ 34 |
| 5×5 | 456 | 456.1 |
| **パネルの幅** | 844 を前提にしていた | **480**（x = 182）——**`max-width: var(--shell-max-width)` で止まっている** |
| 隙間 | 12 が 4 つ | **12 が 3 つ**（パネルの上下＋表示欄と盤面の間）＋ **keypad の gap 8 が 2 つ** |

`68 + 12 + 154.2 + 12 + 34 + 8 + 34 + 8 + 456.1 + 12 + 33 = 831.3`。
**667×375 も同じ 831**（幅だけ違う）。**縦持ち 390×844 はページ 844・表示欄 143.6。**

### 2.1 配置

```
844×390（ホーム画面から開いたとき）
┌────────────────────────────────────────────┐
│           Nav（中央寄せ 343px）               │ 68
├─────────────────────────┬──────────────────┤
│   123.456               │                  │
│  （表示欄 154px）         │   いまの 5×5      │
├─────────────────────────┤   25 キー・そのまま │
│ 関数キー（7 列）           │   j も Exp も動かず│
│ 第 2 関数列（7 列）        │                  │
└─────────────────────────┴──────────────────┘
│         Footer（中央寄せ 288px）              │ 33
└────────────────────────────────────────────┘
      ← パネルだけが全幅（820px）→
```

**Nav とフッタは全幅ではない**——**中身の幅（実測 343 / 288）で中央に寄る。**
**全幅になるのはパネルだけ**である（§2.4）。

### 2.2 数（実測から組み直した）

| | 844×390 | 667×375（いちばん厳しい） |
|---|---|---|
| パネルの余白 | 12 | **8 に詰める** |
| **キーの高さ** | `68+12+(5k+32)+12+33 ≤ 390` → **46px** | `68+8+(5k+32)+8+33 ≤ 375` → **45px**（余裕 1.2px） |
| 左の段の下限 | **356px**（関数 7 列 × 44 ＋ 隙間 6×8） | 同じ 356px |
| 右の段 | 残り（820 − 12 − 356 = 452 まで） | 667 − 16 − 12 − 356 = **283** |

**初稿の 47 / 46 は差し替えた。** **床の 44px は割らない**が、**667×375 の余裕は 1.2px** である。

### 2.2.1 ★ 「1 画面に収まる」は、ホーム画面から開いたときに限る

**390 / 375 はホーム画面の高さである。** **Safari のタブでは違う**
（Playwright の端末定義の実測、レビュー役）:

| 端末（横） | viewport |
|---|---|
| iPhone 13 | **750 × 342** |
| iPhone 14 Pro Max | 814 × 380 |
| iPhone SE | 568 × 320 |

**342 では `5×44 + 32 + 68 + 33 + 24 = 377 > 342`**——**床を守ったまま 1 画面には入らない**
（**35px スクロールする**）。**SE の横（568）は 660 の段にすら入らない。**

**だから約束はこう書く**——**「横向きで 1 画面に収まるのは、ホーム画面から開いたとき」。**
**README の「1 画面に収まること。収まるように確かめているのは、ホーム画面から開いたときの高さ」
と同じ限定**である。**タブの寸法は「スクロールするが全部に届く」側**——
**`short-screens.spec.ts` に足す。**

### 2.3 仕組み——`.keypad` を `display: contents`、高さは viewport から導く

**横向きのときだけ**、`.keypad` を箱から外し、**パネルを 2 列の格子**にする。
**区画がパネルのマスになる**ので、**表示欄と関数 2 段を左、5×5 を右**へ置ける。

**★ キーの高さを手で書かない**（レビュー役の条件 B1）。**`aspect-ratio` を外すと高さは
中身（`min-height: 44`）になり、46px は誰も作らない。** **1 画面に収まることを構造で出す**:

- `.shell` は `min-height: 100dvh` の flex 列、`.main` は `flex: 1`（既存）
- パネルを `height: 100%`、**パネルの格子を `grid-template-rows: 1fr`**
- **右の `fieldset` の行を `1fr`** にして、**行の高さ ＝（残り − 32）÷ 5**

**手で 46 と書くと、Nav が 1px 動いた日に腐る。**

**`display: contents` を当てる相手は `div.keypad` だけ**（レビュー役の注記 C2）。
**区画の `fieldset` に当てると、ブラウザによって group が消える**ので、
**当てる相手を番人の註に固定する。**
**DOM の順（表示欄 → 関数 → 関数 2 → 5×5）と見た目の順（左の上から下、次に右）が
一致する**ので、**フォーカスの順は崩れない。**

### 2.4 段の条件と、`--shell-max-width` を解くこと

```css
@media (min-width: 660px) and (max-height: 840px) {
  /* ★ これが無いとパネルは 480px のままで、左の段の下限 356 を引くと
     右に 88px しか残らない——5 列 × 44 = 252 は入らない。 */
  :root { --shell-max-width: none; }
}
```

**★ 初稿にはこの 1 行が無かった**（レビュー役の阻止 A1）。**パネルが 844 いっぱいに
なる前提で 476＋332 と書いていたが、その前提を作るものが設計に無かった。**

**そして、この 1 行があって初めて §2.4 の重なりが解ける**——**タブレットの横向きは
「短辺 600px 以上」の段（`--shell-max-width: calc(…) = 496px`）にも当たる。**
**同じプロパティを後の段が上書きする**ので、**`none` が勝つ。**
**別のプロパティが両方効く形だと、iPad の横向きは 496px の枠に 2 列を詰めて壊れる。**

- **660px** は `667×375` から（**それより狭い横向きでは、左の段に関数 7 列が入らない**）
- **840px** は**積んだ配置の中身が 831px** だから（**それより高ければ積んだままで収まる**）

**当たる／当たらないの表は、Playwright の端末定義（viewport）で書く**
（レビュー役の条件 B5）——**screen の数で書くと、タブの寸法が落ちる。**

### 2.5 格子の器は、電卓ごとに名指しする

**「最後の `fieldset` が 5×5」は成り立たない**（レビュー役の条件 B2）。
**`DataScalePanel.tsx:329` が Keypad の後ろに
`<fieldset aria-label="主に表示する単位系を選ぶ">` を置いている**
——`fieldset:last-of-type` で右へ送ると、**DataScale ではその区画が右へ行く。**
**Convert も器が違う**（`ConvertPanel` の `div` ＞ `CategorySelect` ＋ `UnitPanel` の
`section.panel` に表示欄と盤面）。

**★ 器に印を付けて、規則は 1 か所に置く**（レビュー役の条件 B4）。
**器の CSS は 6 ファイルに分かれている**ので、**同じ媒体条件と格子を 6 つ写すと、
1.1 の設計書 §1.3 が数えた「同じ 6 行の写し 8 ファイル」と同じ穴**になる。
**あちらは「パネルごとに違う幅が要るとわかった日に共通化する」と書いた——その日が来た。**

**採る形**: **格子の器に `data-board` を付け**、**媒体条件と格子の規則を `tokens.css`
（唯一のグローバル）に 1 回だけ書く。** **番人は「6 つの器すべてに `data-board` が在る」
と「`data-board` を読む規則は 1 か所だけ」。**

## 3. 作らないもの

- **Shift の裏を表に出すこと。** **関数の段が 4 行必要**（7 列 × 4 = 28 マスで 23 キー）で、
  **`154 + 12 + 160 = 326`** に対し、**左の予算は実測で `390 − 68 − 33 − 24 = 265`**
  ——**入らない**（初稿は 271 と書いたが出どころが不明だった。**どちらでも入らない**）。
  **タブレットの話として後に。** **ここで混ぜない。**
- **`<main>` を箱から外すこと**（Nav とフッタを左へ入れる案）。**キーは 47 → 66px に育つ**が、
  **`<main>` はランドマークで、箱から外すと読み上げの木から消えるおそれがある**（未確認）。
  **利用者の裁定「CSS だけでできるほうがよさそう」**（2026-09-30）。
- **キーの配列の変更。** **1 つも触らない。**

**いまの設計では構造上満たされる**が、**「構造上そうだ」は将来の変更を止めない。**
