## §0 製品方針: 決定的概算

**通貨は円のみ・整数。実額一致は非目標**——機関ごとに端数処理・手数料・
日割りが異なり、「どの銀行とも一致」は達成不能な目標である。代わりに
**決定的**であることを保証する: 同じ入力は常に同じ答を返し、計算方法は
本 spec に明文化され、Python 独立実装で検証される。**UI に免責表示を常設**
（「実際の返済額は金融機関の計算方法により異なります」の趣旨）。

M6 スコープ =「20 年前の銀行員の金融電卓」の中核 + 残価:
- **正算**: 元利均等の月額（+残価 B、既定 0）
- **逆算 2 種**: 借入可能額（月額から）・期間（月額から）
- **ボーナス併用**（正算と借入可能額のみ。§4）
- 月利換算は年利÷12 のみ（換算オプションなし）

## §1 数値経路（最重要）

**numerical-policy に第 3 分類を追記する**: Scientific = 浮動小数点 /
Data Scale = 厳密整数 / **Loan = 決定的概算**（月額決定のみ f64、償還表は
厳密整数）。

1. **償還表の各行利息は f64 を通さない。**
   利息 = floor(残高 × 月利分子 / 月利分母) を**厳密整数演算**で計算する
   （Rust は u128 中間、Python は int）。
   根拠（実測）: f64 経由では普通の入力で 1 円狂う——年 2.7%・残高
   1,200 万円で f64 は 26,999 円、厳密値は 27,000 円。丸い元本では利息が
   円境界ちょうどに乗るのが**常態**である（3,000 万円は全 bp 刻み金利で
   境界上）。「境界はまれ」という直感は逆で、丸い元本 × bp 刻み金利という
   最頻の入力がまさに境界を踏む。
2. **金額の保持は u64 円。利息乗算の中間だけ u128**（残高×分子は u64 を
   溢れる）。不採用案:「エンジン全体を u128 固定小数点にする」——採ったのは
   乗算中間の u128 のみであり、両者は別物（区別して記録する）。
3. **f64 は閉形式による月額決定のみ。** `(1+r)^n − 1` を直接計算せず
   **`expm1(n·log1p(r))`** で評価する（低金利での桁落ち回避）。誤差上限は
   入力依存で概ね 月額 × max(n·ε/2, ε/(2r))。素朴式は年 0.001% で
   ~1e-5 円まで悪化する（注意: 「~1e-13 円」という旧見積りは 3 桁誤り
   だった——本 spec の数字が実測に基づく正）。
4. **境界近接拒否ガード（±1e-6 円）は「f64 を floor する全出力」に適用する**
   （月額決定と借入可能額。期間は §5 の表確定方式により対象外）。各行利息は
   厳密計算なのでガード不要——境界ちょうどを正しく扱える。
   ガードの第 2 の根拠（レビュー指摘）: golden 生成と CI は x86、実行は
   ブラウザ（wasm32）で、**expm1/log1p の libm 実装が異なり ulp 差があり
   得る**。境界から離しておくことは、このクロスプラットフォーム差の実質的な
   吸収層でもある。
   **採録上の注意**: 1 回払い（月額 = P(1+r)）と金利 0%（月額 = P/n）は
   丸い元本だと理論値が**常に**境界ちょうどでガードに全拒否される
   （f64 の floor は 500 金利中 76 で 1 円落ち、かつ式の書き方で結果が
   変わる）。**これらの必須ケースは端数の出る元本（例 2,999,999 円）で
   採録する**。
5. **金利入力はパーセント文字列 → 分数**（f64 直変換しない）。
   例: "1.5" → 年利 15/1000 → 月利分数 15/(1000·100·…) を約分せず正確に
   保持し、償還表（整数経路）と月額決定（f64 化は分数の除算 1 回）が同じ
   分数から出発する。

## §2 償還表コア + 直交オプション（設計の中心）

```
償還表エンジン（共通）: 残高 → 利息 = floor(残高×分子/分母)（厳密整数）
                        → 元金 = 支払額 − 利息 → 残高更新 → 最終回で端数吸収
  ├─ 内部は「期間ごとの利率列」を受けられる形
  │   （公開 API は単一金利。変動金利 M7-8 への拡張点として内部だけ列）
  ├─ 残価 B（既定 0、正算のみ。§3）
  ├─ ボーナス併用（第 2 の償還列。§4）
  └─ 将来スロット: 元金均等、単利/アドオン、繰上返済
```

- **丸めは「全金銭計算、円未満切り捨て」の 1 語で固定**（月額・各行利息
  とも）。根拠: 実務の月額丸めは機関で割れているが、**利息の切り捨ては
  ほぼ一致**しており、同方向に揃えると仕様が 1 語で書けて一貫する
  （base-spec §37 の趣旨で 1 つに固定）。
  注意: 旧根拠「切り上げだと返金方向になるから」は**事実誤認だった**ので
  使わない。根拠は一貫性である。
- **最終回 = 残高_{n−1} + その回の利息**で端数を吸収する。調整は**増減
  どちらもあり得る**（例: 3,000 万・35 年・1.5% で −93 円）。
- **縮退入力**（極小元本 × 長期間で、残高が n 回より前に 0 になる）:
  残高が 0 になった回で償還表を打ち切り、以後の回は支払 0 とする。実際の
  回数と総支払額を出力に含め、golden ケース化する。
- **エラー**（`CalcError` を再利用、新型は作らない）:
  - 回数 0 / **元本 0** / 残価 ≥ 元本 / **月額 ≤ 初回利息（期間逆算で
    発散）** → SyntaxError
  - u64 越え → Overflow
  - 元本 0 をエラーにする判断（ブリーフから委任）: P=0 は正算では自明の
    全ゼロだが、期間逆算では n=0、借入可能額では入力側なので、モードに
    よって意味が割れる。割れる入力は弾くほうが決定的概算の明瞭さに合う。

## §3 残価設定（実慣行モデル）

**採用: 均等月額 ×(n−1) 回 + 最終回 = 残価のみ。**
月額は **P = A·annuity(n−1) + B/(1+r)^n** を A について解く
（annuity(m) = (1−(1+r)^{−m})/r）。

- 根拠: 残クレの実際の支払構造（SUBARU・日産・トヨタ系の公式支払例で
  確認済み）。**旧ブリーフの「n 回均等 + 最終回に B 併課」は 1 期ずれの
  独自モデルで、慣行に合うという記述は誤りだった**（訂正済み、ここに記録）。
- 端数調整は**定例最終回（n−1 回目）**で吸収（最終回は残価のみで固定）。
- **総支払額（golden の比較対象）は B を含む完済総額**。「利息は残価込みの
  全残高にかかる」実費を見せるのが提供価値であり、それと整合する。
  B 抜きの月々合計は表示上の補助出力（表示の形は UI 実装時に決める）。
- **B=0 で通常ローンに完全退化する**——回帰恒等式として golden 化。
- 残価は正算のみ（逆算 2 種では欄を無効化）。

## §4 ボーナス併用（これは「決定」であり「慣行」ではない）

モデル: 元本を月払い分 P1 とボーナス分 P2 に分割し、**2 本の償還列を独立に
併走**させる。ボーナス列は年 2 回・**半年利 = 年利 ÷ 2**・6 の倍数月・
初回端数期間なし。

- これは**ウェブシミュレータ標準の簡略化を採用する決定**である
  （keisan.site・貸金業協会のシミュレータ仕様と同型）。実務には
  複利半年利 (1+年利/12)^6 − 1・日割り・初回オフセットが併存しており、
  「慣行」と呼べる単一の方式は無い——golden 完全一致の世界では別物になる
  ため、どれを採るかは決定として明記する（不採用案と理由ごと記録）。
- 制約: **P2 ≤ P の 50%**。違反は SyntaxError。
- **逆算との組み合わせ**:
  - (a) **期間逆算 × ボーナスは M6 では無効化**。2 列結合の期間は閉形式で
    解けず反復解法になる——金利逆算を次送りにした理由と揃える。UI は期間
    モードでボーナス欄を無効化（残価と同じ扱い）。
  - (b) **借入可能額 × ボーナスは採用**: 入力は「月々の支払額」と
    「ボーナス回の支払額」の 2 つ → **2 本の独立な閉形式逆算**で
    P = P1 + P2。≤50% 制約は**解いた後に** P2/P で検証し、違反はエラー。
    不採用案「割合入力（ボーナス分は P の x%）」は、金融電卓の操作感
    （支払額から引ける）に合わないため不採用（理由ごと記録）。

## §5 逆算 2 種 — 原則:「f64 が候補を出し、厳密整数の償還表が確定する」

f64 の閉形式は**候補**を出すだけで、答は厳密整数の償還表（§2 のエンジン）が
確定する。これで 3 モードすべての出力が決定的になり、境界ケースを golden の
必須指定にしても安全に採録できる（レビュー指摘 R1/R3 を採用。R1 の背景:
f64 対数経路の ceil は真値が整数ちょうどのときコイントスになり、§1-4 が
1 回払い・0% で回避したのと同型の衝突を、期間逆算の必須境界ケースが再演
してしまう）。

- **期間**: 候補 m = −ln(1−P·r/A)/ln(1+r) を f64 で出し、n = ceil(m) の
  近傍 {n−1, n, n+1} を**厳密償還表で走査**して「残高が 0 以下になる最小の
  n」に確定。端数は最終回で吸収（正算と同じ表なので自然に接続）。
  **A ≤ 初回利息（= floor(P×月利)）なら発散**——SyntaxError（§2）。
  0% は n = ceil(P/A)（整数演算で ceil できるので f64 不要）。
- **借入可能額**: 候補 P₀ = A·annuity(n) を f64 で出し、**「n 回以内に
  厳密償還表が残高 0 以下になる最大の P」**として P₀ 近傍を厳密表で検証して
  確定（P が可、P+1 が不可、を確認）。0% は P = A·n（整数演算）。
- 逆算の f64 候補には §1-4 のガードを適用（表確定が最終防衛だが、golden
  生成時に境界近接を落とす番人はガードが担う）。
- **金利逆算は M6 に入れない**: 閉形式が無く反復解法（二分法等）になる。
  決定的概算の「方法を 1 語で書ける」性質を守るため、反復解法群
  （金利逆算・期間×ボーナス）はまとめて次送り（ロードマップ §11）。

## §6 Python 参照の独立軸（base-spec §30）

- **Rust**: 閉形式（f64、expm1/log1p）で月額決定 + 厳密整数の償還表。
- **Python**: 月額導出は **Decimal 高精度**（閉形式を Decimal で評価）、
  償還表は **int で愚直にシミュレート**。
- **「各行利息 = floor(残高×分子/分母) の厳密整数演算」だけは両者共通の
  公開契約**——アルゴリズムの共有ではなく、base-spec §37 型の丸め契約
  （data_scale の u128 上限・表示丸め契約と同じ位置づけ。契約を知らなければ
  独立検証は書けない）。
- 境界近接ガード（§1-4: f64 を floor する全出力）は **Python 生成側が担う**
  （golden に境界近接ケースを入れない番人）。

## §7 golden（`testdata/finance.json`）

- **完全一致・tolerance なし**（金額は整数円。data_scale と同じ流儀で、
  u64 域の値は JSON では文字列）。
- 必須ケース（ブリーフの列挙と同期。植え漏れは red-check の対象）:
  - 住宅基準例（3,000 万・35 年・1.5% 級）、車例（300 万・5 年・残価 40% 級）
  - 最終回調整が大きい組
  - **金利 0% を 3 モード全部**（正算の 0 割 / 期間逆算の log1p(0)=0 割 /
    借入可能額の r=0——各実装分岐が必須）
  - 1 回払い（**端数元本で**。§1-4）、最長 600 回、u64 域境界、縮退入力
  - **借入可能額逆算 ⇄ 正算の往復一致**
  - **期間逆算: ちょうど割り切れる n と、n+ε で繰り上がる境界 + 最終回**
    （§5 の表確定方式により境界ちょうどでも決定的——だからこそ必須指定できる）
  - **ボーナス併用: 割合 50% 境界、ボーナス 0 円 = 通常式一致の回帰恒等式、
    半年利の丸め**
  - **借入可能額 × ボーナス（≤50% 境界含む）**
  - **B=0 の残価退化恒等式**、B = P−1 近傍
  - （元金均等ケースは削除済み——後続 spec の資産）
- **赤確認 6 種**（新設検査は壊して赤を見てから信じる）:
  1. 丸め方向の取り違え（切り捨て→切り上げ）
  2. 最終回調整の欠落
  3. **残価の利息を (P−B) にだけ掛ける誤実装**（正: 残価込み全残高）
  4. **期間逆算の ceil → floor 取り違え**
  5. **月額 ≤ 初回利息を検出せず発散**
  6. **ボーナス分利息を半年利でなく月利で計算**

## §8 UI

- フォーム型 + **「何を求めるか」セレクタ**（月額 / 借入可能額 / 期間）。
- 残価欄は月額モードのみ、ボーナス欄は期間モードで無効（§3/§4）。
- 金利はパーセント文字列で受けて分数へ（§1-5。f64 直変換しない）。
- 出力: 求めた値 + 総支払額・総利息（残価時は B 込み総額 + 補助表示）。
- **免責表示を常設**。返済予定表（償還表そのものの表示）はスコープ外。
- Data Scale と同じ規約: framework 非依存ラッパー（React import 禁止）、
  未入力は中立表示、日本語アクセシブルネーム、`<main>` はシェル所有、
  ナビにタブ追加（3 つ目——**ナビ変更と a11y は E2E 必須**）。

## §9 モジュール構造（#7 の分離原則を踏襲）

- `crates/calcarc-core/src/loan/`: モジュール専用の値型とロジック
  （u64 円、月利分数、償還表エンジン）。`Value`/`engine`/`data_scale` と
  相互 import しない。共有はエラー分類（`CalcError`）・表示原則・UI 基盤の
  3 つだけ（D14 方式で本 spec が決定の記録）。
- WASM 境界は data_scale と同じ**純関数**（フォーム → 即計算）。金額は
  文字列で往復（u64 は 2^53 を超えうる）。
- root 再エクスポートはしない（api-style.md の玄関基準）。
